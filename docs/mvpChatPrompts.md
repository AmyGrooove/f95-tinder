# Bisky: промпты для проектирования и реализации MVP API

## Как пользоваться

Рабочая папка каждого чата: C:\Users\vanya\Desktop\f95-tinder.
Копируй один блок промпта целиком. Каждый блок ссылается на этот файл, чтобы новый чат прочитал общие правила без истории переписки.

1. Чаты 1–4 проектируют MVP и дополняют один документ docs/mvpDesign.md.
2. Чат 5 создаёт общий план docs/mvpImplementationPlan.md.
3. Чаты 6–10 реализуют согласованные этапы.
4. Чат 11 проверяет полный цикл и закрывает оставшиеся разрывы.

Запускай чаты последовательно. Не запускай реализацию одновременно в одном рабочем дереве.
Перед переходом сохрани результаты предыдущего чата в документах. Обсуди спорные решения и попроси агента записать подтверждённый вариант. Предложение агента само по себе не считается утверждённым решением.
Этот файл задаёт порядок работы; он не заменяет технический дизайн и план.

## Общие правила для каждого чата

- Отвечай по-русски. Следуй применимым AGENTS.md и инструкциям пользователя. Для изменений сначала используй Amy route-project-changes, затем подходящие навыки. Процессные навыки не расширяют разрешённый объём.
- Источник продуктовых требований — docs/projectVision.md с учётом более поздних явно подтверждённых решений в docs/mvpDesign.md и текущем запросе. При противоречии используй актуальное подтверждённое решение, обозначая устаревший текст; техническое предложение не заменяет согласованное требование. Фокус: backend movie-only MVP в apps/api. Устанавливай текущее состояние по production-коду; старые документы и память не доказывают реализацию.
- Прочитай apps/api/AGENTS.md, apps/api/docs/agents/index.md и нужные тематические документы. Проверяй существование ссылок: отсутствие документа не означает отсутствие кода.
- Проверь рабочее дерево и сохрани чужие изменения. Не делай коммиты, не меняй Git-историю, не создавай worktree и не разворачивай приложение публично. Не запускай подагентов без отдельного указания пользователя или применимых инструкций среды.
- Не читай, не запускай, не создавай и не меняй тесты и Storybook. Проверяй только существование по именам. Эти промпты не разрешают тестовые файлы. Проверяй, что команды не запускают запрещённые задачи косвенно.
- Переиспользуй текущие инфраструктуру, архитектуру, зависимости и инструменты. Не добавляй generic CRUD-фасады, универсальную plugin-платформу, дублирующие клиенты или массовую нормализацию. Не добавляй комментарии, TODO и FIXME в код.
- Не читай секреты без необходимости и не выводи их. Изменение схем не разрешает удаление, миграцию или перезапись существующих данных; эти операции требуют отдельного разрешения с известными параметрами.
- В проектировании выясняй существенные решения, рутинные выборы делай по проекту. Не объявляй предложенный дизайн согласованным без ответа пользователя. Явный промпт реализации разрешает выполнить указанный этап согласованного плана без повторного разрешения на обычные правки.
- docs/mvpDesign.md хранит контракты, обоснования, статусы «предложено/согласовано», существенные открытые вопросы и соответствие vision. Дополняй нужный раздел, сохраняя остальные. Материальное изменение прежнего решения обсуждай с указанием зависимых разделов.
- docs/mvpImplementationPlan.md хранит задачи и прогресс. После этапа записывай изменения, выполненные проверки, ограничения и зависимости следующего чата. Отделяй «реализовано» от «проверено в runtime».
- Поддерживай актуальную документацию уже описанных затронутых контрактов. Не создавай дополнительные workflow-файлы без необходимости.
- Запускай минимальные разрешённые type-check, lint и форматирование изменённых файлов, build при необходимости и git diff --check. Сначала проверь scripts. Не запускай широкие lint:fix/format. Runtime-проверки — только на явно выбранных изолированных локальных данных при разрешении соответствующего промпта.
- Готовность оценивай по всем 11 критериям Definition of Done из vision. Другие типы контента, cross-media качество, социальные функции, публичные коллекции, полноценная модерация, плеер, монетизация, обязательные embeddings и автоматические AI API-вызовы вне MVP.

## Актуальные решения для следующих чатов

Подробные контракты и статусы находятся в docs/mvpDesign.md. Ниже только подтверждённые продуктовые решения; этот список не утверждает весь технический дизайн.

- Обычные сохраняемые аккаунты вместо temporary/permanent сценария: сгенерированный логин и постоянный перевыпускаемый секретный код либо регистрация через внешний сервис. Привязка способа входа сохраняет userId; вход в другой аккаунт не объединяет данные.
- Яндекс для пользователей в РФ, Google вне РФ. Email необязателен; восстановление через подтверждённый email предусмотрено дизайном. Без кода, доступного привязанного провайдера и verified email доступ не восстанавливается; support bypass/резервный ключ не добавляются.
- Rolling-сессия четыре месяца с продлением через refresh; аккаунт и история не удаляются по неактивности. Ручной прогресс фильма — в минутах.
- При split собственные данные приоритетны, копии их не перезаписывают; альтернативы и история сохраняются. Неоднозначный not_interested действует для обоих Item до отдельных отмен. Копии не создают новые независимые события вкуса/показа.
- Рекомендации: watch_now допускает planned/on_hold, исключает in_progress, завершённые/брошенные попытки и оценённые фильмы; discover_later исключает фильмы с любым статусом, оценкой, избранным или историей попыток. Точные predicates — в разделе рекомендаций дизайна.
- Стартовые параметры: повтор Item после показа через 24 часа, после пропуска через 7 дней; мягкое снижение похожих карточек с полураспадом 3 дня; до трёх центров интереса и 20% exploration. Правила округления/квот для малой выдачи и остальные формулы пока технические предложения.
- Источники и доступные реальные материалы ещё не выбраны. Предпочтение удалять ненужные материалы зафиксировано, но сроки/состав и сохранение доказательств для replay не согласованы. Не считать предложенные 90 дней выбранным retention.
