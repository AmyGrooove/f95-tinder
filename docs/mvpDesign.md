### 1. Границы ядра и ID

Item — небольшой общий заголовок произведения: постоянный ID, тип, текущая пригодность записи для выдачи, служебное исключение, redirect и опубликованная ревизия. Movie — полноценная запись фильма: названия, описания и специфичные сведения. Item не собирает поля будущих Game/Book и не заменяет их коллекции.

Предложено использовать один заранее созданный ObjectId в Item._id и Movie._id. Movie._id одновременно ссылается на Item._id; дополнительный movieId/itemId не нужен. Это две коллекции с отношением 1:1, а не два разных ID одного фильма. Сериализация id глобальным toJSON plugin не создаёт новую identity.

ItemId остаётся вложенным объектом { type: movie, id: Item._id }. Во всех общих ссылках id означает Item, включая источники, теги, признаки, отношения, библиотеку, события, метрики и рекомендации. type проверяется против Item.type; ref/populate сам по себе не обеспечивает существование или соответствие типа. Проверяет сервис операции. В MVP допустим только movie.

Обновление текста, перевода, источников или правил нормализации не меняет ID. Переводы и редакции выпуска относятся к тому же произведению; ремейк — отдельный Item. Название и год не являются уникальным ключом фильма. Новый Item создаётся только после решения, что внешняя запись не относится к существующему. Отсутствие второй записи источника не препятствует созданию.

Core владеет ссылками, решениями обработки, словарями, действиями и общими входами рекомендаций. Movie владеет сведениями фильма и подготовкой его поискового документа/признаков. API будущих типов, динамический реестр адаптеров, work/release/edition, актёры как Item и франшизы как коллекции сейчас не проектируются.

### 2. Общие правила полей и записи

Ниже поля без «nullable» или «по умолчанию» обязательны. ObjectId — внутренние ссылки; даты — UTC Date; строки ключей непустые; числовые значения конечные. У корневых документов есть _id, createdAt, updatedAt. Nullable означает отсутствие известного значения, а не пустую строку или выдуманное число. Массивы по умолчанию пустые, без null-элементов.

Управляемые вложенные объекты отключают собственные _id, id, timestamps и versionKey, как текущие child schemas. ID события, попытки или текстового значения при необходимости — явно объявленное поле. Root versionKey:false не заменяет контроль конкурентных изменений: вводится явная revision и условное обновление по ожидаемой revision.

Логические ссылки и межколлекционные инварианты проверяет сервис операции. Entity-owned репозитории продолжают композицию существующих read/write/pagination/bulk/aggregation; новый generic CRUD-фасад не нужен. Обновления bulk/pipeline не считаются автоматически проверенными по всем бизнес-инвариантам.

Создание Item/Movie, публикация ревизии, merge/split и запись события вместе с пользовательским состоянием требуют транзакции через MongoTransactionService с передачей session каждому участвующему запросу. Конфигурация и возможность транзакций в реальной MongoDB проверяются следующими чатами; к БД этот чат не подключается.

### 3. Item и Movie

| Сущность | Предложенные поля | Ограничения |
| --- | --- | --- |
| Item | _id; type=movie; availability= draft/available/unavailable (по умолчанию draft); isExcluded=false; redirectTo: ObjectId nullable; revision: целое >=0; currentDecision: CatalogDecision nullable до первой публикации | Тип неизменяемый. ID не переиспользуется. Redirect не означает удаление исходного Item. |
| Movie | _id=Item._id; revision; titles: LocalizedTitle[]; descriptions: LocalizedText[]; releaseYear nullable; runtimeMinutes nullable; originalLanguage nullable; countryCodes=[]; poster nullable; sourceMetrics=[]; fieldOrigins=[] | Для available нужна Movie той же revision и хотя бы одно название. RU/EN ожидаются в обычной подготовке, но отсутствие перевода не запрещает хранение. |

availability — пригодность записи каталога для публичного использования, не наличие фильма в онлайн-кинотеатре. draft не опубликован; unavailable временно недоступен по данным/служебному решению. isExcluded — отдельный устойчивый запрет служебной выдачи, отменяемый только явным решением. redirectTo — отдельное перенаправление после объединения дублей. Для выдачи нужны available, отсутствие isExcluded и redirectTo, корректный Movie. Эти проверки применяются ко всем стратегиям и перед ответом клиенту; устаревший поисковый индекс не разрешает обход.

Item с исключением или недоступностью сохраняет библиотеку и историю. Импорт не снимает isExcluded и не отменяет redirect. Исключение, недоступность, redirect и пользовательское not_interested — разные причины, их нельзя хранить одним status. Исключённая исходная identity не становится доступной через redirect; служебный merge с доступной записью должен явно решить состояние, а не обойти запрет.

Точный набор Movie-полей расширяется только под реальные данные фильма. Предложенный старт: releaseYear — положительное целое без искусственного запрета будущих премьер; runtimeMinutes — число >0; originalLanguage — известный языковой тег; countryCodes — уникальные коды стран; poster — nullable ссылка на сохранённый объект с происхождением. Неизвестный возрастной рейтинг не означает разрешение для любой аудитории; политика допуска определяется отдельно до запуска. Плеер, места просмотра и данные будущих типов не добавляются.

sourceMetrics — раздельные наблюдения { source, metricKey, value, scaleMin nullable, scaleMax nullable, sampleCount nullable, observedAt, origin }. Шкала рейтинга проверяется, sampleCount — целое >=0. Популярность разных источников не складывается напрямую. Эти наблюдения нужны baseline; правила их нормализации и выбора задаёт чат 4. Они отделены от ItemMetric с внутренними пользовательскими агрегатами.

Для scalar-поля Movie fieldOrigins содержит путь и Origin; каждое опубликованное непустое значение имеет происхождение. Для массивов происхождение находится на элементе или привязано к устойчивому elementKey, а не к изменяемому номеру элемента. Поля availability/isExcluded/redirectTo имеют свои служебные решения. Отдельная коллекция на каждое scalar-значение не нужна.

### 4. Тексты и происхождение

Предложенный общий Origin: { kind: source/manual/ai/derived, decision: CatalogDecision, evidence: [{ artifact: SourceArtifact, pointer: JSON Pointer }], processingRun: ProcessingRun nullable }. Источник доказательства неизменяемый и проверяемый по хешу. source требует evidence; ai требует processingRun и сохранённый AI-результат; manual требует решение с автором и причиной и может не иметь source evidence; derived требует ссылки на исходные значения и версию преобразования. Несколько источников одного утверждения сохраняются, даже когда canonical значение одно.

Movie.titles: { key, locale nullable, role: original/title/alias, text, origin }. key устойчив в пределах фильма, text непустой. locale=null допустим для неизвестного языка исходного названия; угадывать его запрещено. Роль original означает оригинальное название, title — выбранное отображаемое название locale, alias — альтернативное написание. Перевод не становится original автоматически. Максимум один выбранный title на locale; повторный импорт не размножает одинаковые варианты. Исходные варианты и написание остаются в материалах даже при дедупликации canonical aliases.

Movie.descriptions и подписи словарей: { key, locale, text, origin }, без ролей original/title/alias у описаний. Tag.aliases используют тот же locale-контракт. Активные переводы и предпочтительные тексты — ru/en; original/alias могут иметь другой известный locale. Старый фиксированный LanguageText заменяется этим вложенным контрактом у затронутых сущностей.

Нормальный путь владельца: подготовить оба перевода через нейронку. Fallback названий согласован позднее в разделе «Импорт и поиск»; прежний статус предложения закрыт: title запрошенного locale → original → title ru/en в установленном порядке → alias. При fallback возвращаются фактический locale и роль; текст не выдаётся за отсутствующий перевод. Для описания допустим другой активный locale или отсутствие. Поиск индексирует все доступные titles/aliases в исходном написании и отдаёт одну текущую canonical запись.

### 5. Tag, Feature и связи

| Сущность | Поля и обязательность | Правила |
| --- | --- | --- |
| Tag | key; group; name: locale-значения; description=[]; aliases=[]; scope=common/type_specific; applicableTypes=[movie]; tasteTransfer=none/explicit; transferTypes=[]; revision; definitionOrigin; embedding nullable | key уникален и не меняется при переводе. Хотя бы одна подпись; AI-предложение не равно опубликованному Tag. |
| Feature | key; group; name; description=[]; valueType=string/number/boolean/date; unit nullable; valueConstraints; scope/applicableTypes/tasteTransfer/transferTypes; revision; definitionOrigin | Правила переноса такие же, как у Tag. Тип, единица и семантика существующего ключа не меняются незаметно. |
| ItemTag | item: ItemId; tag: ObjectId; relevanceScore; origin; revision | Одна выбранная привязка пары Item/Tag. Предложено relevanceScore в [0,1]; это выраженность признака, не уверенность AI. |
| ItemFeature | item: ItemId; feature: ObjectId; featureRevision; value; origin; revision | Одна выбранная привязка пары Item/Feature; значение соответствует конкретной версии определения. |
| TagRelation | from/to Tag; type; origin | Сохранить существующие связи; не трактовать близость/синоним как автоматический перенос вкуса. |
| Relation / ItemRelationRole | Сохранить стороны, роли, key/group, перевести подписи на locale-контракт; добавить происхождение отношения | Связь фильмов, например ремейк/продолжение, не объединяет их ID, оценки или историю. |

scope=common означает общую семантику признака, но не автоматический перенос. Перенос допускается только явной политикой и для перечисленных типов, включённых в applicableTypes. В MVP все активные привязки movie; будущие типы не активируются ради заполнения transferTypes. По умолчанию tasteTransfer=none. Идентичная подпись и embedding не заменяют policy. Алгоритм переноса между типами отложен.

Feature.valueConstraints — ограничения выбранного типа: min/max и integerOnly для number, allowedValues для string при необходимости. number не принимает строку с числом; boolean не принимает 0/1; date хранится Date после явного преобразования входного ISO-значения; null не является ItemFeature.value. Отсутствие значения означает отсутствие привязки. Для нечислового Feature unit=null; числовой безразмерный Feature тоже имеет unit=null. Числовой с единицей хранит значение в единственной объявленной единице, например minute. Входные секунды преобразуются до записи; исходная единица и правило преобразования остаются в evidence/ProcessingRun. Неподдержанная единица отклоняется. Межколлекционная проверка учитывает applicableTypes, valueType, unit, ограничения и featureRevision.

Семантическое изменение определения требует нового ключа либо явной версионируемой операции пересборки привязок, не простого переименования. Технические поля Movie, например длительность, могут проецироваться в Feature. Тогда Movie и ItemFeature не являются двумя независимо редактируемыми источниками истины: проекция имеет derived origin от поля Movie и обновляется в той же опубликованной ревизии.

Предложения новых Tag/Feature и их соответствия словарю сохраняются в AI-артефакте и ProcessingRun. CatalogDecision фиксирует принятие, отклонение или сопоставление существующему ключу. Отдельная коллекция предложений и пользовательская модерация для MVP не нужны. Только принятые словари и привязки доступны поиску и рекомендациям.

### 6. Источники, файлы и решения обработки

Согласованный цикл: независимый сбор записей источников → сохранённые raw JSON → скачивание владельцем → ручная AI-подготовка с существующими данными БД → сохранённый пакет нормализации → проверка → публикация Movie и общих привязок. Cron и AI API позже используют те же границы, не требуют отдельного формата canonical данных.

| Сущность | Предложенные поля | Граница |
| --- | --- | --- |
| Source | Существующие key/name/description/type/baseUrl/apiUrl; подписи по locale-контракту | Поставщик данных. API и scraper — способы получения, не разные фильмы. Секреты здесь не хранятся. |
| SourceItem | source; namespace; externalId; externalUrl nullable; item: ItemId nullable; bindingDecision nullable; revision | Независимая внешняя запись; nullable item позволяет сохранить материал до сопоставления. Несколько SourceItem одного Source могут принадлежать Item. |
| SourceArtifact | kind=raw/normalized/ai_result/context/package; sourceItem nullable; processingRun nullable; storageRef; sha256; schemaVersion; capturedAt; mediaType | Неизменяемые bytes в S3 или другом сохранённом хранилище и запись метаданных в MongoDB. Для raw требуется sourceItem. |
| ProcessingRun | schemaVersion; inputArtifacts[]; databaseContextArtifact nullable; normalizerVersion; matchingVersion; reconciliationVersion; ai nullable; outputArtifacts[]; status; createdBy | Сохранённый контекст обработки. ai при использовании содержит provider/model/promptVersion, сохранённый результат и режим manual/api. |
| CatalogDecision | operationKey; kind; actor; reason; processingRun nullable; subjects[]; expectedRevisions[]; previousDecision nullable; reversesDecision nullable; changesArtifact; appliedAt | Неизменяемое принятое решение публикации/исправления/исключения/сопоставления/merge/split/словаря. |

namespace — область внешнего ID, например movie. Точный выбор namespace и нормализация внешних ID принадлежат чату 2. Сохраняются точные внешние ID после согласованного преобразования; регистр нельзя менять общей утилитой без правил источника. SourceItem.item — текущая проекция принятого сопоставления, а история привязок находится в CatalogDecision.

storageRef предложен как { backend, bucket nullable, key }; ссылка должна указывать на реально сохранённый неизменяемый объект, а не только на внешний URL или истекающую presigned-ссылку. sha256 проверяет bytes, не доказывает смысловую эквивалентность JSON. Пакет нормализации хранит новые данные Movie, Tag/Feature, привязки и Relation; конкретная структура, схема и порядок загрузки относятся к чату 2.

databaseContextArtifact сохраняет именно переданные нейронке существующие значения, ID и revision. Одних ID недостаточно, иначе после обновления БД нельзя объяснить результат сравнения. Независимая новая внешняя запись может не иметь database context.

changesArtifact хранит до/после изменённых значений, source bindings, overrides и redirects, а также правила присвоения неоднозначных связей при split. Большие результаты и snapshots не разрастаются внутри одного MongoDB-документа. История решений и объектов не удаляется при пересборке текущего состояния.

Повторная доставка operationKey с тем же содержимым возвращает прежнее решение; другое содержимое с тем же ключом — конфликт. Повторный пакет не создаёт новые Item, привязки или пользовательские сигналы. Публикация использует expectedRevisions: результат, подготовленный по устаревшему состоянию, нельзя молча записать поверх более новых данных. CatalogDecision появляется как принятое в той же транзакции, что изменения; результат неудачного запуска относится к ProcessingRun, а не маскируется под применённое решение.

Ручной override хранится как отдельное решение по полю/привязке и действует до явной отмены. Новый импорт и AI-пакет могут предлагать изменение, но не снимают override или исключение автоматически. Для отката исправления публикуется новое решение; не требуется удалять старое.

Нейронка может предлагать объединение. Публикация проверяет структуру, ссылки и противоречащие внешние ID; сходства названий недостаточно. Неоднозначный результат остаётся неопубликованным до решения владельца. Точные пороги и механизм проверки определяются в чате 2.

### 7. Merge/split и пользовательские данные

Merge A+B→A сохраняет Item B и его Movie/материалы, устанавливает B.redirectTo=A и фиксирует источники, состояния и историю решения. Внешние записи могут получить текущую привязку A; предшествующее распределение сохраняется. Исходная identity B не удаляется, не переиспользуется и не превращается в новую Movie. Служебные исправления, исключения и overrides обоих участников рассматриваются явно. Redirect между разными типами, на себя и циклы запрещены; цепочки разрешаются до живого Item без потери истории.

Событие пользователя хранит requestedItem (ссылка, через которую выполнено действие) и resolvedItem (canonical на момент действия); sourceItem/exposure nullable дают дополнительное основание. Сохранённые события и показы никогда не переписываются под новый ID. Для чтения текущей библиотеки применяется актуальная карта решений identity; конфликтующие оценки/статусы не складываются и не усредняются автоматически.

При отмене ошибочного merge восстанавливаются A и B, прежние bindings и отдельные canonical данные, с учётом принятых после merge исправлений. Нельзя без проверки вернуть старые bytes поверх всех последующих изменений. Новое решение split хранит, какие новые source records и правки назначены A/B.

Пользовательские связи, однозначно относящиеся к A или B по исходному адресу/контексту, возвращаются своему фильму. Для спорной связи согласована возможность копирования пользовательских данных обоим фильмам. Техническое предложение: копировать через правило проекции в CatalogDecision с ссылкой на исходные event IDs, не создавать фиктивные rated/saved/shown. Заметки и попытки тоже не теряются. Это меняет исходное направление vision «не назначать неоднозначные связи произвольно»: здесь назначение обоим объектам является явным служебным исключением по выбору владельца.

Фактический exposure остаётся одним показом, даже если его карточка после split признана неоднозначной. Он хранит исходный ID/контент; не заявляется, что пользователь видел две разные карточки. Копирование оценки не создаёт два независимых наблюдения вкуса. Чат 4 обязан определить учёт lineage одного события, а чат 3 — конфликт копии с уже существующим состоянием фильма и последующие независимые изменения пользователем.

Согласовано позднее: при неоднозначном not_interested оба фильма исключены до независимых явных отмен. Сохранение исходного времени cooldown остаётся техническим предложением; показ/копирование не создают новое независимое событие. Split не запускает незаметное объединение пользовательских аккаунтов.

### 8. Пользовательское состояние и события

User и Session остаются первичными данными аккаунта/доступа. Конверсия temporary→permanent сохраняет userId; вход в существующий аккаунт не объединяет профили. UserSetting сохраняется, новые поля только под решения чата 3. Password/temporary code и другие способы входа не становятся активным MVP только из-за наличия полей. UserSourceAccount полезен для будущей синхронизации, но сейчас вне активного пути.

| Сущность | Предложенные поля/изменения | Ограничения |
| --- | --- | --- |
| UserAction (новая) | eventId; schemaVersion; user; sequence; occurredAt; recordedAt; requestedItem; resolvedItem; kind; payload; sourceItem nullable; exposure nullable; expectedStateRevision nullable | Append-only, серверный порядок sequence по пользователю. eventId идемпотентен в пределах пользователя; повтор с другим payload — конфликт. |
| UserItem | Сохранить user/item/status/rating/isFavorite/note/attempts; добавить revision и projectionCheckpoint | rating=null либо целое 1–10; пять существующих статусов либо null. Пересобирается из действий и CatalogDecision. |
| ItemAttempt | Существующие поля + явный attemptId | Повторные просмотры различимы; progress>=0, известная единица, согласованные даты. Единицу и переходы задаёт чат 3. |
| UserRecommendationState | Сохранить счётчики, nextEligibleAt/isExcluded; firstShownAt/lastShownAt сделать nullable; добавить версии расчёта/checkpoint | Можно исключить фильм до первого показа. Постоянное исключение не истекает вместе с cooldown/кешем. |
| UserTasteProfile | Сохранить владельца; добавить version/checkpoint/catalog basis и представление нескольких интересов | Пересобираемая проекция; конкретное тело и confidence определит чат 4. Embedding необязателен. |
| ItemMetric | Сохранить агрегаты; добавить calculationVersion/checkpoint | Пересчитывается из реальных действий/показов, без удвоения от повторной доставки и служебных копий. |

Общий event envelope закрепляется здесь как предложение. kind/payload дискриминированы: rating set/clear, favorite set, status set/clear, note set/clear, attempt create/update/remove, saved, skipped, not_interested set/clear. Payload содержит явное новое значение либо адрес отменяемого действия в согласованном контракте; удаление из библиотеки не удаляет журнал. Детальные переходы, точная типизация payload и API принадлежат чату 3.

saved не сбрасывает начатый/завершённый статус; skipped не становится постоянным dislike; оценка, статус и избранное независимы. UserRecommendationState не является единственным первичным местом хранения not_interested: исключение восстанавливается из UserAction и проверяется как обязательное ограничение. При задержке проекции явный запрет пользователя не должен обходиться; стратегия синхронной записи запрета и checkpoint определяется в чатах 3–4.

Согласованность события и изменяемого состояния обеспечивается одной транзакцией, revision и sequence. occurredAt от клиента не определяет порядок применения; повтор имеет прежний sequence и не обновляет профиль второй раз. Значение eventId не доказывает владение: user задаётся проверенным контекстом. Одни MongoDB unique indexes не обеспечивают авторизацию.

### 9. Запросы, результаты, показы и снимки рекомендаций

| Сущность | Предложенные обязательные данные | Граница |
| --- | --- | --- |
| RecommendationRequest | requestId; user; createdAt; status; context; strategyId; strategyVersion; parameterVersion; parameters; featurePreparationVersion; profileCalculationVersion; snapshot; seed nullable; evaluationTime; results=[] | Один формат для baseline и персональной стратегии. В completed зафиксированы упорядоченные результаты, scores и причины. |
| RecommendationExposure | exposureId; user; request; resultKey; requestedItem; resolvedItem; occurredAt; recordedAt; displayContext; contentSnapshot nullable | Подтверждение реального показа, а не факт серверной выдачи. |
| RecommendationSnapshot | kind=catalog/profile/context; schemaVersion; preparation/calculationVersion; sha256; storageRef; createdAt; basis | Неизменяемые сохранённые входные значения; никакого универсального snapshot-сервиса для всех доменов. |

context содержит movie-only types, locale, режим выбора, фильтры и размер выдачи. results содержит resultKey, ItemId, rank, конечный score и структурированные reasons, ссылки на использованную ревизию/данные. Baseline не выдаёт отсутствие профиля за персонализацию. Один показ конкретного resultKey может иметь повторные доставки одного exposureId; новый показ того же результата получает новый exposureId. Результат серверной выдачи не увеличивает shownCount.

exposure проверяется против пользователя запроса и реально выданного resultKey. UserAction.exposure допустим только для того же пользователя и показанного объекта с учётом сохранённой карты identity; библиотечное действие exposure=null. Внешний ключ сам по себе не доказывает корректность feedback.

snapshot у запроса ссылается на неизменяемые catalog/profile/context snapshots. Сохраняются все входы, влияющие на кандидатов, scoring, exclusions и diversity: полный допустимый набор кандидатов и его признаки/метрики, определения словаря, профиль, состояние библиотеки/исключений, недавние показы, параметры, identity mapping, точное время вычисления и seed при случайности. Допустимо разделять snapshots между запросами, но digest проверяет неизменность содержимого. Одних ID кандидатов, top-N и номеров версий недостаточно.

Контекст снимка отделён от текущих данных: обновление Movie или вкуса не разрушает воспроизводимость прошлого сравнения. Удаление входов до окончания хранения запроса запрещает заявлять воспроизводимость. Как сохранять размеры, повторно использовать снимки и читать их без широкого копирования — чат 4. Версия алгоритма должна ссылаться на восстанавливаемую реализацию/конфигурацию. Сам факт наличия снимков не доказывает детерминизм алгоритма.

Проверка актуальных запретов перед выдачей может отличаться от сохранённого расчёта: результат после фильтрации и фактически возвращённый порядок должны сохраняться явно. Replay исторического расчёта и новая живая выдача — разные операции. До публичного интерфейса будущий чат определяет повторную проверку доступности при подтверждении устаревшей карточки.

Уникальность ролей title на locale, applicableTypes, Origin, Feature.unit/valueType и соответствие Item/Movie — сервисные/внутридокументные инварианты, не обещание одного unique multikey index. Точные имена новых индексов и миграции фиксирует общий план после уточнения операций. RU/EN/alias-поиск обеспечивается текущим Meilisearch, не новым универсальным MongoDB text index.

### 2. Выбор источников и демонстрационный набор

Источники **не выбраны**. Владелец подтверждает названия, способ получения и доступный объём материалов. Критерии: устойчивые ID произведений и понятная гранулярность work/release; сохранение JSON либо ручной JSON-транскрипции с исходным снимком; заметное пересечение; дополняющие RU/EN названия/aliases и характеристики; различимые rating scales/counts; конфликты и ремейки; возможность использовать выбранные материалы в демонстрации и сохранять provenance. Доступность API не предполагается. ID редакции требует отдельного согласованного namespace и сопоставления произведению. Платные API и секреты не обязательны.

Выбор/доступность материалов блокирует реальные пакеты и per-source правила, но не обсуждение общего контракта; сбор не начинается.

### 3. Формат bisky.catalog-import/1

Предложен каталог manifest.json + raw/ + normalized/ + ai/ + context/ + decisions/. Без архива в первом MVP. JSON — UTF-8; format=bisky.catalog-import, schemaVersion=1. Неизвестная версия отклоняется до публикации; преобразование версии создаёт новый ProcessingRun. Формальная JSON Schema будет артефактом реализации; здесь фиксируется её предполагаемый контракт.

Manifest содержит packageId (UUID), createdAt UTC, mode=manual, synthetic boolean; версии normalizer/matching/reconciliation; sourceProfilesArtifact и databaseContextArtifact nullable; files с artifactKey/kind/path/mediaType/sizeBytes/sha256; records с recordKey/sourceKey/namespace/externalId/capturedAt/externalUrl и rawArtifact/normalizedArtifact/aiArtifact nullable; units с unitKey/action/records/proposedItem/proposalArtifact/dependsOn. Один publish unit — один новый фильм либо новая ревизия существующего со всеми его привязками. Для нового proposedItem={kind:new,localKey}, для существующего {kind:existing,itemId,expectedRevision}. IDs назначает сервер в транзакции и сохраняет в результате; AI не назначает ObjectId.

Словарные решения — отдельные units до зависимых фильмов; межфильмовые Relation — после обоих endpoints. Зависимости явные; циклы и конфликтующие записи одного subject в разных units отклоняются. Несколько source records одного фильма входят в одну группу. Merge/split/исключение не исполняются как скрытые AI-инструкции: отдельный рассмотренный служебный запрос с diff/revisions. Records без matching сохраняются без publish unit.

Сокращённый **синтетический** пример; placeholders и неполный files делают его пояснением структуры, а не готовым импортным пакетом:

```text
normalized/b-77.json

```

### 4. Материалы, версии и provenance

Raw — неизменённые bytes исходного JSON. Для сохранённой страницы raw JSON явно обозначает ручную транскрипцию, URL/время, точные извлечённые значения и original snapshot как raw artifact подходящего mediaType. Транскрипция не выдаётся за ответ API. Парсер страниц не требуется. Независимый normalized JSON каждой записи и целый AI-результат, включая rejected proposals, сохраняются отдельно. AI metadata: mode=manual, provider/model либо явно unknown, promptVersion, сохранённый prompt/input, result artifact, preparedAt. Повторная генерация создаёт новые artifacts/run.

Context содержит переданные canonical значения, IDs/revisions, определения словаря, кандидатов и правила source priorities. Пользовательские данные/полная БД не передаются. Номер версии ссылается на сохранённые правила/конфигурацию и идентифицируемую реализацию. Ручная генерация не обязана повторяться побитово: объяснение опирается на сохранённый результат и решение.

storageRef={backend:s3,bucket:bucket приложения,key:catalog/artifacts/<artifactId>/<sha256>.<ext>}. Ключ назначает импорт; новые bytes — новый ID/key. До Mongo commit проверяются фактические size/hash сохранённого объекта. Неизменяемость обеспечивается правилами приложения/доступа, текущий PutObject её не гарантирует. Public URL StorageService не используется для raw/AI/context; доступ только служебный. Закрытая bucket policy — зависимость запуска, не проверенный факт. Постер необязателен; публичный media artifact отделён от приватных материалов. URL источника/presigned URL не заменяет storageRef.

Origin сохраняет kind, CatalogDecision, evidence [{artifact,pointer}], ProcessingRun и ссылки на inputs/правило derived. Scalar использует fieldOrigins; текст/alias/элемент — устойчивый key+origin; привязка — собственный origin. AI-перевод остаётся ai после ручного принятия; ручная замена имеет manual origin. Совпадающие source claims сохраняются как несколько evidence. Неизвестный исходный locale=null; предположение AI о языке не выдаётся за сообщение источника. Raw не переписывается при исправлении.

**Ответ владельца:** предпочтительно удалять материалы, а не хранить всё бессрочно. Предложение безусловного хранения без TTL не принято. Срок, состав удаления и сохранность файлов, поддерживающих опубликованные данные, ещё не определены; до их выбора автоматическое удаление не считается согласованным контрактом. Предложенный вариант для обсуждения: через 90 дней удалять только промежуточные/отклонённые artifacts, не используемые принятыми решениями, provenance, before/after и snapshots. Это предложение, не выбранный срок. Удаление исходников принятых данных ограничит прежние обещания пересборки/объяснения в §§6,10 модели и DoD 3,7,11; такое изменение требует явного решения о сохраняемых доказательствах. UserAction, identity, активные запреты и журнал решений не считаются разрешёнными к удалению общим ответом о материалах. Отсутствующий artifact нельзя заменять выдуманными данными.

Исторический replay использует принятые bindings/identity/decisions и сохранённые outputs, не выполняет AI/matching заново. Обработка по новым правилам создаёт новый run и diff с прежними Item IDs/активными overrides/blocks; изменение identity только отдельным решением. Перед применением проверяются revisions. Это отличает восстановление опубликованного состояния от предложения новой reconciliation.

### 5. ID, повтор и частичный сбой

Уникальность SourceItem: (Source._id,namespace,externalId), базовый namespace=movie. ID остаётся строкой: не терять ведущие нули, не менять регистр и не преобразовывать в number; преобразование допустимо только по сохранённому профилю Source. Профиль задаёт формат/гранулярность/namespace. Его изменение, меняющее identity, требует отдельной операции, не незаметной нормализации. API/scraper/import поставщика используют один Source. Один Item может иметь несколько SourceItem одного Source.

Cross-source identifiers — claims {authoritySourceKey,namespace,value,evidence}. Авторитетный ID ищется через SourceItem соответствующего authority Source. Подтверждённый cross-reference резервирует такую identity в транзакции matching; запись authority без собственного raw имеет evidence другого источника в CatalogDecision. Поздний raw дополняет ту же SourceItem. AI-only ID не резервируется автоматически. Это **уточнение SourceItem**: внешняя identity может быть известна до получения собственной записи. Unique constraint защищает конкурентное назначение ID разным Item; альтернативные/отклонённые claims остаются в artifacts.

ProcessingRun.packageId unique; packageDigest — SHA-256 bytes manifest с file hashes. Та же packageId с другими bytes — конфликт; исправленный пакет имеет новый UUID. OperationKey=<packageId>/<unitKey>; contentDigest фиксирует действие, inputs и expectedRevisions. Принятое решение проверяется до stale-revision проверки: тот же key/digest возвращает прежний результат/назначенные IDs; иной payload конфликтует. Новый packageId с прежними records сначала проходит matching по внешним identity, не создаёт новый Item. Неизменившиеся canonical значения/evidence дают no-op без увеличения revision; новый snapshot получения может сохраняться отдельно.

Статусы run: staged → validated → applying → completed или partial/pending/failed/cancelled. unitResultsArtifact содержит applied/noop/pending/failed/skipped_dependency и decision/error на каждый unit. Статус run — проекция; истина принятия unit — CatalogDecision. Сохранение raw не означает публикацию. SourceItem.item=null до принятия matching; metadata имеет идемпотентные keys. Run создаётся до upload; artifact IDs/keys сохраняются для resume. Непривязанные S3 objects не удаляются автоматически; cleanup проверяет ссылки и требует отдельно разрешённого запуска.

На unit одна MongoTransactionService.run: проверка revisions/ID/blocks, Item+Movie одной revision, bindings/признаки и CatalogDecision. Session передаётся всем операциям последовательно. Upload/AI/Meilisearch/queue вне callback; IDs/keys и changesArtifact готовятся заранее, callback может повторяться. Потеря ответа после commit обнаруживается по operationKey. Без принятого решения canonical unit не считается опубликованным. Ошибка другой группы не откатывает принятые: отчёт partial. Retry продолжает непринятые units; stale proposal требует нового рассмотренного пакета.

Multi-document transactions требуют поддерживающего deployment MongoDB; standalone их не поддерживает ([официальные ограничения](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)). Серверная версия/topology здесь не установлены: DatabaseModule читает MONGO_URL, пример URL без replicaSet не доказывает topology. До приёмки нужна изолированная подходящая БД; подключений и изменения deployment не было. Цепочка обычных writes не является атомарным fallback.

Cancellation проверяется между units; committed группы сохраняются, даже если job cancelled. Отмена публикации — новое CatalogDecision с текущими revisions. Временные storage/DB/search сбои допускают retry; invalid package/ID conflict/stale revision требуют исправления. Job state не заменяет run report. Правка/exclusion между validate и commit защищена revisions; autoIndex не разрешает менять работающие индексы.

### 6. Matching и ручные решения

Порядок: собственная внешняя identity → подтверждённые IDs авторитетных источников → кандидаты по названиям. Уже bound record не создаёт другой Item. Несколько trusted IDs к одному живому Item дают automatic match при отсутствии противоречащих accepted claims/suppression. Redirect учитывает исходную identity/запреты. IDs к разным Item — conflict, даже при одинаковом названии; импорт не делает merge. AI sameAs само по себе не trusted ID. Новый ID без доказанного match допускает создание только после рассмотрения кандидатов.

Для сравнения названий: Unicode-нормализация, lower case, пробелы/пунктуация; исходные bytes/тексты сохраняются. RU/EN/original/aliases дают top-10 кандидатов с evidence и расхождениями года/страны/длительности/режиссёра, если известны. Режиссёр — contextual строка normalized, не новая Item-сущность. Год может отличаться из-за даты релиза. Название+год не unique и не доказательство identity; числовой score не включает auto-merge. Малый набор допускает поиск по canonical названиям MongoDB; отставший Meilisearch не доказывает отсутствие совпадений.

Решения: match_existing, create_new, defer, reject/suppress_source_record, correct_identifier с исходным claim/причиной либо отдельный merge. Rebind уже связанной записи — отдельное решение, не side effect import. Хранятся actor/reason/evidence/candidates/context и expectedRevisions Item/SourceItem/dictionary. Разные trusted IDs не принимаются принудительно без исправления ошибочного claim либо обоснованного merge. Pending record не публикует карточку. AI mappings новых ключей/неоднозначных отношений принимаются отдельно.

### 7. Reconciliation, Movie и overrides

Movie v1 использует предложенные поля модели: titles/descriptions, releaseYear, runtimeMinutes, originalLanguage, countryCodes, poster nullable, sourceMetrics, fieldOrigins. Publication gate: непустое название, валидная identity, согласованные dictionary bindings, provenance всех выбранных значений. Неизвестный scalar=null/массив пустой; нет выдуманных года/длительности/рейтинга. Согласованный fallback названия: title нужного ru/en → original → title другого активного языка → alias; actualLocale/role возвращаются честно. Технически предложен устойчивый порядок key при выборе aliases. Для descriptions: нужная locale → другая ru/en → null. Выбор при нескольких originals фиксирует решение. Поиск aliases не зависит от fallback.

**Ответ владельца:** допускается публикация без одного перевода; предложенный fallback названий согласован ответом на вопрос с указанным порядком. Это закрывает соответствующий вопрос §§3,4 модели: RU/EN ожидаются при подготовке, но не являются обязательной парой для available. Детали descriptions/порядка нескольких originals остаются техническим предложением.

Reconciliation v1 выбирает по field/locale: (1) активный manual override, включая clear/block; (2) принятые source claims по сохранённому per-field/per-locale приоритету; (3) принятое AI enrichment/translation для пропуска; (4) отсутствие. Конкретный порядок источников отложен. AI-transform имеет ai/derived origin и evidence исходного claim, не повышает достоверность названием модели. Равный приоритет и разные существенные значения — ручной конфликт. Identity/допуск конфликтуют — unit pending; допустимый field conflict публикуется только с рассмотренным выбором winner/alternatives. Годы/длительности/рейтинги не усредняются. Поздний snapshot заменяет claim того же источника по правилам; capturedAt не заменяет observedAt метрики.

Названия/aliases/страны объединяются с provenance. Aliases дедуплицируются по locale+сравнительному тексту; роли original/title не исчезают. Preferred title выбирается per locale. ItemTag одна пара, relevanceScore [0,1]; AI confidence остаётся отдельно в предложении. Разные relevanceScore выбираются по правилу/решению, не суммируются. Feature соответствует valueType/unit/constraints/definitionRevision; преобразование единицы сохраняет rule/evidence. sourceMetrics разделены по source/scale/metricKey/time; baseline нормализуется в чате 4. Runtime→Feature derived обновляется с Movie: две независимо редактируемые длительности запрещены.

Override адресуется Item+field path+locale/elementKey либо паре Item/Tag, Item/Feature, Relation, не индексу массива. Решение: set/clear/block, значение, actor/reason, expected revision, supersededDecision. Clear фиксирует отсутствие. Block запрещает поле/материал, включая повторно полученный вариант, до explicit release_block. Import показывает альтернативу, но не снимает override. Его отмена пересчитывает из актуальных разрешённых claims, не слепо возвращает старые bytes. Material block может дополнительно адресовать source record+pointer/digest; whole-field block защищает от косметического изменения bytes.

Отсутствующее поле delta не удаляет значение. Normalized record объявляет coverage и mode=delta/full: delta заменяет присутствующие claims; full заменяет claims записи только в declared coverage. Явный null отзывает scalar claim источника, пустой список — его claims списка; manual overrides/другие источники сохраняются. Исчезновение записи из пакета не удаляет её. Отзыв единственного обязательного названия переводит Item в unavailable после принятого решения, сохраняя identity.

Relation хранит стороны/role keys. Направленность задана словарём; направленный tuple сохраняет порядок, явно симметричный сортирует стороны по ItemId. Canonical одинаковые tuples не размножаются, evidence дополняется. Relation не sameAs. Неоднозначные endpoints остаются pending, не получают ближайшее название.

### 8. Merge/split, исправление и исключение

Merge A+B→A — отдельный diff с revisions обоих Item, SourceItem и решений. Сохраняются B/Movie, прежние bindings/redirects, before/after. Текущие bindings переходят к A, B.redirectTo=A; reconciliation сохраняет alternatives. Конфликты source ID, overrides, blocks, Relation endpoints/control state решаются явно; конфликтующий merge pending. Циклы/self/different-type redirects запрещены. Исключение любого участника сохраняется на общем результате до отдельного release decision; merge не обходит запрет.

Split/reverse_merge — новое решение reversesDecision с текущими revisions и планом назначения: прежние records назад; новые после merge A/B/pending; поля/overrides/blocks/Relation конкретному получателю либо явно обоим. Восстанавливаются прежние A/B IDs, redirect B снимается. Новые части настоящего разделения получают новые IDs, старые не переиспользуются. Поздние правки не заменяются старым snapshot. Nested merge требует учёта входящих redirects. Неоднозначный source binding=null до решения, спорный Relation не публикуется произвольным ребром.

UserAction/exposures не переписываются. Предложенное правило проекций: до merge — прежняя identity; после через прежний B или однозначный SourceItem — B; действие по общей A без различимого контекста — явно ambiguous. Copy-to-both задаётся CatalogDecision согласно прежнему выбору владельца. Lineage ссылается на исходные eventId/attemptId; фиктивных rated/saved/shown нет. Один exposure остаётся одним показом. Самостоятельные оценки/статусы/заметки получателя копия не перезаписывает: правило конфликта определяет чат 3, иначе такой split pending. Чат 4 исключает двойной вклад исходного события. **Согласовано владельцем:** после split неоднозначный not_interested исключает оба фильма из рекомендаций до явной отмены пользователем; отмена для одного фильма не снимает запрет с другого. Это закрывает вопрос not_interested в §7 модели. Сохранение исходного времени cooldown остаётся предложением, отдельно не утверждено.

Correction — override/clear/block с diff/provenance. Item exclusion сохраняет isExcluded+decision без удаления библиотеки/истории. SourceItem suppression запрещает matching/publication ещё до Item; повтор сохраняет raw, но не создаёт карточку. Rebind/split учитывают suppression/blocks. Новые ID исключённого фильма не разрешают обход: exact match уважает запрет, подозрительный дубль ожидает решения. Полностью неузнаваемый дубль без evidence нельзя гарантированно обнаружить, поэтому create_new требует рассмотрения кандидатов. Release всегда отдельное решение, не полномочие AI-пакета.

Исключённый Item отсутствует в публичном каталоге/поиске/рекомендациях; библиотечная история сохраняется по приватному контракту чата 3. Block материала убирает его из карточки/alias/поиска/публичной ссылки; утрата обязательного текста делает Item unavailable. Raw не служит запасным публичным текстом. Отзыв доступа к media/bucket отдельно необходим: удаление поискового документа не отзывает выданную presigned ссылку.

### 9. Служебный запуск и полномочия

Предложен доверенный локальный CLI через Nest application context и существующие services/repositories: validate/dry-run, stage/apply, inspect run/pending, decide matching/dictionary, correct/exclude, merge/split, rebuild-search. Это названия проектируемых операций, готовых команд сейчас нет. Вход — явно заданная папка/environment target. Actor — существующий служебный User с catalog.manage; роль/actor из AI JSON не доверенные. Запуск в MVP ограничен владельцем с административным доступом к машине и credentials окружения; знание userId не удостоверяет caller. Общедоступный HTTP import endpoint не требуется. Если нужен HTTP позже, обязательны AccessTokenGuard+RolesGuard и серверная выдача роли — зависимость чата 3.

catalog.manage разрешает import/ручные решения/identity/исправление/исключение; обычная регистрация роль не выдаёт. Выдача — отдельное административное действие. Каталог не предоставляет чтение чужих пользовательских данных: split использует identity mapping/lineage, не разрешает оператору читать личные заметки для решения конфликтов. Audit фиксирует реального actor, способ запуска и reason. Публичная атрибуция служебному аккаунту не меняет происхождение.

Apply/rebuild jobs: payload {runId}, version=1, handler в owning module; JSON не переносится в Redis. Queue IDs/deduplication — оптимизация, повторы защищены Mongo keys. Принятое CatalogDecision в MongoDB — долговечная основа доставки: диспетчер дочитывает неподтверждённые решения после аварии commit→JobService.add. Retention удаляет завершённые jobs, но не решения/run. Универсальная outbox-платформа не требуется.

### 10. Поисковый документ, API и восстановление

Один search document на живой eligible Item; id=строка Item._id. Предложено searchDocumentVersion=1: id, type=movie, catalogRevision, titlesRu[], titlesEn[], originals[], aliases[], tagKeys[], tagNamesRu[], tagNamesEn[], tagAliases[], releaseYear/runtimeMinutes nullable, countryCodes[], originalLanguage nullable, features с allowlisted типизированными ключами. Originals/aliases сохраняют разрешённые написания другого/неизвестного locale. Отсутствующий перевод не заменяется ложной locale. Raw/AI proposals/redirected IDs/запрещённые тексты не индексируются. Descriptions остаются Movie; поиск v1 по названиям/тегам/характеристикам, не всему raw.

searchableAttributes: titlesRu, titlesEn, originals, aliases, tagNamesRu, tagNamesEn, tagAliases. Filterable: type, tagKeys, releaseYear, runtimeMinutes, countryCodes, originalLanguage и конкретные разрешённые features. Sortable: releaseYear, runtimeMinutes, id; пустой query — устойчивый id, query — relevance с id tie-breaker. Поддержку выбранной сортировки подтвердить установленным Meilisearch при реализации. Рейтинги не превращаются в универсальную popularity до чата 4. Фильтры: год/длительность диапазоном, страны/язык, tagKeys (OR внутри группы, AND между группами), согласованные Features с типом/единицей. Неизвестный key/type/unit отклоняется. Adult/age policy остаётся открытой зависимостью публичного запуска, не выдуманным фильтром допуска.

Будущие movie-only методы: GET /catalog/movies (query, filters, limit, offset, locale), GET /catalog/movies/:id (карточка/разрешённый redirect). DTO возвращает canonical id/revision, выбранное название+actualLocale/role и разрешённые сведения, без приватных artifacts/решений. Limit 1–100, offset>=0, query до 200 символов. Клиент не задаёт filter expression/Mongo filters/index name; сервис строит запрос из allowlist. Ошибка фильтра — 400, недоступная публичная карточка — 404. Доступный старый duplicate ID возвращает requestedId/resolvedId, но redirect не обходит exclusion. Каталог не регистрирует exposure.

После Meilisearch hits сервис перечитывает Item/Movie, проверяет current availability/exclusion/redirect, revision и filters; DTO строится из текущих canonical данных. Устаревший alias не обходит material block. При stale revision hit не возвращается до актуализации; можно дочитать следующие с ограниченным бюджетом. EstimatedTotalHits не выдаётся за точный total после фильтрации. Отставание индекса ограничивает полноту новых результатов. Непустой query при search failure — 503, не ложная пустая выдача; пустой query может обходить MongoDB с реализованными фильтрами/устойчивым id и признаком degraded. Locale меняет отображение, не отсекает aliases другого языка.

Incremental sync перечитывает текущее состояние затронутых Item: upsert живого документа или delete невыдаваемого/redirected ID. Старый job не пишет свой старый snapshot. Один сериализованный writer на movie index, lease/fencing, проверка revision после task; новая revision требует повторного sync до checkpoint. Checkpoint продвигается только после подтверждённого succeeded; crash после Meilisearch до checkpoint безопасно повторяет sync. CatalogDecision.catalogSequence unique назначается counter в SearchIndexState в той же транзакции публикации: устойчивый порядок, не только appliedAt. Это сериализует публикации маленького MVP, не создаёт новый Item ID. Sync словаря затрагивает все Item с изменившейся подписью/привязкой.

Текущий SearchService waitForTask недостаточен для подтверждения domain sync: нужно явное succeeded/failed всех settings/upsert/delete tasks и taskUid либо эквивалентное проверяемое подтверждение. Это предложенное минимальное изменение инфраструктурного API, не сделанная правка. Между MongoDB и поиском общей транзакции нет. Mongo fencing сам не останавливает старый запрос к Meilisearch: после потери lease новый writer ждёт завершения прежнего writer/tasks либо восстанавливает индекс, не начинает конкурирующие записи.

Rebuild: создать bisky_movies_v1_<generation> и settings → подтвердить успех → приостановить служебные catalog writes/incremental writer → зафиксировать catalogSequence → обойти текущие eligible Item по _id пакетами → построить из MongoDB → дождаться succeeded → проверить count/revisions, RU/EN/alias queries и отсутствие forbidden/redirect IDs → атомарно сменить activeIndex в SearchIndexState и checkpoint → возобновить writes. Пауза для маленького набора проще snapshot+delta catch-up; она не блокирует пользовательские события, не участвующие в search document. При ошибке старый index остаётся active, failed rebuild сохраняется, writes возобновляются.

Search читает activeIndex через служебную запись; кеш указателя не должен переживать удаление старого индекса. Старый индекс сохраняется до завершения запросов и отдельной очистки; rollback pointer требует актуализации новых запретов. Index swap API текущего SearchService не нужен. Потеря всего Meilisearch восстанавливается полной пересборкой без смены MongoDB IDs/overrides. Rebuild не восстанавливает недостающие canonical artifacts; это отдельная операция replay решений.

Это будущие сценарии на изолированном наборе, **не выполненные runtime-проверки**.

### 2. Пользовательский путь и доступ

**Актуальное решение владельца заменяет прежнюю temporary/permanent модель:** в продукте только обычные сохраняемые аккаунты. Два направления регистрации: локально с сгенерированным логином и постоянным секретным кодом либо через доступный внешний сервис. Код можно перевыпустить; email необязателен. Для пользователей в РФ выбран Яндекс, вне РФ — Google. Это явное расширение прежнего Google-only MVP, а не реализация дополнительных способов входа без запроса. Production enum/type/поля пока прежние.

Регистрация → обычная Session → рекомендации/поиск → подтверждённые показы → библиотека/попытки/прогресс в минутах. Начальная оценка знакомых фильмов необязательна. При подключении способа входа к текущему аккаунту сохраняются User._id/все данные; отдельный вход в существующий аккаунт меняет активный principal, но не объединяет библиотеки/события. Прежний аккаунт сохраняется и доступен по своему коду/провайдеру; отдельная guest cookie и автоматический возврат guest после logout больше не нужны. После logout пользователь выбирает вход или создание нового аккаунта.

Локальная регистрация создаёт User с заранее назначенным _id, сгенерированным уникальным username=bisky_<random>, displayName=Пользователь, locale=ru/en, role=user, linkedAccounts=[]. Client не задаёт userId/role/type/username. Одной транзакцией создаются User, Session, credential hash и receipt операции. Не заводить аккаунт только потому, что посетитель открыл каталог: создание — отдельное действие. Регистрация через сервис создаёт тот же обычный User с сгенерированным логином; локальный код первоначально отсутствует и может быть добавлен после свежего подтверждения входа у провайдера.

Согласовано: аккаунты/библиотека/история не удаляются по времени или неактивности; rolling Session действует четыре календарных месяца с продлением через refresh. Истечение Session прекращает доступ, не удаляет User. Access JWT остаётся 15 минут. Пересмотр оснований хранения/удаление по законному запросу владельца данных — отдельная политика; «не удалять по времени» не означает запрет выполнения таких требований.

Одна активная refresh cookie HttpOnly, Secure в HTTPS, host-only без Domain, Path=/auth, SameSite=Lax для same-site web/API. Access JWT в памяти клиента, Bearer; refresh не выдаётся в JSON/localStorage. При переключении аккаунта клиент очищает память/owner caches и загружает нового владельца. Прежняя Session браузера отзывается при явном переключении, но User/данные не удаляются. Чужие сессии прежнего аккаунта не отзываются только из-за переключения.

Cookie-операции: allowlisted Origin, JSON и anti-CSRF header с server-issued browser/session proof; CORS credentials сам по себе не защита. Bootstrap выдаёт proof, не создаёт User и не восстанавливает владение по логину/IP. Публичный OAuth callback проверяет своё одноразовое state+browser binding. Cross-site deployment требует отдельной cookie/CSRF конфигурации; локальное исключение Secure допустимо только в явно локальном HTTP dev-режиме.

### 2.1. Постоянный код, защита и перевыпуск

Согласован постоянный код, а не одноразовый OTP. Техническое предложение: криптографически случайные 24 bytes, base64url без padding (32 символа, 192 bits); это секрет, не короткий PIN. Логин не секрет. Код хранится как select:false accessCodeHash через существующий bcrypt helper с rounds=12; длина меньше ограничения bcrypt, raw не хранится в User/Session/логах/URL. Не использовать temporaryCodeHash для постоянного credential. В интерфейсе код можно скопировать/сохранить; повторный просмотр существующего кода не предоставляется.

LoginDto={login,accessCode}; сервер нормализует только login по User.username contract, код сравнивает точно. Ошибка неверного логина/кода одна и та же, включая HTTP и сопоставимое время обработки; для неизвестного login выполнять dummy hash comparison. Лимиты попыток по аккаунту и источнику независимо (стартовое предложение: 5 неудач за 15 минут на login, 30 за 15 минут на источник, нарастающая задержка); ограничения регистрации/восстановления отдельно. Не блокировать аккаунт навсегда из-за чужих попыток. CAPTCHA — дополнительная мера после подозрительных запросов, не замена длинному коду. HTTPS/no-store обязательны для выдачи секрета, secret поля редактируются логгером. Это один фактор, не MFA.

Перевыпуск требует живой Session и свежего доказательства: текущий accessCode либо одноразовый reauthentication grant после успешного разрешённого provider flow (предложено не старше 5 минут). Одной украденной Session недостаточно. Генерация/hash до callback; CAS User credentialVersion+revision, новый hash и AccountAccessEvent, отзыв всех Session и создание заменяющей Session — одна транзакция. Старый код немедленно недействителен, новый срок существования не ограничен Session expiry. Concurrent regenerate: один победитель, второй 409 CREDENTIAL_CONFLICT. Новый код не отправляется в email/support logs.

Для потери ответа registration/regenerate предложен короткий CredentialOperationReceipt: unique operationId, browser/owner binding, intentDigest, outcome IDs, retryUntil и encryptedSecret. Секрет зашифрован AEAD отдельным серверным ключом, не сохранён открыто или под JWT secrets; срок выдачи предложен 5 минут, логического expired достаточно для отказа, отдельная очистка ciphertext не удаляет аккаунт/журнал. Точный retry с тем же proof возвращает прежний результат, другой intent — 409. Отсутствие working encryption/delivery contract блокирует обещание надёжного повторного получения, не допускает генерацию ещё одного кода под тем же ключом. После окна секрет не выдаётся; дальнейший перевыпуск требует доказательства/восстановления. Не создавать receipt из client userId.

### 2.2. Необязательный email и потеря ключа

**Последний ответ владельца заменяет предложение поддержки:** постоянный код и есть ключ доступа. Без него, доступа к подтверждённому email и привязанного доступного provider восстановление невозможно; поддержка не выполняет обход. Отдельный резервный ключ не вводится. Аккаунт/библиотека/история сохраняются, отсутствие доступа не является удалением. Это ограничение сообщается при выдаче кода. Действующая Session позволяет пользоваться аккаунтом до её expiry/revoke, но не заменяет свежую проверку кода/provider для перевыпуска или добавления recovery email.

Email необязателен и пригоден для recovery только после отдельного подтверждения владельцем. Не использовать email провайдера для auto-link и не назначать Bisky подтверждение без собственного challenge. Add/change требует свежего reauthentication proof; verification token случайный, одноразовый, hash в Mongo, expiry 30 минут, bound user+email+credentialVersion. Unique email collision не раскрывает другой User. Неподтверждённый/удалённый адрес не разрешает reset. Изменение адреса атомарно отзывает старые recovery challenges; прежний verified email действует до подтверждения нового. Notification/verification отправляются через существующий queue-only mail flow, templates — будущая реализация.

Email recovery: start всегда одинаковый 202; только соответствующему verified email отправляется краткоживущий reset token (предложено 30 минут), хранится только hash. Complete с token создаёт новый постоянный код и защищённый receipt, увеличивает credentialVersion, отзывает все Session, потребляет challenge и пишет AccountAccessEvent одной транзакцией. Новый код и Session выдаются пользователю; старый код не раскрывается. Параллельный перевыпуск/смена email делает прежний challenge невалидным. Email используется для recovery, не отдельный OTP-login. В письме reset link, не accessCode; токен не попадает в referer/логи и не потребляется обычным GET/link scanner. Account existence не раскрывается через start/errors.

Пользователь с действующим привязанным разрешённым provider может войти им и перевыпустить код после reauth. Если нет ни кода, ни verified email, ни доступного provider, логин/IP/история фильмов/рассказ пользователя не позволяют восстановить доступ. Support bypass, account.recover permission, tickets, ручные reset grants и резервные recovery keys не входят в MVP. Общие полномочия оператора базы технически шире API, но административное редактирование credentials не считается предусмотренным способом восстановления.

### 3. Refresh, rotation, revoke и конкурентность

Session._id — identity одной семьи refresh, сохраняется при rotation. Добавить rotation>=0, currentRefreshJti (случайный UUID), refreshIssuedAt, revokedAt nullable, revokeReason nullable и revision. Refresh JWT: существующие sub/sessionId/type плюс jti/rotation; iss/aud/exp/iat проверяет Bisky verifier. Access остаётся 15 минут; refresh expiresAt совпадает с exp; согласован rolling срок **четыре месяца** с момента создания/успешной rotation для всех пользовательских сессий. Техническая конкретизация: прибавить четыре месяца к UTC дате с ограничением дня последним днём целевого месяца; затем вычислить exp. Это не 120 дней и не строка 4m (минуты) для JWT. Текущую JWT_REFRESH_EXPIRATION=30d потребуется заменить явным exp/параметром срока при P3. Raw токены не записываются в Mongo/logs/URL. Для высокоэнтропийного refresh JWT — детерминированный SHA-256 полного токена в refreshTokenHash для точного CAS; bcrypt hashValue остаётся для коротких секретов/будущих паролей, не применяется напрямую к длинному JWT. Это конкретизация поля, не изменение работающей базы.

Rotation: проверить signature/type/claims/expiry → сверить user/session, current hash+jti+rotation, revokedAt и expiresAt → CAS прежнего поколения → записать новое hash/jti/rotation/время/expiry → commit → Set-Cookie и access. Новые jti/iat/exp/token bytes и operationId готовятся до повторяемого callback; JWT helper должен уметь подписывать именно эти claims с фиксированным iat/exp. Signatures Google не проверяются Bisky HS256 secrets.

Предложен refresh DTO {operationId: UUID}. Для retry после потери ответа Session хранит один короткий rotationReceipt: operationId, digest запроса, previousTokenHash, fromRotation/toRotation, nextJti, issuedAt/expiresAt, retryUntil. В течение 30 секунд точный повтор того же старого credential и operationId возвращает то же поколение refresh, восстанавливаемое подписью фиксированных claims; hash результата должен совпасть с currentRefreshHash. Access можно выдать заново. Receipt не продлевает срок и не вращает повторно. После следующей rotation прежний receipt недействителен. Клиент сериализует refresh между вкладками и повторяет тот же operationId, не выпускает параллельно разные операции.

Валидно подписанный старый токен с чужим operationId, иным payload либо вне retry-window — reuse: отдельная committed запись revokedAt/reason=refresh_reuse, очистка cookie, 401. Отзыв нельзя откатить исключением внутри той же transaction. Недостоверный токен не позволяет отозвать Session по непроверенному sessionId. Случайный сетевой replay после окна неотличим от кражи; повторный вход возможен через свой постоянный код или разрешённый provider, при потере обоих — recovery по подтверждённому email; без него и разрешённого provider доступ восстановить нельзя. Это явная цена bounded retry, не обещание exactly-once HTTP.

AccessTokenGuard после JWT проверяет Session.user=sub, отсутствие revokedAt, expiresAt>now и существование User; principal роли строит из актуального User.role/служебных permissions, не доверяет устаревшему roles в JWT. Немедленный revoke действует на последующие проверки; уже принятый запрос не отменяется магически. Для state-changing транзакций повторно проверять и обновлять Session revision/lastUsedAt, чтобы concurrent revoke и mutation сериализовались на одной Session. Если logout commit раньше, mutation не применяется; если mutation раньше, logout не отменяет принятое событие. Переключения аккаунтов не повышают роль и не меняют владельца прежней Session.

### 4. Внешние сервисы и географический допуск

Согласован выбор владельца: Яндекс для пользователей в РФ, Google вне РФ. Правовая норма для подпадающего под неё российского владельца относится к пользователям, **находящимся** в РФ, а не только живущим там/имеющим российское гражданство. Перечень и условия системы задаёт [149-ФЗ, статья 8, часть 10](https://www.consultant.ru/document/cons_doc_LAW_61798/78b773a28f3ad19eb234697b20ab1d48c09f748a/). Региональная маршрутизация — мера реализации выбора, не доказательство полной юридической совместимости сайта: нужны данные владельца/оператора, требований защиты и обработки ПД.

GET /auth/methods возвращает доступные методы для текущего запроса: local_code и региональный provider. Сервер определяет регион по доверенному edge/геолокации адреса, не client country, locale, email domain или произвольному X-Forwarded-For. При РФ или неопределённом регионе Google запрещён на begin/complete/link/reauth, включая прямой API вызов; unknown предлагает локальный вход/Яндекс. При outside-RF разрешён Google. Точный геосервис/edge и эксплуатационные исключения выбираются до запуска; VPN/proxy/IP errors означают отсутствие абсолютной гарантии фактического местонахождения. Не обещать, что кнопка или IP доказали выполнение закона. Не собирать паспорт/точную геолокацию ради этого без отдельного решения.

Не блокировать чтение уже принадлежащей пользователю библиотеки по provider источнику аккаунта. Google-only аккаунт при нахождении в РФ должен использовать ранее настроенный локальный код/доступный привязанный Яндекс/recovery; Google reauth сервер не разрешает в этом регионе. Provider fallback не связывает аккаунты по одинаковому email. Пользователь вправе заранее добавить локальный код/другой доступный способ к тому же User._id, подтвердив контроль текущего аккаунта и нового провайдера.

Два явных intent: sign_in и link. sign_in после проверки (provider,externalId) входит в существующий User либо создаёт обычный новый User с генерируемым username; текущий другой аккаунт остаётся отдельно, без merge. link требует текущего User и свежего reauth, создаёт новую linked identity **на том же userId**; identity другого User даёт 409 IDENTITY_ALREADY_LINKED, без переноса данных и без молчаливого sign_in. Provider нельзя переключить в существующей попытке; роль/полномочия/внутренний userId из claims не принимаются.

Temporary OAuth state does not require a dedicated MongoDB entity in the MVP. Choose storage and retry behavior during authentication implementation. Preserve browser/owner/session binding, required state/nonce/PKCE checks, expiry validation and provider-verified identity. Linking requires owner confirmation. Persisted completed-retry results are not mandatory. Perform provider exchange outside Mongo callbacks; consumed one-time codes may require a new attempt. Link commits use User.revision CAS and the complete linkedAccounts array; matching email alone does not authorize linking.

Google: web GIS ID-token callback, credential отправляется API по HTTPS с attempt/browser proof. Проверять публичную подпись/allowlisted algorithm, issuer Google, aud настроенного client ID, exp/iat, nonce и sub. Identity=(google,sub), не email. Использовать официальный verifier (предложен google-auth-library), Bisky HS256 secrets не пригодны. Provider API токены не нужны для identity и не сохраняются. Настройки: web OAuth client, origins, consent/audience/test users, GOOGLE_CLIENT_ID, разрешённый outbound keys access; client secret для GIS callback-mode не нужен. Основание: [Google verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

Яндекс: authorization-code flow с state и PKCE S256; API строит authorize URL, redirect_uri точный зарегистрированный, backend принимает callback и обменивает code на OAuth token, затем сам читает https://login.yandex.ru/info через Authorization: OAuth <token>. Identity=(yandex,id из ответа API), не email/login_hint/данные браузера. Запросить минимальные права профиля login:info; email/avatar не нужны для входа. Provider token живёт только для проверки, не используется как Bisky Session; raw не логируется/не выдаётся клиенту. Отказ обмена/профиля не создаёт User. Настройки будущего запуска: зарегистрированное Yandex OAuth приложение, YANDEX_CLIENT_ID, серверный YANDEX_CLIENT_SECRET при confidential flow, YANDEX_REDIRECT_URI, соответствующие scopes/согласие/проверка приложения и HTTPS. Контракт сверён через Context7 и официальные [code flow](https://yandex.ru/dev/id/doc/ru/codes/code-url), [user information](https://yandex.ru/dev/id/doc/ru/user-information); зарегистрированные приложения/credentials ещё не проверены.

Unique(provider,externalId) и lookup через $elemMatch обязательны. Две регистрации одного provider subject дают один User после duplicate-key/повторного lookup, не два аккаунта. Google и Яндекс с одинаковым email не объединяются. Добавить YANDEX в ELinkedAccountProvider — необходимая будущая schema-правка. Email recovery подтверждается отдельным Bisky challenge, provider email автоматически не копируется. Служебная атрибуция и права не следуют из профиля провайдера.

### 5. Библиотека и попытки

UserItem — текущая проекция одного user/Item, не замена журнала. Nullable status означает отсутствие выбранного списка, а не шестой статус. Rating=null либо integer 1–10; favorite независим; note=null либо plain text до предложенных 5000 символов, без выполнения HTML. Пустой note нормализуется в null. Очистка любого поля не очищает остальные. Служебное исключение Item не удаляет эти данные.

| Команда | Переход/инвариант |
| --- | --- |
| saved {} | Установить planned, только если нет начатых/завершённых попыток и status=null/planned. При in_progress/on_hold/completed/dropped либо истории просмотра — сохранить статус/attempts. Не создавать отдельный like. |
| status.set {status} | Явный пользовательский выбор одного из пяти списков. planned не удаляет прошлые попытки; переход в in_progress создаёт первую попытку либо возобновляет открытую. |
| status.clear {} | Снять общий статус; attempts/rating/favorite/note сохраняются. При открытой попытке — 409, сначала закрыть/удалить её. |
| rating.set {rating}; rating.clear {} | Изменить число/снять оценку независимо от статуса и числа просмотров. Оценка знакомого фильма не выдумывает просмотр/показ. |
| favorite.set {isFavorite} | Явное boolean, без toggle; повтор безопасен. |
| note.set {note}; note.clear {} | Новое значение/очистка; прежний текст сохраняется в приватном событии, не в публичном логе. |
| attempt.start {attemptId} | Новый явный UUID; создать in_progress. Из completed/dropped начинается повторный просмотр, старые попытки сохраняются. Не больше одной открытой попытки. |
| attempt.status {attemptId,status} | in_progress ↔ on_hold; in_progress/on_hold → completed/dropped. Терминальная попытка не переоткрывается; следующий просмотр — новый ID. |
| attempt.progress {attemptId,progressMinutes} | Ручной прогресс integer>=0 в минутах; отдельная команда и событие. Не меняет status и не завершает фильм автоматически. |
| attempt.remove {attemptId} | Исправление ошибочной записи: убрать из текущего массива, оставить remove и прежние значения в истории. Не уменьшать журнал и не переиспользовать ID. |

planned → on_hold/dropped без попытки — только список с намерением/решением, не утверждение просмотра. Прямое completed при отсутствии открытой попытки создаёт завершённую попытку с startedAt=null: дата начала неизвестна, не выдумана. При открытой попытке completed/dropped/on_hold меняют её одновременно с общим статусом. Перевод открытого просмотра обратно в planned — 409 INVALID_TRANSITION, сначала закрыть либо удалить ошибочную попытку. При удалении открытой/последней попытки общий статус пересчитывается из последней сохранившейся попытки; если попыток нет — null. Более старую терминальную попытку можно удалить, не меняя текущую. Поля rating/favorite/note никогда не сбрасываются этими переходами.

ItemAttempt дополнить attemptId, createdSequence/updatedSequence. startedAt фиксируется сервером при начале; completedAt только при completed, при dropped=null. Историческое прямое completed имеет completedAt=recordedAt, то есть время регистрации завершения, не доказанную дату просмотра. Не давать клиенту произвольные completedAt, unit или массив attempts целиком. Даты истории события и пользовательские даты просмотра имеют разные смыслы.

**Ответ владельца Q2:** «Нужен прогресс в минутах». **Согласовано:** ручной прогресс относится к конкретной попытке; новый просмотр начинается с нуля, предыдущая попытка и её прогресс сохраняются. Техническое предложение: unit=minute (добавить MINUTE в EProgressUnit), progress=null либо целое >=0; новая начатая попытка progress=0. Прямое completed без известного прогресса хранит null, не выдуманную полную длительность. DTO возвращает progressMinutes nullable; команда attempt.progress {attemptId,progressMinutes} задаёт число. Число не завершает просмотр автоматически; completed не подставляет Movie.runtimeMinutes. Импортная длительность может быть неизвестной/неточной, поэтому не является жёстким верхним ограничением ручного прогресса; базовый технический лимит — safe integer. Коррекция прогресса терминальной попытки допустима с новой revision/event, без переоткрытия и стирания прежнего значения. startedAt/completedAt от коррекции не меняются.

Payload и schema/service validators проверяют целое значение, существование attemptId и owner; нельзя менять unit или чужую попытку. Поле прогресса в событии сохраняет before/after, при replay изменение применяется только своей попытке. Удаление попытки оставляет прогресс в истории.

Удаление записи библиотеки не входит отдельным DELETE whole-record: clear-поля и attempt.remove выражают необходимые отмены без скрытого стирания нескольких независимых сигналов. Пустая UserItem может сохраняться как projection/tombstone с revision; в списке её не показывать. Это предотвращает сброс revision до 0 и конфликт с поздними командами.

### 6. Команды, событие, порядок и согласованность

Предложен один owning endpoint для библиотечных команд, а не generic Mongo CRUD. CommandDto: {eventId: UUID, schemaVersion: 1, expectedRevision: integer>=0, occurredAt?: ISO UTC, kind, payload, context}. kind/payload — строгий discriminated union из таблиц, unknown fields/version отклоняются. Нет client userId, sequence, recordedAt, resolvedItem или ролей. Item из path; type=movie. Client время сохраняется как occurredAt, default=recordedAt; порядок и cooldown определяются серверным recordedAt/sequence, не задним числом client clock. Будущие offline-события с произвольным прошлым порядком не поддерживаются.

UserAction envelope дополняет §8 модели: eventId, schemaVersion=1, user, sequence (safe integer>0), occurredAt, recordedAt, sessionId, kind, payload, requestedItem, resolvedItem, identityDecision/catalogRevision на момент применения, sourceItem nullable, exposure nullable, context, commandDigest, expectedStateRevision, resultingRevision, changed и сохранённый receipt. Для отмен — новое clear/remove/set=false событие; старое не изменяется. Generic undo не разрешён, так как может затереть последующие действия. В event хранить нормализованный intent, конкретные до/после изменённых полей и назначенные attempt IDs: одной текущей UserItem для replay недостаточно.

ContextDto: origin=library/catalog/onboarding/recommendation; exposureId обязателен только для recommendation, иначе null; surface из короткого allowlist, locale ru/en. sourceItem допускается только после проверки реальной binding на дату действия; клиентские arbitrary context/strategy IDs не доверенные. Для recommendation сервер достраивает requestId/resultKey/rank/strategy versions из exposure. Собственные заметки не участвуют в ranking snapshots и не отправляются Google/служебному импорту.

Счётчик User.actionSequence и явная User revision сериализуют поток действий одного владельца; sequence общий для библиотечных команд и shown, без глобального порядка разных пользователей. Повтор eventId не увеличивает sequence. UserItem.revision — общий номер изменения пары user/Item, включая действия на RecommendationState; копия identity-проекции тоже повышает его. expectedRevision=0 только до первой материализации. Идемпотентность проверяется **раньше** stale revision/текущего redirect: duplicate после merge всё ещё возвращает прежний receipt, не перепривязывается. Digest включает версию, path/requestedItem, kind/payload, client occurredAt (включая факт отсутствия), expectedRevision и нормализованный context; transport access token и requestId не входят.

Точная повторная команда одного владельца возвращает прежний eventId/sequence/resultingRevision/receipt, не сегодняшнее состояние под видом прежнего результата. Тот же eventId с иным digest — 409 IDEMPOTENCY_CONFLICT, без записи. Повтор действия новым eventId при том же значении сохраняет accepted no-op event с changed=false; не создаёт повторного сигнала вкуса/метрики. skipped является отдельной реакцией на exposure, не no-op. Reusing eventId другого пользователя не даёт доступа к его receipt.

Одна MongoTransactionService.run: (1) проверить receipt; (2) проверить/обновить live Session и User.actionSequence; (3) проверить Item/identity/context; (4) условно обновить по owner+item+expectedRevision UserItem и при необходимости RecommendationState; (5) записать UserAction и receipt; (6) commit. Все чтения/записи с той же session последовательно. Нет Promise.all, Google/Redis/Meilisearch/jobs внутри callback. Ответ и cookie/notifications только после commit. IDs и входные время/digest готовы до callback; retry не создаёт новый eventId. Ошибка откатывает и событие, и состояние, и sequence.

Unique(user,eventId) и unique(user,sequence), существующие unique user/item защищают конкуренцию/первый upsert. Два разных изменения одной пары с одинаковым expectedRevision: одно принято, второе 409 STATE_CONFLICT с currentRevision; client перечитывает запись и принимает новое решение с новым eventId. Не делать автоматический last-write-wins заметок/оценок. Duplicate-key race одного eventId после abort дочитывает committed receipt вне aborted transaction, сравнивает digest. Unknown commit result не означает, что команда не применена: retry с прежним eventId, GET receipt. Ошибка receipt-чтения — 503, не повтор без ключа.

Hard exclusions и библиотека обновляются синхронно. Вкус/агрегаты могут обновляться фоном из committed последовательности с calculationVersion/checkpoint; очередь лишь ускоряет, recovery дочитывает Mongo. Кеш не является authority запрета. Rebuild обязан читать UserAction+CatalogDecision и публиковать projection только при неизменившемся source checkpoint/User revision; иначе дочитать хвост/повторить. Новый not_interested нельзя затереть старой пересборкой. Чат 4 определяет веса и подробную delivery/rebuild процедуру.

### 7. Skipped, not_interested и показ

not_interested.set {} запрещает рекомендации до not_interested.clear {}; не очищает UserItem и не назначает отрицательные предпочтения тегам. Первая команда из каталога без exposure материализует RecommendationState: shownCount=0, skippedCount=0, firstShownAt/lastShownAt=null, isExcluded=true, expiresAt=null. И user/item state revision, и событие создаются атомарно. На clear shown dates не выдумываются; прежний cooldown не обнуляется автоматически. Повтор set новым eventId changed=false.

skipped {} допустим для конкретного подтверждённого exposure: временная реакция, skippedCount+1 и nextEligibleAt по версионированной cooldown policy чата 4. UserItem.status/rating не меняются. Библиотечное действие «не предлагать» не требует exposure; библиотечный skipped без показа отклоняется. Один exposure может иметь не больше одного принятого skipped; повтор с новым eventId — 409 FEEDBACK_ALREADY_RECORDED, а точный повтор старого eventId возвращает receipt. Ни skippedCount, ни expiresAt не заменяют историю и не снимают isExcluded. Cooldown после identity split использует исходное время, не стартует заново; параметр длительности ещё не утверждён.

RecommendationRequest завершает выдачу с неизменяемыми results/resultKey, порядком, snapshots/versions; выдача не увеличивает shownCount и не создаёт shown. ExposureDto: {exposureId: UUID, schemaVersion:1, requestId:UUID, resultKey:string, occurredAt?:ISO UTC, displayContext:{surface,locale}}. Client отправляет после фактического отображения. Сервер проверяет owner запроса, completed, существование resultKey и snapshot Item, а не принимает произвольный itemId. Первый показ данного результата — новый exposureId; точный повтор доставки не новый показ; реальный повторный показ — новый ID.

Предложено хранить shown как UserAction с eventId=exposureId и ссылкой на отдельный RecommendationExposure (детали request/result/display/snapshot). Это уточняет прежний event union: **добавляется kind=shown**, две записи в одной транзакции, один sequence/одно наблюдение. Exposure unique(user,exposureId); envelope digest включает DTO показа. RecommendationState shownCount и nullable dates обновляются одновременно. Feedback через context.exposureId проверяет того же owner и исходную показанную identity с учётом сохранённого mapping, а не любой текущий фильм. Несовпадающий объект/контекст — 409; чужой exposure — такой же 404, как отсутствующий. Разные действия по одному exposure допустимы; повторное saved/rating того же значения не удваивает вкус.

До принятия первого показa перечитать текущую Item/redirect/availability/exclusion и актуальный user запрет. Устаревшая recommendation карточка исключена между выдачей и display acknowledgement: 409 ITEM_NOT_ELIGIBLE, exposure/shown/count не записывать, client скрывает её/запрашивает замену. Это не доказывает, что устаревшие bytes физически не мелькнули до проверки: клиентский acknowledgement не является телеметрией, которой сервер может запретить уже отрисованный экран. Для MVP exposure означает принятое подтверждение eligible показа; rejected stale acknowledgement не используется как положительный показ или feedback. При retry **уже принятого** exposure после exclusion вернуть старый receipt, не потерять принятую историю.

Только транзакционного чтения Item недостаточно против concurrent exclusion. Предложено короткое условное обновление Item.interactionFence (служебный integer, отдельный от catalogRevision) в exposure и всех новых библиотечных командах, включая изменения существующей записи; catalog exclusion/merge/split меняют тот же Item document. User.actionSequence write так же сериализует exposure с пользовательским запретом. Поэтому один commit предшествует другому; запрет, committed до exposure, не обходится старым snapshot. Читать и fence-обновлять все участвующие requested/resolved Item в устойчивом порядке; identity revisions проверять снова. Это дополнительное поле §3 модели, не существующий код; альтернатива без fence не даёт заявленную гарантию race.

Для excluded/unavailable фильма публичная карточка 404; владелец получает в библиотеке stub {itemId,availability} плюс свои состояния/attempts, без запрещённых titles/poster/aliases/raw. Не размножать запрещённый материал в event receipts/DTO. Владелец может изменить/снять свои состояния по уже существующей записи или прежнему exposure; новая библиотечная привязка к невыдаваемому фильму отклоняется. Feedback старого принятого exposure может изменить личное состояние, но не делает фильм eligible. Item служебный запрет и user not_interested остаются независимы.

Любой endpoint /me строит owner filter из проверенного principal. Admin/catalog.manage не разрешают читать чужую библиотеку, заметки, оценки, Google claims или auth receipts. catalog.manage — отдельно выдаваемое сервером право import/corrections/identity/exclusion; обычная регистрация/link его не получают. Tokens/claims/private payload исключаются из логов; private API no-store; кеши клиента/сервера ключуются owner и сбрасываются при смене principal. Backups и operator credentials требуют ограничения доступа, не новой социальной модели приватности.

**Ответ владельца Q3:** «Да, оставить собственные данные» на уточнённый пример собственной оценки 5 и скопированной 8. **Согласовано:** собственная оценка/статус/заметка остаётся основной; копия не перезаписывает её, альтернативные значения остаются в приватной истории, история попыток сохраняется целиком.

Техническая конкретизация: direct lineage приоритетнее copied lineage для rating/status/note/favorite, включая явный clear/false, а не только непустые значения; при отсутствии direct выбрать последнее исходное событие по sequence, сохранить alternatives. Attempts объединить по original attemptId+sourceEventId без выдуманных просмотров; конфликт двух открытых попыток оставляет direct active, copied доступна в истории. User может исправить через обычную команду новой revision; никакого молчаливого overwrite. CatalogDecision хранит правило/IDs исходных событий, не текст чужих заметок. Собственные попытки/заметки служебный оператор не читает для принятия split.

При merge текущая библиотека показывает одну группу с явными conflicts и сохранёнными раздельными lineage; ни одна история не стирается. После split однозначные связи возвращаются своему Item; ambiguous копируются обоим по согласованному исключению. Копия не создаёт новые UserAction/exposures. Каждый получатель далее редактируется независимо; отмена not_interested A не отменяет B. И прямой clear после split имеет приоритет над прежней копией запрета. Recommendation/taste replay учитывает source event один раз, не два наблюдения: подробные правила чата 4. Lazy projection refresh проверяет актуальную CatalogDecision basis и повышает stateRevision до принятия следующей команды; stale client получает 409, а не запись в старую карту identity.

### 10. MongoDB: статическая проверка и ограничения

Фабрика читает MONGO_URL, допускает mongodb/mongodb+srv; DatabaseModule передаёт URI и autoIndex:true. .env.example содержит локальный URL без replicaSet. Без вывода credentials проверены только topology признаки фактического apps/api/.env: mongodb, loopback, directConnection=true, replicaSet option отсутствует. В текущем checkout Compose/replica-set initialization не обнаружены. Серверная версия и реальная topology не установлены; directConnection не доказывает standalone, отсутствие replicaSet в URI не исключает server replica set.

Multi-document atomicity требует replica set либо sharded cluster; standalone не поддерживает требуемые транзакции ([MongoDB production considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)). Предложена отдельная изолированная локальная replica set для P6; single-node допустима для функциональной приёмки, не доказывает отказоустойчивость. До записи должны быть отдельно подтверждены server version/FCV, replica-set readiness, transaction permissions, readConcern snapshot/writeConcern majority и deployed unique indexes. Текущий run не принимает TransactionOptions: если эти concerns не обеспечены connection defaults, потребуется минимальное расширение service либо настройки согласованного deployment. Не подменять transaction цепочкой обычных writes.

Этот этап не подключался к MongoDB, не запускал API/Docker и не изменял .env/индексы/данные. autoIndex при будущем старте способен затронуть индексы: использовать выбранную изолированную среду, не существующую базу. Transaction readiness остаётся **не подтверждена**, а не «сломана» или «проверена». Google credentials/настоящий вход также не проверены в runtime.

## Рекомендации и производные данные

Дата: 8 октября 2026 года. Этап: проектирование первой movie-only системы. Библиотечные фильтры двух режимов и стартовые параметры **согласованы владельцем**; остальные формулы, поля и API этого раздела **предложены**. Требования vision к двум стратегиям, нескольким интересам, раздельным силе/уверенности, истории и запретам уже приняты; они не означают принятие описанного алгоритма. Production-код не изменяется. A/B-платформа, другие media types, обязательные embeddings и онлайн-LLM вне этапа.

### 1. Основания и выбранный подход

Проверены текущие production-схемы UserTasteProfile/TasteItemTypeProfile/TasteTagPreference, UserRecommendationState, ItemMetric/RatingDistribution/UserItemStatusCounts, Tag, Feature, ItemTag, ItemFeature и их enums, а также API agent context/data-access. Сейчас профиль содержит одну пару nullable embeddings на тип, tagPreferences со score/samples и interactionsCount; нет центров интереса, confidence, Feature preferences или версий. RecommendationState требует обе даты показа даже до первого shown. ItemMetric хранит views, ratingsCount/average/distribution, statusCounts/favoritesCount, но не происхождение агрегатов, checkpoints и временные окна. ItemTag проверяет лишь конечность relevanceScore; ItemFeature — базовый тип значения. Это возможность хранения, не реализованная рекомендательная система.

Актуальные контракты берутся из разделов «Импорт и поиск» и «Аккаунт, библиотека и события»: постоянный ItemId, обычный аккаунт без автоматического merge аккаунтов, UserAction с sequence/changed/receipt, shown вместе с RecommendationExposure в одной транзакции, явные set/clear, копии через lineage. Поздние решения имеют приоритет над временным аккаунтом в раннем тексте vision/модели. Физические контракты прошлых разделов остаются предложенными; здесь нет их молчаливого утверждения.

Рассмотрены три подхода: один усреднённый вектор прост, но теряет независимые интересы; несколько кластеров явных признаков сохраняют их и дают проверяемые причины; embeddings/обучаемый ranking требуют данных и усложняют объяснение. Предлагается второй подход, рядом с отдельным baseline. На ограниченном каталоге кандидаты — полный подготовленный movie-набор, без approximate retrieval и зависимости scoring от Meilisearch. Увеличение каталога потребует отдельной версии candidate generation.

### 2. Общий pipeline и обязательная пригодность

Порядок: захват согласованных входов → полный набор кандидатов → ранняя eligibility-фильтрация → baseline/personal scoring → повторные ограничения → распределение мест, diversity/exploration → устойчивый ranking → live gate и сохранение фактически выданного результата → принятое подтверждение показа → feedback → производные проекции. Получение кандидатов и фильтры общие; смена стратегии не снимает запреты.

Обязательная eligibility: Item существует, type=movie, availability=available, isExcluded=false, redirectTo=null, опубликованные Movie/Item/привязки согласованы по revision; нет пользовательского not_interested; проходит фильтры запроса и выбранный серверный content policy; evaluationTime >= nextEligibleAt; нет повторного ItemId внутри ответа. Redirect разрешается с учётом запретов всей identity-группы: исключённый alias не обходит запрет через живую цель. Ремейки не дедуплицируются как одно произведение. Неверный Feature/неопубликованный Tag не участвуют в признаках. Отсутствующий перевод, постер, рейтинг или Feature сами по себе не исключают otherwise eligible Item.

**Согласовано владельцем:** mode=watch_now допускает planned/on_hold, исключает in_progress, completed/dropped, любую сохранившуюся попытку completed/dropped и оценённые фильмы; mode=discover_later исключает записи с любым status, rating, favorite=true или сохранившейся попыткой. Одна заметка не означает известный фильм. Повторный просмотр остаётся действием библиотеки, отдельный режим rewatch сейчас не добавляется. Для watch_now on_hold с незавершённой попыткой допустим как возвращение к отложенному. Явная низкая оценка дополнительно не переносится в hard запрет похожих фильмов.

Фильтры movie API: Tag IDs с заданным AND/OR, releaseYear min/max, runtimeMinutes max, originalLanguage/countryCodes. Movie-адаптер превращает их в общие допустимые IDs/типизированные predicates по подготовленным данным. Для явного ограничения неизвестное значение не проходит; отсутствующий фильтр не требует его. Текстовый поиск остаётся отдельным API. Locale влияет на представление причин/карточек, не на перенос вкуса.

До живой выдачи перечитать authoritative Item и user запреты, библиотеку/cooldown; stale кандидатов удалить и добрать из сохранённого ранжированного пула с теми же правилами. Сохранить исходный calculatedRanking, liveGateBasis, удалённые IDs/reason codes и returnedResults. Укороченный ответ имеет shortageReasons; нельзя дополнять его запрещёнными Item. При недоступности authority — 503, не выдача из кеша. Concurrent catalog changes сериализовать предложенным interactionFence в короткой финальной транзакции для выбранных Item и owner revision; повторная проверка и запись completed request в той же транзакции, storage/queue вне неё. Это уточнение предложения прошлого раздела, требует транзакционной MongoDB. Запрет после commit выдачи проверяется снова при exposure; сервер не обещает предотвращать уже отрисованные клиентом bytes.

### 3. Подготовленные признаки и независимый вход движка

Movie-адаптер вне движка читает Movie/sourceMetrics и опубликованные связи. Candidate={item:ItemId, itemRevision, identityBasis, eligibility, facets, features:[{key,definitionRevision,family,x,originRef}], qualityObservations, popularityObservations, completeness}. x конечен в [0,1]; key включает вид признака и стабильный ключ/категорию. Движок принимает plain immutable данные, не Mongoose documents, Movie repositories или названия полей Movie. Identity map, словарь и metadata входят в snapshot; будущие адаптеры не реализуются.

featurePreparationVersion=movie-features/1 задаёт allowlist, единицы, bins, family budget и нормализацию. Tag даёт x=relevanceScore; одинаковые aliases не добавляют отдельные признаки. String Feature из контролируемого словаря — one-hot по key/value; boolean — отдельные true/false категории, отсутствие не равно false. Number/date — фиксированные интервалы из feature manifest, с включённой нижней и исключённой верхней границей, последний интервал включён сверху. Стартовая проекция длительности в minute: (0,90), [90,120), [120,180), [180,+infinity). Год: десятилетие floor(year/10)*10. Другие number/date не включать без определённого manifest. Произвольные строки/ID/описания/заметки не становятся признаками вкуса. Выбор bin для runtime берётся из одного derived Feature, без второго независимого признака того же Movie-поля.

Семьи: tags budget=0.8, features budget=0.2; внутри каждой активной семьи a_if=x_if/sum(x_i семейства), затем a_if умножить на её budget. Если одна семья отсутствует, активную перенормировать до 1; сумма a_if=1 для Item с признаками. Это бюджет одного наблюдения, а не одинаковое уверенное подтверждение всех тегов. Для cluster similarity сохранить x и нормированные a отдельно. Нулевые x игнорировать; Item без признаков годится для baseline/exploration, но не формирует интерес.

На полном опубликованном пригодном movie-каталоге, до личных фильтров, N=число distinct canonical Item, df_f=число Item с x_if>0. Поправка информативности d_f=clip(ln((N+1)/(df_f+1))/ln(N+1),0.1,1), при N=0 набор пуст. Хранить N/df/d в snapshot с определениями. Узкие фильтры запроса не меняют d и не переписывают предпочтение. TagRelation/embedding не распространяют оценку; tasteTransfer=none/explicit сохраняется, cross-media переноса здесь нет.

### 4. Baseline: качество, наблюдения, популярность и полнота

baseline/1 получает те же ограничения, повторы и diversity, но не использует личный вкус. Формулы ниже — стартовая модель ранжирования, не статистическая гарантия независимости источников.

Для каждого настроенного рейтингового канала s выбрать одно последнее принятое наблюдение Item на cutoff по observedAt, затем устойчивому observation ID. Повтор той же source/metric не новый канал. z_s=clip((value-scaleMin)/(scaleMax-scaleMin),0,1); нужна известная корректная шкала, value внутри неё. Неверное наблюдение исключить из расчёта с причиной. n_s — число оценок, не views; count=0 даёт c_s=0, известное n>0 даёт c_s=n/(n+50), неизвестное n даёт c_s=0.1. q_s=0.5+c_s*(z_s-0.5). Отсутствующий канал даёт q_s=0.5, confidence=0, не рейтинг zero. Среднее Q=sum(q_s)/S по фиксированному manifest каналов с равными весами; если S=0, Q=0.5. Внутренний канал Bisky — normalized ratingAverage 1–10 с distinct current ratingsCount, тот же shrinkage. Внешние counts не складываются с внутренними и друг с другом: пользователи источников могут пересекаться. qualityConfidence=sum(c_s)/S — операционная мера покрытия доказательствами, не вероятность качества.

Для внешнего popularity-канала профиль источника явно задаёт направление и значение (counts либо score), отличие от rating и sampleCount; неподдерживаемая/неизвестная шкала не угадывается. p_s — percentile rank нормализованного значения среди Item с наблюдением этого канала на том же cutoff: (число меньших + 0.5*число равных)/число известных. Отсутствие даёт 0; канал с единственным наблюдением даёт 0.5 и coverage 1/N. Если канал имеет underlying sampleCount, его вклад умножить на n/(n+100), неизвестный count на 0.1. Для score без смысла sampleCount использовать коэффициент 1, но manifest должен явно это разрешить. Источники пока не выбраны: до per-source manifest внешний channel выключен, значения не выдумываются.

Внутренняя популярность: U=distinct пользователей с changed saved, favorite=true либо rating.set в последние 30 UTC суток; действия одного user/Item дают максимум один вклад, сам запрашивающий пользователь исключается из этого channel. Отменённые/заменённые положительные действия не остаются текущим доказательством; rating любой величины здесь лишь интерес аудитории, не положительное качество. P_internal=U/(U+10). shown/views не поднимать популярность, чтобы не усиливать собственную выдачу. P — равное среднее по включённым popularity-каналам, отсутствие данных=0; при отсутствии каналов P=0. Внутренние popularity evidence и cutoff сохраняются без раскрытия чужих user IDs клиенту.

K=0.2*hasTitle + 0.2*hasDescription + 0.15*hasReleaseYear + 0.15*hasRuntime + 0.3*hasAcceptedTasteFeature. Индикаторы 0/1, берутся из разрешённых canonical данных; оба перевода/постер/число источников не обязательны. K — полнота входов, не confidence предпочтения. Итог B_i=0.7*Q_i+0.2*P_i+0.1*K_i в [0,1]. Нехватка данных объясняется reason=limited_data. Остальные доступные фильмы остаются в exploration; missing нельзя превращать в fake average/ratingCount. Профили шкал/каналов и интервалы популярности сохраняются в parameters, parameterVersion и snapshot.

### 5. Один независимый сигнал на произведение

Пересобрать эффективные состояния по sequence до user cutoff; события set/clear заменяют или убирают прежний сигнал, changed=false его не добавляет. Один повторный просмотр/изменение оценки не создаёт ещё один независимый фильм. Evidence unit — distinct произведение с original lineage, а не число кликов/attempts.

Если текущая rating есть: y_i=(rating-5.5)/4.5, reliability h_i=1. Если rating нет, favorite=true: y_i=0.6, h_i=0.5. Если нет rating/favorite и есть действующее намерение saved: y_i=0.25, h_i=0.25. Иначе сигнала вкуса нет. Saved намерение сохраняется только пока planned относится к changed saved; status.clear/переход из planned убирает слабое свидетельство намерения, не создавая dislike. favorite=false и rating.clear убирают свой сигнал; более слабый текущий сигнал может остаться. При rating+favorite использовать рейтинг, без второго наблюдения; противоречие низкого rating и favorite сохранить как исходные данные, не маскировать. Status/completed/dropped/progress/note/shown/skipped/not_interested не входят в постоянный вкус. Значения y/h — предложение стартовых весов.

Для каждого признака m_if=h_i*a_if. По набору evidence E: M_f=sum(m_if); s_f=sum(m_if*y_i)/M_f (0 при M=0), сила в [-1,1]. u_f=число distinct evidence с m_if>0; c_f=[M_f/(M_f+3)]*[u_f/(u_f+2)] — confidence. Противоречащие реакции уменьшают s; c означает достаточность наблюдений, не согласие со знаком. Отдельно v_f=число distinct evidence с m_if>0 и y_i>=0.2, saturation t_f=v_f/(v_f+4). Постоянный положительный вклад w_f=max(s_f,0)*c_f*t_f. Отрицательный вклад b_f=max(-s_f,0)*c_f*[uNegative_f/(uNegative_f+4)], где uNegative считает y_i<=-0.2. Все величины ограничены; сотня оценок не даёт неограниченного веса. Рейтинг и признаки не затухают лишь из-за времени; последующее исправление отменяет старое evidence. c, t, d хранятся раздельно, не одним score.

Это консервативная эвристика атрибуции, не установление причины оценки. Если признаки всегда встречаются вместе, алгоритм не может доказать, какой из них нравится; причины результата должны говорить «совпадает с признаками оценённых фильмов», а не «вы любите каждый тег». Раздельные наблюдения на других произведениях уточняют оценку; похожие произведения не считаются полностью независимыми в статистическом смысле.

### 6. Несколько центров интереса и персональное scoring

Детерминированное выделение центров на положительных evidence y>=0.2 с непустыми признаками. Weighted Jaccard J(i,j)=sum_f[d_f*min(a_if,a_jf)]/sum_f[d_f*max(a_if,a_jf)], пустой denominator даёт 0. Начать с singleton clusters, сортированных по stable evidence key. Complete-link similarity двух clusters — минимум J между их членами. Сливать пару с максимальной similarity, пока она >=0.35. При равенстве — лексикографическая пара ключей; cluster ID=min evidence key. Если осталось больше Kmax=3, сливать максимальную пару до трёх независимо от порога и отметить forced_merge. Это ограничение MVP: более трёх несвязанных интересов не обещаются как отдельные центры; объединённые evidence не теряются.

В каждом центре вычислить s/c/t/w по его evidence. C_k=nPositive_k/(nPositive_k+3), evidence без признаков не учитывается. Центр подтверждён при nPositive>=2, sum(h_i) по его evidence >=1 и C_k>=0.4; два слабых saved сами по себе ещё не подтверждение. Одна высокая оценка даёт provisional центр, без обязательной квоты. Negative evidence рассчитывается отдельно глобально как b_f; оно не сливает разные положительные интересы в один вектор и не создаёт hard veto тегов.

A_ik=sum_f[a_if*d_f*w_kf] — положительное совпадение центра; D_i=sum_f[a_if*d_f*b_f]. Ни A, ни D не нормировать на сумму весов профиля: такая нормировка могла бы превратить слабый единичный сигнал в уверенный score=1. Для кандидата вне квот A_i=max_k(A_ik), не среднее центров. При отсутствии центров A=0. alpha=0.7*max_k(C_k); basePersonal_i=(1-alpha)*B_i+alpha*(A_i-0.5*D_i). При пустом вкусе alpha=0, точный baseline fallback с причиной cold_start. Квотный слот центра k использует A_ik вместо max; blend alpha общий. Постоянный вкус доступен для ranking только с сохранёнными profile/calculation versions.

Для L>=числа допустимых подтверждённых центров сначала зарезервировать каждому по одному уникальному кандидату с A_ik>0, потом остаток personal мест распределять round-robin по центрам с доступными совпадениями. Внутри центра ранжировать по его скору и поправкам §7. Резервирование при overlap: построить двудольное сопоставление центров/кандидатов с максимальным числом покрытых центров, среди них максимальной суммой scores, затем lexicographic IDs. При K<=3 допустим перебор резервов на малом наборе. Нельзя жадно отдать общий единственный кандидат первому центру, если есть другое полное покрытие. Когда уникальных кандидатов не хватает, сообщить center_shortage, не заявлять покрытие обоих одной карточкой. Soft diversity не отменяет зарезервированные места.

Когда L меньше числа центров (включая L=1), оба в одном ответе математически невозможны. Выбирать least-served центр по числу принятых exposures его lane в последних 20 показах, tie по center ID. Для нового profile mapping lane пересчитывается из сохранённых признаков exposures на текущие центры; не переписывать прежние request reasons. Покрытие оценивается по последовательности подтверждённых показов; выдача без shown не продвигает счётчик. Provisional центры участвуют в оставшихся местах без гарантии. Пустые квоты перераспределяются, ограничения не ослабляются.

### 7. Повторы, cooldown, временный skip и exploration

Согласованные стартовые параметры: cooldown после принятого shown 24 часа; после skipped 7*24 часа. nextEligibleAt=max всех ещё действующих deadlines от серверных recordedAt; стратегия не меняет сроки прошлых deadlines своим parameterVersion. Событие/receipt shown/skipped сохраняет policyVersion и конкретный deadline; это дополнительное поле предлагаемых payload/result для пересборки, без изменения client DTO. На not_interested.clear прежний cooldown сохраняется. shownCount/skippedCount — lifetime audit counters, не число независимых вкусовых observations. expiresAt=null, никакого TTL постоянного запрета. После deadline Item снова допустим без ручного снятия skipped.

Недавние показы: последние 50 принятых exposures за 14 дней. Вес каждого e: l_e=2^(-ageDays/7). r_f=sum(l_e*a_ef)/sum(l_e), при пустом окне 0. R_i=sum(a_if*r_f). Similarity-proportional временный skip: по skipped exposures за 30 дней H_i=min(1,sum_e[2^(-ageDays/3)*J(i,e)]); один source skip lineage ровно один e. Item cooldown — hard временное ограничение, H — мягкое снижение похожего контента, не negative preference. После 30 дней вклад skip отсутствует. Повтор одного Item после deadline дополнительно I_i=min(1,sum recent l_e для того же identity), независимо от повторяемости его тегов.

При выборе следующего Item из lane максимизировать T_i=baseScore_i -0.15*R_i -0.15*H_i -0.10*I_i -0.15*maxSelected J(i,selected). Последний член=0 для первого результата. Все штрафы неотрицательны, конечные; score может быть отрицательным, не считается вероятностью. Для baseline baseScore=B; для personal — §6. Насыщение t, распространённость d и повторяемость R действуют в разных местах; показ не стирает предпочтение. Diversity действует и на cold start. Sparse/no-feature кандидаты не получают ложного similarity с любым фильмом.

Exploration fraction epsilon=0.2. Для L>=2 explorationSlots=min(floor(epsilon*L), max(0,L-reservedCenters)); сначала выполнить резервы, exploration размещать последними слотами. Для маленького batch floor может дать 0; для L=1 каждый пятый принятый показ общей movie-рекомендационной последовательности — exploration lane, остальные least-served personal/baseline. До принятия пятого показa повторный запрос остаётся exploration без продвижения счётчика; нет фиктивных exposures ради квот. На L=1 гарантии интересов относятся к personal слотам последовательности, а не каждой карточке.

Exploration выбирает eligible невыбранные кандидаты: разделить по P на low (<0.33), medium (<0.67), high; взять корзину с наименьшим числом последних 20 exposures, равенство по low/medium/high; в ней выбирать наименьший SHA-256 UTF-8 канонического JSON массива [seed,lane,item.type,item.id], tie ItemId. Пустые корзины пропускать. Это даёт место менее популярным и missing-data записям без обязательного minimum rating. Selection фиксирует reason=exploration и score components; не называет этот слот уверенным taste match. Если кандидатов нет, слот перераспределить с shortageReason. Для replay seed обязателен, хранится строкой; никакого ambient Math.random.

Все сортировки: score округлить до 1e-9 → score desc → stable ItemId asc; у exploration hash asc → ItemId asc. Summation по feature/evidence IDs asc, UTC evaluationTime фиксирован. Артефакт реализации/версия JS runtime и правила канонизации чисел входят в version manifest. При том же входе/seed/version результат должен совпадать; это требование будущей приёмки, а не доказанный детерминизм реализованной системы.

### 8. Общий запрос, результат, exposure и feedback

Предложен POST /me/recommendations: {requestId:UUID, schemaVersion:1, strategyId:baseline|personal, mode:watch_now|discover_later, types:[movie], locale:ru|en, filters, limit:integer 1..50, seed?:string}. Owner задаёт principal; клиент не передаёт профиль, scores, permission, versions или arbitrary параметры. Сервер выбирает зарегистрированные версии/конфигурацию, seed при отсутствии назначает один раз и сохраняет до расчёта. Retry owner+requestId+intentDigest возвращает прежний расчёт; иной intent — 409 IDEMPOTENCY_CONFLICT. Новая живая выдача после changes требует нового requestId. Исторический receipt не является новым разрешением показать stale Item: client проходит текущий exposure gate. Получение owner истории по requestId возвращает immutable ranking metadata, а текущие запрещённые публичные поля карточки закрыты. Private no-store, никаких shared caches по одному URL.

EngineInput={context, evaluationTime, seed, versions, parameters, candidateSnapshot, profileSnapshot, stateSnapshot, recentExposures, identitySnapshot, manifest}. EngineOutput={strategyId, strategyVersion, parameterVersion, rankedCandidates:[{item,resultKey,rank,score,components,centerId|null,lane,reasons}], diagnostics}. Интерфейс scoring не импортирует Movie. Даже baseline получает одинаковый input shape, явно игнорируя profile для вкуса.

RecommendationRequest сохраняет status=pending/completed/failed, intentDigest, evaluationTime, все versions и concrete parameters, snapshots, calculatedRanking, liveGateBasis, returnedResults, diagnostics/errorCode. resultKey устойчив в запросе, например r0001 до live gate; returned rank может отличаться и сохранён явно. Компоненты: Q/qualityConfidence/P/K/B/alpha/A/D/R/H/I/diversityPenalty, плюс final score и center/lane. Причины структурированы {code,featureKeys?,evidenceCount?,contribution?,snapshotRef}; максимум три крупнейших положительных вклада, baseline/limited_data/cold_start/exploration и уместная diversity причина. Конфликтующие/слабые признаки не объясняются как достоверная любовь; причины принадлежат snapshot, не генерируются онлайн-LLM. RU/EN templates используют сохранённые подписи; нет private notes или чужих оценок в ответе.

Exposure использует **прежний** POST /me/recommendation-exposures и ExposureDto, без новых стратегических коллекций. Сервер достраивает request/resultKey/rank/strategy versions/issued identity/content feature snapshot. Один accepted shown в UserAction с eventId=exposureId и один RecommendationExposure, один sequence, не два наблюдения. Новое фактическое отображение — новый exposureId; точный retry прежнего receipt не увеличивает counts даже после текущего запрета. Accepted stale-card semantics, interactionFence и 409 ITEM_NOT_ELIGIBLE остаются из предыдущего раздела.

Feedback использует **прежний** POST /me/library/movies/:itemId/actions и CommandDto: rating.set/clear, favorite.set, saved, skipped, not_interested.set/clear и другие библиотечные команды. context.origin=recommendation требует проверенный exposureId того же owner и issued identity с lineage; library/catalog/onboarding допускают null. Нет второй модели Feedback collection: feedback — эти UserAction, reference к exposure и сохранённые до/после. Повтор skipped по одному exposure отклоняется, прочие разные действия допустимы. Действие без exposure не приписывается успеху рекомендации. Rating через exposure и rated в библиотеке имеют один смысл вкуса, а attribution сохраняется отдельно.

### 9. Версии и неизменяемые входные значения

Стартовый bundle: strategyId baseline/personal; strategyVersion baseline/1 или tag-centers/1; parameterVersion movie-recommendations/1 с полным JSON параметров; featurePreparationVersion movie-features/1; profileCalculationVersion taste-centers/1; metricCalculationVersion item-metrics/1; stateCalculationVersion recommendation-state/1; cooldownPolicyVersion cooldown/1; candidateGenerationVersion full-movie/1; snapshot schemaVersion=1. Profile revision — конкретное содержимое отдельного пользователя, не версия алгоритма. Catalog basis/revisions — конкретные данные, не featurePreparationVersion. Version manifest содержит digest правил, allowlist/bins, каналов, templates и восстанавливаемый код/артефакт реализации; одного имени версии недостаточно.

RecommendationSnapshot kind=catalog/profile/context из модели остаётся единым форматом. Catalog: полный список candidates до личной фильтрации с eligibility, facets/x/a, N/df/d, channel raw values/scales/counts/observedAt, Q/P/K, dictionary definitions и identity map. Profile: concrete centres/evidence keys/s/c/t/w/b, revision/calculationVersion и source basis. Context: фильтры, исключения, library summary без notes, cooldown deadlines/policy, недавние accepted exposures со frozen features/time/lane, skip history, evaluationTime, seeds и owner checkpoints. Top-N или ID/hash без bytes не заменяют эти данные.

Один catalog snapshot можно переиспользовать между запросами с тем же source basis; профиль также по digest, контекст отдельный. Manifest и chunks bounded size сохраняются через existing storage с private immutable keys recommendation/snapshots/<snapshotId>/<sha256>; Mongo хранит metadata/hash/size и список chunks. До completed request проверить сохранённые bytes/hash, загрузка вне транзакции. Нельзя держать весь каталог в одном неограниченном Mongo документе. Публичные URLs/presigned links не являются долгосрочным storageRef. Разрешения snapshot owner/service; raw private state не выдаётся другим пользователям.

**Дополнение event-контракта для replay:** changed rating/favorite/saved сохраняет featureBasisRef + featurePreparationVersion с конкретными признаками/словарём/catalogRevision на момент сигнала, либо ссылку на уже существующий immutable snapshot с теми же значениями. Exposure всегда получает свой frozen feature basis. event хранит ссылку/digest, не переписываемый vector в текущем Item. Для личного feedback featureBasis брать из подтверждённой карточки exposure; для библиотеки — каталог на дату принятия действия. Если доступных признаков нет, сохранить пустой basis с причиной, без выдумывания. Отсутствие feature snapshot у старого события делает точный прежний replay невозможным; backfill новой версией явно фиксирует reconstruction policy и source cutoff, не объявляется восстановлением оригинальных значений.

Два режима: exact replay использует прежние входные значения, code manifest и cutoff; refresh/new calculation использует новый каталог/словарь по явно заданному basis и новой revision, сохраняя прежний snapshot. Если extraction/profile logic изменена, повысить соответствующую calculation/preparation version. Пересчёт старых оценок по новым признакам не меняет UserAction bytes и является новым derived result. Для сравнения baseline/personal фиксировать один catalog/profile/context/evaluationTime/seed; два request IDs и compareGroupId служат связью, не A/B assignment platform. Live gates хранить отдельно: нельзя объяснять различия gate сменой scoring.

Предпочтение владельца удалять ненужные материалы сохраняется. **Предложено** не удалять snapshot bytes/manifests, поддерживающие хранимые запросы и evidence, пока обещается replay; срок retention ещё не выбран. Удаление такого snapshot должно явно лишить соответствующий request replayable статуса с missing_artifact, а не незаметно читать актуальные данные. Это зависимость DoD 3/7/10/11, не согласие на бессрочное хранение всего raw. Автоматическая очистка/TTL этого этапа не проектируется.

### 10. Проекции, identity lineage и восстановление после сбоев

UserTasteProfile: profiles movie с centres [{centerId,evidenceKeys,nPositive,C,confirmed,forcedMerge,preferences:[key,s,c,M,u,v,t,w]}], global negative preferences, featurePreparationVersion/profileCalculationVersion, revision, checkpoint userSequence, catalog/identity basis, inputDigest и evidence snapshot references. samples прежней схемы не является confidence; interactionsCount можно оставить audit числом distinct эффективных evidence, embeddings nullable и не используются. Sparse preferences/chunks bounded, без бесконечного массива event payloads в документе профиля.

UserRecommendationState: прежние counters, dates nullable, lastSkippedAt, nextEligibleAt/isExcluded, policy versions, source userSequence/identity basis/revision; exposure lineage и deadlines исходного времени. Для счётчиков читать UserAction shown или joined exposure один раз, не суммировать оба журнала. Изменения hard state синхронны по контракту прошлого раздела; фоновая пересборка никогда не overwrites новый запрет.

ItemMetric: views определить как число distinct принятых exposureId (это рекомендации, не доказанные просмотры фильма); completedAttemptsCount хранить отдельно при необходимости, statusCounts не равно просмотры. ratingsCount/distribution/average — текущее эффективное rating одного user/identity, clear/change удаляет/заменяет прежний bucket; favoritesCount/statusCounts аналогично по effective state. Distribution остаётся целочисленной 1..10. Для internal P нужны distinct 30-day user evidence: либо вычислять aggregation из истории на ограниченном наборе, либо версионированный вспомогательный chunk, не ошибочно использовать lifetime views. calculationVersion/generation/inputDigest/source cutoff обязательны. Внешние sourceMetrics не превращать в Bisky counts.

Identity replay: read accepted CatalogDecision до зафиксированного catalogSequence, сохранить original event IDs/requested/resolved identities. При merge разные оценки одной пары user/merged Item конфликтуют: direct lineage приоритетнее copied, иначе последняя sequence по согласованной библиотечной проекции; raw alternatives остаются. В текущем вкусе один effective фильм, не две независимые оценки одного объединённого произведения. Показ с двумя отдельными accepted exposure IDs до merge остаётся двумя реальными показами, duplicate одного exposureId не становится двумя.

При split copied library состояния остаются видимыми обоим по согласованному правилу, direct даже clear/false имеет приоритет. Для вкуса ambiguous original event group участвует **один раз** со frozen признаками исходного показанного/оценённого объекта; не учить два центра двумя копиями. Если обе копии effective, одна evidence group; если только одна, всё ещё одна; когда все копии замещены/очищены, прежнее evidence неактивно. Прямая новая оценка конкретного получателя — новое независимое evidence этой identity, замещает её копию, не затрагивая другой Item. При конфликте изменения source channels применять rating>favorite>saved внутри effective group, sequence tie-break. Group key — original lineage item/decision, с reference к исходным events, не новый UserAction. Прежние раздельные до-merge evidence после корректного split восстанавливаются своему Item.

Для **item-local метрик** ambiguous скопированное наблюдение не назначать двум фильмам: сохранить один unresolved lineage bucket вне рейтинговых counts обоих до прямого уточнения/однозначного решения. Прямая оценка получателя учитывается его rating; оставшаяся копия остаётся unresolved. Это предложенная политика метрик, не потеря библиотечных данных; сохраняет integer histogram и не выдумывает двух пользователей. Ambiguous exposure также один unresolved observation; нельзя заявить два views. Исторические request/exposure snapshots не меняются. not_interested копируется обоим как hard policy, cooldown обоим с прежними deadlines, не двумя новыми skipped. Будущие independent clear для A/B учитываются отдельно.

Пересборка использует durable историю, очередь лишь запускает работу. User jobs key=(user,projectionVersion,targetSequence,identityBasis); metric jobs key=(generation,catalogSequence,sourceCutoffDigest). Выполнение может повторяться: пересчитать effective contributions/set result, не blindly increment по delivery. Pending/running/completed/failed generation и inputDigest/checkpoints фиксируются в служебном rebuild manifest; после commit до enqueue scanner находит отставание из Mongo. Lost/retried jobs и retention BullMQ не стирают source history.

Для пользователя: (1) зафиксировать User revision/sequence и catalogSequence, прочитать consistent source; (2) построить scratch профиль/state вне публикации; (3) дочитать хвост или повторить при изменённом basis; (4) в короткой транзакции CAS проверить source revision/checkpoints и identity basis, атомарно опубликовать проекции и их checkpoint. Hard state rebuild сравнивает revision, не заменяет новый not_interested/cooldown устаревшим scratch. Нужен служебный reader consistent cut, не обычная пагинация updatedAt. Сбой до swap оставляет active generation, после swap retry сверяет digest и даёт no-op. Не хранить внешние вызовы в transaction callback.

Для общих метрик нет одного глобального userSequence: rebuild manifest фиксирует catalogSequence и вектор (userId,actionSequence) по **всем** пользователям cutoff с consistent membership. Долгую вычислительную работу не держать в одной транзакции: durable immutable source-cut chunks, затем scratch ItemMetric по generation. Delta по новым user sequences/materialized contribution sets, сравнить cut и закрыть gap перед publish; request snapshot может зафиксировать честную lagging metrics generation, hard gates всегда live. New users/identity decisions делают следующий cut, не теряются. Active metrics generation публикуется pointer CAS, mixed generation внутри catalog snapshot запрещена. Нужен proposed RecommendationProjectionState/manifest, общий служебный state для generation/cut/lease, не коллекция под стратегию. Existing unique metric_item при нескольких поколениях потребует unique(generation,item.type,item.id); миграция работающей БД этим дизайном не разрешена. Profile/state scratch можно держать private immutable artifact и swap текущего owner документа, сохраняя прежние snapshots.

Missing artifact/unsupported eventVersion/sequence gap — fail rebuild с конкретной причиной и сохранением старой проекции; нельзя пропустить неизвестное событие и повысить checkpoint. Lease помогает против параллельных jobs, но CAS/digests обеспечивают корректность. Cancel между chunks сохраняет progress и старую generation, restart использует тот же source cut. Refresh profile по новым Feature rules и exact replay старого snapshot имеют разные output IDs. Для ranking при lagging taste допустим сохранённый профиль с указанным checkpoint либо baseline; authoritative hard state/eligibility нельзя заменить lagging projection.

### 11. Расчётные примеры и сценарии будущей приёмки

Это арифметические иллюстрации предложенных формул, **не runtime-проверки**, не результаты работы API и не измерение пользовательской пользы.

**Два интереса.** Шесть высоко оценённых комедий и два мрачных триллера, rating=10, один выраженный тег на каждом, h=a=1. Пересечение кластеров J=0, внутри каждого J=1: два центра. Комедия: M=u=v=6, s=1, c=(6/9)*(6/8)=0.5, t=6/10=0.6, w=0.3, C=6/9=0.667. Триллер: M=u=v=2, c=(2/5)*(2/4)=0.2, t=2/6=0.333, w=0.0667, C=2/5=0.4. Оба подтверждены. При одинаковых d=0.5 и B=0.5, без штрафов alpha=0.467: A_comedy=0.15, A_thriller=0.0333, personal scores примерно 0.3367 и 0.2822. Для L=5 резерв один комедии и один триллеру, один exploration, два personal round-robin: при достаточных уникальных кандидатах оба интереса остаются, несмотря на меньший score второго. Для L=1 последовательность personal показов least-served чередует центры; пятый показ exploration. Это пример квот, не доказательство качества кластеризации.

**Единичная оценка.** Один фильм rating=10, десять одинаково выраженных тегов, без Feature: m=0.1 каждому, s=1, u=v=1. c=(0.1/3.1)*(1/3)=0.01075, t=1/5=0.2, w=0.00215. У provisional центра C=1/4, обязательной квоты нет. Даже при d=1 совпадение всех десяти признаков даёт A=sum(0.1*0.00215)=0.00215, не десять уверенных предпочтений. С одним тегом c=(1/4)*(1/3)=0.0833, w=0.0167: уверенность тоже мала. Влияние нормировать до единицы запрещено; одна высокая оценка чуть меняет ranking, не доказывает любовь к каждому тегу.

**Частый тег.** N=1000, df_common=800, df_rare=50: d_common=ln(1001/801)/ln(1001)=0.0323 → floor 0.1; d_rare=ln(1001/51)/ln(1001)≈0.4309. Сто положительных independent evidence с одним тегом: c=(100/103)*(100/102)≈0.9518, t=100/104≈0.9615, w≈0.9152. При 200: c≈0.9754, t≈0.9804, w≈0.9563; вклад ограничен единицей и прирост меньше. До повторов w*d_common≈0.0915, w*d_rare≈0.3944. Если recent r_common=0.8, r_rare=0.1, repetition penalties для однопризнакового кандидата 0.12 и 0.015. Это три отдельных числа: t насыщает evidence, d корректирует распространённость, R временно раздвигает выдачу. Ни d, ни R не понижают сохранённый s=1.

**Пропуск.** Один skipped в t0: Item недоступен до t0+7 суток; для полностью похожего другого Item H=1 сейчас, 0.5 через 3 суток, 0.1984 через 7, 0 после окна 30 суток. При коэффициенте 0.15 штрафы 0.15/0.075/0.0298/0. Профиль s/c/w не меняется. not_interested, напротив, не истекает в t0+7 и требует clear.

**Количество рейтингов.** z=0.9 при n=1 даёт q=0.5+(1/51)*0.4≈0.50784; при n=1000 q≈0.88095; при unknown count q=0.54. missing даёт 0.5 с confidence=0. Большая цифра рейтинга без наблюдений не автоматически побеждает подтверждённую. Это shrinkage illustration, без заявления о независимости разных источников.

Будущие сценарии на изолированном наборе: два центра с непересекающимися/общими единственными кандидатами; одна оценка с 1/10/50 тегами; frequent tag 80% каталога и 100/200 signals; negative rating/favorite conflict/clear; cooldown boundaries UTC и delayed client clock; not_interested до первого shown/clear с cooldown; разные seed/один seed и shuffled DB order; missing metrics/features/catalog source; issue без shown и duplicate exposure; repeated no-op/set/clear/skip; lost enqueue/job retry/CAS race и rebuild с новыми событиями; artifact обновлён/утрачен; ошибочный merge/split с direct/copy conflict и unresolved metric bucket; live запрет между scoring/commit/exposure; baseline/personal comparison на одинаковых bytes. Ожидаемые исходы заданы §§2–10, выполнение оставлено P5/P6.

## Согласованность и зависимости плана P1–P6

Дата: 8 октября 2026 года. [План реализации](mvpImplementationPlan.md) подготовлен для согласования; production не изменён, P1 не начат. Этот раздел уточняет статусы и зависимости, не утверждает технические предложения.

### Актуальные основания

- Обычный сохраняемый аккаунт/local-code/provider вместо temporary/permanent conversion и Google-only. Ранние строки модели о временном аккаунте относятся к прежнему сценарию; статические факты о текущем EUserType остаются верны. Поздний раздел аккаунта и общие правила mvpChatPrompts задают актуальный путь.
- Названия: публикация без одного перевода и fallback title locale → original → title другого активного языка → alias уже согласованы. Детали descriptions/нескольких originals остаются предложением.
- Split: собственные данные приоритетны, альтернативы/попытки сохраняются, ambiguous not_interested обоим до независимых отмен; копии не создают новые независимые события. Direct clear/false precedence, source lineage/group representation, исходные cooldown deadlines и unresolved item-local metric bucket — техническая конкретизация, не новое подтверждение владельца.
- Rolling срок четыре месяца согласован. Прибавление календарных месяцев в UTC с clamp дня — техническое предложение; слово «календарных» в отдельных прежних формулировках не служит доказательством его принятия.
- interactionFence нужен предложенной реализации гонок, но физическое поле и способ сериализации не утверждены. В рекомендациях прежнее слово «согласованным» исправлено на «предложенным».
- Library predicates watch_now/discover_later и 24h/7d/3d/Kmax3/exploration20% согласованы. Формулы, quotas/rounding, версии/manifest/API/physical schemas требуют отдельного принятия.

### Зависимости и существенные предложения

План содержит реестр D1–D15 с точными блокируемыми задачами. D1: physical модель; D2: import/matching/reconciliation; D3: источники/данные/source profiles; D4: referenced evidence retention/cleanup; D5: isolated transaction environment; D6: CLI operator bootstrap до P3; D7: auth/session/code/receipts; D8: providers/apps; D9: server region/content policy; D10: verified email delivery/recovery; D11: command/lineage/fences/exposure; D12: feature/profile/scoring/quotas; D13: snapshots/cuts/generations/replay; D14: filter DTO; D15: fresh provider reauthentication. Ни названия файлов, ни общий план не меняют эти статусы на «согласовано».

Уточнения предлагаются для совместимости с текущим кодом:

1. LiveSessionGuard и проверка актуальных User/Session/permissions — в endpoints/auth поверх portable JWT AccessTokenGuard. Infrastructure не импортирует entities. State-changing service повторно проверяет live Session в своей transaction. Исходный текст о DB-check AccessTokenGuard описывает поведение цепочки защиты, а не разрешение обратного импорта.
2. P2 получает отдельный CLI context/operator-bootstrap с machine/env access и audit. Регистрация P3 не нужна для первого наполнения и не выдаёт catalog.manage. Actor из AI JSON не удостоверяет оператора. Narrow validate/dry-run context не запускает HTTP/queue worker/S3-search init; его database bootstrap задаёт autoIndex:false/autoCreate:false, иначе обещание dry-run без записи не выполняется. Scoped bootstrap options в текущем DatabaseModule — предложение плана, не реализованная возможность.
3. Feature preparation manifest и immutable basis IO реализуются в P4 до первого changed rating/favorite/saved, scorer остаётся P5. Basis для feedback берётся из exposure; другие actions используют принятый catalogue basis. refs без bytes не replay. Общий RecommendationSnapshot catalog-kind покрывает feature basis, отдельная vector collection не нужна.
4. P4 exposure receiver зависит от completed RecommendationRequest, producer появляется в P5. До этого нельзя создавать fake requests/shown ради проверки; runtime полного цикла в P6.
5. P5 source cut/metric state предшествует taste publication; snapshot membership+user sequence vector и catalogSequence нужны для shared aggregates, одного global userSequence нет. Snapshot bytes/code manifests и версии сохраняются отдельно от projection revisions.
6. Filter formats сейчас расходятся: поиск tagKeys+runtime диапазон, рекомендации Tag IDs+runtime max. D14 предлагает общий movie filter DTO, сохраняя уже принятые library predicates; это не утверждённый API.
7. Provider attempt sign_in/link не полностью описывает reauth grant для regenerate/email/link. D15 предлагает явный server-bound reauth intent/proof; fresh nonce/state сами не доказывают новое активное подтверждение пользователем. Этот пробел нельзя закрыть неявным доверием текущей Session.
8. Durable recovery challenge delivery state и защищённый dispatch token artifact предлагаются для сбоя commit→mail enqueue. Recovery использует существующий Resend queue-only flow; transport migration не часть MVP.

Первый раздел предлагал девять новых корневых сущностей. Совокупный вариант поздних разделов/плана добавляет SearchIndexState, OAuthAttempt, CredentialOperationReceipt, RecoveryChallenge, AccountAccessEvent и RecommendationProjectionState: **15 новых корневых сущностей**, вместе с 17 существующими — 32, если принят этот physical вариант. Это счёт предложенных схем, не уже созданных коллекций. Не требуется отдельная Feedback, GoogleAuthAttempt, Identity или коллекция каждой strategy. UserSourceAccount и необязательные embeddings сохраняются вне активного поведения, не удаляются ради числа коллекций.

### DoD 5, vision и приёмка

Temporary/Google-only в projectVision («Первая работающая основа», сценарий conversion, таблица аккаунта, DoD5 и открытые вопросы о единственном входе) устарели относительно согласованного ordinary-account пути. **Старый conversion не обязательная приёмка.** Актуальные сценарии: регистрация обычного аккаунта/code-return/refresh; real регионально доступный provider; link того же userId с сохранением library/events; sign_in другого account без merge; regenerate/revoke и optional verified-email recovery; refusal без доступных доказательств. Полные сценарии и 11-DoD матрица находятся в плане.

Vision не изменён: его продуктовые формулировки и DoD5 требуют отдельного разрешения на синхронизацию. DoD11 также должен учитывать согласованную explicit copy-to-both exception с сохранением alternatives и single evidence. mvpChatPrompts уже содержит актуальные P3/P4/P6; его scope не меняется этим уточнением.

### Границы проверки

Статическая source-сверка показывает существующие schema/repository/infrastructure границы, но не runtime readiness. MongoTransactionService сейчас run(callback) без TransactionOptions; предлагается совместимый optional options для новых transactional operations с explicit concerns. autoIndex:true при старте способен менять БД: schemas не разрешают запуск/миграцию существующих данных. API config сейчас Garage/S3 и Resend, не историческая Compose/MinIO/Stalwart конфигурация из памяти. Actual server versions/topology/OAuth apps/private bucket/mail delivery неизвестны.

В плане все implementation задачи «не начато», static/runtime отдельно. Runtime выполняется только после фактического разрешения чата P6 на подтверждённых isolated Mongo/Redis/storage/search namespaces. Synthetic dataset не доказывает реальные источники; provider/mail имитации не доказывают реальные вход/доставку. Retention90д и бессрочное хранение не приняты, автоматическое удаление не разрешено.

## Реализованный persistence-контракт P1

Общий ObjectId Item/Movie и ItemId={type,id}, locale/origin, journals, auth evidence, requests/snapshots/projection generations приняты в пределах P1. Всего 32 root schemas (17 прежних + 15 новых). Production-схемы находятся в apps/api/src/entities; source paths, поля/ограничения, static checks и границы следующего этапа перечислены в отчёте P1 плана.

Уточнения physical реализации: SourceArtifact и RecommendationSnapshot используют поле ref: StorageRef, соответствующее artifact_storage(ref.backend,ref.bucket,ref.key); Movie.poster также StorageRef, provenance — fieldOrigins. CatalogDecision.subjects включают movie и словари/связи; expectedRevisions={subject,revision}, assignedIds={key,subject}. Origin.derived хранит inputs={decision,path,elementKey} и ruleVersion. Nullable состояния не заменены fake values.

Точные UserAction payload выражены TUserActionCommand и checkIsUserActionCommand: set/clear, attempts, saved, skipped, not_interested и shown. Command schema требует подходящий payload без лишних ключей; пустой payload сохраняется с minimize:false. Feature basis для shown и changed rating/favorite/saved обязателен. Receipt согласуется с envelope; реальные inter-collection invariants/семантические переходы остаются P4. Surface ограничен длиной 64; endpoint allowlist определит P4, новые UI поверхности не выбраны.

Inline bounds physical модели: до трёх taste centres, 1024 snapshot chunks, 50 calculatedRanking/returnedResults, восемь reasons на result, 256 evidenceKeys/evidenceRefs/unresolvedRefs и 4096 preferences per centre/negative list/прежнее tagPreferences. Полные candidate inputs находятся в snapshot bytes; request сохраняет ограниченный расчёт выдачи. Snapshot refs сохраняют большие доказательства; caps отклоняют переполнение, не обрезают историю. Параметры Feature, ranking и profile computation не вычисляются P1. До P3 JWT helper по-прежнему использует прежний refresh срок 30d: новые rolling Session поля сами не реализуют четыре месяца.

autoIndex:true не изменён. Никакая база не подключалась, данные/индексы не мигрировались; уникальность объявлена, не доказана на deployed MongoDB. Source bytes, encrypted receipts, publication, transactions, replay и append-only прикладное поведение требуют реализации следующих этапов и изолированной приёмки.
