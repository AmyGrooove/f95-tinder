## Получение кандидатов

1. После входа запрашивать рекомендации с `filter.statuses: {"anyOf":["outside"]}` и выбранными фильтрами. Для исключения анонсов получить через [QUERY /tags](../requestFlows/catalog.md#tags) тег с `group: "releaseStatus"` и `key: "releaseStatusAnnounced"`, затем передать его `id` в `filter.tags: [{"noneOf":["<id тега>"]}]`. Для поиска ID можно читать группу через `groups: {"anyOf":["releaseStatus"]}` и искать точный `key` в ответах словаря.
2. Брать страницы по `nextCursor` с прежними фильтрами и размером порции. Карточки показывать по одной. Считать только первый показ каждого ID в текущем Пике и остановиться после 25 уникальных показов или исчерпания кандидатов. Пустая порция с курсором допускает продолжение.
3. При `410 HTTP_410` начать новую выдачу без курсора с теми же условиями и `excludeItemIds` из уже показанных ID. Счётчик подбора сохраняется. На обычных запросах с курсором поле можно опустить.

## Реакции и ошибки

В запросе сохранения передавать явно выбранный библиотечный статус, например `planned`. После `204` можно перейти дальше. Открытие подробностей или страницы произведения само по себе реакцию не записывает.

При сбое сети, `429` или `5xx` сохранять текущую карточку и давать повторить действие. При `409` показать ошибку на текущей карточке. Конфликт может означать ограничение выбранного статуса или уже существующую запись после параллельного действия либо запроса с потерянным ответом. Запись сохраняется в прежнем состоянии, конфликт не подтверждает действие Пика. Если пользователь решит продолжить подбор, обновить очередь с актуальными условиями и показанными ID. При `404` сообщить, что произведение недоступно, и продолжить выдачу. Действующий `skipped` исключается из рекомендаций, повторный POST не продлевает срок.
