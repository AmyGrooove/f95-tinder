## Как проходит запрос

[«Эндпоинты API»](endpoints.md) — каталог продуктовых и служебных маршрутов с доступом и ссылками на отдельные схемы, примеры и ошибки. Наглядный формат, общие обозначения и правила актуализации описаны в разделе [«Как проходят запросы»](requestFlows/readme.md). Обновляйте каталог и затронутые схемы вместе с маршрутами и общими фоновыми обработчиками.

В [AppModule](../../../src/app/app.module.ts) подключены AuthModule, AccountModule, UserItemEndpointModule, CollectionEndpointModule, SearchEndpointModule и TagEndpointModule. Контроллер определяет метод и путь, принимает DTO и cookie, вызывает сервис и формирует HTTP-ответ. Глобальный [ValidationPipe](../../../src/app/functions/configureApplication/core/configureApplication.ts) преобразует входные DTO и отклоняет неизвестные поля. Составные сегменты путей пишутся в camelCase; у этих маршрутов нет общего префикса или выбранной версии.

Сервисы `endpoints/*/services` выполняют пользовательскую операцию: проверяют доступ и бизнес-правила, координируют репозитории и транзакции, явно отображают результат в response DTO. Репозитории `entities/*/services` работают со своей моделью MongoDB. Они экспортируются модулем сущности; репозиторий не определяет HTTP-ошибки и не открывает транзакцию вместо вызывающего сервиса.

Защищённые операции используют cookie `__Host-accessToken`, проверку JWT и серверной сессии; проверки выполняются в сервисах конкретных операций. Наличие JWT само по себе не заменяет проверку сессии. Обновление токенов использует `__Host-refreshToken` и атомарное сравнение сохранённого хеша. Cookie изменяются через SecurityCookieService. Отдельный Bearer AccessTokenGuard не заменяет эту схему. Подробности — в [контракте](contracts/accountAndAuthSpec.md#токены-и-проверка-доступа) и [security context](../../../agents/security.md).

Многодокументные изменения подборки и изменения библиотеки с чтением и обновлением попыток выполняются через MongoTransactionService. Его session явно передаётся участвующим запросам. Удаление UserItem физически удаляет запись вместе с попытками; удаление Collection только выставляет deletedAt. Единого автоматического поведения удаления для всех сущностей нет.

## Как связаны данные

`Item` — единая карточка произведения; EItemType содержит семь типов видео и игр. Точные характеристики хранятся в общих полях и блоках movie/series/game. Tag задаёт справочник категорий, TagItem — связь тега с конкретным Item. Полный список полей и связей — в [сущностях](entities.md).

`UserItem` — личная запись пользователя о произведении: статус, оценка, избранное, заметка и история попыток. Пара пользователь/Item уникальна. Семь статусов включают skipped на 90 дней и бессрочный blocked, вне обычной библиотеки. Попытки содержат isCompleted вместо status; их изменения не меняют статус UserItem. Установка completed отмечает последнюю попытку завершённой. QUERY /userItems возвращает краткие собственные записи по ID UserItem; чтения по Item и полного чтения библиотеки пока нет.

`Collection` — публичная подборка. Пользовательские подборки имеют ручной состав; сайтовые подборки тегов автоматически следуют прямым назначениям TagItem. Она хранит метаданные и порядок блоков group/text; ItemCollection отдельно хранит Item, groupId, позицию и заметку включения. UserCollection хранит реакции на саму подборку. Состав подборки и библиотека UserItem независимы: включение фильма в подборку не добавляет его в библиотеку.

При редактировании подборки клиент передаёт version. Сервис проверяет автора, итоговые блоки и ссылки на группы; репозиторий условно обновляет документ с совпавшей версией, а изменения состава выполняются в той же транзакции. Устаревшая версия даёт 409. Чтение состава публичное и возвращает порцию Item в сохранённом порядке вместе с блоками текущей порции, без ID групп и позиций включений. Курсор привязан к ID и версии подборки.

### Обучение и загрузка модели

Локальный Python trainer читает JSON-каталог и историю взаимодействий. Он строит одну разреженную матрицу «пользователь × произведение» для всех типов Item. Каждая положительная пара даёт единицу, а произведения без положительных сигналов остаются за пределами модели. ItemCF запоминает произведения, которые нравились одним и тем же людям. ALS находит числовые признаки произведений, по которым API сможет вычислить предпочтения конкретного пользователя. Вывод CLI для выбранного пользователя показывает диагностических кандидатов до применения фильтров API. [Код trainer](../../../tools/recommendationTrainer/main.py) · [Команды запуска](../todos/recommendations/implementationPlan.md#запуск-обучения)

Опция `--output` создаёт BSON-файл с версией формата, ID произведений, соседями ItemCF, факторами ALS и обучающей популярностью. Опция `--save-to-mongo` записывает тот же документ в коллекцию `RecommendationModel` базы из `MONGO_URL`. Внутренний сервис читает модель из MongoDB. При сборке новой подборки с достаточной историей он выбирает новейший документ по `trainedAt`, при равенстве дат по `_id`, и проверяет формат и числовые массивы. ### Как собирается подборка

1. Сервис проверяет access-токен, действующую сессию и наличие пользователя. Страну берёт из сессии. На первом запросе он читает текущие записи `UserItem`. Положительный сигнал даёт оценка 8–10 либо избранное без оценки или с оценкой 5–10. `skipped` исключается из истории. `blocked` исключает карточку из выдачи, при этом сохранённые оценка и избранное могут дать сигнал по тем же правилам. Сам статус, завершённые попытки и прогресс веса не добавляют. Для персонализации нужны пять разных положительных произведений из всего каталога, которые существуют, не помечены удалёнными и известны модели.
2. ItemCF суммирует веса соседей положительных произведений. ALS вычисляет вектор пользователя из этой же истории и оценивает близость к нему каждого произведения модели. Сервис применяет общие правила допустимости и берёт до 500 прошедших отбор кандидатов каждого алгоритма на каждый тип. RRF (reciprocal rank fusion) добавляет кандидату `0.5 / (60 + место)` за каждый список, в который тот попал, считая места с единицы. Так один личный список учитывает позиции обоих алгоритмов.
3. Если библиотечный фильтр допускает `planned` вместе с другими статусами, запланированные произведения получают +5% к баллу внутри своего источника. В личном списке прямой `sequel` к существующему положительному произведению получает +50%, если исходное произведение проходит проверку пропусков, блокировок и запретов. Бонусы меняют порядок уже допустимых кандидатов. Применяется больший из двух.
4. Для каждого типа сервис собирает до 100 уникальных ID с целевыми долями 70% личных рекомендаций, 20% новинок и 10% популярного. При нехватке кандидатов в источнике места занимают доступные произведения из остальных источников. Если личных кандидатов для типа нет, действует fallback из 60% популярного и 40% новинок. Вся выдача переходит на этот состав, если сигналов меньше пяти, новейшая модель отсутствует или не проходит проверку либо расчёт ALS завершился ошибкой. Готовые списки типов чередуются по одному произведению в порядке `EItemType`. Доли относятся к списку типа и могут отличаться в отдельной порции.

### Как понимать источники и фильтры

- «Популярное» сортируется по рейтингу с поправкой на число оценок `(n × R + 20 × C) / (n + 20)`, где `n` — число оценок, `R` — средняя оценка произведения, `C` — средняя оценка сайта (по умолчанию 5,5). Нужна хотя бы одна оценка.
- «Новинка» — произведение с `Item.releaseDate` между текущим моментом и датой 90 дней назад, включительно. Без рейтингового фильтра подходит и новинка без оценок. Для сезона `releaseDate` соответствует дате первой серии.
- Все источники проверяют тип, наличие и `deletedAt` карточки, теги, библиотеку, границы рейтинга и запреты. Без `library` выбираются произведения вне библиотеки. Явное `library: {}` допускает все пять библиотечных статусов и `outside`. `blocked` и действующий `skipped` исключаются всегда. Просроченный `skipped` считается `outside`. Положительное произведение из истории может попасть в выдачу, если проходит эти условия.
- Условия групп тегов соединяются через И; внутри группы allOf/anyOf/noneOf действуют одновременно. Проверяются прямые назначения, родители автоматически не разворачиваются. anyOf=[] означает отсутствие совпадений, а не отсутствие фильтра.
- Границы rating относятся к обычному ItemStats.ratingAverage, а не к ratingScore; нужны сохранённые оценки. Глобальные и совпадающие со страной ItemBan также исключают произведение.

Конец ограниченного fallback-списка не означает конец каталога. Например, старое произведение без оценок не попадает ни в популярное, ни в новинки; при таком каталоге fallback может оказаться пустым. Автоматического третьего источника, ослабляющего эти правила, сейчас нет.

### Первый вызов и продолжение

Метод принимает `accessToken` и параметры `filter`, `limit`, `cursor`. Размер порции — 10, 20 или 50, по умолчанию 20. Результат содержит `items`, фактический `count` и `nextCursor`. В карточке возвращаются `_id`, `type`, `title` и `media` только с постерами.

```typescript
const filter = { types: [EItemType.MOVIE] }
const first = await recommendationFeedService.readPage(accessToken, {
  filter,
  limit: 10,
})

if (first.nextCursor !== null) {
  const next = await recommendationFeedService.readPage(accessToken, {
    filter,
    limit: 10,
    cursor: first.nextCursor,
  })
}
```

Первый вызов сохраняет порядок ID в Redis на 10 минут. Курсор связан с пользователем, страной сессии, фильтрами, размером порции и видом выдачи. Продолжение берёт фиксированный отрезок сохранённых ID без пересчёта модели и продления TTL. Сервис заново проверяет допустимость и читает актуальные карточки. Например, если после первой порции пользователь заблокировал произведение из следующих десяти позиций, вернутся девять карточек, а курсор продолжит список после исходных десяти позиций. Ориентируйтесь на `nextCursor`, включая случаи с пустой порцией. Если срок жизни снимка истёк или снимок пропал, сервис выбрасывает ошибку `RECOMMENDATION_CURSOR_EXPIRED`. Для новой подборки вызовите метод без курсора.
