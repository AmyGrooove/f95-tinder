# Задачи по страницам

[Покрытие API](../api/pages/readme.md) · [Продуктовые требования](../product/pages/readme.md)

## Зависимости и порядок

Сохраняется [выбранный порядок backend-этапов](roadmap.md#согласованный-порядок-следующих-этапов): каталог → чтение библиотеки → рекомендации и реакции → сбор и импорт. Практические зависимости страниц:

1. `SEARCH-01/02` и `ITEM-01` дают каталог, поиск добавляемых произведений и публичные данные карточек.
2. `LIB-01/02` и `PROFILE-01/02` дают собственную и публичную библиотеку с разграничением данных. Они нужны главной, инструментам и личным формам.
3. `ITEM-02/03`, `COLLECTION-01/02` и `SEARCH-03` закрывают статистику, прогресс и выдачи коллекций. Их порядок относительно рекомендаций выбирается при планировании; это зависимости, а не новый согласованный этап.
4. `REC-01/02`, `PICK-01/02`, `HOME-01/02` закрывают рекомендательные сценарии и ленту. Оценка и Баттл используют общие чтения, их дополнительный backend-объём зависит от выбранного хранения очереди.

Аватар, обложка и история выделены в собственные пункты, чтобы не скрывать их за наличием базового CRUD. Сбор и импорт не относятся к пользовательским страницам; их отдельный этап эта карта не специфицирует.

## Общие операции

| ID     | Состояние | Результат и потребители                                                                                                                                                                                     |
| ------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| LIB-01 | Частично  | Есть краткое пакетное чтение по известным ID UserItem. Нет поиска по Item и полного чтения с заметкой и попытками. Нужно странице произведения и полному редактору из любых карточек                        |
| LIB-02 | Нет       | Чтение библиотеки с поиском, условиями и пагинацией; собственный и публичный варианты с безопасным составом полей. Нужны профилю, главной, Баттлу и Оценке; подробности условий — у соответствующих страниц |
| REC-01 | Нет       | Выдача стартовых и персональных рекомендаций с обязательным исключением «Не рекомендовать»; общая основа главной, рекомендательного режима каталога и Пика                                                  |
| REC-02 | Частично  | Создание skipped/blocked, смена статуса и удаление через UserItem реализованы; есть краткое чтение по известным ID UserItem; чтения по Item и рекомендательной выдачи с применением исключений пока нет     |

- [ ] `LIB-01`: определить и реализовать чтение по Item и загрузку полного редактора.
- [ ] `LIB-02`: определить и реализовать чтение библиотеки с разделением собственных и публичных данных.
- [ ] `REC-01`: определить и реализовать общую рекомендательную выдачу.
- [ ] `REC-02`: добавить чтение состояния через LIB-01 и применение исключений в будущих рекомендациях и явных фильтрах выдач.

### Вопросы API

- Способ поиска личной записи, состав ответа и загрузка попыток; `null`/404 для отсутствующей записи и поведение удалённого Item.
- Общие параметры чтения библиотеки, граница публичного прогресса; заметка и подробные попытки остаются приватными.
- Контракт рекомендаций и реакций, поведение повторов и обновления выдачи. Соблюдать [ограничения рекомендаций](../product/foundations/recommendations.md), не переносить обязательные исключения в обычный поиск без явного фильтра.
- Для гостя личные действия требуют входа. Операция не выполняется автоматически после входа; отображение ошибок и обновление состояния карточки относятся также к клиенту.

### Вопросы интерфейса

Точные URL и параметры переходов, поведение системной кнопки «Назад» для окон, возврат фокуса, удержание позиции страницы и условия показа панелей определяются при детализации интерфейса. Доступность инструментов гостю и восстановление их состояния описываются отдельно для каждого инструмента.

## Главная

- [ ] `HOME-01`: определить и реализовать выдачу фиксированного начала и дополнительной части, догрузку с сохранением дневного порядка и явное окончание ленты. Фиксированное начало не входит в лимит; дополнительных блоков не более 20. Пустые блоки пропускаются, повторами лента не заполняется.
- [ ] `HOME-02`: реализовать ежедневное формирование и сохранение общего порядка дополнительных блоков; четыре коллекции → факт → однократные анонсы, далее четвёрки коллекций со вставкой факта или инструмента. Открытая лента сохраняет порядок при смене дня до обновления страницы.
- [ ] `HOME-03`: сформировать данные блоков: новинки по выходу, популярное по собственной активности сайта, анонсы, факты и только официальные коллекции. Подключить `LIB-02`, `REC-01/02`, публичные карточки и статистику из [каталога](../api/pages/search.md) и [произведения](../api/pages/item.md).
- [ ] `HOME-04`: определить хранение выбранных типов и переключателей между посещениями; реализовать backend-часть, если она нужна. По умолчанию скрывать completed/dropped, скрытые коллекции и «Не рекомендовать»; условия распространяются и на произведения внутри блоков коллекций.

### Вопросы API

Размеры рядов, периоды новизны и популярности, сигналы активности, подбор официальных коллекций, источники фактов, чередование вставок и повторы Item между блоками. Выбор одного/нескольких типов, недостаток анонсов и формат продолжения ленты требуют контракта. Для MVP допускается только movie.

Переходы «Посмотреть все» требуют соответствующих режимов [каталога](../api/pages/search.md), библиотеки или коллекции и передачи применимых условий. Выключение скрытия не отменяет обязательный запрет «Не рекомендовать» внутри рекомендаций. Эти переходы не означают отдельный endpoint для каждой кнопки.

### Проверка результата

Проверять порядок и общий лимит блоков, единственность анонсов, окончание без повторов, продолжение через смену дня, пропуск пустых блоков, гостевую выдачу и личные исключения.

### Вопросы интерфейса

При дальнейшей детализации определяются размеры рядов, периоды новизны и популярности, показатели собственной активности, правила подбора коллекций и чередования фактов с инструментами, источники фактов, повторения одного произведения в разных блоках и дополнительные быстрые действия на карточке сверх общих действий с библиотекой. Также уточняются выбор одного или нескольких типов Item и поведение анонсов при недостатке подходящего содержимого. Эти вопросы не отменяют согласованную композицию страницы.

## Поиск и каталог

- [ ] `SEARCH-01`: реализовать каталог movie без обязательного запроса и сортировку по популярности.
- [ ] `SEARCH-02`: определить и реализовать получение доступных справочников/значений фильтров произведений. Коллекционные фасеты ограничены составом конкретной коллекции и не заменяют глобальные данные.
- [ ] `SEARCH-03`: реализовать фильтры от сайта/пользовательские, мои, избранные и исключение скрытых и сортировку по общей оценке. Карточке нужны данные автора, размер и общая оценка; поисковая карточка содержит только authorId и не содержит размера и оценки.
- [ ] `SEARCH-04`: подключить личное состояние и условия произведений: статусы, избранное, личная оценка, наличие/отсутствие в библиотеке, скрытие completed/dropped и «Не рекомендовать». Использовать `LIB-02` и `REC-02` без раскрытия приватных данных.
- [ ] `SEARCH-05`: реализовать рекомендательный каталог без запроса и переходы с главной с сохранением условий блока. Переиспользовать `REC-01`, не подменять обычный поиск рекомендательной выдачей.

### Вопросы API

Для будущего каталога без запроса остаются иерархия тегов и сочетания внутри групп, формула популярности, справочники фильтров и расширение карточок оценками и личным состоянием. См. [действующий контракт текстового поиска](../api/pages/search.md#реализованный-общий-поиск).

### Проверка результата

Проверять поиск по альтернативным названиям, совместное применение условий и пагинации, различия обычного и рекомендательного режимов, гостевые/личные поля, отсутствие нуля вместо неизвестной оценки. Сохранение query в URL страницы — задача клиента.

### Вопросы интерфейса

Точные диапазоны и сочетания фильтров, иерархия тегов, порядок без запроса, направления сортировок, размер страницы, состав критериев популярности, дополнительные быстрые действия на карточках и состояния загрузки, ошибки и пустой выдачи уточняются позднее. Отдельно определяется поведение режима рекомендаций при переходе с главной. Описание страницы не устанавливает DTO или новые эндпоинты: они выводятся после обсуждения пользовательских страниц и сверки существующего API.

## Пик

- [ ] `PICK-01`: определить и реализовать получение кандидатов вне библиотеки с рекомендательным порядком внутри выбранных фильтров. Переиспользовать `REC-01/02`, данные `ITEM-01/03` и справочники `SEARCH-02` в согласованном объёме.
- [ ] `PICK-02`: реализовать интеграцию 90-дневного skipped, обработку повторного запроса, клиентских исключаемых ID и исключение уже сохранённых кандидатов. Не подменять временный пропуск постоянным «Не рекомендовать».
- [ ] `PICK-03`: реализовать необходимую backend-часть общего рекомендательного запроса с исключаемыми ID. По [согласованному решению](../product/foundations/recommendations.md) клиент хранит ID и счётчик до 25 разных карточек. Учесть гонку с добавлением Item из другой вкладки и ошибку сохранения, которая не должна считаться успешным действием.

### Вопросы API

Доступ гостя, фильтры, исключение анонсов (пока предложение), возврат к предыдущей карточке, учёт повторных показов в лимите, восстановление после обновления и возможность менять размер подбора. Отдельные действия оценки и «Не предлагать» на странице не согласованы.

Пик использует общий рекомендательный каталог с клиентским состоянием текущего подбора. Конкретный HTTP-контракт ещё определяется. Открытие информации или страницы Item не считается реакцией. Возврат не означает автоматический откат уже сохранённых данных.

### Проверка результата

Проверять отсутствие библиотечных кандидатов, фильтры и рекомендательный порядок, лимит показов, пустой набор, ошибки/повторы сохранения и независимость просмотра информации от продвижения.

## Баттл

- [ ] `BATTLE-01`: определить и обеспечить получение полного набора кандидатов из библиотеки или коллекции: условия, порядок, объём и поведение при изменении источника во время сравнения. Переиспользовать `LIB-02` и существующее чтение коллекций; отдельный endpoint создавать только при необходимости выбранного контракта.
- [ ] `BATTLE-02`: определить границу клиентского состояния и backend; реализовать выбранные серверные операции восстановления/сравнений, если они входят в этап. Если серверная часть не нужна, закрыть пункт со ссылкой на принятое решение и контракт источника.

### Вопросы API

Минимум два кандидата и исключение completed/dropped/«Не рекомендовать» по умолчанию для коллекции пока являются предложениями. Требуют решения фильтры и их изменение, порядок, лимит набора, шаг назад, восстановление, доступ гостя и запись сравнений как относительных предпочтений.

Победа и поражение не меняют статус библиотеки и числовую оценку. Для них нельзя использовать мутации UserItem как замену отдельному сигналу предпочтений. Открытие информации не выбирает победителя. Запуск со страницы коллекции передаёт источник в настройку, а не автоматически изменяет личные данные.

### Проверка результата

Проверять соответствие набора источнику, отсутствие потери кандидатов из-за пагинации, механику «победитель остаётся», итог и отсутствие побочных изменений библиотеки.

## Оценка

- [ ] `RATING-01`: через `LIB-02` обеспечить очередь только собственных completed с `rating=null`, ID UserItem для записи и данными кандидата. Исключать уже оценённые, не заполнять ими исчерпанную очередь.
- [ ] `RATING-02`: определить порядок, пропуски, длину и восстановление; реализовать необходимую backend-часть. Отдельный маршрут для каждого действия не требуется автоматически.

### Вопросы API

Когда повторно показывать пропущенное, как получать следующего кандидата после изменения библиотеки в другой вкладке и хранить ли очередь на сервере. После успешного сохранения клиент переходит дальше; ошибка оставляет кандидата. Инструмент не создаёт UserItem, не меняет статус и не пересматривает существующие оценки.

### Проверка результата

Проверять completed + отсутствие оценки, сохранение по ID UserItem, отсутствие записи при пропуске, окончание очереди и сохранение текущего кандидата при ошибке.

Статистические формулы, отдельное чтение личной записи по Item и переход к полному списку коллекций. Плеер и публичное чтение чужих подробных попыток в состав страницы не входят.

### Вопросы интерфейса

При подготовке спецификации определяются точные поля и догрузка блоков, представление неполных переводов и отсутствующего изображения, правила расчёта статистики, отображение удалённого произведения и параметры перехода к коллекциям. Наличие этих блоков в описании страницы не означает, что необходимые операции чтения и пересчёта уже реализованы.

Повтор пароля, предпросмотр и предупреждение о несохранённом — клиентские сценарии, новые поля API для них не нужны.

При подготовке спецификации уточняются требования к аватару, состояния подтверждений и ошибок, поведение несохранённых изменений и представление сессий без user agent. Согласованный состав страницы не означает готовую реализацию всех её операций.

## Редактор коллекции

Поиск добавляемых произведений — зависимость `SEARCH-01/02`, а не новый поиск внутри редактора. Для превью выбранного произведения нужны публичные данные `ITEM-01`.

### Вопросы API

Выбор типа коллекции, работа с RU/EN, требования к обложке, сохранение формы при конфликте версии и при частично загруженном составе. Очерёдность локальных действий, кнопка сохранения и предупреждение об уходе относятся к клиенту; сервер уже выполняет единый PATCH атомарно. Управление официальными коллекциями обычному автору не предоставляется.

### Проверка результата

Проверять сохранение перестановок и переносов без потери незагруженных включений, конфликты version, уникальность Item, удаление группы и отсутствие изменений библиотеки.

- [ ] `PROFILE-02`: определить и реализовать сводку: дата регистрации, распределение по пяти статусам, число оценённых и избранных. Последние действия выдаются только владельцу из `PROFILE-03`.
- [ ] `PROFILE-03`: определить события и хранение истории добавлений, смен статуса, оценок и избранного, затем подключить их запись к мутациям и реализовать чтение с датами и переходами только владельцу. Определить поведение удаления UserItem и исправления/повторного сохранения значения.

Общие зависимости: `LIB-02` должен покрывать поиск, фильтры, сортировку, тип Item и статус; вкладка избранного — та же библиотека с фильтром. `LIB-01` загружает полное редактирование владельцу. `SEARCH-03` должен дать созданные и избранные публичные коллекции с определённой видимостью избранного в чужом профиле согласно требованиям страницы.

### Вопросы API

Фильтры, сортировки и пагинацию библиотеки, формулы сводки, фон, публичный прогресс и сроки/правила хранения истории. Чужая библиотека, оценки и избранное публичны; заметки, подробные попытки и вся история приватны. Возможные настройки приватности ещё не определены и не добавляются предположением.

Отдельные именованные списки для пяти статусов не нужны. Управление аватаром отслеживается в [настройках](../api/pages/settings.md), произвольные приватные списки — вне текущей карты реализации.

### Проверка результата

Проверять свой/чужой профиль и гостя, отсутствие личных заметок и попыток в публичных ответах, совпадение сводки с данными библиотеки и приватность истории после удаления записи.

### Вопросы интерфейса

При подготовке спецификации уточняются фильтры, сортировки, пагинация, расчёт сводки, оформление фона, объём публичного прогресса и правила хранения истории, включая удаление записи библиотеки. Необходимость настройки приватности отдельных публичных разделов пока не определена. Числа сводки рассчитываются по данным пользователя; формулы определяются отдельно.

## Коллекция

| ID                    | Состояние | Пробел                                                                                                                                                                                             |
| --------------------- | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| COLLECTION-01         | Частично  | Шапка содержит authorId, но не публичное представление автора; нет общей оценки/числа оценок и избранного. total состава — число совпадений с фильтрами, а не гарантированное число всей коллекции |
| COLLECTION-02         | Нет       | Нет «Завершено X из Y» по всей коллекции независимо от фильтров и страницы                                                                                                                         |
| Карточки произведений | Частично  | Личное состояние требует отдельного чтения LIB-01; ответ `/items` не содержит общей оценки Item; расширение согласовать с `ITEM-03`                                                                |
| Запуск Баттла         | Частично  | Источник состава есть; подготовка набора и остальная ответственность описаны в `BATTLE-01/02`                                                                                                      |

- [ ] `COLLECTION-01`: определить расчёт/обновление и чтение общей статистики, полного числа доступных произведений и публичных данных автора/отметки сайта. Использовать `PROFILE-01` или согласованное краткое представление автора; не раскрывать защищённый `/account`.
- [ ] `COLLECTION-02`: определить и реализовать полный личный прогресс X/Y, учитывая удалённые произведения. Не рассчитывать его по одной странице или выдаче с активными фильтрами.

### Вопросы API

Формулы статистики, правила X/Y при удалённых Item, пустые состояния и переход в настройку Баттла. Официальность определяется `authorId=null`; обычные пользовательские маршруты не управляют коллекциями сайта. Административные операции не входят в задачу страницы.

### Проверка результата

Проверять неизменность X/Y и общей статистики при смене страницы/фильтров, гостевое чтение, независимость реакций от библиотеки и отсутствие запрета прямого чтения после скрытия.

### Вопросы интерфейса

При подготовке недостающих контрактов уточняются расчёт общей статистики и личного прогресса, учёт удалённых произведений в X/Y, представление пустых состояний и переход в настройку Баттла. Новые показатели страницы не считаются уже реализованными на основании существующих маршрутов.

Интерфейсы библиотеки и списков, операции управления ими и конкретные правила работы инструментов определяются отдельно.
