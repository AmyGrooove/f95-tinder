## 1. Контракт выдачи: согласованные части

Пункт ещё не утверждён целиком. [Вход и результат описаны типами](../../../src/endpoints/recommendations/services/recommendationsService/index.ts). Правила выдачи ниже относятся к будущей реализации.

### Входной интерфейс

```typescript
interface IFindRecommendationsProps extends ICursorPagination {
  sessionId: Types.ObjectId

  filter?: IRecommendationFilter
}

interface IRecommendationFilter {
  types?: readonly EItemType[]
  tags?: readonly IValueFilter<Types.ObjectId>[]
  library?: IValueFilter<TLibraryStatus | "outside">

  rating?: {
    min?: number
    max?: number
  }
}
```

- limit и cursor наследуются из общего ICursorPagination.
- types допускает любой из перечисленных типов; при отсутствии поля типы не ограничиваются.
- collectionId и groupId в первую версию нового рекомендательного контракта не включаются. Рекомендации внутри заданной подборки или её группы в этот объём не входят.

### Пользователь и страна

- Во внутренний сервис передаётся `sessionId: Types.ObjectId` текущей аутентифицированной сессии.
- Пользователь и страна определяются на сервере по проверенной сессии. Отдельные пользовательские входные поля `userId` и `country` для нового контракта не нужны.
- Произвольный ID сессии не заменяет аутентификацию; сессия должна быть действующей и принадлежать вызывающему пользователю.

### Порции и результат

- Для продолжения используется курсорная пагинация и общий `ICursorPagination` из задачи унификации пагинации.
- Размер порции: `TPageSize = 10 | 20 | 50`, по умолчанию 20.
- Результат использует общий `ICursorPaginationResult<TItem>` — новое имя существующего IListResponse. Поля результата: `items`, `count`, `nextCursor`.
- Внутренний результат сервиса — `ICursorPaginationResult<IRecommendationItem>` со следующим контрактом карточки:

```typescript
interface IRecommendationItem {
  _id: Types.ObjectId
  type: EItemType
  title: LanguageText
  media: (MediaSrc & { type: EMediaType.POSTER })[]
}
```

- В media возвращать только элементы с type = EMediaType.POSTER. Скриншоты и трейлеры не загружать в карточку рекомендации; если постеров нет, возвращать пустой массив. Отдельный выбор одного постера или языка этим контрактом не вводится.
- count равен items.length — фактическому количеству возвращённых карточек. Компоненты старой формулы tasteScore, baseScore, plannedBoost, relationBoost и finalScore в новый результат не переносить; ratingScore также не входит в минимальную карточку.
- Порция соответствует фиксированному отрезку сохранённого списка. Недопустимые Items удаляются из ответа без добора из следующего отрезка: например, из 50 позиций возвращается 48 карточек, а курсор продолжает список после исходных 50 позиций. Наличие продолжения определяется nextCursor, а не сравнением count с limit.
- В курсорном ответе не вводится точный total всего каталога. Сам курсор не является обещанием такого подсчёта.
- Это внутренний контракт сервиса; HTTP-представление и транспортные DTO согласуются отдельно при подключении endpoint.

### Формирование персональной выдачи

- Общая CF/ALS-модель обучается заранее в фоне.
- При первом запросе пользователя формируется ограниченный персональный список рекомендаций и сохраняется в Redis для продолжения выдачи.
- Следующие порции читаются из сохранённого списка по курсору, с сохранением его порядка.
- Перед возвратом очередной порции перепроверяется текущая допустимость Items и загружаются актуальные карточки.
- Буфер в Redis обеспечивает продолжение сформированной выдачи. Фоновая подготовка персональных списков заранее для всех пользователей в выбранный вариант не входит; её необходимость может оцениваться по измерениям первого запроса.

### Размер списка и контекст фильтров

- За одно формирование сохраняется до 100 допустимых произведений каждого выбранного типа на конкретный набор условий запроса. Лимит на тип хранится в static; это исходный параметр для проверки качества и стоимости, а не обещание найти 100 допустимых Items.
- Общий предел 200 заменяется лимитом на тип: для одного типа получится до 100 произведений, для трёх — до 300. При отсутствии ограничения types участвуют все поддерживаемые типы.
- Разные условия запроса, включая выбранные типы, теги и библиотечные условия, образуют отдельные контексты со своими списками и курсорами.
- Для каждого типа сохраняется внутренний порядок рекомендаций. Итоговый список формируется поочерёдным выбором одного следующего Item каждого типа в стабильном порядке типов; исчерпанные списки пропускаются. Один и тот же набор выбранных типов в разном порядке не меняет контекст или порядок смешивания.
- Если подходящих произведений типа меньше 100, сохраняется найденное число. Другие типы не превышают свой лимит для компенсации нехватки.
- В Redis сохраняются IDs и итоговый порядок смешанной выдачи. Актуальные карточки загружаются при чтении порций; размер порции применяется ко всей смешанной выдаче.
- После окончания сохранённого списка возвращается `nextCursor: null`. Это конец сформированной выдачи, а не подтверждение исчерпания всего допустимого каталога.
- Отбор и смешивание работают с набором значений EItemType без отдельного алгоритма для каждого медиаформата. Добавление поддерживаемого типа, например книг, должно позволять применять те же лимит, фильтры, пропорции источников, fallback и курсорную выдачу без переписывания смешивания.
- Новому типу не требуется отдельная CF/ALS-модель для участия в выдаче. До включения его данных в пригодную общую модель используется согласованный fallback; затем применяется общий путь CF/ALS. Расширение каталога и подготовка обучающих данных для нового типа остаются отдельными задачами.

### Сброс персональной выдачи

- Изменение оценки, избранного или явных предпочтений делает персональную выдачу пользователя недействительной.
- Создание/удаление библиотечной записи, смена её статуса, skip и block также делают выдачу недействительной: изменяются библиотечные условия или допустимость кандидатов.
- Изменения заметки, прогресса и других данных без влияния на вкус или отбор не требуют сброса выдачи. Если операция одновременно меняет значимые поля, применяется правило для этих полей.
- Сброс выполняется после успешного сохранения действия в MongoDB и затрагивает персональные списки этого пользователя, а не весь Redis.
- После сброса новый список формируется при следующем запросе рекомендаций; немедленный пересчёт после каждого действия не запускается.
- Старые курсоры сброшенных списков становятся недействительными; клиент начинает новую выдачу.
- Общая CF/ALS-модель не переобучается после каждой реакции. Пользовательский ALS-вектор пересчитывается из актуальных сигналов.
- Уже запущенный устаревший расчёт не должен сохранить свой результат после сброса персональной выдачи. Актуальность исходных данных проверяется перед публикацией результата.

### Срок жизни списка и курсор

- Персональный список хранится в Redis 10 минут с момента создания. Это исходный параметр для последующей проверки нагрузкой; чтение порций не продлевает срок жизни.
- Повторный запрос с тем же курсором возвращает ту же позиционную порцию сохранённого списка с учётом актуальных исключений и текущих карточек. Чтение курсора не сдвигает общую изменяемую позицию.
- При истечении срока жизни или сбросе списка старый курсор приводит к ошибке с кодом `RECOMMENDATION_CURSOR_EXPIRED`.
- После этой ошибки клиент начинает новую выдачу запросом без курсора. HTTP-статус ошибки определяется при отдельном согласовании HTTP-контракта.
- При продолжении старого списка новый список не подставляется незаметно: иначе нарушаются порядок и границы порций.

### Фильтрация по тегам

- В новом контракте рекомендаций убрать `filter.fields` с точными числовыми и временными границами (`EItemField`, `min`, `max`).
- Фронт переводит выбор диапазонных категорий в один или несколько IDs тегов и передаёт их серверу. Например, длительность выбирается через существующие категории 90–120 минут и другие нужные категории.
- Бэкенд фильтрует по назначенным тегам. Нужно обеспечить корректность соответствующей разметки; отсутствие назначения не доказывает соответствие выбранной категории.
- Точные значения в каноническом Item сохраняются: правила групп тегов уже используют их как sourceField, а другие сценарии продолжают на них опираться.
- Решение относится к новому рекомендательному контракту; точные фильтры поиска и подборок этой задачей не меняются.

Для условий используется общий `IValueFilter<TValue>` из `infrastructure/database/types`:

```typescript
interface IValueFilter<TValue> {
  allOf?: readonly TValue[]
  anyOf?: readonly TValue[]
  noneOf?: readonly TValue[]
}
```

В рекомендательном фильтре `tags?: readonly IValueFilter<Types.ObjectId>[]`. Между элементами массива действует И. В каждой группе allOf требует все перечисленные назначения, anyOf — хотя бы одно, noneOf — отсутствие всех перечисленных назначений; заданные условия группы также действуют одновременно.

Пример: одна группа требует романтику и фэнтези, другая разрешает любую из нескольких категорий длительности, третья — любой из выбранных годов. Такое представление позволяет независимо выбирать альтернативы для разных признаков.

### Библиотечные условия

Используется тот же общий тип:

```typescript
type TLibraryStatus =
  "planned" | "inProgress" | "onHold" | "completed" | "dropped"

interface IRecommendationLibraryFilter {
  library?: IValueFilter<TLibraryStatus | "outside">
}
```

- `outside` — значение только в условии запроса, обозначающее отсутствие библиотечного статуса; новый статус UserItem не создаётся.
- Если filter.library не передан, применять условие anyOf: ["outside"]: по умолчанию выдавать только произведения вне библиотеки. Явно переданный библиотечный фильтр задаёт допустимые статусы вместо этого значения по умолчанию.
- Одно и то же библиотечное условие действует для всех источников, включая ручной, новинки и fallback. Наличие оценки или известность Item модели сами по себе не исключают его, когда он разрешён явно заданным библиотечным фильтром; автоматическая маска известных Items не должна отменять этот фильтр.
- `anyOf: ["outside", "planned"]` допускает произведения вне библиотеки и запланированные.
- `anyOf: ["planned"]` допускает только запланированные.
- `noneOf: ["completed"]` исключает завершённые, сохраняя остальные допустимые произведения.
- Прежние специальные `include`, `exclude`, `only` в новом рекомендательном контракте заменяются общими операциями IValueFilter.
- Blocked, активный skipped и bans исключаются независимо от библиотечных условий. Просроченный skipped не считается библиотечным статусом.

### Фильтр рейтинга

- Передавать необязательные границы в `filter.rating.min` и `filter.rating.max`, как в фильтре рейтинга Search.
- Границы относятся к обычному среднему рейтингу `ItemStats.ratingAverage`, а не к CF/ALS-score или сглаженному рейтингу.
- Границы — конечные числа от 1 до 10 включительно, допускаются дробные значения. Если заданы обе границы, `min` не превышает `max`.
- Кандидат без известного среднего рейтинга не проходит заданное рейтинговое условие. Если границы не заданы, отсутствие рейтинга само по себе не исключает Item.
- Это самостоятельное условие по агрегату оценок; решение убрать точные диапазоны metadata из filter.fields на него не распространяется.

### Дополнительные общие изменения

Общие изменения перечислены в [истории улучшений API](../api/sharedApiImprovements.md). `IValueFilter` уже используется в типах; исполнение условий фильтрации остаётся [открытой задачей](apiImprovementsTodo.md).

## 2. Данные для разработки и порядок проверки

- Сбор и подготовка реальных данных других сайтов переносятся на завершающий этап, после реализации рекомендательной системы.
- Для текущей разработки подготовить воспроизводимые искусственные каталоги, пользователей и истории взаимодействий на изолированных тестовых данных.
- Искусственные взаимодействия для обучения подготовить в JSON-файле. IDs произведений в файле должны соответствовать каталогу, на котором проверяется выдача; при подготовке моков использовать согласованные IDs для JSON и тестового Mongo-каталога.
- На искусственных данных запускать настоящее обучение ItemCF/ALS, загрузку моделей, получение кандидатов и общий путь выдачи. Готовые ответы вместо модели не заменяют такую проверку.
- Наборы должны позволять проверить разные вкусы, пустые и длинные истории, новые Items, библиотечные условия, теговые группы, рейтинги, bans, skips и изменения пользовательских сигналов.
- Искусственные данные используются для функциональной проверки и измерения стоимости заданных сценариев. Они не подтверждают качество рекомендаций для реальных пользователей.

### Временные бот-профили

- Для начального периода работы сайта пользователь выбрал временные бот-профили, основанные на данных других платформ. Ориентировочный срок — первые полгода–год; впоследствии боты удаляются.
- Добавить BOT = "bot" в существующий EUserRole. Бот определяется по User.role; отдельное поле type/kind/isBot для этого не вводить.
- Для сайта и его функций BOT эквивалентен USER: обычные пользовательские операции, библиотека, оценки, избранное, рекомендации и другие пользовательские сценарии работают по одним правилам. Проверки доступа к обычным пользовательским функциям должны допускать обе роли; административные права остаются отдельными.
- Действия ботов участвуют в ItemStats, SiteStats, публичных рейтингах, счётчиках и обучении CF/ALS наравне с действиями USER. Не вводить отдельные ботские агрегаты, коэффициенты или исключение из обучения по признаку роли.
- При удалении учитывать связанные UserItem и вклад в агрегаты: удаление ботов не должно оставлять их оценки и счётчики в статистике.
- Создание, импорт, расписание и дальнейшее поведение ботов пока не проектировать; пользователь отложил эти вопросы.
- Переключатель источника trainer и ранее согласованные этапы сохраняются. В режиме MongoDB данные BOT и USER обрабатываются по одним правилам; проектирование создания и поведения ботов не требуется для определения этих правил.

## 3. Обучение и хранение моделей

### Единая модель каталога

- Использовать один общий комплект ItemCF/ALS для всех поддерживаемых EItemType: общую пользовательско-предметную матрицу и совместно обученные артефакты CF и ALS. Отдельные модели по типам или медиадоменам не вводить.
- Разделение выдачи по типам применяется при получении кандидатов и формировании списков до 100 Items на тип. Оно не требует отдельного обучения или отдельной модели для каждого типа.
- Порог 5 положительных взаимодействий считается по всей общей модели, а не отдельно для каждого типа. Пользовательский ALS-вектор строится по всем допустимым положительным взаимодействиям с известными общей модели произведениями.
- Единое обучение допускает использование межтиповых связей в историях одних и тех же пользователей. Это выбранное устройство системы; качество такого переноса исследованием не подтверждено и проверяется на реальных данных. Несвязанные пользовательские IDs разных внешних источников не объединять.

### Сигналы обучения

- Для первой ItemCF/ALS-модели использовать бинарные положительные сигналы: оценка 8–10 либо isFavorite при отсутствии оценки или оценке 5–10.
- Оценка 1–4 не является положительным сигналом, даже при isFavorite. Оценки 5–7 без избранного не становятся подтверждёнными положительными или явными отрицательными сигналами CF/ALS.
- Разную силу положительных оценок 8, 9 и 10 в первой модели не вводить. Сравнение со взвешенными сигналами оставить для проверки на реальных данных.
- Одна текущая пара user/item даёт один положительный сигнал. Повторные попытки или прохождения не увеличивают его количество.
- Skipped-записи исключаются из входных сигналов. Сам block не кодируется как обучающий dislike и не понижает похожие произведения автоматически; сохранённые rating/isFavorite оцениваются по общим правилам. Сам заблокированный Item всегда исключён из выдачи.
- Завершение, прогресс и заметка сами по себе не означают симпатию.
- Текущая шкала вычисляемого content-профиля сохраняется для использующих её сценариев: отрицательные оценки 1–4 влияют отрицательно, 5–6 без избранного нейтральны, 7 без избранного остаётся слабым плюсом. В новой выдаче рассчитанные weight/count не добавляются поверх истории CF/ALS; ручной слой использует только explicitWeight. Явное отрицательное обучение ALS в первую версию не включать.
- Правила отнесения сигналов к положительным — стартовая конфигурация, а не доказанный оптимум для пользователей Bisky. При последующей замене источника данных переиспользовать один и тот же согласованный способ подготовки сигналов для обучения и пользовательского fold-in.

### Запуск обучения

- Добавить отдельный Docker-образ и одноразовый сервис `recommendation-trainer` с Python, библиотеками обучения и скриптом проекта.
- Сразу реализовать автоматический запуск контейнера раз в сутки на уровне окружения развёртывания для обоих источников данных. Точное время запуска и конкретное средство планирования задаются при реализации конфигурации развёртывания.
- Ручной запуск сохранить дополнительно: `docker compose run --rm recommendation-trainer` после появления соответствующей конфигурации. Команда является будущим интерфейсом запуска, а не уже существующим сервисом.
- Trainer читает подготовленный набор взаимодействий, обучает ItemCF/ALS, сохраняет артефакты в MongoDB и завершает работу.
- Контейнер запускается окружением развёртывания. API не получает доступ к Docker daemon и не управляет контейнерами.
- API сохраняет отдельный Node-образ. Python не запускается на запрос рекомендаций; trainer имеет собственные ограничения CPU и памяти.
- Перед обучением проверять, изменились ли подготовленные обучающие данные, источник или параметры относительно соответствующего успешного обучения. Если ничего не изменилось, повторный fit не выполнять. Неудачное обучение не помечать успешным обработанным набором.

### Выбор источника обучения

- В static самого trainer разместить один переключатель `USE_SITE_DATA`. Не дублировать независимые переключатели источника в API и Python.
- `USE_SITE_DATA = True` — читать взаимодействия сайта из MongoDB.
- `USE_SITE_DATA = False` — читать взаимодействия из JSON-файла. На этапе разработки применяется этот режим с моковыми данными; позднее через тот же формат можно передавать подготовленные внешние данные.
- После чтения оба источника приводятся к единому входу и проходят одинаковые согласованные правила формирования положительных сигналов, обучение и публикацию модели. Переключение источника не требует переписывания CF/ALS.
- Автоматический и ручной запуск используют один и тот же переключатель и путь обучения. Смена источника учитывается при проверке необходимости нового обучения.
- Сохранять источник и идентификатор подготовленного набора в метаданных модели, чтобы различать результаты обучения на MongoDB и JSON.

### Хранение и подключение модели

- В MongoDB хранить отдельное описание `RecommendationModel`: generated _id, unique semantic key, scope, state, trainedAt, itemCount и параметры ALS/CF. Для выбранной единой модели scope охватывает весь поддерживаемый каталог.
- Бинарные артефакты хранить в `RecommendationModelChunk`: generated _id, model, kind, part, checksum, data. Большие массивы разбиваются на части, чтобы не превышать предел одного Mongo-документа.
- В артефактах сохраняются факторы ALS, необходимые данные для fold-in, CF-соседи, соответствие Item IDs строкам и обучающая популярность. Параметры и форматы должны позволять одинаковую интерпретацию в Python и Node.
- Сначала полностью сохранить и проверить части, затем перевести описание в ready. Неудачное обучение не заменяет предыдущую рабочую модель.
- Node загружает артефакты в память при подключении модели и выполняет выдачу в worker threads; запросы не перечитывают факторы и соседей из MongoDB каждый раз.
- Числовые массивы модели переиспользуются workers как одна общая неизменяемая копия в RAM, а не загружаются независимо в каждый worker. Факторы всех пользователей в памяти API не хранятся; пользовательский вектор рассчитывается по актуальным взаимодействиям.
- Постоянные артефакты остаются в MongoDB и загружаются заново после перезапуска API. Дополнительная копия самой модели в Redis не требуется; Redis используется для персональных списков.
- Новое обучение создаёт новую версию. Переключение на неё выполняется после полной успешной загрузки; выполняющийся запрос использует согласованный комплект одной модели.
- Каждый экземпляр API проверяет готовую версию в MongoDB при запуске и затем раз в час. Проверяется идентификатор версии; неизменившиеся артефакты повторно не загружаются. Интервал хранится в static рекомендательного модуля.
- После обнаружения новой готовой версии API загружает и проверяет её, затем переключает workers. При ошибке загрузки или проверки сохраняется предыдущая рабочая версия. HTTP-запрос из Python для запуска синхронизации не требуется.
- Ежедневный запуск trainer и ежечасная проверка API независимы. После публикации версии задержка её обнаружения работающим API составляет до часа при исправной проверке; время загрузки и проверки артефактов добавляется отдельно.

## 4. Состав и смешивание выдачи

- Базовая пропорция источников без положительного ручного источника: 70% персональных рекомендаций CF/ALS, 20% новинок и 10% популярного. При наличии положительных ручных интересов до 10 мест на тип выделяется внутри персональной доли по правилу ниже. Если collaborative-персонализация неприменима, действует fallback.
- Пропорции применяются отдельно к списку каждого типа: для 100 произведений это целевые 70 персональных, 20 новинок и 10 популярных. Затем списки типов смешиваются; точные пропорции источников в каждой отдельной порции не гарантируются.
- Новинки и популярное равномерно вставляются среди персональных карточек, а не выдаются отдельным блоком в конце.
- Все источники проходят одинаковые фильтры и ограничения. Один Item не повторяется из-за попадания в несколько источников.
- При нехватке кандидатов в одном источнике свободные места заполняются из остальных допустимых источников. Доли являются целевыми, а не причиной ослаблять фильтры или возвращать дубли.
- Пропорции хранятся в static рекомендательного модуля. Это стартовая настройка для последующей проверки качества и стоимости.

### Объединение CF и ALS

- Для каждого выбранного типа каждый collaborative-источник возвращает до 500 кандидатов этого типа из общей модели, затем их списки объединяются без дублей. Ранги и RRF считаются внутри соответствующего типа, чтобы общий top500 не вытеснял другие типы из их персональных списков.
- Использовать bounded weighted RRF с начальным равным весом CF и ALS (0.5/0.5). Вес и предел списка задаются в static и позже проверяются на реальных данных, включая сравнение с каждым одиночным алгоритмом.
- Сохраняется проверенная форма исследования: сумма `weight / (60 + rank)` по источникам, где rank начинается с 1. Отсутствие Item в top500 источника даёт нулевой вклад от этого источника; полные ранги вне списка не подставляются.
- Сырые CF- и ALS-scores напрямую не складываются из-за разных шкал.
- Для CF сохранить обучающую popularity tie-fill политику, участвовавшую в исследовании; равные model scores разрешать по обучающей популярности и Item ID. Выбор общего рейтинга для отдельного канала популярного этого правила не меняет.
- Общий порядок используется как основа персональной части выдачи перед ручной корректировкой. Полный вычисляемый content-профиль и старый recommendation pipeline в новый serving не подключаются; узкий источник по прямым ручным настройкам используется по правилу ниже.

### Ручные предпочтения по тегам

- Учитывать актуальные ненулевые explicitWeight из UserTasteProfile. Ноль означает отсутствие ручной поправки; рассчитанные weight/count вместо него не подставляются. Общая CF/ALS-модель, положительные обучающие сигналы и порог 5 взаимодействий остаются прежними.
- Ручной вес мягко меняет порядок, но не удаляет Item и не создаёт фиктивные likes/dislikes. Он не стирает соответствующие связи из обученной модели и не обещает буквального замещения признака внутри ALS. Для строгого исключения используются фильтры запроса и block.
- Для ограниченного пула кандидатов пакетно получать назначенные ручные теги с положительным relevanceScore. Учитывать taste-enabled группы и применимость к EItemType; среди совпавших ручных тегов подавлять назначенных предков более конкретными назначенными тегами. Ненастроенный ребёнок не подавляет ручного родителя; назначения родителей автоматически не выводятся.
- Ручная оценка e — сумма explicitWeight × relevanceScore × weightModifier, делённая на сумму weightModifier совпавших ручных тегов после подавления предков. При пустом наборе или нулевом знаменателе e = 0. Отсутствующая разметка не доказывает отсутствия нежелательной темы.
- Использовать поправку S = B + λ × e отдельно внутри каждого канала. Для CF/ALS B = 61 × согласованный bounded RRF; для популярного и новинок B = 61 / (60 + базовый ранг). Каналы смешиваются по квотам, а не сравнением их scores. При равенстве S сохраняется базовый порядок канала. Стартовый λ = 0.25 хранится в static и требует проверки на данных.
- Поправку применять к персональным кандидатам, популярному и новинкам. Для новинок сохраняются окно 90 дней и запрет будущего; при активных настройках итоговый порядок может отличаться от строгой хронологии. При пустом ручном профиле пропускать ручной слой и сохранять базовый порядок.
- Дополнительно получать ограниченный пул допустимых Items по положительным применимым ручным тегам, включая кандидатов вне CF/ALS top500. В ручной источник входят Items с итоговым e > 0. Несколько интересов допускаются независимо, не как обязательное совпадение всех тегов; отбор должен поддерживать их детерминированное чередование.
- Для списка 100 данного типа резервировать до 10 ручных мест внутри существующих 70 персональных либо 60 рейтинговых мест fallback. При достаточных кандидатах состав — 60 CF/ALS + 10 ручных + 20 новинок + 10 популярных; в fallback — 50 популярных + 10 ручных рейтинговых + 40 новинок. При только отрицательных настройках отдельного ручного источника нет, исходные доли сохраняются.
- В warm-режиме ручной Item может не иметь model vector или оценок, если проходит фильтры. В fallback ручные места сохраняют условия рейтинговой доли: ratingsCount > 0 и известный ratingAverage. Правило для каталога без собственных оценок согласуется отдельно.
- Недоступные ручные места возвращаются основной доле; ручной источник не расширяется сверх своего резерва из-за нехватки CF/ALS. Для неполных списков применять детерминированное пропорциональное распределение с верхней границей ручных мест. Дубли между источниками удаляются; фильтры не ослабляются.
- Корректировка и смешивание выполняются при формировании списка. В Redis сохраняется окончательный порядок; на следующих порциях его не пересчитывать. Изменение explicitWeight инвалидирует списки по общему правилу после Mongo commit, без переобучения модели или ожидания вычисляемого content-профиля.
- Резерв 10 и λ = 0.25 — стартовые настройки, а не доказанный оптимум. Результаты и ограничения описаны в разделе 13 [исследования](../research/recommendationSystemStudy.md): отдельно проверить стоимость Mongo retrieval и сквозного формирования, затем полезность для реальных пользователей.

### Fallback без collaborative-персонализации

- Включать CF/ALS при наличии пригодной рабочей модели и хотя бы 5 уникальных положительных взаимодействий пользователя с известными этой модели произведениями. Положительность определяется согласованными правилами оценок и избранного; порог хранится в static как стартовая настройка для последующей проверки на данных.
- При недостаточной истории для CF/ALS или отсутствии пригодной рабочей модели использовать общий ratingScore как основу fallback с ручной корректировкой и ручными местами по согласованному правилу.
- Использовать те же отбор, порядок и ограничения, что у источника популярного; отдельный scorer для этого fallback не создавать.
- При отсутствии CF/ALS базовый состав списка соответствующего типа — 60% общего рейтинга и 40% новинок: для 100 произведений это 60/40. До 10 мест рейтинговой доли может занимать источник по положительным ручным интересам. Между источниками нет дублей; при нехватке кандидатов действует общее правило заполнения недостающих мест в пределах лимита этого типа.
- Полный старый content-fallback не используется. Узкий ручной источник и поправка дополняют этот режим; CF/ALS применяется при пригодной модели и истории.

### Определение новинки

- Новинка определяется по Item.releaseDate: дата первого выпуска Item попадает в последние 90 дней и не находится в будущем. Окно хранится в static рекомендательного модуля.
- Для сериальных типов Item представляет отдельный сезон, а releaseDate означает дату первой серии этого сезона. Выход следующих серий не меняет releaseDate.
- Статус ongoing сам по себе не делает давно начавшийся сезон новинкой.
- Отдельное nullable-поле Item.series.lastReleasedEpisodeAt хранит дату последней уже вышедшей серии сезона. Оно не заменяет releaseDate в правиле новизны.
- Базовый порядок новинок соответствующего типа — releaseDate по убыванию, затем существующий ratingScore по убыванию и Item._id по возрастанию. При активных ручных настройках применяется согласованная поправка S_new; строгая хронология тогда не гарантируется.
- Наличие оценок не требуется для попадания в новинки. При отсутствии оценок используется существующее поведение вычисления ratingScore; явно заданные рейтинговые фильтры продолжают действовать по общим правилам.

### Общий рейтинг для 10% популярного

- Для этого источника выбирать допустимые произведения с ratingsCount > 0 и известным ItemStats.ratingAverage.
- Основной порядок — ratingScore по убыванию. Общая функция [calculateItemRatingScore](../../../src/entities/itemStats/functions/calculateItemRatingScore/index.ts) использует формулу `(n * R + 20 * C) / (n + 20)`, где n — ItemStats.ratingsCount, R — ItemStats.ratingAverage, C — сохранённый средний рейтинг сайта из SiteStats.
- При одинаковом ratingScore сортировать по ratingsCount по убыванию, затем по Item._id по возрастанию.
- Среднее по сайту читать через `SiteRatingsStatsRepository.readAverage()`, при отсутствии использовать 5,5. Для отбора в MongoDB предстоит применить те же правила расчёта до ограничения числа кандидатов. Новый счётчик популярности для этого источника не добавлять.
- По смыслу канал выбирает высоко оценённые произведения с поправкой на число голосов. При нехватке кандидатов действует общее правило заполнения из остальных источников без ослабления фильтров.
- Правило задаёт базовый порядок отдельного источника 10% выдачи и рейтинговой доли fallback перед ручной корректировкой. Обучающую популярность для CF/ALS и её роль в разрешении равных model scores оно не заменяет.

После проверки нового пути заменить старую реализацию RecommendationsService.find и удалить неиспользуемый createRecommendationPipeline, старый readRecommendations и принадлежащие только им типы и зависимости. Перед удалением проверить потребителей; общие фильтры, рейтинг и используемые другими сценариями части UserTasteProfile сохранить. Обновить затронутую документацию по фактическому поведению.

Постоянное сопровождение двух полноценных рекомендательных реализаций в итоговый вариант не входит. Завершающий этап с реальными данными выполняется после этой последовательности.

## Завершающий этап: реальные данные

- После завершения реализации подготовить реальные данные нескольких сайтов для обучения и оценки, переиспользуя подходящие сохранённые материалы исследования.
- Внешние данные рассматриваются как временный источник до накопления достаточных собственных взаимодействий Bisky. Переход на собственные данные должен использовать тот же путь обучения и загрузки моделей.
- Совместимость внешних Item IDs с каталогом Bisky и различия пользовательских сигналов проверить при подготовке реальных данных; несвязанных пользователей разных сайтов не объединять.
- Подготовка искусственных наборов не отменяет последующую проверку качества на настоящих взаимодействиях. Сохранённые исследовательские datasets и доказательства этой перестановкой этапов не удаляются.
