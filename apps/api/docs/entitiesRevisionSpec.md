# Спецификация правок схем сущностей

## Статус и границы

Спецификация составляется по результатам последовательного разбора текущих `apps/api/src/entities/*/schemas` с владельцем проекта. Здесь фиксируются только согласованные решения. Исходный код в ходе разбора не меняется.

После полного прохода необходимо проверить зависимости и противоречия, выделить общие требования и требования отдельных сущностей, затем подготовить самостоятельный промпт для реализации в новом чате.

Предыдущие изменения рабочего дерева сохраняются. Тесты и Storybook не входят в разрешённую область. Коммиты и операции с внешней базой данных не разрешены.

## Общие требования

Пока не согласованы.

## Решения по сущностям

### accountAccessEvent — удалить

Решение владельца: сущность не нужна в MVP.

- Удалить папку `apps/api/src/entities/accountAccessEvent` со схемой, репозиторием и модулем.
- Удалить импорт и подключение `AccountAccessEventModule` в `AppModule`.
- Найти и убрать оставшиеся ссылки на удаляемую сущность в production-коде, если они есть.
- Удалить требования записи `AccountAccessEvent` из связанных сценариев проектной документации; актуализировать существующие описания состава сущностей и модулей.
- Не удалять и не упрощать другие сущности авторизации на основании этого решения: они рассматриваются отдельно.
- Удаление исходных файлов не означает разрешения удалять коллекцию или данные во внешней MongoDB.

### catalogDecision — удалить

Решение владельца: сущность не нужна.

- Удалить папку `apps/api/src/entities/catalogDecision`, включая основную схему, вложенные `CatalogSubject`, `CatalogRevision`, `CatalogAssignedId`, репозиторий и модуль.
- Удалить импорт и подключение `CatalogDecisionModule` в `AppModule`.
- Проверить ссылки на решения каталога в остальных схемах и production-коде; удалить или согласованно заменить зависимые поля и контракты. Конкретные решения по этим сущностям фиксируются при их разборе.
- Исключить требования ведения истории операций через `CatalogDecision` из проектной документации и актуализировать существующие описания состава сущностей и модулей.
- При итоговом анализе пересмотреть зависимые сценарии импорта, повторной обработки, обновления поиска, объединения и разделения фильмов. Защита импорта от повторной обработки и версии самих сущностей должны сохраняться; конкретный механизм ещё не выбран.
- Не создавать новую сущность истории вместо удаляемой без отдельного согласованного требования.
- Удаление исходных файлов не означает разрешения удалять коллекцию или данные во внешней MongoDB.

### credentialOperationReceipt — удалить из MVP

Решение владельца: механизм пока не нужен.

- Удалить папку `apps/api/src/entities/credentialOperationReceipt` со схемой, репозиторием и модулем.
- Удалить импорт и подключение `CredentialOperationReceiptModule` в `AppModule`; проверить оставшиеся ссылки в production-коде.
- Исключить требования создания этого receipt и повторной выдачи сохранённого кода из сценариев регистрации, перевыпуска и восстановления в проектной документации; актуализировать существующие описания состава сущностей и модулей.
- В MVP не обещать повторное получение ранее выданного кода после потери ответа через этот механизм. При итоговом анализе согласовать упрощённое поведение соответствующих сценариев без хранения зашифрованного результата операции.
- Не удалять общую схему `ProtectedSecret` автоматически: проверить её использование другими сущностями при разборе `shared`.
- Не удалять другие сущности авторизации или защиты от повторных запросов на основании этого решения.
- Удаление исходных файлов не означает разрешения удалять коллекцию или данные во внешней MongoDB.
