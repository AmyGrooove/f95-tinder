## Как читать документы

Раздел `api` описывает реализованные операции и явно отмечает ограничения и будущие расширения. Раздел `product` хранит согласованные требования и идеи; наличие пункта в нём не означает готовую реализацию. `sources` содержит справочные данные и правила сопоставления, `legacyBiskyV3` — исторические референсы.

При расхождениях фактическое поведение сверяется с исходниками, требования — с соответствующей спецификацией и основами, объём этапа — с MVP и отдельно согласованными контрактами. Расхождение кода и требований нужно обозначить явно. Статическая сверка API выполнена 24 октября 2026 года; она не подтверждает поведение запущенного приложения, состояние БД и индексов.

## Соглашения об именовании

Составные имена сегментов путей API и файлов документации пишем в camelCase: например, `/userItems`, `/account/displayName`, `accountAndAuthSpec.md`. Дефисы и подчёркивания для разделения слов в именах сегментов API не используем.

## Согласованный порядок следующих этапов

1. Реализовать пользовательские эндпоинты каталога: список фильмов, карточку, поиск, фильтры и справочники тегов и характеристик.
2. Реализовать личную библиотеку: статусы «Запланировано», «В процессе», «Отложено», «Завершено», «Брошено»; независимые оценку, избранное и заметку, а также прогресс просмотра. Маршруты изменения этих данных и попыток уже реализованы; GET-маршруты чтения библиотеки ещё не добавлены.
3. Реализовать стартовые и простые персональные рекомендации, сохранение показов, пропусков и действия «Не предлагать».
4. Реализовать наполнение каталога: сбор фильмов Kodik в S3, формат подготовленного JSON-пакета, проверку и импорт без дублей, согласования, сохранение ручных исправлений и отчёт.

Порядок выбран 21 октября 2026 года. До реализации импорта для разработки и проверки пользовательских сценариев нужен небольшой набор фильмов и связанных справочников в БД, который можно подготовить вручную. На таком наборе можно проверить поведение рекомендаций; оценка их качества требует достаточного объёма реальных данных.

Стандартные разделы библиотеки формируются по статусам. Публичные ручные подборки реализованы отдельным [контрактом](api/collectionsSpec.md); приватные списки он не определяет. Полная админка, расписания сбора и embedding также требуют выбора объёма согласно [границам MVP](product/mvpScope.md). Порядок этапов не заменяет детальные контракты их реализации.
