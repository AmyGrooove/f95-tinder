# 3. Система рекомендаций

[Все основы проекта](../foundations.md) · [Предыдущий пункт: наполнение каталога](catalogWorkflow.md) · [Следующий пункт: личная библиотека и списки](library.md)

Согласованное решение первой версии от 26 октября 2026 года, расчёт профиля уточнён 27 октября. Feature объединены с Tag; точные значения хранятся в Item, профиль вкуса содержит только tagPreferences. Ежедневный пересчёт Tag.weightModifier и фоновая пересборка TasteProfile после операций библиотеки реализованы; редактирование явных настроек и рекомендательная выдача ещё предстоят. [Первоначальное исследование](../../research/recommendationSystem.md) и [исследование кросс-рекомендаций](../../research/crossTypeRecommendations.md) сохраняются как исследовательские материалы. Для реализации V1 следует опираться на решения этого документа.

## Цель и общая основа

Bisky помогает быстрее находить подходящее произведение и сохранять удовлетворённость выбором. Личная библиотека и списки также имеют самостоятельную ценность.

Рекомендации используют общий профиль предпочтений по тегам, включая согласованные диапазонные категории для всех семи типов Item. Интерес к мрачной атмосфере или киберпанку в играх помогает подбирать фильмы, аниме и другой контент. Разные интересы, например к уютным историям и мрачной фантастике, представлены отдельными весами признаков.

Общие канонические теги имеют одинаковый смысл на разных типах контента. Разные понятия, например выживание как тема и survival как игровая механика, представлены разными тегами. Алиасы одного понятия не создают дополнительных подтверждений. Общий профиль не делает несопоставимые свойства одинаковыми: предпочтение RPG влияет только на кандидатов с соответствующим содержательным признаком.

Каталог рекомендаций, главная и Пик используют общий механизм с условиями конкретного сценария. При запросе фильмов результат содержит только фильмы; данные игр меняют выбор внутри разрешённого типа.

Механизм остаётся заменяемым: реализации используют общий формат запроса и результата, активные правила выбираются конфигурацией. Изменение алгоритма допускает пересборку вычисляемых предпочтений с сохранением пользовательских данных и явных настроек. Объяснимые веса и количество подтверждений позволяют впоследствии визуализировать вкус; вид такого экрана определяется отдельно.

## Сигналы пользователя

Начальные коэффициенты вкладов одного произведения:

| Сигнал                                               |                                                                         Вклад |
| ---------------------------------------------------- | ----------------------------------------------------------------------------: |
| Оценка 10 / 9 / 8 / 7                                |                                                     +1 / +0,75 / +0,5 / +0,25 |
| Оценка 5–6                                           |                                                                             0 |
| Оценка 4 / 3 / 2 / 1                                 |                                                     −0,25 / −0,5 / −0,75 / −1 |
| Избранное без оценки или с оценкой 5–6               |                                                                          +0,8 |
| Запланированное                                      | 0 для weight/count; бонус самому кандидату в допускающих библиотеку сценариях |
| Остальные статусы, завершённость, попытки и прогресс |                                                                             0 |
| Открытие карточки и отсутствие реакции               |                                                                             0 |

Оценка учитывается независимо от завершённости. Избранное усиливает положительную оценку, при этом вклад одного произведения ограничен +1. При низкой оценке 1–4 используется отрицательный вклад оценки: избранное его не усиливает и не отменяет. Например, оценка 1 вместе с избранным даёт −1. Исходные rating и isFavorite остаются независимыми пользовательскими полями.

Для оценки 7–10 с избранным вклад = 0,8 + 0,2 × вкладОценки: соответственно 0,85 / 0,9 / 0,95 / 1. Нейтральные оценки 5–6 без избранного участвуют в среднем с нулевым вкладом и увеличивают count. Отсутствие оценки и избранного не создаёт подтверждения. planned сам по себе не создаёт вклад; сохранённые rating/isFavorite учитываются независимо от статуса, кроме skipped.

Одно произведение даёт одно подтверждение признака. Повторная установка оценки, несколько попыток и сочетание оценки с избранным не увеличивают число подтверждений. planned не входит в weight/count; его бонус применяется к самому запланированному кандидату вне Пика.

Завершение само по себе не означает симпатию. Статус «Бросил» неоднозначен. Реакция на подборку не переносится автоматически на каждый её Item. Сравнения в Баттле пока не сохраняются и не меняют числовые оценки; проигрыш не создаёт отрицательный вклад.

Пропуск исключает конкретный Item на 90 суток. Блокировка исключает его до изменения или удаления записи. Эти действия не меняют веса признаков сами по себе. Сохранённые явные rating/isFavorite у blocked остаются пользовательскими данными для расчёта; skipped не служит источником вкуса. Срок пропуска проверяется по времени независимо от физической TTL-очистки.

## UserTasteProfile

Один документ на пользователя, уникальный индекс по user. Единственный массив tagPreferences содержит предпочтения, общие для всех типов контента. Отдельных featurePreferences и селекторов value/range нет: каждый диапазон представлен собственным Tag.

| Поле предпочтения | Назначение                                                       |
| ----------------- | ---------------------------------------------------------------- |
| tag               | Ссылка на конкретный Tag                                         |
| weight            | Рассчитанное предпочтение, конечное число в диапазоне [−1, +1]   |
| count             | Число текущих произведений, участвовавших в расчёте предпочтения |
| explicitWeight    | Явное предпочтение пользователя в [−1, +1], по умолчанию 0       |

Профиль допускает максимум 4096 уникальных тегов. Участие группы во вкусе задаётся isUsedForTaste в [TAG_GROUP_RULES](../../../src/entities/tag/static/TAG_GROUP_RULES.ts). Диапазоны duration фильма и mainStoryDuration игры имеют разный смысл и разные Tag. Точное значение Item не даёт второй независимый вклад поверх диапазонного тега.

Пример документа; строки tag обозначают условные ObjectId тегов, а не их key:

```json
{
  "user": "userId",
  "tagPreferences": [
    { "tag": "cyberpunkTagId", "weight": 0.7, "count": 5, "explicitWeight": 1 },
    {
      "tag": "duration90To120TagId",
      "weight": 0,
      "count": 0,
      "explicitWeight": 1
    }
  ]
}
```

### Явные предпочтения

Пользователь может указать интерес к обычному или диапазонному тегу до накопления библиотеки. Положительные значения означают симпатию, отрицательные — неприязнь. Ноль означает отсутствие явной настройки; при нуле работает рассчитанный weight.

```text
используемый вес = explicitWeight !== 0 ? explicitWeight : weight
```

Явный выбор имеет приоритет над рассчитанным весом того же признака и значения/диапазона. Рассчитанный weight продолжает обновляться независимо. Очистка явной настройки возвращает использование рассчитанного значения. explicitWeight не увеличивает count.

После пересчёта или изменения явной настройки элемент удаляется, если count == 0 и explicitWeight == 0. При count > 0 элемент сохраняется даже с нулевым weight. Предпочтение с explicitWeight != 0 сохраняется и при count == 0.

Профиль сочетает вычисляемые данные и пользовательские настройки. Пересборка обновляет weight/count, сохраняя актуальные explicitWeight, в том числе настройки, изменённые во время расчёта. Нельзя заменить документ старой копией и затереть явный выбор. UI и операции редактирования задаются отдельным контрактом перед реализацией.

## Расчёт весов и значимость признаков

Вклады текущих произведений усредняются; число подтверждений учитывается отдельно при определении уверенности. Частый признак не усиливается бесконечно простой суммой. Исходные данные для пересборки — текущие UserItem, ItemTag и Tag. Точные поля Item используются для получения производных тегов при подготовке каталога. Исправленная оценка заменяет прежний вклад; удалённая запись перестаёт участвовать в следующем опубликованном расчёте.

Реализованный расчёт для каждого тега: weight = Σ(вкладПроизведения × ItemTag.relevanceScore) / count. count — число текущих произведений с оценкой или избранным и положительной выраженностью этого тега. Нулевая выраженность не участвует ни в сумме, ни в count. Слабовыраженный признак ослабляет вклад: единственное произведение с оценкой 10 и relevanceScore=0,2 даёт weight=0,2,count=1. При выраженности 1 оценки 10 и 6 дают weight=0,5,count=2. Учитываются существующие неудалённые Item, существующие Tag из taste-enabled групп и допустимые для группы типы Item. Родительские теги автоматически не добавляются. Tag.weightModifier и уверенность по count не изменяют сохраняемый weight; они предназначены для ранжирования.

Tag.weightModifier — конечное неотрицательное число, по умолчанию 1. Фоновая задача анализирует распространённость в каталоге и перезаписывает это поле; отдельного ручного множителя значимости и отдельной частотной поправки в Redis не требуется. У каждого диапазонного Tag собственный коэффициент. Один scalar weightModifier не хранит разные коэффициенты для разных типов Item.

Ежедневно в 03:00 по Москве scheduler ставит задачу в BullMQ. Для каждой участвующей во вкусе группы N — число уникальных неудалённых произведений допустимых для группы типов с хотя бы одним её тегом, n — число этих произведений с конкретным тегом. Наличие тега считается рабочим приближением заполненности группы; отсутствие разметки не трактуется как отсутствие свойства. relevanceScore при подсчёте частоты не используется.

Формула V1: weightModifier = min(2, max(0.25, ln((N + 1) / (n + 1)))). При N = 0 или n = 0 записывается 1. Не участвующие во вкусе группы и теги без группы не изменяются. Пределы 0.25–2 — стартовые настройки, качество которых ещё предстоит проверить на каталоге.

Повторные постановки объединяются, пока задача ожидает, выполняется или повторяется после ошибки. Запись идёт по группам, без атомарной публикации всего каталога; повторный расчёт исправляет частично обновлённый результат. Пропущенный при остановленном приложении ежедневный запуск автоматически не воспроизводится.

Участие группы во вкусе определяется TAG_GROUP_RULES.isUsedForTaste. Сейчас включены genre, subgenre, keyword, format, style, gameMode, gameMechanic, perspective, duration, episodeDuration, mainStoryDuration и fullCompletionDuration. Остальные группы используются для карточки и фильтров. Изменение флага требует согласования и пересборки вычисляемых данных; сам справочник не запускает расчёт.

Сила предпочтения, уверенность по count и частотная поправка — разные показатели. Пользовательский weight остаётся в [−1, +1]. Нормализация итогового балла должна исключать преимущество кандидатов только за большее количество тегов; формула ещё определяется.

relevanceScore в ItemTag сохраняет смысл выраженности признака, а не уверенности разметчика или пользовательской симпатии. Пропуски метаданных означают неизвестность. Родители и поджанры одной ветви не дают независимого многократного усиления.

## Пересчёт

После успешного сохранения изменения вкусовых входов запускается фоновая пересборка через BullMQ. На пользователя выполняется один расчёт. Несколько изменений объединяются; если во время работы поступило новое изменение, после завершения выполняется ещё один расчёт по актуальным источникам.

Подключённый триггер — успешные create/skip/block/update/remove и создание/изменение попыток через UserItemService. Для транзакционных изменений постановка выполняется после commit. Периодического запуска нет. UserTasteProfileRecalculationService.enqueue ставит задачу userTasteProfile.recalculate с ID пользователя, retry 5/30/120 секунд и deduplication.keepLastIfActive. Пока задача ожидает или повторяется, запросы объединяются; изменение во время выполнения сохраняет следующий запуск. BullMQ атомарно завершает задачу и создаёт сохранённую следующую, исключая потерю уведомления на этой границе.

Пока идёт пересборка, используется старый профиль. Поэтому исправленная или удалённая оценка может влиять до публикации нового результата. При завершении публикуются новые рассчитанные предпочтения с сохранением актуальных явных настроек. Доступность кандидатов проверяется по текущим данным независимо от возраста профиля.

Публикация заменяет весь валидируемый массив и условно сопоставляет его с прочитанной актуальной версией массива. Если параллельно изменились явные настройки, публикация перечитывает профиль и повторяет слияние. Явные предпочтения без рассчитанных подтверждений сохраняются с weight=0,count=0; остальные устаревшие элементы удаляются. При отсутствии профиля и любых предпочтений пустой документ не создаётся.

Состояние очереди и необходимости повторного запуска находится в Redis/BullMQ. Отметка нового изменения и переход между завершением и повторным запуском должны исключать потерю уведомления на этой границе. После потери Redis требуется восстановительная полная пересборка профилей; конкретный эксплуатационный механизм ещё определяется.

Запись MongoDB и постановка BullMQ не являются общей транзакцией: ошибка постановки передаётся вызывающему коду, хотя изменение UserItem уже сохранено. Восстановление после сбоя между commit и enqueue, потери Redis и автоматические триггеры изменений каталога пока не реализованы. Прямые записи в MongoDB и generic repository вне UserItemService автоматически задачи не создают.

Пересчёт необходим при изменении используемых пользовательских сигналов, значимых исходных признаков и правил построения профиля. Явное предпочтение сохраняется как пользовательская настройка и доступно при подборе независимо от фонового обновления вычисляемой части.

## Продолжения и связанные произведения

Связанные кандидаты находятся при запросе по текущим пользовательским данным через существующие Relation и ItemRelationRole: продолжения, следующие сезоны, приквелы, спин-оффы и адаптации.

Связь с понравившимся произведением даёт ограниченный бонус итоговому баллу кандидата. Сила симпатии к исходному Item влияет на величину бонуса. Прямое продолжение или следующий сезон получает более сильный бонус, чем спин-офф или адаптация. Завершённость помогает определить своевременность предложения, но не заменяет положительную оценку или избранное. Только planned не даёт основания для сильного бонуса продолжению.

Бонус связи применяется как множитель положительного базового балла кандидата. Настроенная величина хранится в ItemRelationRole.bonusMultiplier для роли рекомендуемого Item относительно исходного: конечное число >= 1, по умолчанию 1 (без усиления). Схема поля реализована; применение в ранжировании ещё предстоит. Существующие документы БД не обновлялись.

Если кандидат связан с несколькими понравившимися произведениями, используется максимальный бонус, а не сумма. Условия применения и учёт силы симпатии задаются рекомендателем. Преобразование соответствия вкусу в положительный базовый балл и конкретные значения множителей ещё определяются; ограничения запроса остаются обязательными.

Роль рекомендуемого Item определяется через ItemRelationRole: например, sequel относительно previousPart, adaptation относительно adaptationSource. Позиции first/second в Relation сами по себе не задают хронологию. Для следующего сезона используется прямая связь соседних сезонов. Принадлежность Collection типа franchise помогает находить связанные произведения, но не устанавливает, какое из них следующее.

## Поток выдачи

1. Пользователь задаёт условия: целевой тип, фильтры и сценарий.
2. Система читает действующий UserTasteProfile с явными настройками.
3. Находит кандидатов по признакам и связям с произведениями пользователя.
4. Проверяет допустимость: существование Item, deletedAt, глобальные запреты через SourceItem/BannedItem, blocked, активный skipped, тип, фильтры и библиотечную политику сценария.
5. Считает соответствие признаков весам пользователя с учётом значимости, распространённости и подтверждений.
6. Добавляет бонусы связей и формирует порядок. Среди сопоставимых кандидатов немного варьирует выбор при новом подборе.
7. Возвращает результат с понятными причинами там, где они следуют из расчёта.
8. Действия сохраняются обычными операциями библиотеки и явных настроек; затронутые вычисляемые данные пересчитываются.

Для нового пользователя подбор использует явные предпочтения. При их отсутствии доступны неперсональные кандидаты; рейтинги и популярность могут участвовать после появления корректно пересчитываемых агрегатов ItemMetric. Полезность оценивается по подходящему выбору и последующим реакциям.

Отрицательные веса влияют на ранжирование, а не заменяют явные фильтры. Неизвестная длительность не подтверждает условие «до двух часов». Строгие отрицательные фильтры требуют подтверждённой полноты разметки: отсутствие ItemTag само по себе не доказывает отсутствие темы. Фильтры и запреты не ослабляются ради наполнения выдачи.

### Пик

Пик вызывает общий рекомендательный каталог в режиме инструмента. Клиент хранит полученные ID и счётчик карточек, передаёт исключаемые ID при следующем запросе. В пределах подбора предлагается до 25 разных произведений вне библиотеки; при нехватке допустимых кандидатов подбор заканчивается раньше. Прочие сценарии задают свою библиотечную политику.

Открытие каталога и отсутствие реакции не меняют веса и не понижают произведение. Повторы внутри текущего Пика исключаются переданными ID; вариативность следующих подборов обеспечивается выбором среди сопоставимых кандидатов и новыми пользовательскими данными. Границы бюджетов поиска должны отличаться от фактического исчерпания допустимого каталога.

## Состав изменений и оставшиеся параметры

В production-коде Feature/ItemFeature удалены, UserTasteProfile содержит только tagPreferences. Точные метаданные хранятся в Item, категории — в Tag/ItemTag. Существующие UserItem, Relation, ItemRelationRole, Collection и CollectionItem сохраняют свои роли. Данных для миграции нет; миграция и наполнение не выполнялись. Это целевые требования; [инвентарь сущностей API](../../api/entities.md) описывает текущее состояние production-кода.

Перед реализацией конкретизируются:

- Формула уверенности по count при ранжировании; усреднение, нейтральные вклады и усиление избранным уже определены и реализованы.
- Проверка частотной поправки на каталоге и нормализация итогового балла.
- Наполнение Tag со стабильными ключами из TAG_GROUP_RULES, обработка неизвестных значений и синхронизация производных тегов при импорте; границы диапазонов уже согласованы.
- Калибровка relevanceScore и обработка иерархии тегов без двойного учёта одной ветви при ранжировании; ослабление вкладов профиля по relevanceScore уже реализовано.
- Величины бонусов связей, учёт противоречивых rating/isFavorite исходного произведения и степень вариативности выдачи.
- Восстановление фонового пересчёта и триггеры изменений каталога, бюджет и задержка расчёта на фактических данных; публикация с сохранением актуальных явных настроек реализована.
- Контракты запросов рекомендаций и редактирования явных предпочтений, пагинация и ограничения клиентских исключений.

Коэффициенты действий выше приняты как начальные настройки V1. Эффективность формул и рекомендаций предстоит проверить на данных Bisky; наличие исследований не доказывает улучшение выбора.
