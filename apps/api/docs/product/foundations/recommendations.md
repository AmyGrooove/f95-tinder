## Цель и общая основа

Bisky помогает быстрее находить подходящее произведение и сохранять удовлетворённость выбором. Личная библиотека и списки также имеют самостоятельную ценность.

Рекомендации используют общий профиль предпочтений по тегам, включая согласованные диапазонные категории для всех семи типов Item. Интерес к мрачной атмосфере или киберпанку в играх помогает подбирать фильмы, аниме и другой контент. Разные интересы, например к уютным историям и мрачной фантастике, представлены отдельными весами признаков.

Общие канонические теги имеют одинаковый смысл на разных типах контента. Разные понятия, например выживание как тема и survival как игровая механика, представлены разными тегами. Алиасы одного понятия не создают дополнительных подтверждений. Общий профиль не делает несопоставимые свойства одинаковыми: предпочтение RPG влияет только на кандидатов с соответствующим содержательным признаком.

Каталоги, главная, подборки и другие потребители используют общий механизм с условиями конкретного сценария. Пик — один из потребителей и не определяет архитектуру общего механизма. При запросе фильмов результат содержит только фильмы; данные игр меняют выбор внутри разрешённого типа.

Механизм сам находит допустимые произведения, рассчитывает порядок всей выборки и возвращает нужную страницу. Пересортировка уже загруженной страницы не заменяет общий поиск. Основа V1 — MongoDB, где находятся теги, профиль, библиотека и связи. Meilisearch предназначен для текстового поиска и опечаток; профиль и персональные баллы туда не синхронизируются. Связка текстовой релевантности с персонализацией выделена в следующий этап: ограниченный rerank результатов поиска не считается глобальным персональным порядком.

Механизм остаётся заменяемым: реализации используют общий формат запроса и результата, активные правила выбираются конфигурацией. Изменение алгоритма допускает пересборку вычисляемых предпочтений с сохранением пользовательских данных и явных настроек. Объяснимые веса и количество подтверждений позволяют впоследствии визуализировать вкус; вид такого экрана определяется отдельно.

## Сигналы пользователя

Начальные коэффициенты вкладов одного произведения; правило избранного упрощено 29 октября 2026 года:

| Сигнал                                 |                                                                         Вклад |
| -------------------------------------- | ----------------------------------------------------------------------------: |
| Оценка 10 / 9 / 8 / 7                  |                                                     +1 / +0,75 / +0,5 / +0,25 |
| Оценка 5–6                             |                                                                             0 |
| Оценка 4 / 3 / 2 / 1                   |                                                     −0,25 / −0,5 / −0,75 / −1 |
| Избранное без оценки или с оценкой 5–6 |                                                                          +0,5 |
| Запланированное                        | 0 для weight/count; бонус самому кандидату в допускающих библиотеку сценариях |
| Завершённые попытки                    |                                                                             0 |
| Открытие карточки и отсутствие реакции |                                                                             0 |

Оценка учитывается независимо от завершённости. Избранное задаёт нижнюю границу положительного вклада +0,5, а не складывается с оценкой; вклад одного произведения ограничен +1. При низкой оценке 1–4 используется отрицательный вклад оценки: избранное его не усиливает и не отменяет. Например, оценка 1 вместе с избранным даёт −1. Исходные rating и isFavorite остаются независимыми пользовательскими полями.

Для оценки 7–10 с избранным вклад = max(0,5, (rating − 6) / 4): соответственно 0,5 / 0,5 / 0,75 / 1. Без избранного вклад оценки 1–4 равен (rating − 5) / 4, для 5–6 — 0, для 7–10 — (rating − 6) / 4. Нейтральные оценки 5–6 без избранного участвуют в среднем с нулевым вкладом и увеличивают count. Без оценки и избранного произведение не участвует в weight/count. Попытки независимо от завершённости, даты и прогресс вклада не дают. planned сам по себе не создаёт вклад; сохранённые rating/isFavorite учитываются независимо от статуса, кроме skipped.

Это объяснимая исходная модель, а не оптимум, подтверждённый пользовательскими данными. Сохранение прежней формулы избранного давало бы 0,85–1 для оценок 7–10 и почти стирало различия между ними. Порог 0,5 соответствует положительной оценке 8: отдельная отметка сообщает симпатию без предположения о почти максимальной оценке. Компромисс — оценки 7 и 8 с избранным дают одинаковый вклад, а при 8–10 отметка не добавляет бонуса вкусу. Нейтральная зона 5–6 сохранена: без продуктового определения шестёрки нет оснований автоматически считать её симпатией, а пятёрку — неприязнью, как при равномерном отображении шкалы 1–10 в [−1, +1]. Качество этих решений требует проверки на реальных реакциях и результатах выбора.

Одно произведение даёт одно подтверждение признака. Повторная установка оценки, несколько попыток и сочетание оценки с избранным не увеличивают число подтверждений. planned сам по себе не входит в weight/count; сохранённые сигналы учитываются по общим правилам, а бонус planned применяется к самому запланированному кандидату вне Пика.

Завершение и повторное прохождение сами по себе не считаются положительной реакцией и не усиливают оценку или избранное. Статус «Бросил» неоднозначен. Реакция на подборку не переносится автоматически на каждый её Item. Сравнения в Баттле пока не сохраняются и не меняют числовые оценки; проигрыш не создаёт отрицательный вклад.

Пропуск исключает конкретный Item на 90 суток. Блокировка исключает его до изменения или удаления записи. Эти действия не меняют веса признаков сами по себе. Сохранённые rating/isFavorite у blocked остаются пользовательскими данными для расчёта; skipped не служит источником вкуса. Срок пропуска проверяется по времени независимо от физической TTL-очистки.

## UserTasteProfile

Один документ на пользователя, уникальный индекс по user. Единственный массив tagPreferences содержит предпочтения, общие для всех типов контента. Отдельных featurePreferences и селекторов value/range нет: каждый диапазон представлен собственным Tag.

| Поле предпочтения | Назначение                                                       |
| ----------------- | ---------------------------------------------------------------- |
| tag               | Ссылка на конкретный Tag                                         |
| weight            | Рассчитанное предпочтение, конечное число в диапазоне [−1, +1]   |
| count             | Число текущих произведений, участвовавших в расчёте предпочтения |
| explicitWeight    | Явное предпочтение пользователя в [−1, +1], по умолчанию 0       |

Профиль допускает максимум 4096 уникальных тегов. Участие группы во вкусе задаётся isUsedForTaste в [TAG_GROUP_RULES](../../../src/entities/tag/static/TAG_GROUP_RULES.ts). Диапазоны duration фильма и mainStoryDuration игры имеют разный смысл и разные Tag. Точное значение Item не даёт второй независимый вклад поверх диапазонного тега.

Пример документа; строки tag обозначают условные ObjectId тегов, а не их key:

```json
{
  "user": "userId",
  "tagPreferences": [
    { "tag": "cyberpunkTagId", "weight": 0.7, "count": 5, "explicitWeight": 1 },
    {
      "tag": "duration90To120TagId",
      "weight": 0,
      "count": 0,
      "explicitWeight": 1
    }
  ]
}
```

### Явные предпочтения

Пользователь может указать интерес к обычному или диапазонному тегу до накопления библиотеки. Положительные значения означают симпатию, отрицательные — неприязнь. Ноль означает отсутствие явной настройки; при нуле работает рассчитанный weight.

```text
используемый вес = explicitWeight !== 0 ? explicitWeight : weight
```

Явный выбор имеет приоритет над рассчитанным весом того же признака и значения/диапазона. Рассчитанный weight продолжает обновляться независимо. Очистка явной настройки возвращает использование рассчитанного значения. explicitWeight не увеличивает count.

После пересчёта или изменения явной настройки элемент удаляется, если count == 0 и explicitWeight == 0. При count > 0 элемент сохраняется даже с нулевым weight. Предпочтение с explicitWeight != 0 сохраняется и при count == 0.

Профиль сочетает вычисляемые данные и пользовательские настройки. Пересборка обновляет weight/count, сохраняя актуальные explicitWeight, в том числе настройки, изменённые во время расчёта. Нельзя заменить документ старой копией и затереть явный выбор. UI и операции редактирования задаются отдельным контрактом перед реализацией.

## Расчёт весов и значимость признаков

Вклады текущих произведений усредняются; число подтверждений учитывается отдельно при определении уверенности. Частый признак не усиливается бесконечно простой суммой. Исходные данные для пересборки — текущие UserItem, ItemTag и Tag. Точные поля Item используются для получения производных тегов при подготовке каталога. Исправленная оценка заменяет прежний вклад; удалённая запись перестаёт участвовать в следующем опубликованном расчёте.

Реализованный расчёт для каждого тега: weight = Σ(вкладПроизведения × ItemTag.relevanceScore) / count. count — число текущих произведений с оценкой или избранным и положительной выраженностью этого тега. Нулевая выраженность не участвует ни в сумме, ни в count. Слабовыраженный признак ослабляет вклад: единственное произведение с оценкой 10 и relevanceScore=0,2 даёт weight=0,2,count=1. При выраженности 1 оценки 10 и 6 дают weight=0,5,count=2. Учитываются существующие неудалённые Item, существующие Tag из taste-enabled групп и допустимые для группы типы Item. Родительские теги автоматически не добавляются. Tag.weightModifier и уверенность по count не изменяют сохраняемый weight; они предназначены для ранжирования.

Tag.weightModifier — конечное неотрицательное число, по умолчанию 1. Фоновая задача анализирует распространённость в каталоге и перезаписывает это поле; отдельного ручного множителя значимости и отдельной частотной поправки в Redis не требуется. У каждого диапазонного Tag собственный коэффициент. Один scalar weightModifier не хранит разные коэффициенты для разных типов Item.

Ежедневно в 03:00 по Москве scheduler ставит задачу в BullMQ. Для каждой участвующей во вкусе группы N — число уникальных неудалённых произведений допустимых для группы типов с хотя бы одним её тегом, n — число этих произведений с конкретным тегом. Наличие тега считается рабочим приближением заполненности группы; отсутствие разметки не трактуется как отсутствие свойства. relevanceScore при подсчёте частоты не используется.

Формула V1: weightModifier = min(2, max(0.25, ln((N + 1) / (n + 1)))). При N = 0 или n = 0 записывается 1. Не участвующие во вкусе группы и теги без группы не изменяются. Пределы 0.25–2 — стартовые настройки, качество которых ещё предстоит проверить на каталоге.

Повторные постановки объединяются, пока задача ожидает, выполняется или повторяется после ошибки. Запись идёт по группам, без атомарной публикации всего каталога; повторный расчёт исправляет частично обновлённый результат. Пропущенный при остановленном приложении ежедневный запуск автоматически не воспроизводится.

Участие группы во вкусе определяется TAG_GROUP_RULES.isUsedForTaste. Сейчас включены genre, subgenre, keyword, format, style, gameMode, gameMechanic, perspective, duration, episodeDuration, mainStoryDuration и fullCompletionDuration. Остальные группы используются для карточки и фильтров. Изменение флага требует согласования и пересборки вычисляемых данных; сам справочник не запускает расчёт.

Сила предпочтения, уверенность по count и частотная поправка — разные показатели. Пользовательский weight остаётся в [−1, +1]. Нормализация балла кандидата определяется ниже и исключает преимущество только за большее количество тегов.

relevanceScore в ItemTag сохраняет смысл выраженности признака, а не уверенности разметчика или пользовательской симпатии. Пропуски метаданных означают неизвестность. Родители и поджанры одной ветви не дают независимого многократного усиления.

### Соответствие кандидата вкусу

Ранжирование использует опубликованный профиль и актуальные признаки кандидата. Формулы этого раздела не меняют сохраняемые weight/count и уже реализованный расчёт профиля.

Знакомый тег — назначенный кандидату существующий Tag, для которого в профиле есть count > 0 или explicitWeight != 0. Учитываются только taste-enabled группы, допустимые для типа кандидата, и ItemTag с relevanceScore > 0. Незнакомые теги пропускаются и не входят в знаменатель: дополнительная неизвестная разметка не повышает и не снижает балл. Рассчитанный weight=0 при count > 0 участвует как известный нейтральный сигнал.

Среди назначенных знакомых родителя и поджанра одной ветви используется более конкретный тег. Предпочтение поджанра заменяет родительское и при противоположных знаках. Родители автоматически не добавляются; самостоятельные признаки сохраняются. Связи child/parent берутся из Tag.parents, а не из названий или принадлежности к Tag.group.

Для каждого оставшегося тега:

```text
confidence = count / (count + 5)
preference = explicitWeight != 0 ? explicitWeight : weight × confidence

tasteScore = Σ(preference × relevanceScore × weightModifier)
             / Σ(weightModifier)
```

Уверенность плавно насыщается: count=1 даёт примерно 17% силы рассчитанного предпочтения, count=5 — 50%, count=20 — 80%. Она одинаково ослабляет положительные и отрицательные рассчитанные предпочтения. Явный explicitWeight используется без этой поправки и не требует подтверждений библиотекой. Параметр 5 принят как стартовая настройка V1; это сила сглаживания к нулю, эквивалентная пяти дополнительным нейтральным наблюдениям, а не вероятность правильной рекомендации.

Для рассчитанного предпочтения формулы сводятся к preference = Σ(вкладПроизведения × relevanceScore) / (count + 5). Например, один Item с оценкой 10 и relevanceScore=0,2 даёт weight=0,2, count=1 и preference≈0,0333. При relevanceScore=1 оценки 10 и 6 дают weight=0,5, count=2 и preference=1/7≈0,1429. Пять избранных без оценки с выраженностью 1 дают weight=0,5, count=5 и preference=0,25. Нейтральная оценка считается наблюдением равнодушия; отсутствие оценки и избранного — отсутствием наблюдения. relevanceScore ослабляет свидетельство о вкусе; деление на сумму relevanceScore вместо count отменило бы это ослабление для единственного слабого тега. При оценке кандидата его собственная выраженность применяется отдельно.

relevanceScore кандидата стоит только в числителе, чтобы слабая выраженность действительно ослабляла вклад, в том числе при единственном знакомом теге. weightModifier задаёт относительную значимость и входит в числитель и знаменатель. Если учитывать нечего или сумма weightModifier равна нулю, tasteScore=0.

Общий tasteScore находится в [−1, +1]. Усреднение выполняется по всем участвующим тегам, без промежуточных средних по группам и без гарантированных долей влияния жанра, тематики или длительности. При одинаковой значимости два вклада +0,8 дают +0,8, а двадцать вкладов +0,4 дают +0,4. Большее количество признаков само по себе не повышает результат; один неподходящий признак меньше влияет при множестве подходящих.

## Рейтинг сайта для сортировки

После персонального балла равенство разрешается общим сглаженным рейтингом сайта:

```text
n = ItemMetric.ratingsCount
R = ItemMetric.ratingAverage
C = среднее всех пользовательских оценок сайта
ratingScore = (n × R + 20 × C) / (n + 20)
```

Каждая пользовательская оценка имеет одинаковый вес в C; это не среднее средних оценок произведений. Если оценок на сайте ещё нет, C=5,5. Если у кандидата нет оценок, ratingScore=C: отсутствующий ratingAverage не участвует в арифметике. При n=20 средняя произведения и средняя сайта влияют поровну; с ростом числа оценок ratingScore приближается к R. Параметр 20 принят как стартовая настройка V1.

ratingAverage остаётся обычной средней оценкой, ratingsCount — количеством оценок. ratingScore в ItemMetric не сохраняется: [createItemRatingScoreExpression](../../../src/entities/itemMetric/functions/createItemRatingScoreExpression/index.ts) вычисляет его для кандидатов при ранжировании до сортировки и пагинации. Публичные rating-фильтры и обычные сортировки поиска/подборок сохраняют смысл ratingAverage.

Общая статистика хранится в коллекции SiteMetric: автоматически создаваемый ObjectId, уникальный key="ratings", sum, count и average. average сохраняется как sum/count, при count=0 — null. Для сглаживания отсутствие средней заменяется DEFAULT_SITE_RATING_AVERAGE=5,5. Никакого обхода всех метрик для получения C при выдаче нет: читается сохранённая average.

При каждом изменении UserItem [UserItemMetricsService](../../../src/endpoints/userItem/services/userItemMetrics.service.ts) получает снимки до/после и применяет разницу в той же MongoDB-транзакции: ItemMetric — распределение оценок, число оценок, избранное, статусы и завершённые попытки; SiteMetric — сумму и число оценок, только если оценка изменилась. Средняя Item выводится из десяти счётчиков ratingDistribution, отдельная ratingsSum не хранится. Создание и удаление используют null вместо отсутствующего состояния. Неизменные значения не вызывают запись метрик. Прямые записи UserItem обязаны соблюдать этот же контракт; generic repository сам метрики не обновляет. Фоновые задачи пересчёта ItemMetric, пяти­минутный cron и массовое обновление ratingScore удалены. При ошибке метрик транзакция UserItem откатывается. Рекомендации читают C отдельно от запроса кандидатов, поэтому единый снимок между этими чтениями не гарантируется. Стоимость ранжирования и конкуренция записей общего документа требуют runtime-проверки.

Для нового пользователя без предпочтений и бонусов все персональные баллы одинаковы, поэтому порядок определяется ratingScore. Название этой сортировки в интерфейсе выбирается отдельно; формула не является самостоятельным счётчиком активности или популярности.

## Пересчёт

После успешного сохранения изменения вкусовых входов запускается фоновая пересборка через BullMQ. Задания объединяются по паре пользователь/Item; изменения разных Item не вытесняют друг друга. Пересчитываются только теги затронутого Item, но с учётом всех текущих произведений пользователя с этими тегами. Если во время работы поступило новое изменение того же Item, после завершения выполняется ещё один расчёт по актуальным источникам.

Подключённые триггеры — успешные create/skip/block/remove; update и изменение попыток запускают пересчёт только при изменении оценки, избранного или участия в skipped. Изменение только заметки или попыток, включая завершение, даты и прогресс, задачу не создаёт. Для транзакционных изменений постановка выполняется после commit. Периодического запуска нет. UserTasteProfileRecalculationService.enqueue ставит задачу userTasteProfile.recalculate с ID пользователя и Item (payload version 2), retry 5/30/120 секунд и deduplication.keepLastIfActive. Пока задача ожидает или повторяется, запросы объединяются; изменение во время выполнения сохраняет следующий запуск. BullMQ атомарно завершает задачу и создаёт сохранённую следующую, исключая потерю уведомления на этой границе.

Пока идёт пересборка, используется старый профиль. Поэтому исправленная или удалённая оценка может влиять до публикации нового результата. При завершении публикуются новые рассчитанные предпочтения с сохранением актуальных явных настроек. Доступность кандидатов проверяется по текущим данным независимо от возраста профиля.

Публикация сохраняет нетронутые теги и заменяет весь валидируемый массив с проверкой исходного снимка, прочитанного до расчёта. Если профиль параллельно изменился, задача перечитывает его и заново вычисляет затронутые теги. Явные предпочтения затронутых тегов без рассчитанных подтверждений сохраняются с weight=0,count=0; остальные неподдерживаемые записи затронутых тегов удаляются. При отсутствии профиля и любых предпочтений пустой документ не создаётся.

Состояние очереди и необходимости повторного запуска находится в Redis/BullMQ. Отметка нового изменения и переход между завершением и повторным запуском должны исключать потерю уведомления на этой границе. После потери Redis требуется восстановительная полная пересборка профилей; конкретный эксплуатационный механизм ещё определяется.

Запись MongoDB и постановка BullMQ не являются общей транзакцией: ошибка постановки передаётся вызывающему коду, хотя изменение UserItem уже сохранено. Восстановление после сбоя между commit и enqueue, потери Redis и автоматические триггеры изменений каталога пока не реализованы. Прямые записи в MongoDB и generic repository вне UserItemService автоматически задачи не создают.

Пересчёт необходим при изменении используемых пользовательских сигналов, значимых исходных признаков и правил построения профиля. Явное предпочтение сохраняется как пользовательская настройка и доступно при подборе независимо от фонового обновления вычисляемой части.

## Продолжения и связанные произведения

Связанные кандидаты находятся при запросе по текущим пользовательским данным через существующие Relation и ItemRelationRole: продолжения, следующие сезоны, приквелы, спин-оффы и адаптации.

Связь с понравившимся произведением даёт бонус итоговому баллу кандидата. Сила симпатии к исходному Item влияет на величину бонуса. Прямое продолжение или следующий сезон получает более сильный бонус, чем спин-офф или адаптация. В V1 положительной реакции достаточно и без завершения исходного произведения; дополнительного усиления или обязательного условия по completed нет. Только planned не создаёт симпатию и не даёт бонус связи.

Бонус связи применяется как множитель положительного базового балла кандидата. Настроенная величина хранится в ItemRelationRole.bonusMultiplier для роли рекомендуемого Item относительно исходного: конечное число >= 1, по умолчанию 1 (без усиления). Схема поля и применение в ранжировании реализованы. Существующие документы БД не обновлялись; отсутствующий в записи множитель читается как 1.

Сила симпатии — положительная часть вклада исходного произведения по согласованным правилам rating/isFavorite из раздела «Сигналы пользователя», в диапазоне [0, 1]. Отрицательная или нейтральная реакция даёт нулевой бонус связи; низкая оценка сохраняет приоритет над избранным. Для каждой допустимой связи:

```text
relationBoost = (ItemRelationRole.bonusMultiplier − 1) × силаСимпатии
```

Если кандидат связан с несколькими понравившимися произведениями, используется максимальный relationBoost, а не сумма. При отсутствии подходящих связей relationBoost=0. Конкретные bonusMultiplier для ролей ещё требуется настроить; ограничения запроса остаются обязательными.

Роль рекомендуемого Item определяется через ItemRelationRole: например, sequel относительно previousPart, adaptation относительно adaptationSource. Позиции first/second в Relation сами по себе не задают хронологию. Для следующего сезона используется прямая связь соседних сезонов. Принадлежность Collection типа franchise помогает находить связанные произведения, но не устанавливает, какое из них следующее.

## Итоговый персональный балл

```text
baseScore = 1 + tasteScore / 2
plannedBoost = 0,2 для запланированного кандидата, иначе 0
finalScore = baseScore × (1 + plannedBoost + relationBoost)
```

plannedBoost применяется только к самому кандидату со статусом planned, если условия запроса допускают его присутствие. Он не создаёт предпочтений в профиле и не усиливает связанные с ним произведения.

baseScore положителен и находится в [0,5, 1,5]; нейтральному вкусу соответствует 1. Бонусы складываются как прибавки сверх единицы: +20% и +50% дают общий множитель 1,7. finalScore не ограничивается единицей.

Строгих групп «подходящее / нейтральное / неподходящее» нет: бонус может поднять неподходящего кандидата выше нейтрального. Например, tasteScore=−0,4 даёт baseScore=0,8, а бонус +50% поднимает finalScore до 1,2. Это выше нейтрального кандидата без бонусов с finalScore=1.

Порядок V1: finalScore по убыванию, затем ratingScore по убыванию, затем Item._id по возрастанию. В реализации finalScore округляется до 12 знаков после запятой, чтобы погрешность арифметики не мешала разрешению равенства: например, 0,8 × 1,5 и 1 × 1,2 дают одинаковые 1,2. Рейтинг сайта разрешает равенство итоговых персональных баллов, а не заменяет вкус для всех отрицательных кандидатов. Случайного перемешивания в V1 нет; при неизменных входных данных порядок детерминирован.

## Внутренний контракт поиска рекомендаций

Публичный внутри приложения метод recommendations.find принимает один объект. Это контракт общего механизма, а не согласование нового HTTP endpoint:

```text
recommendations.find({
  userId,
  filter,
  library,
  excludeItemIds,
  pagination: { page, limit }
})
```

userId определяет профиль, библиотеку и персональные исключения. Метод возвращает персональный порядок; direction управляет направлением finalScore (по умолчанию desc), а ratingScore и ID остаются разрешением равенств. candidateItemIds при наличии ограничивает исходный набор, пустой массив даёт пустую выдачу. Обычные сортировки каталога принадлежат его собственному контракту. QUERY /search не использует персональное ранжирование: items.sort=recommended не поддерживается и отклоняется с 400. Самостоятельный RecommendationsService.find сохраняет описанный рекомендательный контракт.

Реализованный вход — [RecommendationsService.find](../../../src/endpoints/recommendations/services/recommendations.service.ts), тип запроса — [IFindRecommendationsProps](../../../src/endpoints/recommendations/types/IFindRecommendationsProps.ts). [RecommendationsModule](../../../src/endpoints/recommendations/recommendations.module.ts) подключён в AppModule и экспортирует сервис для модулей-потребителей; контроллеров у него нет. UserId и остальные ID передаются как Types.ObjectId, границы дат — как Date. Сервис проверяет совместимость библиотечных условий, диапазоны полей/рейтинга, принадлежность группы подборке и допустимый offset страницы. Сам запрос MongoDB принадлежит ItemRepository.readRecommendations.

### Условия отбора

filter поддерживает:

| Поле                  | Условие                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| types                 | Разрешённые типы Item                                                                                                           |
| collectionId          | Только участники указанной подборки                                                                                             |
| groupId               | Дополнительное ограничение группой внутри указанной подборки                                                                    |
| tagIds                | Все перечисленные теги должны быть назначены кандидату                                                                          |
| fields                | Диапазоны существующих точных полей Item: дата выпуска, длительность, время прохождения и другие поля из ITEM_FIELD_DEFINITIONS |
| ratingMin / ratingMax | Диапазон обычного ItemMetric.ratingAverage, как в текущих подборках; не сглаженного ratingScore                                 |

Все заданные условия объединяются через И. Отсутствующее условие ничего не ограничивает. Неизвестное точное значение не проходит заданный диапазон; кандидат без оценок не проходит заданный диапазон ratingAverage. Неограниченный список кандидатов не сводится к совпадениям с профилем: рассматриваются все произведения, удовлетворяющие условиям и актуальной допустимости.

Доступ к закрытой подборке проверяет вызывающий сервис перед обращением к рекомендателю. Механизм ограничивает выборку членством в подборке, но сам факт передачи collectionId не предоставляет доступ.

### Библиотечные условия и исключения

library содержит необязательные массивы статусов include, exclude и only. Здесь библиотечные статусы — planned, inProgress, onHold, completed и dropped; это не типы Item.

| Условие              | Допустимая область                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| library не передан   | Все допустимые произведения, включая библиотеку                                                 |
| include: [planned]   | Произведения вне библиотеки плюс запланированные; остальные библиотечные статусы не допускаются |
| include: []          | Только вне библиотеки                                                                           |
| exclude: [completed] | Все допустимые произведения, кроме завершённых                                                  |
| only: [planned]      | Только запланированные                                                                          |

exclude имеет приоритет и дополнительно исключает указанные статусы. only нельзя сочетать с include: они по-разному определяют область поиска. only: [] даёт пустую выборку; exclude: [] не добавляет ограничений. Blocked и действующий skipped по умолчанию исключаются и не могут быть возвращены только через библиотечные условия. Флаг isIncludingExcluded=true сохраняет их и кандидатов с глобальными рекомендательными запретами в отдельной последней группе; направление finalScore не меняет положение этой группы. В поиске флаг включён, в остальных вызовах по умолчанию выключен. Просроченный skipped не считается библиотечным произведением и не запрещает кандидата только из-за не выполненной ещё TTL-очистки. Запись skipped без срока истечения не открывает доступ кандидату автоматически.

excludeItemIds — дополнительные исключения конкретного вызова. Они применяются до подсчёта total и пагинации. Удаление, фильтры, библиотечные условия и excludeItemIds остаются обязательными при обоих значениях isIncludingExcluded. Только автоматические персональные и глобальные рекомендательные исключения при включённом флаге заменяются понижением в конец.

### Результат и пагинация

Метод возвращает уникальные произведения с данными карточек в существующем формате пагинации:

```text
{
  items,
  page,
  limit,
  total,
  pages,
  isNextPage,
  isPreviousPage
}
```

total — количество допустимых уникальных произведений после всех условий и исключений, включая нейтральные и отрицательные по вкусу. Сначала рассчитывается общий порядок, затем выделяется страница. Нейтральные и отрицательные кандидаты естественно заполняют оставшиеся места; отдельного ослабляющего фильтры fallback нет.

Внутренний элемент результата [IRecommendedItem](../../../src/entities/item/types/IRecommendedItem.ts) содержит _id, type, title, media и компоненты расчёта tasteScore, baseScore, plannedBoost, relationBoost, finalScore, ratingScore. Это явная проекция карточки, а не полный документ Item; отображение и транспортные DTO принадлежат потребителям.

В V1 используется обычная пагинация page/limit с существующими normalizePagination и createPaginatedResult: по умолчанию page=1, limit=20, явный limit нормализуется в 1–100. Сортировка выполняется до $facet с items и total; агрегация разрешает allowDiskUse для сортировки. Детерминированный порядок при неизменных данных не означает фиксации выдачи между запросами: изменение профиля, библиотеки, метрик или каталога может сдвинуть страницы. Серверная сессия выдачи не требуется.

## Поток выдачи

1. Потребитель передаёт userId, условия отбора, библиотечные условия, исключаемые ID и пагинацию.
2. Система читает действующий UserTasteProfile с явными настройками и текущие пользовательские данные для бонусов и исключений.
3. Находит все произведения, удовлетворяющие условиям; наличие совпадений с профилем или связей не обязательно.
4. Проверяет допустимость: существование Item, deletedAt, глобальные и региональные запреты через SourceItem/BannedItem, blocked, активный skipped, тип, фильтры, библиотечные условия и excludeItemIds. Пустой BannedItem.countries означает глобальный запрет; непустой список применяется при совпадении с переданной страной country. Отсутствующая страна считается unknown.
5. Считает tasteScore, положительный baseScore, plannedBoost/relationBoost и finalScore; получает общий ratingScore.
6. Ставит включённых исключённых кандидатов после остальных, сортирует внутри групп по finalScore, ratingScore и Item._id; подсчитывает total и выделяет страницу.
7. Возвращает уникальные произведения с компонентами балла и метаданные пагинации. Текстовые объяснения и транспортные представления определяются контрактами потребителей и должны следовать из расчёта.
8. Действия сохраняются обычными операциями библиотеки и явных настроек; затронутые вычисляемые данные пересчитываются.

Для нового пользователя подбор использует явные предпочтения. При отсутствии предпочтений и бонусов кандидаты равны по finalScore и упорядочиваются по сглаженному рейтингу сайта, затем ID. Полезность оценивается по подходящему выбору и последующим реакциям.

Отрицательные веса влияют на ранжирование, а не заменяют явные фильтры. Неизвестная длительность не подтверждает условие «до двух часов». Строгие отрицательные фильтры требуют подтверждённой полноты разметки: отсутствие ItemTag само по себе не доказывает отсутствие темы. Фильтры не ослабляются ради наполнения выдачи; включение обычно исключаемых кандидатов задаётся только явным isIncludingExcluded=true.

### Пик

Пик вызывает общий рекомендательный каталог в режиме инструмента. Клиент хранит полученные ID и счётчик карточек, передаёт исключаемые ID при следующем запросе. В пределах подбора предлагается до 25 разных произведений вне библиотеки; при нехватке допустимых кандидатов подбор заканчивается раньше. Прочие сценарии задают свою библиотечную политику.

Открытие каталога и отсутствие реакции не меняют веса и не понижают произведение. Повторы внутри текущего Пика исключаются переданными ID. Случайная вариативность следующих подборов в V1 не применяется; порядок меняется при изменении входных данных. Границы бюджетов поиска должны отличаться от фактического исчерпания допустимого каталога. Детали интеграции этого потребителя не входят в текущую реализацию общего механизма.

## Состав изменений и оставшиеся параметры

В production-коде Feature/ItemFeature удалены, UserTasteProfile содержит только tagPreferences. Точные метаданные хранятся в Item, категории — в Tag/ItemTag. Существующие UserItem, Relation, ItemRelationRole, Collection и CollectionItem сохраняют свои роли. Данных для миграции нет; миграция и наполнение не выполнялись. Это целевые требования; [инвентарь сущностей API](../../api/entities.md) описывает текущее состояние production-кода.

Формулы уверенности, нормализации, положительной основы и бонусов, порядок сортировки, сглаживание рейтинга и внутренний find реализованы. Оставшиеся задачи:

- Проверка общего recommendations.find на живой MongoDB: допустимость, формулы, иерархия, бонусы, total/страницы и производительность на реальном объёме данных.
- Калибровка стартовых параметров 5, 20 и plannedBoost=0,2 на данных каталога; оценка стоимости получения C по всем оценкам при каждом вызове.
- Наполнение Tag со стабильными ключами из TAG_GROUP_RULES, обработка неизвестных значений и синхронизация производных тегов при импорте; границы диапазонов уже согласованы.
- Калибровка relevanceScore и частотной поправки; проверка качества выбора более конкретных знакомых тегов по Tag.parents на каталоге.
- Настройка bonusMultiplier ролей: продолжение/следующий сезон сильнее спин-оффа/адаптации. Значение 1 по умолчанию оставляет связь без усиления; реализация не записывает новые настройки ролей в БД.
- Восстановление фонового пересчёта и триггеры изменений каталога, бюджет и задержка расчёта на фактических данных; публикация с сохранением актуальных явных настроек реализована.
- Подключение потребителей и их транспортных карточек/объяснений; ограничения размеров входных массивов согласуются при появлении внешнего запроса.
- Связка текстового поиска с персонализацией: соотношение релевантности и вкуса, полнота кандидатов и пагинация.
- Контракты HTTP-потребителей и редактирования явных предпочтений согласуются отдельно; внутренний find не является разрешением создавать новые endpoints.

Коэффициенты действий выше приняты как начальные настройки V1. Эффективность формул и рекомендаций предстоит проверить на данных Bisky; наличие исследований не доказывает улучшение выбора.
