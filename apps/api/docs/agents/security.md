# Security

Read for authentication, roles, token creation or rate limits. HTTP/CORS configuration is in [runtime](runtime.md).

[SecurityModule](../../src/infrastructure/security/security.module.ts) exports `SecurityJwtService`, `SecurityCookieService`, `AccessTokenGuard` and `RolesGuard`. AuthModule and AccountModule import it for their cookie-based routes. None of these guards is configured as the global authentication guard; no movie-import controller currently consumes them.

[SecurityCookieService.setAuthCookies(reply, tokens)](../../src/infrastructure/security/services/cookie.service.ts) uses Nest's HttpAdapterHost to set `__Host-accessToken` and `__Host-refreshToken` with HttpOnly, Secure, SameSite=Strict and Path=/. Max-Age values reuse the JWT expiration constants in seconds. Controllers pass the native response through `@Res({ passthrough: true })` and an IAuthTokens object; the service does not issue tokens or create server sessions.

`SecurityCookieService.clearAuthCookies(reply)` clears both auth cookies through the same adapter with matching Path=/, HttpOnly, Secure and SameSite=Strict options. [AuthController.logout](../../src/endpoints/auth/controllers/auth.controller.ts) calls it only after successful server-session deletion.

[SecurityJwtService](../../src/infrastructure/security/services/jwt.service.ts) signs/verifies access and refresh tokens using separate configured secrets and HS256. Access expiration is 600 seconds (10 minutes); refresh expiration is 10,368,000 seconds (120 days). Both expiration constants use seconds and are shared with registration cookie lifetimes. Issuer is the app name and audience is `<appName>-api`. Access payloads carry `sub`, `sessionId`, a single `role: string` and `type: "access"`; refresh payloads carry `sub`, `sessionId`, `type: "refresh"` and are rejected if they contain `role` or the legacy `roles` field. Verification checks token type and payload field types and converts failures into UnauthorizedException.

[AccessTokenGuard](../../src/infrastructure/security/guards/accessToken.guard.ts) requires a single Bearer token and stores `{ id, sessionId, role }` on `request.authPrincipal`. [CurrentUser](../../src/infrastructure/security/decorators/CurrentUser/core/CurrentUser.ts) reads this principal. These objects do not query a user/session database or establish refresh rotation, logout or revocation semantics.

[Roles](../../src/infrastructure/security/decorators/Roles/core/Roles.ts) sets metadata consumed by [RolesGuard](../../src/infrastructure/security/guards/roles.guard.ts). Method metadata takes priority over controller metadata. Empty/missing roles permit access; otherwise the principal's single role must be included in the allowed role list. Access JWTs carrying only the former `roles` array are rejected; callers need a newly issued access token. Run the access guard before the roles guard for a protected endpoint.

Password helpers already exist as [hashValue](../../src/infrastructure/security/functions/hashValue/core/hashValue.ts) and [compareHash](../../src/infrastructure/security/functions/compareHash/core/compareHash.ts); inspect them before adding another hashing implementation.

[ThrottlingModule](../../src/infrastructure/throttling/throttling.module.ts), unlike SecurityModule, is imported by AppModule and registers a global `ThrottlerGuard` with Redis storage. Its [default](../../src/infrastructure/throttling/static/THROTTLE_DEFAULTS.ts) is 100 requests per 60,000 ms. Health routes currently have no local throttling exemption.

[AuthModule](../../src/endpoints/auth/auth.module.ts) exports AuthService for account endpoints. AuthService.verifyAccessToken validates the cookie value, JWT and ObjectId claims; it does not check session existence. AuthService.getSession delegates to SessionRepository.findActive to read an owned, unexpired Session, selecting id and expiration. Callers still reject a missing session and validate the User required by their operation. AuthService.issueTokens signs both token types, while its private createSession shares registration and login session creation and accepts the registration transaction session. AccountModule imports AuthModule; the dependency is one-way.

[ConfirmationService.consume](../../src/endpoints/auth/services/confirmation.service.ts) is exported by AuthModule for setup, email change and password reset. It accepts the caller's Redis client and operation key, checks the shared [IConfirmation](../../src/endpoints/auth/types/IConfirmation.ts) fields and attempt bounds, invokes the operation-specific type guard, verifies the bcrypt code and executes one shared [CONFIRMATION_SCRIPT](../../src/endpoints/auth/static/CONFIRMATION_SCRIPT.ts). The script atomically consumes a matching challenge or decrements its remaining attempts without extending TTL; codeHash and userId checks protect replacement challenges. Each scenario retains its own identity/payload validation, Redis keys, save/discard policy, database writes and error message.

## Account and authentication routes

[CollectionAuthService.authenticate](../../src/endpoints/collection/services/collectionAuth.service.ts) centralizes access-cookie JWT, active owned Session and existing User checks for collection endpoints and sets the request-context user ID. CollectionContentService skips authentication only when the access cookie is absent; personal filters still require authentication.

`POST /auth/password/reset` uses [PasswordResetController.requestPasswordReset](../../src/endpoints/auth/controllers/passwordReset.controller.ts), [PasswordResetBodyDto](../../src/endpoints/auth/dto/body/passwordReset.body.ts) and [PasswordResetService](../../src/endpoints/auth/services/passwordReset.service.ts). It accepts a trimmed lowercase email of at most 254 characters without authentication. Valid requests return 204 with Cache-Control:no-store for unknown accounts, accounts without a password, cooldown requests and mail queue submission failures. The IP limit is 5 requests per minute; global CSRF protection applies. It preserves User, Session and cookies.

AuthModule imports MailModule, LoggerModule and a local named `auth` Redis client. [PASSWORD_RESET](../../src/endpoints/auth/static/PASSWORD_RESET.ts) atomically enforces a one-minute cooldown for every requested email and replaces eligible confirmations with a four-hour TTL. Keys are `<appName>:auth:passwordReset:{<sha256(normalizedEmail)>}` and its `:cooldown` sibling in the same Redis hash slot. [IPasswordReset](../../src/endpoints/auth/types/IPasswordReset.ts) stores userId, confirmed email, current passwordHash, bcrypt codeHash and attemptsRemaining initialized to 3. Hashing is also performed for unknown accounts. MailService queues the six-digit code only for accounts with an email and password. Queue submission failures are logged and conditionally remove only the matching confirmation while retaining the cooldown; cleanup failures are logged without changing the response. No live mail delivery or Redis/MongoDB verification was performed.

`PATCH /auth/password/reset` uses [PasswordResetController.confirmPasswordReset](../../src/endpoints/auth/controllers/passwordReset.controller.ts), [ConfirmPasswordResetBodyDto](../../src/endpoints/auth/dto/body/confirmPasswordReset.body.ts) and [PasswordResetService.confirmReset](../../src/endpoints/auth/services/passwordReset.service.ts). It requires no authentication and accepts normalized email, a six-digit string code preserving leading zeros, and newPassword (at least 8 characters, at most 72 UTF-8 bytes, without normalization). Atomic Lua consumes the matching confirmation on success or decrements its attempt budget without extending the TTL; the third incorrect attempt deletes it. Matching codeHash and userId prevents concurrent requests from consuming a replacement confirmation or successfully reusing one code. Invalid, expired, exhausted, consumed or superseded confirmations return 400. One MongoTransactionService transaction conditionally replaces the password only while userId, email and the original passwordHash still match, then deletes all sessions of that user. Database failure rolls back both changes; a consumed confirmation is not restored, so a new reset request is required. Success returns 204 without a body with Cache-Control:no-store, clears both auth cookies and requires a new login. The IP limit is 5 requests per minute; global CSRF protection applies. No schema/index changes or live Redis/MongoDB verification were performed.

`POST /account/email` is handled by [AccountEmailController.requestEmail](../../src/endpoints/account/controllers/accountEmail.controller.ts) and [AccountEmailService.requestEmail](../../src/endpoints/account/services/accountEmail.service.ts). [EmailBodyDto](../../src/endpoints/account/dto/body/email.body.ts) accepts normalized email (trimmed, lowercase, at most 254 characters) and currentPassword (at least 8 characters, at most 72 UTF-8 bytes, without normalization). It requires a valid access cookie JWT, ObjectId claims, an explicitly unexpired owned Session, and an existing User with both email and passwordHash. It verifies the bcrypt password before checking email availability, including rejecting the current address as occupied. Missing authorization or an invalid password returns 401; incomplete setup or an occupied address returns 409.

The named `account` Redis client stores this operation separately at `<appName>:account:email:{<userId>}` with a `:cooldown` key in the same hash slot. [ACCOUNT_CONFIRMATION](../../src/endpoints/account/static/ACCOUNT_CONFIRMATION.ts) atomically replaces the pending confirmation with a four-hour TTL and enforces a one-minute per-account cooldown. [IAccountEmail](../../src/endpoints/account/types/IAccountEmail.ts) records userId, proposed email, currentEmail, the verified passwordHash, bcrypt codeHash and attemptsRemaining initialized to 3. MailService queues the six-digit code. Queue submission failure conditionally discards only this request's pending confirmation and cooldown and returns 503. If Redis cleanup fails, AccountEmailService logs the cleanup error and still throws 503 with the mail error as its cause. AccountModule imports LoggerModule for this handling. Success returns 204 with Cache-Control:no-store; User, Session and cookies are unchanged. The route allows 5 requests per minute per IP in addition to the Redis cooldown; global CSRF protection applies. Email availability is a precheck; confirmation handles the unique email index. No live delivery was verified.

`PATCH /account/email` is handled by [AccountEmailController.confirmEmail](../../src/endpoints/account/controllers/accountEmail.controller.ts) and [AccountEmailService.confirmEmail](../../src/endpoints/account/services/accountEmail.service.ts). [ConfirmEmailBodyDto](../../src/endpoints/account/dto/body/confirmEmail.body.ts) accepts only a six-digit string code, preserving leading zeros. The service requires a valid access cookie JWT, ObjectId claims, an explicitly unexpired owned Session and a User with both email and passwordHash. It reads and validates the pending confirmation, verifies its bcrypt codeHash and uses atomic Lua to consume it on success or decrement attemptsRemaining without extending the TTL. The third incorrect attempt deletes the confirmation. Comparing the current codeHash and userId prevents a concurrent request from consuming or decrementing a replacement confirmation. An expired, consumed, superseded or invalid code returns 400. One atomic User update applies the proposed email only while currentEmail and passwordHash still match the values captured by the request; changes to either make confirmation invalid. Duplicate email index errors return 409. The code stays consumed if the User update fails, including address conflicts, so the user must request a new code. Success returns 204 without a body with Cache-Control:no-store; password, sessions and cookies are preserved. The route permits 5 requests per minute per IP and uses global CSRF protection. No schema/index changes or live Redis/MongoDB verification were performed.

`PATCH /account/password` is handled by [AccountCredentialsController.updatePassword](../../src/endpoints/account/controllers/accountCredentials.controller.ts) and [AccountService.updatePassword](../../src/endpoints/account/services/account.service.ts). [PasswordBodyDto](../../src/endpoints/account/dto/body/password.body.ts) accepts currentPassword and newPassword, each at least 8 characters and at most 72 UTF-8 bytes without normalization. The service verifies the access cookie JWT, ObjectId claims, an explicitly unexpired owned Session and the existing bcrypt password. Missing authorization or a wrong current password returns 401; an account without a password returns 409. One MongoTransactionService transaction conditionally replaces the verified password hash, rotates the current Session refresh hash, extends it by 120 days, records lastRefreshedAt and deletes all other sessions. The conditional hash filter prevents concurrent use of a superseded password. Failure rolls back database changes and leaves cookies untouched. Success returns 204 without a body, sets both auth cookies and uses Cache-Control:no-store. The route permits 5 requests per minute; global CSRF protection applies. No schema or index changes are required.

`POST /auth/login` is handled by [AuthController.login](../../src/endpoints/auth/controllers/auth.controller.ts) and [AuthService.login](../../src/endpoints/auth/services/auth.service.ts). [LoginBodyDto](../../src/endpoints/auth/dto/body/login.body.ts) trims and lowercases username using the existing USERNAME_REGEX and accepts a password of at least 8 characters and at most 72 UTF-8 bytes without normalization. The service explicitly selects passwordHash and verifies it with the existing bcrypt compareHash helper. Unknown usernames, accounts without a password and wrong passwords return the same 401. Success creates a new Session with userAgent, preserves other sessions, sets both auth cookies and returns 204 without a body with Cache-Control:no-store. Tokens and hashes are not returned in JSON. The route permits 5 requests per 60,000 ms; global CSRF protection applies. No persistence schema or index changes are required.

`POST /account/setup` is handled by [AccountSetupController.requestSetup](../../src/endpoints/account/controllers/accountSetup.controller.ts) and [AccountSetupService.requestSetup](../../src/endpoints/account/services/accountSetup.service.ts). [SetupBodyDto](../../src/endpoints/account/dto/body/setup.body.ts) accepts normalized email (trimmed, lowercase, at most 254 characters), a password of at least 8 characters and at most 72 UTF-8 bytes without normalization, and the current 32-character accessCode. It verifies the access cookie JWT, ObjectId claims, an explicitly unexpired owned Session, an existing User without email/password and the SHA-256 access-code digest. Invalid credentials return 401; an already configured account or currently occupied email returns 409. Email availability is only a precheck: confirmation must still handle the unique index and recheck current account credentials.

AccountModule imports MailModule and a local named `account` Redis client configured through InfrastructureConfigService. [ACCOUNT_CONFIRMATION](../../src/endpoints/account/static/ACCOUNT_CONFIRMATION.ts) defines atomic Lua save/discard operations, a four-hour confirmation TTL and a one-minute account-wide resend cooldown. The raw Redis key is `<appName>:account:setup:{<userId>}`, with a `:cooldown` key in the same hash slot; this is not a CacheService/Keyv key. Its JSON follows [IAccountSetup](../../src/endpoints/account/types/IAccountSetup.ts): userId, normalized email, bcrypt passwordHash, the accessCodeHash used for authorization, bcrypt codeHash and attemptsRemaining initialized to 3. A new accepted request replaces the previous challenge. The `PATCH /account/setup` confirmation uses an atomic Lua operation to enforce the attempt budget and consume the current challenge without extending its TTL; concurrent attempts cannot overwrite the counter or consume a newer challenge. No plaintext password is stored. MailService queues a six-digit confirmation code; success returns 204 with Cache-Control:no-store and does not change User, Session or cookies. Queue submission failure conditionally discards only this request's challenge/cooldown and returns 503. AccountSetupService logs Redis cleanup failures separately, preserving 503 with the original mail error as its cause. The route permits 5 requests per minute per IP in addition to the atomic per-account minute cooldown; global CSRF protection applies. No MongoDB schema/index changes or live delivery verification are part of this endpoint.

`PATCH /account/setup` applies email, passwordHash and removal of accessCodeHash in one conditional User update after validating the access token, current session and Redis confirmation. The filter requires the original accessCodeHash and an account without email or password. This single-document mutation needs no MongoDB transaction or second session lookup; already running requests are not cancelled by session revocation. A duplicate email returns 409; an invalidated account state returns 400. The confirmation remains consumed on failure.

`PATCH /account/username` is handled by [AccountController.updateUsername](../../src/endpoints/account/controllers/account.controller.ts) and [AccountService.updateUsername](../../src/endpoints/account/services/account.service.ts). [UsernameBodyDto](../../src/endpoints/account/dto/body/username.body.ts) trims and lowercases string input and validates the existing User USERNAME_REGEX (`^[a-z0-9_]+$`); missing, empty, invalid or extra fields return 400. The service verifies the access cookie JWT and ObjectId claims, requires an explicitly unexpired Session belonging to that user, then updates only that User's username through the existing repository. Missing authorization or User returns 401. MongoDB duplicate-key errors for username map to 409 using the existing unique index; no availability precheck or index change is introduced. Reusing the current username succeeds. Success returns 204 without a body and Cache-Control:no-store; displayName, sessions and cookies are preserved. Global CSRF protection and throttling apply.

`GET /account` is handled by [AccountController.getAccount](../../src/endpoints/account/controllers/account.controller.ts) and [AccountService.getAccount](../../src/endpoints/account/services/account.service.ts). It requires the access cookie JWT with valid ObjectId claims, an explicitly unexpired Session belonging to that user and an existing User, returning 401 if authorization fails. [AccountResponseDto](../../src/endpoints/account/dto/response/account.response.ts) extends the brief user DTO with nullable confirmed email, isPasswordSet, isAccessCodeSet and ISO 8601 createdAt/updatedAt. Credential hashes are explicitly selected only to derive the boolean flags; an explicit response allowlist excludes hashes, tokens and linked-provider identifiers. Success returns 200 with Cache-Control:no-store. Global throttling applies; this read does not change sessions or cookies.

`PATCH /auth/login/code` is handled by [AccountCredentialsController.reissueCode](../../src/endpoints/account/controllers/accountCredentials.controller.ts) and [AuthService.reissueCode](../../src/endpoints/auth/services/auth.service.ts). It requires a valid access cookie JWT with ObjectId claims, the current unexpired server Session and the current code in `LoginCodeBodyDto`. One MongoTransactionService transaction conditionally replaces the User's SHA-256 accessCodeHash only while passwordHash is null and the old code matches, rotates the current Session's refresh hash, extends it by 120 days, records lastRefreshedAt and deletes all other sessions of that user. The current session id and device metadata are preserved. Failure rolls back all database changes and leaves cookies untouched; concurrent requests with the same old code cannot both succeed. Success returns 200 with only `{ accessCode }` through [LoginCodeResponseDto](../../src/endpoints/auth/dto/response/loginCode.response.ts), sets both auth cookies and uses Cache-Control:no-store. Invalid credentials or session return 401; invalid input returns 400. The route allows 5 requests per 60,000 ms; global CSRF protection applies. No persistence schema or index changes are required.

`DELETE /auth/session/:sessionId` is handled by [SessionController.deleteSession](../../src/endpoints/auth/controllers/session.controller.ts) and [SessionService.deleteSession](../../src/endpoints/auth/services/session.service.ts). [MongoObjectIdHandler](../../src/infrastructure/database/handlers/mongoObjectId.handler.ts) validates the route parameter as a 24-character hex ObjectId and converts it to Types.ObjectId. The service verifies the access cookie JWT and ObjectId claims, requires an existing User and an explicitly unexpired current Session belonging to that user, then atomically deletes only the requested unexpired Session with an owner filter. Missing authorization returns 401; another user's, absent or expired target returns the same 404. Success returns 204 with Cache-Control:no-store and clears both auth cookies only when deleting the current Session. Other cookies and sessions are preserved. Global CSRF protection and throttling apply.

`DELETE /auth/session/others` is handled by `SessionController.deleteOtherSessions` and [SessionService.deleteOtherSessions](../../src/endpoints/auth/services/session.service.ts). The static route is declared before `:sessionId`. It verifies the access cookie JWT and ObjectId claims, requires an existing User and an explicitly unexpired owned current Session, then calls `SessionRepository.deleteOthers` with the user and current session IDs. All other sessions of that user, including expired records, are deleted. Success returns 204 with Cache-Control:no-store and preserves current-session cookies, including when there are no other sessions. Missing authorization returns 401; global CSRF protection and throttling apply.

`GET /auth/session` is handled by [SessionController.getSessions](../../src/endpoints/auth/controllers/session.controller.ts) and [SessionService.getSessions](../../src/endpoints/auth/services/session.service.ts). It verifies the access cookie JWT and ObjectId claims, requires an existing User and the current Session among that user's explicitly unexpired sessions, and returns 401 if any authorization requirement fails. The response is a direct array of [SessionResponseDto](../../src/endpoints/auth/dto/response/session.response.ts) objects: id, nullable userAgent, createdAt, expiresAt, nullable lastRefreshedAt and isCurrent. Dates are ISO 8601; sessions are sorted by createdAt and id descending. Queries select only response fields, and mapping exposes no tokens or hashes. Success uses Cache-Control:no-store; the global request throttle applies. It does not use the Bearer-only guard or change session state.

`POST /auth/login/code` is handled by [AuthController.loginByCode](../../src/endpoints/auth/controllers/auth.controller.ts) and [AuthService.loginByCode](../../src/endpoints/auth/services/auth.service.ts). [LoginCodeBodyDto](../../src/endpoints/auth/dto/body/loginCode.body.ts) accepts only the case-sensitive 32-character base64url access code; no username is required. The service finds the User by the code's SHA-256 hex digest with passwordHash required to be null and selects only id and role. Registration generates 24 random bytes and stores the same SHA-256 digest in accessCodeHash. User declares the partial unique userAccessCodeHashUnique index for string hashes. Previously issued bcrypt-backed codes are unsupported; no data migration or deployed-index verification was performed. Wrong codes and accounts with a password return the same 401; malformed, missing or extra input fields return 400. Success creates a new Session with userAgent through SessionRepository.createNew, preserves other sessions, sets both auth cookies and returns 204 without a body with Cache-Control:no-store. Tokens and hashes are not returned in JSON. The route allows 5 requests per 60,000 ms per the existing IP-based throttling; global CSRF protection applies.

`GET /account/whoami` is handled by [AccountController](../../src/endpoints/account/controllers/account.controller.ts) and [AccountService](../../src/endpoints/account/services/account.service.ts). Nest's built-in `@Cookies` extracts `__Host-accessToken` without an extra cookie plugin. The service verifies the access JWT, validates ObjectId claims, requires a Session matching both sessionId and user with expiresAt greater than the current time, and requires an existing User. Authorization is local to this use case; it does not use the Bearer guard or establish a shared session guard. The response explicitly maps `user: { id, username, displayName, avatarUrl, role }` and `session: { id, expiresAt }`, with the role read from the current User and the expiry serialized as ISO 8601. Successful responses use Cache-Control:no-store. Missing or invalid credentials, users or sessions produce 401. Swagger declares the `accessCookie` security scheme in bootstrap. No tokens or hashes are returned.

[User](../../src/entities/user/schemas/user.schema.ts) retains accessCodeHash and passwordHash with select:false; credentialVersion, revision/actionSequence, accessCodeChangedAt, catalogPermissions and locale were removed. [Session](../../src/entities/session/schemas/session.schema.ts) retains user, refreshTokenHash (select:false), userAgent, expiresAt and lastRefreshedAt; rotation/jti/issuedAt/revision/revoke/receipt fields were removed. UserSetting owns required ELocale.RU/EN with default:ELocale.RU; locale is optional in TCreateUserSetting. Its unique user index is named userSettingUnique. Linked providers remain Google and Yandex; source changes do not migrate stored documents.

Setup, email-change and password-reset confirmations live in Redis through ConfirmationService; there is no RecoveryChallenge entity or encrypted receipt mechanism. OAuth is outside this stage. User has a local toJSON transform removing passwordHash and accessCodeHash, composed with the global JSON plugin. Session has no local hash-removal transform; select:false affects default reads only. Explicit selections, lean, aggregate, toObject and create results still require a transport allowlist.

`PATCH /auth/session/refresh` is handled by [SessionController](../../src/endpoints/auth/controllers/session.controller.ts) and [SessionService.refresh](../../src/endpoints/auth/services/session.service.ts). It takes only `__Host-refreshToken`, verifies the refresh JWT and ObjectId claims, loads the current User role, and atomically replaces the Session hash using a filter on sessionId, user, old SHA-256 refresh hash and expiresAt greater than now. The same Session is extended by 120 days and lastRefreshedAt is recorded. Refresh JWT signing adds a random UUID `jti`, so successive tokens differ even within one second. A concurrent/replayed old token gets 401 without setting or clearing cookies; clients must coordinate refresh across tabs. Success returns 204 with no body, Cache-Control:no-store and both auth cookies. No valid access token is required. The existing global CSRF protection and throttling apply. Bootstrap declares the `refreshCookie` Swagger scheme. Session lifecycle belongs to the auth endpoint layer, not the security infrastructure guards.

`POST /auth/logout` is handled by `AuthController.logout` and [AuthService.logout](../../src/endpoints/auth/services/auth.service.ts). It verifies `__Host-accessToken` and ObjectId claims, then atomically deletes only the Session matching sessionId, user and expiresAt greater than now. Success clears both auth cookies and returns 204 without a body with Cache-Control:no-store. Missing/invalid/expired access credentials or a missing/expired Session return 401 without changing cookies, including repeated logout; an expired access token requires refresh first. Other sessions are preserved. Global CSRF protection and throttling apply. Deletion prevents subsequent whoami and refresh authorization for that Session; the separate Bearer-only AccessTokenGuard still does not query sessions.
