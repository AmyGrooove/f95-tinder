# Endpoint implementation routes

Read when changing HTTP use cases under `src/endpoints`. The [API overview](../../../../docs/api/readme.md) explains implemented behavior; the linked specifications own detailed route contracts. Verify facts against production code before changes.

## Ownership and composition

[AppModule](../../src/app/app.module.ts) imports four endpoint modules, with 37 user-facing routes in total. Controllers own HTTP bindings and DTO boundaries; endpoint services own authentication, business validation, transactions and response mapping. Entity modules export model-specific repositories. Import the owning module and reuse its repository instead of creating another persistence client. See [data access](data-access.md) for generic repositories and transaction semantics, [security](security.md) for cookies and session validation, and [runtime](runtime.md) for global HTTP setup.

## Library invariants

The seven `/userItems` mutations and summary QUERY authenticate the access cookie, active owned session and existing User. The route `:id` is a UserItem ID. Ownership is part of repository read/write filters; foreign and absent records return 404 for mutations. Creation requires a nondeleted Item and maps duplicate user/item pairs to 409. Existing library records remain editable after their Item is soft-deleted. QUERY /userItems accepts JSON {ids} with 1–60 unique UserItem ObjectIds (case-insensitive uniqueness), returns only id/itemId/rating/isFavorite/status in request order and omits foreign, missing and expired skipped entries. It uses an explicit MongoDB projection, makes no writes and remains available after Item soft deletion. It does not read by Item ID or load notes/attempts. Cache-Control is no-store; Accept-Query is application/json.

PATCH `/userItems/:id` accepts one or more of status, rating, isFavorite and note, preserves omitted fields and rejects an empty body. There are no separate field PATCH routes. Rating and note can be cleared with null. All mutations involving attempts read and update in one MongoTransactionService transaction. DELETE removes the UserItem and embedded attempts without changing collection membership. ItemMetric and recommendation projections are not updated.

UserItem has five library statuses plus skipped and blocked. POST /userItems accepts only library statuses; POST /userItems/skip and /block accept itemId and create exclusions, returning 409 for existing pairs. Skipped must have no rating, favorite, note or attempts and expires after 90 days through a partial TTL index. Expired skips are treated as absent by mutations; creation conditionally removes an expired skip. Blocked preserves prior personal data. Switching away from skipped clears expiresAt. InProgress/onHold/completed/dropped require an attempt, created only when none exists; completed marks the last attempt isCompleted=true. Attempts have no status; their create/update does not change the parent status. Planned/blocked retain editable history but forbid new attempts. Progress is nullable nonnegative safe integer minutes or integer percent 0..100. Unknown dates remain null; completedAt cannot precede startedAt. See the library contract for compatibility/migration requirements.

## Collection invariants

Collection stores metadata and ordered group/text blocks with stable ObjectId ids. CollectionItem stores membership, required groupId and position within the group. UserCollection stores independent reactions. All collections are public and manually composed. An author of null means site ownership; the user routes grant no administrative override. Read metadata contains version and blocks, with no membership or user reactions.

CollectionService.create assigns the verified user as author, validates unique block/item IDs and group references, checks nondeleted Items and creates metadata plus membership in one transaction. Update validates the final block set, exact supplied block order, conflicting changes and group references. CollectionRepository.updateVersioned atomically matches ID, author, deletedAt:null and expected version, then stores the next version. Missing stored version is supported as 0. Membership upserts and removals use the same transaction session; moves precede removal of remaining memberships in removed groups. Stale or exhausted versions return 409. DELETE conditionally sets deletedAt and retains membership, reactions and library data.

CollectionContentService checks collection/group availability, validates typed feature conditions and maps responses. CollectionItemRepository.getFilterOptions, countAvailableItemsByGroup and readContentPage own aggregation; [createCollectionItemsPipeline](../../src/entities/collectionItem/functions/createCollectionItemsPipeline) builds item selection. Only existing nondeleted Items in valid group blocks participate. FeatureRepository.findFilterDefinitionsByIds supplies filter definitions. String features are excluded pending explicitly agreed categorical keys. Tags match direct assignments without hierarchy expansion.

Collection item pages use QUERY `/collections/:id/items` with a JSON body (CollectionItemsBodyDto). Tags and excluded tags are ObjectId arrays; features are nested objects, not a serialized JSON string. Collection item pages are public, do not authenticate cookies and do not load or return UserItem data. Personal state can be read through QUERY /userItems only when UserItem IDs are known; lookup by Item remains unimplemented (LIB-01). Personal item filters statuses, isInLibrary and isFavorite are unsupported and rejected as unknown query fields. ratingMin/ratingMax filter by stored ItemMetric.ratingAverage before counting and pagination, are public and accept inclusive numeric bounds 1–10 (including fractions) with min <= max; absent metrics and null averages are excluded. Metric calculation/update is not implemented (ITEM-02). Rating filters hide text blocks like other active filters. Pagination counts Items, not display blocks. Mode availability is global: flat always, grouped for at least two nonempty groups or any text block. Filter options cover the whole collection and reject all query fields, including groupId; item pages still support groupId. See the contract for exact query parsing, sort stability, defaults and errors.

[createCollectionDisplayBlocks](../../src/endpoints/collection/functions/createCollectionDisplayBlocks) repeats group headers for continuation pages and anchors text to the next nonempty group's first Item; trailing text belongs to the last nonempty page. Text appears only in unfiltered grouped mode; groupId is a filter. Itemless collections emit text only on page 1. Collection reads use Cache-Control:no-store; no shared collection cache is implemented.

Reaction reads return false/null/false without inserting absent records. Reaction writes update only the requested field by verified user/collection IDs, using defaults for the first insert. Concurrent first-insert duplicate-key races retry without upsert. A non-null rating of one's own collection returns 409; clearing it is allowed. Hiding does not restrict direct reads. General collection listing, search and site-collection administration are outside the current module.

## Persistence boundaries

Use [the entity inventory](../../../../docs/api/entities.md) to locate the 22 schemas and their relationships. Schema validators and declared indexes do not establish deployed indexes or enforce every cross-document invariant. Generic query/bulk writes bypass some document checks; endpoint services must validate the operation they construct. Current source does not establish migration of earlier records or live MongoDB transaction support.
