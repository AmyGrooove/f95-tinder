# Исследование кросс-рекомендаций Bisky

Дата: 25 октября 2026 года.

Статус: исследование и инженерные предложения. Документ сохраняет полный отчёт исследовательского чата; он не является утверждённой спецификацией или описанием реализованной рекомендательной системы. Предложения развивают первоначальное исследование и определяют вариант V1 с переносом между типами контента.

[Документация проекта](../readme.md) · [Первоначальное исследование](recommendationSystem.md) · [Согласованные продуктовые принципы](../product/foundations/recommendations.md)

**Рекомендую для Bisky первый вариант на канонических метаданных: несколько опорных произведений внутри каждого типа, отдельное представление общих признаков и ограниченный положительный перенос source→target.** Он действительно меняет рекомендации фильмов по истории игр и наоборот, работает без обученной модели и не требует насыщенной матрицы взаимодействий.

Собственные предпочтения целевого типа сохраняют приоритет. Отрицательные оценки между типами в V1 не переносятся. Отсутствие пригодных общих признаков приводит к неперсональному подбору с соблюдением фильтров.

Ниже — инженерное предложение для последующего согласования и реализации. **Полезность алгоритма для Bisky пока не доказана; все предложенные веса, пороги и лимиты — стартовые гипотезы.**

Точечно проверил схемы профиля, ItemTag, ItemFeature, UserItem, библиотечный сервис, транзакционную обёртку и очередь.

Рабочую БД, её наполненность и топологию MongoDB не проверял. Результаты предыдущего review принимаю как переданный контекст; это не мои результаты тестирования. Файлы проекта, тесты, Git-историю и память не менял.

Из внешних источников решающими оказались следующие работы и реализации.

| Источник                    | Что он действительно показывает                                                                                                                                                                       | Следствие для Bisky                                                                           |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **EMCDR**                   | Раздельные латентные пространства можно связать обучаемым mapping. Для обучения нужны сущности, представленные в обоих доменах; авторы отдельно исследуют ухудшение при включении ненадёжных факторов | Обучать перенос до проверки пересечения и качества собственных данных преждевременно          |

| **LightFM**                 | Обучаемый hybrid объединяет embeddings признаков и collaborative feedback, включая item cold-start                                                                                                    | Сильный будущий challenger, но наличие тегов само по себе не даёт обученную модель            |
| **SBERT и multilingual E5** | Предобученные модели позволяют независимо получать и сравнивать смысловые представления текстов                                                                                                       | Собственная большая история для применения embeddings не нужна                                |

| **MMR**                     | Релевантность можно сочетать с уменьшением избыточности результата                                                                                                                                    | Разнообразие следует вводить отдельным проверяемым этапом                                     |

В EMCDR изучены сценарии MovieLens→Netflix и фильмы→книги Douban. Эксперимент с искусственным удалением target-истории полезен для понимания cold-start, но отличается от естественной малой истории Bisky и не доказывает качество game→movie. [Статья EMCDR](https://www.ijcai.org/Proceedings/2017/0343.pdf).

В CoNet изучены cross-connections и разреженный выбор переносимых представлений. Работа прямо отмечает, что невыборочный перенос способен уступать вариантам без переноса. Рассмотрены также [авторский репозиторий](https://github.com/njuhugn/CoNet) и [реализация CoNet в RecBole-CDR](https://github.com/RUCAIBox/RecBole-CDR/blob/main/recbole_cdr/model/cross_domain_recommender/conet.py). Последняя содержит отдельные доменные embeddings, cross-слои и совместную функцию потерь; это экспериментальная основа, а не готовый модуль для Bisky. [Статья CoNet](https://arxiv.org/pdf/1804.06769).

Для LightFM просмотрены модель, [воспроизводимый пример item cold-start](https://making.lyst.com/lightfm/docs/examples/hybrid_crossvalidated.html) и [код авторского эксперимента MovieLens](https://raw.githubusercontent.com/lyst/lightfm-paper/master/experiments/movielens/model.py). В примере используются собственные признаки и определение реакций: переносить вместе с моделью их трактовку положительных и отрицательных данных нельзя. [Статья LightFM](https://arxiv.org/pdf/1507.08439).

Предлагаемые ниже формулы — **мой инженерный выбор**, а не алгоритм, дословно заимствованный из этих публикаций. Численные улучшения из статей не являются прогнозом для Bisky.

## 2. Сравнение вариантов

| Вариант                                                           | Требования                                                             | Преимущества                                                   | Ограничения                                                                         | Решение                              |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------ |
| **Без переноса**: персонализация только по target type            | Метаданные, текущие UserItem                                           | Простой контроль; отсутствует negative transfer                | История игр никак не помогает фильмам                                               | Обязательный baseline                |
| **Общий и частный профиль тегов**                                 | Единый словарь и правила переносимости                                 | Простота, прозрачные веса                                      | Один общий вектор смешивает несовместимые интересы; частый интерес вытесняет редкий | Реалистичная упрощённая альтернатива |
| **Несколько опорных произведений с общей и локальной проекциями** | Те же данные                                                           | Сохраняет разные интересы, их происхождение и границы переноса | Ограниченное число опор; зависит от разметки                                        | **Рекомендуемый V1**                 |
| **Предобученные semantic embeddings + опоры**                     | Описания, inference, версия модели                                     | Находит связи за пределами одинаковых тегов                    | Сюжетная похожесть не равна вкусовой; нужны контроль входов и калибровка            | Первый challenger                    |
| **Обучаемый CF/hybrid/domain-transfer**                           | Пригодные реакции, пересечения доменов, обучение и temporal evaluation | Может находить предпочтения, не выраженные метаданными         | Неизвестна достаточность данных; сложнее отладка и восстановление                   | После измерений                      |

Сохранить семь независимых профилей технически проще, но это не решает поставленную задачу. Объединить их в один общий профиль тоже недостаточно: человек может предпочитать мрачные игры и лёгкие фильмы.

Выбранный вариант сохраняет происхождение каждого направления: **«этот интерес наблюдался в играх; при подборе фильма использованы только такие-то общие признаки»**.

## 3. Что переносить

Одинаковый канонический Tag означает одинаковое понятие. Это необходимое условие сопоставления, но не доказательство одинакового пользовательского отношения к нему в разных типах.

| Признаки                                                         | Внутри типа                  | Между типами в V1                         |
| ---------------------------------------------------------------- | ---------------------------- | ----------------------------------------- |
| Темы: одиночество, дружба, моральные дилеммы, выживание как тема | Да                           | Да                                        |
| Атмосфера: мрачная, уютная, напряжённая                          | Да                           | Да                                        |
| Повествование: нелинейность, сюрреализм, медленный темп          | Да                           | Да, при одинаковом смысле разметки        |
| Общие содержательные жанры: фантастика, комедия, драма           | Да                           | Как дополнительное основание              |
| RPG, FPS, crafting, stealth, survivalGameplay                    | Да для подходящего типа      | Нет                                       |
| Платформы и режимы multiplayer                                   | Фильтры и локальные свойства | Нет                                       |
| Техники анимации                                                 | Да                           | В первоначальный перенос не включать      |
| Страна, originalLanguage                                         | Фильтры                      | Не выводить межтиповой вкус               |
| Год, длительности, число эпизодов, hasDefinedEnd                 | Фильтры                      | Нет автоматического переноса предпочтений |

Первоначальный перенос требует **хотя бы одного прямого совпадения переносимой темы или стиля**. Один общий жанр `drama` или совпавший предок жанровой иерархии его не включает.

Перечень переносимых тегов задаётся версионируемой политикой по каноническим ключам/ID. Использовать целиком `Tag.group=keyword` нельзя: в этой группе одновременно находятся темы и механики.

Различия сохраняются явно:

- **Identity:** один канонический Tag — одно понятие.
- **Aliases:** названия того же понятия; дополнительного веса не дают.
- **Hierarchy:** обобщение понятия с ограниченным бюджетом.
- **Relation:** известная связь произведений, например адаптация.
- **Franchise Collection:** принадлежность подборке-франшизе.
- **Learned similarity:** статистическая или модельная близость; она не устанавливает тождество.

Из связи адаптации можно получить отдельного кандидата и объяснение «адаптация знакомой игры». Из неё нельзя заключить, что перенос вкуса между произвольными играми и фильмами уже работает.

## 4. Представление произведения

Нужны две производные проекции одного Item:

```text
localRepresentation:
    содержательные признаки, пригодные для сравнения внутри типа

sharedRepresentation:
    только признаки, разрешённые политикой межтипового переноса
```

Исходные данные остаются в `Item`, `Tag`, `ItemTag`, `Feature`, `ItemFeature`, `Relation` и коллекциях. У Item не появляется вымышленное существующее поле `tags`.

**Выраженность тегов**

В текущем договорённом смысле `relevanceScore` — выраженность признака, а не доверие к разметке.

Для V1:

```text
relevanceScore == 0 → признак не участвует
relevanceScore > 0  → бинарное присутствие
```

Промежуточные значения пока не сравниваются по величине. Это сохраняет смысл нуля и не предполагает неизвестную калибровку `0.6` против `0.9`.

Отдельно нужны контроль качества и provenance разметки. Низкое доверие к источнику нельзя кодировать понижением выраженности темы.

**Группы и caps**

| Логическая группа              | Вес local | Вес shared | Максимум прямых признаков |
| ------------------------------ | --------: | ---------: | ------------------------: |
| Жанры, включая поджанры        |      0,35 |       0,25 |                         8 |
| Темы / содержательные keywords |      0,35 |       0,40 |                        12 |
| Стиль и атмосфера              |      0,25 |       0,35 |                         8 |
| Формат                         |      0,05 |          0 |                         4 |

В local keywords и style входят применимые специфические признаки, включая игровые. В shared остаётся только разрешённое подмножество.

Фактические теги и `group=null` не участвуют в мягком score V1. Caps действуют **только на ранжирование**, не на проверку фильтров.

**IDF**

Внутри типа:

\[
idf_t(z)=\min\left(3,\ 1+\ln\frac{N_t+1}{df_t(z)+1}\right).
\]

Для shared-проекции нужна одна общая шкала, не зависящая от того, какой тип значительно больше:

\[
f(z)=\frac1{|D|}\sum_{t\in D}\frac{df_t(z)}{N_t},
\]

\[
idf_{shared}(z)=\min\left(3,\ 1+\ln\frac{1+\varepsilon}{f(z)+\varepsilon}\right),
\quad \varepsilon=0.01.
\]

`D` — непустые типы опубликованного поколения представлений. Таким образом, многочисленный movie-каталог не определяет всю межтиповую редкость признаков.

Если группа превышает cap, сохраняются признаки с максимальным IDF; равенства разрешаются по Tag ID. Отброшенное количество сохраняется диагностически.

**Иерархия**

1. Проверить используемый граф на циклы; циклические компоненты не использовать для наследования.
2. Удалить прямого предка из самостоятельных признаков, если присутствует его потомок.
3. Нормировать оставшуюся прямую массу внутри группы до единицы.
4. Отдать 70% массы самому признаку, 30% — его уникальным предкам.
5. Предков учитывать до глубины 4, максимум 16 на прямой признак.
6. При нескольких путях брать кратчайшее расстояние, не складывать пути.
7. Если предков нет, вся масса остаётся прямому признаку.

Родительская часть распределяется пропорционально \(2^{-distance}\). Несколько родителей делят бюджет, а не создают дополнительную массу.

Для hard filters используется полная допустимая семантика иерархии. Усечённое рекомендательное представление для этого непригодно.

**Похожесть и missing data**

Для группы с нормированными распределениями:

\[
J_g(i,j)=
\frac{\sum_z\min(x_{igz},x_{jgz})}
{\sum_z\max(x_{igz},x_{jgz})}.
\]

Пусть \(A_g=1\), если группа непуста у обоих объектов:

\[
q(i,j)=\sum_g w_gA_g,\qquad
m(i,j)=\sum_g w_gA_gJ_g(i,j).
\]

При \(q>0\):

\[
s(i,j)=m(i,j)/q(i,j).
\]

Здесь:

- `s` — сходство по доступному основанию;
- `q` — объём этого основания;
- `m` — используемое в score сходство с учётом покрытия.

Совпадение единственного известного признака не превращается в полное сходство. Missing означает **нет персонализирующего доказательства**, а не «произведение плохое».

## 5. Сигналы пользователя и несколько интересов

Источником профиля служат текущие UserItem. История действий нужна для доставки, диагностики и будущей оценки, но не заменяет текущее состояние.

Предлагаю следующие силы:

\[
p_r(r)=
\begin{cases}
(r-6)/4,&r\ge7\\
0,&иначе
\end{cases}
\]

\[
n_r(r)=
\begin{cases}
(5-r)/4,&r\le4\\
0,&иначе.
\end{cases}
\]

\[
p_i=\max(p_r(r_i),\ 0.8\cdot favorite_i),\qquad n_i=n_r(r_i).
\]

Оценки 5–6 нейтральны в персонализации. Это рабочее разбиение шкалы, требующее проверки, а не установленная пользовательская калибровка.

**Конфликт rating/favorite:** если `rating≤4` и `isFavorite=true`, для этой записи принять `p=n=0`, увеличить `conflictingSignalItems`. Система не выбирает молча, какой из двух явных сигналов считать правильным.

Другие правила:

- Оценка используется независимо от завершённости; наличие завершённости не усиливает симпатию.
- `planned` может быть слабым источником кандидатов, но не повышает confidence оценённого вкуса.
- Статусы, прогресс и число попыток не создают положительного или отрицательного предпочтения.
- `skip` и `block` сами по себе не являются вкусовыми сигналами.
- Сохранившиеся явные rating/favorite у заблокированной записи остаются текущими явными данными; сама карточка исключена.
- Записи `skipped` не используются как taste seeds. Это исключает зависимость вкуса от физического TTL-удаления временной записи.
- Реакции на подборку и проигрыш в Баттле не распространяются на произведения.

**Опоры**

Для каждого типа строятся четыре ограниченных набора:

```text
localPositive[0..8]
localNegative[0..8]

sharedPositive[0..8]
sharedNegative[0..8]
```

`sharedNegative` используется только при запросе **этого же target type**, чтобы ослабить противоречащий ему чужой бонус. В другой тип он не экспортируется.

Раздельный выбор shared-опор важен: восемь игр, представляющих разные механики, могут плохо представлять разные темы этих игр.

Алгоритм для каждого набора одинаков:

```text
seeds = текущие подходящие записи данного типа и знака

1. Выбрать seed с максимальной силой; tie → ItemId
2. Пока опор меньше 8:
   uncovered = seeds, для которых нет опоры:
       s(seed, anchor) >= 0.65 AND q(seed, anchor) >= 0.5

   Если uncovered пуст — остановиться

   Выбрать seed с максимальным:
       (1 - max m(seed, anchors)) * (0.5 + 0.5 * strength(seed))

   tie → ItemId

3. Назначить каждый seed ближайшей допустимой опоре
4. Непокрытые после лимита оставить unrepresented
```

Опора всегда относится к собственной группе. Для shared используются shared-веса и разрешённые признаки.

**Сила и уверенность группы**

Сезоны и связанные версии нельзя считать полностью независимыми подтверждениями. Поэтому вводится производная единица зависимости:

- известные сезоны одной франшизы;
- известные связанные адаптации;
- другие явно установленные зависимые карточки.

Она строится по согласованным ролям и `Collection.type=franchise`, а не по похожести названий. Если связь неизвестна, Item считается отдельной единицей; это ограничение качества данных сохраняется в диагностике.

Для группы опоры:

- сначала усреднить силы внутри единицы зависимости;
- затем усреднить эти значения между единицами;
- \(n_{eff}\) — число различных единиц поддержки.

\[
strength_k=meanFamilyStrength_k,
\qquad
confidence_k=\frac{n_{eff,k}}{n_{eff,k}+2}.
\]

Один объект даёт confidence \(1/3\), три независимых — \(3/5\). Десять сезонов одной франшизы не дают десять независимых подтверждений.

**Confidence — коэффициент усадки, не вероятность истинности интереса.** Отдельного порога «интерес доказан» нет: слабая опора может работать, но с малым влиянием.

Жизненный цикл определяется полной пересборкой:

| Событие                 | Поведение                                                                         |
| ----------------------- | --------------------------------------------------------------------------------- |
| Новый непокрытый сигнал | Может стать опорой                                                                |
| Похожие сигналы         | Назначаются одной опоре                                                           |
| Merge                   | При новой пересборке покрываются одной выбранной опорой                           |
| Split                   | После изменения сигналов/метаданных перестают покрываться и получают разные опоры |
| Correction/delete       | Старый состав не сохраняется; строится заново                                     |
| Достигнут лимит         | Остальные отмечаются `unrepresented`                                              |
| Идентичность интереса   | `projection:sign:anchorItemId` внутри конкретной версии профиля                   |

Постоянный психологический «интерес №3» между пересборками не обещается.

Поддержка нескольких интересов согласуется с направлением MIND, однако приведённый алгоритм представителей не использует его обучаемую capsule routing. [MIND](https://arxiv.org/pdf/1904.08030).

## 6. Точная формула переноса и защита от negative transfer

Для кандидата `i` типа `t` локальное положительное соответствие:

\[
P_t(i)=
\max_{k\in localPositive_t}
strength_k\,confidence_k\,m_{local}(i,a_k).
\]

Пустой максимум равен нулю. Используется **max, не sum**: произведению достаточно соответствовать одному интересу.

Общее положительное соответствие истории source type `s`:

\[
E_s(i)=
\max_{k\in sharedPositive_s}
strength_k\,confidence_k\,m_{shared}(i,a_k)\,I(i,a_k),
\]

где `I=1`, только если есть прямое совпадение разрешённой темы или стиля. Иначе `E=0`.

Стартовая политика коэффициентов:

\[
\tau_{s\to t}=
\begin{cases}
0.45,&s,t\text{ — разные видеотипы}\\
0.25,&ровно один из типов — game.
\end{cases}
\]

Это **ограничения доверия к переносу**, а не корреляции или вероятности. Более низкий game↔video — осторожная гипотеза о различии опыта взаимодействия; её нужно проверять отдельно.

Ручная матрица 7×7 в V1 не требуется. Для направлений можно вводить overrides после измерений. Обучаемая матрица без данных не добавляет обоснованности.

**Уверенность в target-истории**

\[
C_t=\frac{n_{eff,t}}{n_{eff,t}+5},
\]

где учитываются текущие непротиворечивые явные taste-сигналы target type с пригодными метаданными.

Это отдельная величина от confidence каждой source-опоры.

Собственная история постепенно ослабляет чужой бонус:

\[
G_t=1-0.7C_t.
\]

Небольшая target-история не обнуляет помощь; насыщенная оставляет небольшой канал для новых направлений.

**Target-specific конфликт**

Рассчитать по shared-опорам target type:

\[
H_t^-(i)=
\max_{k\in sharedNegative_t}
strength_k\,confidence_k\,m_{shared}(i,a_k),
\]

\[
H_t^+(i)=
\max_{k\in sharedPositive_t}
strength_k\,confidence_k\,m_{shared}(i,a_k).
\]

Для отрицательной части также требуется прямое содержательное совпадение.

\[
V_t(i)=\max(0,H_t^-(i)-H_t^+(i)).
\]

Итоговый перенос:

\[
\boxed{
X_t(i)=
G_t\,(1-V_t(i))^2\,
\max_{s\ne t}\left[\tau_{s\to t}E_s(i)\right]
}
\]

Это положительный бонус. Он не делает жёстких исключений.

Важные последствия:

- Большая source-история насыщается через confidence, а не растёт линейно.
- Шесть source types не складывают шесть бонусов: берётся **max**.
- Сотни игр не получают неограниченного преимущества перед одной собственной оценкой фильма.
- Target-specific отрицательный контекст ослабляет чужую помощь именно для похожего кандидата.
- Совпадающий target-positive контекст уменьшает конфликт.
- Нет общего признака — `X=0`.
- Отрицательное предпочтение source→target в V1 отсутствует.
- Skip не участвует ни в отрицательных опорах, ни в конфликте.
- Число перезаписей одной оценки не увеличивает confidence.

Это защита от известных механизмов negative transfer, **не гарантия его отсутствия**. Даже правильно определённая общая тема может нравиться человеку только в одном формате.

**Локальный отрицательный штраф**

Внутри target type допускается небольшой штраф за близость к отрицательной опоре. Он действует только при известных минимум двух содержательных группах, включая тему или стиль, с суммарным весом основания не ниже 0,6.

\[
h(i,k)=
\left[\max\left(0,\frac{s_{local}(i,a_k)-0.8}{0.2}\right)\right]^2,
\]

\[
N_t(i)=
\max_k strength_k\,confidence_k\,q(i,a_k)\,h(i,k).
\]

При недостаточных данных `N=0`. Одна плохая оценка немного понижает очень близкое произведение; она не создаёт неприязнь ко всему жанру.

**Общий score**

\[
S_t(i)=
0.5+0.4P_t(i)+0.4X_t(i)-0.25N_t(i)
+0.1(Q_t(i)-0.5)+0.05(Pop_t(i)-0.5).
\]

`S` — относительный ранжировочный балл внутри типа, не прогноз оценки.

При отсутствии достоверных метрик принять `Q=Pop=0.5`. Перенос от этого продолжает работать.

**Численный пример**

Есть одна игра с оценкой 10, confidence опоры \(1/3\). У двух допустимых фильмов одинаковые прочие компоненты; первый имеет `m_shared=0.8`, второй не имеет общего признака.

При пустой movie-истории:

\[
X_{movie}(i_1)=0.25\times\tfrac13\times0.8\approx0.067,
\]

\[
\Delta S(i_1)\approx0.027,\qquad \Delta S(i_2)=0.
\]

Это небольшой, но реальный перенос game→movie. При нескольких независимых подтверждениях он усиливается в ограниченных пределах.

## 7. Полный pipeline

```text
условия сценария и eligibility
    ↓
пулы кандидатов нужного типа
    ↓
представления и coverage
    ↓
local score + ограниченный cross-type transfer
    ↓
diversity и exploration
    ↓
неизменяемый snapshot
    ↓
повторная eligibility → authorization
    ↓
попытка отправки → подтверждённая клиентская видимость
    ↓
пользовательское действие
    ↓
атомарное изменение + journal/outbox
    ↓
пересборка производных данных
```

**Eligibility**

Обязательный слой находится вне заменяемого алгоритма:

```text
Item существует и deletedAt == null
AND соответствует target type / явно смешанному режиму
AND нет глобального запрета через SourceItem → BannedItem
AND нет текущего block
AND нет skipped с expiresAt > now
AND выполнены явные фильтры
AND выполнена библиотечная политика сценария
AND выполнена политика повторов
```

Для Пика исключаются пять обычных библиотечных статусов. На главной или в каталоге политика задаётся режимом; «подобрать из запланированного» имеет другой входной набор. Баттл остаётся отдельным процессом без изменения вкуса.

Проверка фильтров трёхзначная: `true / false / unknown`. Например, неизвестная длительность не подтверждает «до 120 минут». Отсутствующий тег не доказывает отсутствие запрещённой темы при неполной разметке.

Для строгих условий `unknown` не проходит. Необходимую полноту разметки нужно подтверждать процессом наполнения, а не придумывать в рекомендательной проекции.

**Пулы кандидатов на одно окно**

| Пул                                                | Максимум уникальных кандидатов |
| -------------------------------------------------- | -----------------------------: |
| По local-опорам target type                        |                            300 |
| По shared-опорам остальных типов                   |                            300 |
| Известные связи: адаптации, связанные произведения |                            100 |
| Неперсональный базовый пул target type             |                            200 |
| Exploration                                        |                            100 |
| **Общий предел после дедупликации**                |                       **1000** |

Это бюджеты поиска, не квоты итоговой выдачи.

Начальные ограничения retrieval: до 32 ограниченных запросов и до 2000 прочитанных строк проекций на окно. Выбор опор распределяется между направлениями; большой source type не занимает все запросы. Курсоры сохраняются, чтобы последующие окна продолжали поиск.

Если пул пуст, бюджет можно перераспределить внутри общего предела. Hard constraints не меняются.

Для строгого селективного фильтра лучше начинать retrieval с его индексированного множества, затем ранжировать по вкусу. Иначе тысячи подходящих по вкусу, но недопустимых карточек исчерпают бюджет.

**Качество и популярность**

После реализации корректных агрегатов:

\[
Q_t(i)=\frac{\sum_j(r_j-1)/9+20\cdot0.5}{n_i+20}.
\]

Это усадка среднего текущих оценок к нейтральному prior.

Популярность можно определять через число текущих библиотечных записей пяти обычных статусов:

\[
Pop_t(i)=0.5+
\frac{v_i}{v_i+20}
\left[F_t(\log(1+v_i))-0.5\right].
\]

`F_t` — percentile внутри типа, с одинаковым правилом для ties. Это не число исторических добавлений и не сумма всех действий.

Показы и `recommendationsCount` не используются как популярность: иначе алгоритм начинает вознаграждать собственную выдачу. Внешние рейтинги в эти формулы не подмешиваются.

**Разнообразие**

Жадный rerank:

\[
R(i\mid L)=
S_t(i)-0.10\max_{j\in L}m_{local}(i,j)
-0.05\,sameFranchise(i,L).
\]

Дополнительные мягкие правила:

- при наличии альтернативы в пределах `0.08` score не давать одному интересу занимать более трёх позиций в окне из пяти;
- при такой же альтернативе не ставить подряд сезоны/произведения одной известной франшизы;
- отсутствие метаданных не считать доказательством разнообразия.

При отсутствии близкой по score альтернативы правила разнообразия уступают релевантности. Явные фильтры не уступают никогда.

Это адаптация идеи MMR; исходная публикация исследовала документы и суммаризацию, а не удовлетворённость медиаконтентом Bisky. [MMR](https://www.cs.cmu.edu/~jgc/publication/The_Use_MMR_Diversity_Based_LTMIR_1998.pdf).

**Exploration**

Каждая пятая позиция может выбираться из отдельного допустимого exploration-пула, если есть подходящий кандидат. Используются seed, версия политики и сохранённая вероятность выбора, когда она вычислима.

Exploration не обязан соответствовать уже известному вкусу и не объясняется как персонально доказанное предпочтение. При отсутствии метрик допустима воспроизводимая выборка через заранее рассчитанный `randomKey`; это приближённая диверсификация, не автоматически равномерная выборка всего каталога.

**Target type и смешанный режим**

Для `targetType=movie` все пулы содержат только `movie`. История game меняет порядок фильмов.

Смешанный режим рекомендую оставить отдельной возможностью. Если он потребуется, использовать:

1. независимые очереди разрешённых типов;
2. явные веса типов запроса, по умолчанию равные;
3. weighted round-robin между непустыми очередями;
4. ранжирование внутри каждой очереди по её score;
5. перенос квоты исчерпанного типа только другим разрешённым типам.

Сырые score разных типов напрямую не сравниваются. Пять movie-позиций не подменяются аниме ради наполнения.

## 8. Рекомендуемый UserTasteProfile

Текущая схема содержит один документ пользователя, массив type-профилей, два embeddings, `tagPreferences.score/samples` и `interactionsCount`. Она не определяет происхождение и семантику этих значений, несколько интересов и версии построения.

Рекомендую заменить внутренний формат:

```text
UserTasteProfile {
  user
  profileKey

  profileFormatVersion
  builderVersion
  builderConfigHash
  representationVersion
  transferPolicyVersion

  sourceTasteRevision
  sourceLibraryRevisionAtRead
  sourceStateHash
  builtAt
  contentHash

  types[<=7] {
    type

    local {
      positive[<=8]: Anchor
      negative[<=8]: Anchor
    }

    shared {
      positive[<=8]: Anchor
      negative[<=8]: Anchor
    }

    currentCounts {

      positiveItems
      negativeItems

```

```text
Anchor {
  anchorItem
  anchorRepresentationHash
  projection
  sign

  strength
  currentSupportItems
  effectiveSupportUnits
  confidence

  membersDigest
  topEvidence[<=3]
}
```

Индексы:

```text
unique(user, profileKey)
```

Общий словарь признаков здесь shared, но **свидетельства не сливаются между типами**. Благодаря этому можно отдельно измерить game→movie и movie→game, убрать один источник или объяснить его вклад.

`private` не требует отдельного дублирующего массива тегов: local-проекция включает shared и специфические признаки, shared-проекция содержит только разрешённые. Для отображения специфическая часть получается по политике представления.

`currentSupportItems` — число текущих объектов. `effectiveSupportUnits` — зависимо скорректированная поддержка. Ни одно поле не является числом событий или попыток.

Полные списки членов всех групп хранить необязательно: они восстанавливаются builder из текущих источников. `membersDigest` и три примера дают ограниченный provenance, но не историческую реконструкцию.

**Инвалидирование и восстановление**

Пересборка требуется при:

- изменении rating/favorite или удалении записи;
- изменении типа/содержательных признаков seed;
- публикации нового представления, IDF или политики переносимости;
- изменении builder/config.

Статус и skip немедленно влияют на eligibility. Для них не нужно каждый раз пересчитывать taste, если используемые явные сигналы не изменились.

Профиль полностью пересобирается из текущих источников. Старый профиль не является входом нового.

Вычисление можно делать вне транзакции:

1. Прочитать согласованный снимок текущих источников и ревизий.
2. Вычислить профиль.
3. Опубликовать через CAS, если `tasteRevision` и поколение представлений ещё актуальны.
4. Иначе повторить по свежему состоянию.

Профиль устарел после correction/delete — его персонализацию временно не использовать. На запросе допустим короткий пересчёт в пределах установленного бюджета; иначе неперсональная выдача и фоновая задача. Это безопаснее продолжения старой отрицательной оценки.

**Почему snapshot отдельно**

Для Пика с одним фиксированным небольшим batch встроенный snapshot в Session был бы достаточен.

Но общий механизм обслуживает также каталог и повторный retrieval после отсева. Число окон заранее не ограничено числом 25. Встраивание всех окон потребует ограничения массива, rollover либо изменения контракта истории.

Отдельная коллекция позволяет:

- дописывать новые неизменяемые окна без роста одного документа;
- обновлять session cursor независимо от аудита ранжирования;
- удалять краткоживущую сессию раньше диагностических snapshots.

Цена — дополнительная коллекция и чтение окна. При неизвестном масштабе это оправданная простота жизненного цикла. Если первоначальный согласованный продукт ограничится одним окном Пика, объединение в четыре коллекции остаётся допустимым упрощением.

- Для строгих отрицательных фильтров: источник подтверждённой полноты разметки по области. Это исходный факт процесса наполнения; производная проекция его только копирует.

## 10. Атомарность, journal/outbox и конкурентность

Точечная проверка кода показала существующую транзакционную обёртку. При этом создание UserItem, очистка просроченного skip и удаление записи имеют отдельные пути; будущий journal должен охватить их вместе с обновлениями.

Нельзя ограничить журнал endpoint рекомендаций. В него должны попадать библиотечные изменения из карточки, библиотеки, Пика, массовых команд, импорта, административных и фоновых операций.

**Одна MongoDB-транзакция**

```text
проверить commandId и payloadHash
прочитать актуальную запись / проверить expectedRevision
выполнить изменение UserItem
увеличить libraryRevision
при изменении вкусового входа увеличить tasteRevision
записать RecommendationEvent + pending outbox
commit
```

Нужны отдельные `eventId` и `commandId`.

```text
eventId
eventSchemaVersion
kind

user, actorKey, item
userItemIdBefore, userItemIdAfter
commandId, commandPayloadHash

libraryRevision, tasteRevision
before, after, changedFields
recordedAt, clientOccurredAt
origin

attribution {
  exposureId
  sessionId
  snapshotId
  actualPlacement
} | null

delivery {
  state
  nextAttemptAt
  leaseUntil
  attempts
  completedAt
}

purgeAt
```

В before/after достаточно рекомендательно значимых полей. Заметки и полные попытки не копируются без текущей необходимости. Поэтому журнал не объявляется полным event sourcing всей библиотеки.

**Идемпотентность**

- Retry одной команды сохраняет `commandId`.
- Новое независимое действие получает новый `commandId`, даже если user/item/kind совпали.
- Повтор команды с другим payload — конфликт.
- Один command может породить несколько событий: unique командной записи нельзя бездумно применять ко всем строкам событий. Нужен один command receipt/основное command-событие и связанные event ID.
- `(user,item,type)` не подходит для дедупликации.
- Гарантия идемпотентности имеет оговорённое окно хранения receipt; вечная гарантия при TTL невозможна.

`eventId`, случайные значения команды и её время формируются так, чтобы повтор transaction callback не создавал новое намерение. В callback нет BullMQ enqueue или других внешних побочных эффектов.

Поддержка multi-document transactions требует подходящей топологии MongoDB; standalone её не предоставляет. Фактическая топология Bisky остаётся открытым вопросом. [MongoDB: ограничения транзакций](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/).

**Отдельная доставка**

Dispatcher:

1. Атомарно арендует pending-запись с lease.
2. Добавляет задачу через существующий `JobService`.
3. После подтверждения фиксирует результат доставки.
4. После сбоя или истечения lease повторяет.

Падение между enqueue и отметкой доставки создаёт повторную задачу. Это ожидаемо: consumer должен быть идемпотентным. Такой dual-write разрыв и решает transactional outbox. [AWS: transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

BullMQ `jobId` уменьшает повторы, но удалённая задача больше не участвует в дедупликации; stalled-задача может выполняться повторно. Поэтому Redis не является долговечным журналом обработанных изменений. [Job IDs](https://docs.bullmq.io/guide/jobs/job-ids), [stalled jobs](https://docs.bullmq.io/guide/jobs/stalled).

В lockfile Bisky разрешены BullMQ `6.3.16` и Mongoose `9.11.2`. Context7 предоставил материалы BullMQ `6.3.11`; рассмотренные гарантии дополнительно сверены с текущей официальной документацией. Здесь не предлагаются непроверенные вызовы нового API.

**Consumer и recovery**

Для профиля задача означает «довести производное состояние до текущей ревизии», а не «навечно прибавить сигнал из события».

- Повтор задачи не увеличивает confidence.
- Позднее событие не откатывает профиль.
- Delete приводит к пересборке без записи.
- Старое `before` из аудита не возвращает удалённую оценку.
- Dispatcher lease восстанавливается после падения.
- Периодическая сверка `desiredRevision` и `builtRevision` восстанавливает пропущенное выполнение или потерю Redis.
- Метрики пересчитываются по текущим UserItem с проверкой актуальности входов.
- Необработанный outbox не удаляется по обычному TTL.
- Прямые обходные записи в БД должны быть запрещены контрактом записи либо выявляться reconciliation; одни change streams не дают вечного восстановления.

TTL-очистка skip — физическое удаление уже логически истёкшего исключения. Она не создаёт новый вкус и не должна быть условием снятия skip.

## 11. Выдача, видимость, повторы и лимит 25

Нужно различать:

| Этап                  | Что известно                                               |
| --------------------- | ---------------------------------------------------------- |
| `generated`           | Кандидат присутствует в snapshot                           |
| `authorized`          | Сервер разрешил конкретную выдачу после повторных проверок |
| `responseAttempted`   | Начата отправка                                            |
| `serverWriteFinished` | Сервер завершил запись ответа                              |
| `clientVisible`       | Клиент сообщил о выполнении критерия видимости             |
| `action`              | Получено самостоятельное пользовательское действие         |

HTTP 200 не доказывает получение и видимость.

Exposure содержит:

```text
exposureId, actorKey, item
sessionId, snapshotId
deliveryOrdinal
plannedPosition
actualPlacement

authorizedAt
responseAttemptedAt
serverWriteFinishedAt

firstClientVisibleReceivedAt
firstClientVisibleOccurredAt
visibilityDefinitionVersion

state
guardActive, guardUntil
retainUntil
```

Начальная гипотеза видимости: карточка активна, документ видим, минимум 50% основной области находится во viewport не менее секунды. Определение должно быть адаптировано к фактическому UI и отдельно версионировано.

Повтор visible callback не создаёт второй показ одной exposure. Действие может прийти без visible callback — это фиксируется, а видимость задним числом не выдумывается.

**Повторная проверка**

Перед авторизацией каждой карточки повторно проверяются:

- существование и удаление Item;
- глобальный ban;
- block и действующий skip;
- библиотечная политика;
- тип и явные фильтры;
- активный repeat guard.

Snapshot не является разрешением на последующую выдачу.

Для сериализации с пользовательскими изменениями авторизация и библиотечный writer должны использовать общий пользовательский revision/fence в короткой транзакции. Тогда block, зафиксированный раньше авторизации, будет учтён. Обычного чтения ревизии без записи/fence для такой гарантии недостаточно.

После авторизации всё ещё возможен block до физической доставки. Атомарно объединить сетевое получение и MongoDB-транзакцию нельзя. Клиент убирает известную ему заблокированную карточку; повторная доставка снова проверяет ограничения. Гарантия сервера относится к моменту авторизации, а не к отсутствию любых последующих изменений.

**Лимит Пика**

Для гарантии «не более 25 разных показанных произведений» сервер должен ограничивать число различных карточек, для которых уже начата потенциальная доставка, максимумом 25. Иначе потерянное visible-подтверждение и замена карточки могут привести к 26 фактическим показам.

- Retry возвращает ту же exposure и тот же Item.
- Потенциально отправленный слот не используется для другого Item.
- Кандидаты, отвергнутые до отправки, лимит не расходуют.
- Подтверждённая видимость считается отдельно.
- При неизвестной доставке возможна сессия с менее чем 25 подтверждёнными показами.

Это допустимый короткий подбор с причиной `deliveryUnknown`, а не повод рисковать превышением лимита или повторять карточки ради наполнения.

**Повторы между сессиями**

Стартовая гипотеза:

- подтверждённо видимый Item — cooldown 30 суток;
- авторизованный, но с неизвестной доставкой — короткая блокировка 24 часа;
- explicit skip — принятые 90 суток;
- block — бессрочно до изменения/удаления.

Точные интервалы требуют продуктового решения.

Partial unique `(actorKey,item)` при `guardActive=true` защищает параллельные выдачи. Истёкший guard снимается атомарно по `guardUntil`; TTL не используется как точный таймер освобождения.

MongoDB прямо указывает, что TTL-удаление может запаздывать. Поэтому eligibility всегда сравнивает время самостоятельно. [MongoDB TTL](https://www.mongodb.com/docs/manual/core/index-ttl/).

Атрибуция действия принимается только после проверки владельца exposure и совпадения Item. `plannedPosition` из snapshot и фактическое место отображения сохраняются раздельно.

## 12. Запросы, фон, кэш и исчерпание

На запросе:

- условия и актуальные ревизии;
- чтение пригодного профиля;
- ограниченный retrieval;
- пакетная eligibility по найденным ID;
- score и rerank;
- snapshot;
- перед выдачей — повторная проверка и exposure.

В фоне:

- представления Item и статистика IDF;
- профиль;
- метрики;
- outbox delivery/recovery;
- очистка guard и TTL;
- диагностика покрытия и stale-состояния.

**Доступ к нормализованным данным**

Существующие индексы пригодны для чтения признаков Item и поиска Item по одному Tag:

```text
ItemTag unique(item,tag)
ItemTag(tag,item)

ItemFeature unique(item,feature)
ItemFeature(feature,item)
```

Индекс `(feature,item)` не является индексом диапазона `value`. Для фактически используемых числовых фильтров потребуется либо проверенный `(feature,value,item)`, либо типизированная производная проекция.

В `ItemRecommendationData` можно хранить:

```text
item, type, representationVersion, inputHash
localSparse, sharedSparse
retrievalTagIds[]
validated filter fields
coverage/provenance
randomKey
```

`retrievalTagIds` — поле **новой проекции**, не Item.

Отдельные индексы нужны для tag retrieval, базового порядка, randomKey и конкретных востребованных range filters. Не следует сразу создавать индекс для каждой комбинации. План проверяется через `explain` на реальных запросах.

Compound multikey индекс нельзя строить одновременно по двум независимым массивам, например тегам и массиву франшиз. [Ограничения MongoDB multikey](https://www.mongodb.com/docs/manual/core/indexes/index-types/index-multikey/).

Большая библиотека не должна целиком передаваться в `$nin` на каждый retrieval. Достаточно пакетно проверять `UserItem` для найденных кандидатов по `(user,item)` и продолжать курсор.

Кэшируются производные представления и ограниченные candidate pools. Ключ персонального кэша включает пользователя, ревизии, условия и версии. Кэш не отменяет последнюю eligibility-проверку.

**Исчерпание**

Необходимо различать:

```text
batchLimitReached
retrievalBudgetReached
eligibleCatalogExhausted
deliveryUnknown
expired
```

`eligibleCatalogExhausted` разрешён только после полного обхода соответствующего конечного множества, а не после первых 1000 кандидатов.

При исчерпании бюджета retrieval:

- сохранить cursors;
- вернуть `searching`/продолжение либо честный `searchBudgetReached`;
- не утверждать, что подходящих произведений больше нет;
- не ослаблять фильтры;
- не повторять ранее выданное ради 25.

Неперсональный индексированный обход по типу обеспечивает путь к дальнейшему покрытию, даже если персональные пулы закончились.

## 13. Поведение в ключевых случаях

| Ситуация                             | Рекомендуемое поведение                                                                                       |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| Новый пользователь                   | Неперсональные допустимые кандидаты, diversity/exploration; taste не выдумывается                             |
| Guest                                | То же; история повторов привязана к ограниченному guest ID, с честной потерей после его сброса                |
| Только game-история, запрос movie    | Переносятся темы/стиль в movie-кандидатов; механики не участвуют                                              |
| Только movie-история, запрос game    | Аналогично; любовь к теме не подтверждает любовь к FPS или crafting                                           |
| История только других видеотипов     | Положительный shared-бонус с отдельным source provenance; тип кандидата сохраняется                           |
| Сезон и отдельный фильм              | Самостоятельные Item; номер сезона и эпизоды не входят в taste similarity                                     |
| Несколько сезонов одной франшизы     | Не раздувают независимую confidence                                                                           |
| Одна положительная оценка            | Слабая опора с confidence \(1/3\)                                                                             |
| Одна отрицательная                   | Небольшой локальный штраф очень близким объектам; межтипового штрафа нет                                      |
| Только отрицательные                 | Неперсональная основа, осторожные локальные штрафы; положительный вкус не достраивается                       |
| Мрачные игры, лёгкие фильмы          | Movie-positive работает локально; movie-negative конфликт ослабляет перенос мрачности из игр                  |
| Низкая оценка и favorite             | Сигнал временно не участвует, учитывается как конфликт                                                        |
| Только механики, без общих тем/стиля | Cross-бонус отсутствует                                                                                       |
| Нет метаданных                       | Карточка может участвовать в базовом пуле, если проходит фильтры; отсутствие признаков не считается качеством |
| Нет метрик/популярности              | Нейтральные `Q/Pop`; перенос продолжает работать                                                              |
| Сотни game-записей и один movie      | Source насыщается, типы не суммируются, target имеет собственные опоры и gate                                 |
| Изменение оценки / favorite          | Старый профиль инвалидируется и пересобирается из нового состояния                                            |
| Удаление UserItem                    | Сигнал исчезает; аудит его не воскрешает                                                                      |
| Skip истёк, TTL ещё не удалил запись | Skip больше не исключает Item; независимый cooldown проверяется отдельно                                      |
| Block/delete после snapshot          | Карточка отбрасывается перед авторизацией                                                                     |
| Retry после block                    | Старая карточка повторно не отправляется                                                                      |
| Повторная задача                     | Производное состояние сходится к текущему; счётчики не растут повторно                                        |
| Параллельные записи                  | Revision/fence и transaction retry; конфликт не превращается в потерянное обновление                          |
| Retrieval-бюджет исчерпан            | Продолжение поиска или честная причина остановки                                                              |
| Допустимых Item меньше 25            | Короткий подбор без повторов и ослабления условий                                                             |

Библиотечные правила завершённости игр и сезонов при этом не меняются. Рекомендатель не переопределяет `hasDefinedEnd`, `announced/ongoing`, единицы прогресса и независимость оценки.

## 14. Как проверить пользу

Проверку разделить на три независимых направления.

**Корректность**

Проверяемые инварианты будущей реализации:

- никакой score не обходит hard constraints;
- target type сохраняется;
- алиасы и несколько путей иерархии не увеличивают доказательство;
- `relevanceScore=0` не становится положительным присутствием;
- missing не превращается в ноль длительности или отрицательное качество;
- source-negative и skip не экспортируются;
- correction/delete дают тот же профиль, что чистая пересборка;
- retries не увеличивают поддержку и метрики;
- лимиты выдачи и идентичность exposure сохраняются;
- просроченный skip не зависит от TTL;
- устаревший snapshot не даёт права выдать заблокированный Item.

Это программа будущей проверки, не утверждение о выполненных тестах.

**Качество**

Нужны как минимум:

1. Неперсональный baseline.
2. Тот же local multi-interest без переноса.
3. Выбранный вариант с переносом.
4. Общий shared/private профиль без нескольких опор.
5. Semantic-embedding challenger.

Все варианты используют одинаковые eligibility и определения результата.

Разделить два эксперимента:

- **ranking-only:** одинаковый объединённый набор кандидатов, меняется score;
- **end-to-end:** меняются также retrieval-пулы.

Иначе улучшение retrieval будет ошибочно приписано формуле переноса.

Полезные ablations:

- убрать shared-бонус;
- убрать target-conflict gate;
- убрать ослабление по target confidence;
- заменить max на sum;
- убрать коррекцию зависимых сезонов/франшиз;
- один интерес против нескольких;
- убрать relations;
- убрать метрики;
- отдельно включить diversity и exploration.

Результаты считать по направлениям source→target, target-cold/warm, объёму пригодных сигналов, покрытию метаданных и фактическому доминирующему источнику.

**Продуктовые показатели**

- доля Пиков с сохранением;
- число уникальных видимых карточек до первого сохранения;
- время до сохранения/явного выбора;
- доля сессий без выбора и досрочных выходов;
- последующие оценки/favorite выбранных произведений с долей ответивших;
- coverage допустимого каталога;
- diversity по известным признакам;
- повторы Item и франшиз;
- доля неперсонального fallback;
- полнота цепочки authorized→attempted→visible→action.

Время среди успешных сессий нельзя оценивать без частоты неуспеха. `planned` означает интерес, но не последующую удовлетворённость. Нет player — нет `time-to-play` и измеренного досмотра.

**Исторические ограничения и bias**

Из нынешнего `UserItem.updatedAt` нельзя честно восстановить время отдельной прежней оценки: она перезаписывалась.

Для будущей оценки:

1. Зафиксировать исходное состояние на `T0`.
2. Использовать глобальное временное разделение.
3. На каждый момент брать только доступные тогда сигналы, метаданные, IDF, метрики и eligibility.
4. Подбирать параметры на следующем интервале.
5. Проверять на более позднем закрытом интервале.

Глобальная временная граница существенна: leave-last-one-out по пользователям может оставить будущее других пользователей в обучении. [Исследование data leakage](https://arxiv.org/pdf/2010.11060).

Дополнительно:

- отдельно оценивать выдачи без известных адаптаций и франшиз;
- группировать сезоны и дубли при разбиении и оценке неопределённости;
- не считать поиск известной экранизации доказательством общего переноса вкуса;
- контролировать будущие правки описаний, тегов и release-данных;
- не объявлять ненаблюдавшиеся Item отрицательными.

Случайно выбранный небольшой набор «негативов» способен менять относительный порядок алгоритмов. Предпочтительна оценка по полному допустимому набору; sampled-протокол нужно описывать отдельно. [On Sampled Metrics](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/).

Наблюдаемые реакции имеют selection и exposure bias; позиция и предыдущая выдача влияют на получение оценки. Один журнал не делает оценку несмещённой. Для IPS-подобных методов нужны пригодные вероятности назначения и достаточное покрытие политики. [Recommendations as Treatments](https://proceedings.mlr.press/v48/schnabel16.pdf).

**Небольшая аудитория**

Начать с проверок инвариантов и слепого парного сравнения выдач для разных реальных вкусов. Затем — наблюдаемые задачи выбора и prospective-сессии.

При A/B назначать вариант на пользователя, учитывать повторные сессии одного человека и оценивать неопределённость по пользователям. Размер исследования определяется базовой частотой результата, вариативностью, practically meaningful effect и нужной точностью. Универсального «N пользователей достаточно» нет.

При недостатке данных вывод: **эффект пока не установлен**.

**Latency**

Измерять отдельно retrieval, eligibility, загрузку признаков, score/rerank и persistence. Фиксировать число просмотренных строк и отвергнутых кандидатов, не только время ответа.

Предлагать ANN, отдельную vector DB или incremental rebuild следует после обнаружения конкретного bottleneck, а не по предполагаемому размеру проекта.

## 15. Embeddings и условия дальнейшего развития

Первый challenger — те же опоры и ограничения, дополненные предобученным текстовым каналом.

Практичный кандидат исследования: `intfloat/multilingual-e5-base`. Авторская карточка описывает многоязычное представление размерности 768, ограничение 512 токенов, правила prefix и нормализации. Эти свойства не означают качество именно cross-type рекомендаций Bisky. [Model card](https://huggingface.co/intfloat/multilingual-e5-base).

Эксперимент должен фиксировать:

```text
modelId + exact revision
embeddingInputVersion
выбранный язык описания
нормализацию и truncation
inputHash
output normalization
```

Вход — краткое содержательное описание и разрешённые признаки. Алиасы и ru/en не размножаются ради веса; locale интерфейса не считается предпочтением языка произведения. Названия и франшизы полезно отдельно исключить в ablation, чтобы выявить эффект узнавания бренда.

Cosine не смешивается с metadata-score как равная шкала. Сначала проверить cross-type retrieval и смысловую похожесть на размеченных примерах; затем подобрать ограниченный вес на отдельном интервале.

SBERT обосновывает независимо вычисляемые смысловые векторы, но его semantic similarity не является вероятностью удовлетворённости контентом. [Sentence-BERT](https://aclanthology.org/D19-1410/).

Отдельная vector DB не обязательна: возможен точный поиск по заранее рассчитанным векторам в памяти/батчах. Пригодность определяется измеренной стоимостью для реального каталога. [Sentence Transformers: semantic search](https://sbert.net/examples/sentence_transformer/applications/semantic-search/README.html).

| Следующее усложнение          | Условие перехода                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------------------ |
| Weighted relevanceScore       | Согласованная калибровка и улучшение относительно бинарного режима                         |
| Semantic embeddings           | Полезное расширение retrieval, улучшение выбора, приемлемая стоимость                      |
| Learned коэффициенты переноса | Достаточное покрытие направлений и стабильное преимущество вне периода подбора             |
| LightFM / hybrid              | Пригодные пересечения реакций и преимущество на temporal holdout                           |
| EMCDR/CoNet-подобный перенос  | Обоснованный выигрыш сверх content transfer и надёжные доменные представления              |
| Incremental profile           | Полная пересборка стала измеренным bottleneck, correction/delete сохраняют эквивалентность |
| ANN                           | Точный retrieval не укладывается в подтверждённые требования                               |
| Bandit                        | Определены reward, последствия exploration и наблюдаемые вероятности выбора                |

## 16. Версии, retention и пределы восстановимости

Версионировать независимо:

| Поле                            | Назначение                                     |
| ------------------------------- | ---------------------------------------------- |
| `algorithmVersion`              | Retrieval, scoring, rerank                     |
| `configHash`                    | Веса, caps, thresholds, budgets                |
| `profileFormatVersion`          | Схема профиля                                  |
| `builderVersion`                | Преобразование текущих источников в профиль    |
| `representationVersion`         | Словарь, IDF, hierarchy, правила признаков     |
| `transferPolicyVersion`         | Разрешённые признаки и направления             |
| `embeddingModelId/revision`     | Конкретные веса модели                         |
| `embeddingInputVersion`         | Подготовка текста                              |
| `eventSchemaVersion`            | Контракт события                               |
| `visibilityDefinitionVersion`   | Определение видимого показа                    |
| `metricDefinitionVersion`       | Семантика агрегатов                            |
| `libraryRevision/tasteRevision` | Изменение текущего пользовательского состояния |

Начальные сроки хранения:

| Данные                              | Предложение                                     |
| ----------------------------------- | ----------------------------------------------- |
| Current profile                     | Пока нужен; всегда пересобираем                 |
| Активные представления Item         | Всё время использования версии                  |
| Session                             | Serve до 24 часов, техническое хранение 7 суток |
| Snapshot                            | 30 суток                                        |
| Exposure                            | 180 суток                                       |
| Завершённые события/command receipt | 180 суток                                       |
| Pending outbox                      | Без TTL до разрешения доставки/ошибки           |

Это параметры для обсуждения, не установленные требования.

Exposure может пережить snapshot. После его удаления остаются ID/хеш, позиция и минимум attribution, но API не обещает доступность прежнего snapshot. Истёкшие ресурсы возвращают явный expired/gone.

Три разные гарантии:

1. **Current rebuild:** текущие UserItem + текущие версии каталога.
2. **Объяснение исторического решения:** сохранённый snapshot и provenance.
3. **Полное детерминированное воспроизведение:** точные кандидаты, профиль, представления, метрики, ограничения, seed, tie-break и исполняемая версия.

Для третьего недостаточно хешей. Нужны сохранённые входы либо checkpoint и полная последующая история. Обычный TTL-журнал такой гарантии не даёт. Расширенные экспериментальные артефакты можно сохранять отдельно в S3 для выбранных запусков.

## 17. Рекомендуемый порядок реализации

1. **Проверить реальные входы.** Наполнение семи типов, общие теги, нулевые relevanceScore, циклы, зависимые сезоны, полноту фильтров и топологию MongoDB. Не превращать неизвестное качество данных в предполагаемый факт.
2. **Согласовать контракт общего рекомендательного запроса и выдачи.** Сценарии, target type, фильтры, библиотечные политики, retry, visibility, причины окончания.
3. **Ввести единый writer, ревизии и journal/outbox.** Охватить create/update/delete, skip/block и будущие массовые пути.
4. **Сделать наблюдаемый неперсональный процесс.** Session, snapshot, exposure, hard constraints, repeat guard и лимит Пика.
5. **Построить версионные local/shared-представления.** Политика тегов, caps, IDF, hierarchy, coverage, retrieval-индексы.
6. **Заменить UserTasteProfile и реализовать полную пересборку.** Силы, конфликт rating/favorite, четыре набора опор, confidence, correction/delete.
7. **Включить local ranking и cross-type transfer как два сравнимых варианта.** На этом этапе первая реализация уже переносит вкус между типами.
8. **Добавить diversity/exploration с отдельной оценкой.**
9. **Включить Q/Pop только после надёжного пересчёта метрик.**
10. **Провести prospective-проверку и embedding challenger.** Усложнять только подтверждённо слабый участок.

Здесь нет отдельной movie-only продуктовой версии с переносом, отложенным на неопределённое будущее. Неперсональный и no-transfer варианты нужны как этапы проверки и контрольные алгоритмы.

## 18. Незакрытые материальные решения

Исследование определяет алгоритм, но следующие вопросы требуют продуктового решения или фактических данных:

- Где и как подтверждается полнота разметки для строгих отрицательных фильтров.
- Пригодность фактической общей разметки; минимальное наполнение для запуска каждого направления.
- Принятие правила конфликтующих rating/favorite и предлагаемого разбиения шкалы.
- Точные cooldown, visibility definition, окно идемпотентности и retention.
- Нужен ли смешанный режим в первом релизе; для target-type переноса он не требуется.
- Точные HTTP-контракты рекомендательного процесса; в этом отчёте они не объявляются согласованными.
- Реальная топология MongoDB и требования к транзакционному deployment.
- Нормализация SourceItem для сезонных источников: решать по примерам импорта; это не блокирует выбранную формулу.
- Приемлемые latency и стоимость пересборки на фактическом наполнении.
- Горизонт оценки последующей удовлетворённости, особенно для длинных сезонов и игр.

Ни одно из этих неизвестных не требует выдумывать обученную модель или большую аудиторию.

## 19. Алгоритм → данные → известное состояние → проверка

| Часть                       | Необходимые данные                             | Что есть / что неизвестно                                | Как проверить                                                      |
| --------------------------- | ---------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| Eligibility                 | Item, SourceItem/BannedItem, UserItem, фильтры | Контракты есть; полнота каталога неизвестна              | Отсутствие нарушений, гонки перед выдачей                          |
| Shared identity             | Канонические Tag, descriptions, aliases        | Предметное правило согласовано; наполнение неизвестно    | Аудит одинакового смысла на разных типах                           |
| Переносимость               | Версионная политика по ключам/ID               | Начальные темы/стили описаны; политики рекомендателя нет | Ложные переносы механик и одноимённых понятий                      |
| Local/shared representation | ItemTag, IDF, hierarchy, coverage              | Схемы есть; калибровки нет                               | Ноль score, caps, ветви, missing, coverage                         |
| Сила предпочтения           | Текущие rating/favorite                        | Поля есть                                                | Конфликты, correction/delete, слепая оценка                        |
| Multi-interest              | Seeds, опоры, единицы зависимости              | Источники предусмотрены; граф может быть неполным        | Разные интересы, unrepresented, зависимости сезонов                |
| Source confidence           | Текущая независимая поддержка опор             | Производного расчёта нет                                 | Насыщение, повтор команды, dominant source                         |
| Target confidence           | Пригодные target-сигналы                       | Доступны при наличии данных                              | Cold/warm, одна запись против сотен source                         |
| Cross-type бонус            | Shared-positive опоры и target-кандидаты       | Реализуется без собственной модели                       | No-transfer baseline по source→target                              |
| Target-conflict gate        | Shared-опоры target обоих знаков               | Требует builder                                          | Несовпадающий вкус типов, ablation gate                            |
| Локальный негатив           | Явные низкие оценки и подробные признаки       | Поля есть; покрытие неизвестно                           | Ошибочные широкие штрафы, единичная оценка                         |
| Relation retrieval          | Роли Relation, franchise Collection            | Разрешены между типами; наполнение неизвестно            | Отдельно адаптации и несвязанные произведения                      |
| Q/Pop                       | Текущие корректные агрегаты                    | Схема не доказывает пересчёт                             | Rebuild, delete/retry, ablation без метрик                         |
| Retrieval                   | Индексированная проекция, cursors              | Новая проекция нужна                                     | Recall, scanned rows, `explain`, budget vs exhaustion              |
| Diversity/exploration       | Похожесть, причины, seed                       | Требует реализации                                       | Покрытие, повторяемость, качество выбора                           |
| Snapshot                    | Версии, компоненты, причины                    | Новое хранение                                           | Объяснимость и честная граница воспроизведения                     |
| Exposure                    | Авторизация и клиентские callbacks             | Автоматической телеметрии нет                            | Retry, поздние callbacks, actual positions, лимит 25               |
| Journal/outbox              | Все библиотечные writers, транзакции           | Обёртка есть; сквозного процесса нет                     | Сбои Mongo/Redis, convergence, отсутствие потерь                   |
| Current rebuild             | Текущие источники и версии                     | Совместимо с моделью данных                              | Эквивалентность чистой пересборке                                  |
| Польза продукта             | Prospective выбор и дальнейшие реакции         | Пока не измерена                                         | Меньше предложений/времени до выбора без падения удовлетворённости |

**Решение, с которого рекомендую переходить к проектированию коллекций: local/shared multi-anchor профиль, положительный ограниченный перенос через общие канонические темы и стиль, target-specific gate, полная пересборка из текущих UserItem и отдельный надёжный процесс выдачи.** Оно определено достаточно конкретно для последовательной реализации; его качество предстоит установить измерениями.
