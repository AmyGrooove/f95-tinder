# Сущности API

Описание текущего содержимого `apps/api/src/entities`: 17 самостоятельных сущностей, отсортированные по алфавиту. Поля корневых и вложенных схем и состав AppModule сверены 24 октября 2026 года; UserItem и состав модулей обновлены 25 октября 2026 года; Item, UserTasteProfile и Tag — 26 октября 2026 года. Пользовательские операции описаны в [обзоре API](readme.md) и отдельных контрактах.

Документ описывает реализацию структур хранения. Целевые требования находятся в [основах проекта](../product/foundations.md), состав первого этапа — в [границах MVP](../product/mvpScope.md).

Для самостоятельных сущностей объявлены отдельные MongoDB-коллекции с такими же именами, `_id`, `createdAt`, `updatedAt`, свой модуль и репозиторий. Временные метки включаются общим плагином `DatabaseModule`. Все 17 модулей подключены в `AppModule`; каждый регистрирует свою модель и экспортирует репозиторий.

В колонке «Связи» стрелка обозначает ссылку на другую сущность, а вложенные структуры указаны отдельно. Ссылки на произведения содержат ObjectId сущности `Item`; тип произведения хранится в самом `Item`.

## Связи с объектами каталога

Relation.bonusMultiplier — конечное число >= 1, по умолчанию 1 (без усиления). Это множитель бонуса для роли рекомендуемого произведения относительно исходного. Применение в ранжировании ещё не реализовано; существующие документы БД не обновлялись.

Ключи Tag и Relation остаются строковыми camelCase-идентификаторами с уникальными индексами. ETagKey именует ключи, используемые правилами библиотеки. Фиксированные и диапазонные Tag.key должны соответствовать TAG_GROUP_RULES; год задаётся ключом releaseYear с целым числом, например releaseYear2026. Документная валидация Tag проверяет соответствие key/group; query/bulk-обновления не гарантируют эту межполевую проверку.

Согласованные начальные значения key по типам Item перечислены в [справочнике ключей каталога](../product/foundations/catalogKeys.md). Этот перечень является контрактом наполнения, а не подтверждением наличия определений и значений в рабочей БД.

Согласованное наполнение Tag находится в едином [tags.json](../../import/tags/tags.json): корневой массив объектов `{group,tags}`, 21 группа, 1184 тега и 216 parent-связей. Группа задана один раз для своего массива тегов; тег содержит `key`, `name:{ru,en}`, `description:{ru,en}`, `aliases:string[]`, `parents:string[]` с ключами непосредственных родителей. При будущей загрузке группу нужно передать в Tag, а ключи parents разрешить в ObjectId. Несколько родителей допустимы, дети и все предки отдельно не хранятся; синонимы хранятся в aliases. Иерархия должна быть без циклов; текущая схема не проверяет циклы всего графа или существование родителей. JSON не содержит `weightModifier=1`, поскольку это default модели. Наличие справочника не означает импорт или готовность импортёра; служебные исследовательские блоки ранее удалены без архивирования.

Текущая проверка `checkIsTagKeyAllowed` с `TAG_GROUP_RULES` принимает все 1184 записи, включая четыре диапазона `releaseYear` и все шесть значений `gameMode`. Отдельные годы подготовлены для 1990–2030; год 0 недопустим. Сохраняется расхождение по составу: production дополнительно определяет `gameLength` с `shortGame` и `longGame`, а согласованный справочник этой группы не содержит. При объединении значения не добавлялись; см. [границы словаря](../product/foundations/catalogKeys.md#расхождения-с-production).

Все произведения хранятся в коллекции `Item`. Поле `type` задаёт вид произведения; перечисление `EItemType` определяет `movie`, `series`, `animatedMovie`, `animatedSeries`, `animeSeries`, `animeMovie` и `game`. Отдельной сущности `Movie` и вложенной ссылки `ItemId` нет: `ItemCollection`, `ItemStats`, `TagItem`, `ItemRelationSide`, `UserItem` ссылаются непосредственно на `Item` через ObjectId.

Согласованные границы карточек описаны в [структуре данных](../product/foundations/dataStructure.md#произведение--item): один сезон — отдельный Item сериального типа, сезоны объединяются коллекцией `franchise`, DLC входят в Item игры. Существующие ссылки позволяют хранить такое объединение и независимые UserItem сезонов. Схема Item проверяет допустимость `type`, но сама по себе не обеспечивает разделение внешних записей по сезонам и исключение отдельных DLC; импорт пока не реализован.

Версии одной игры для разных платформ используют общий Item и общий UserItem пользователя. Перечень доступных платформ хранится через несколько TagItem с Tag группы `platform`, добавленной в ETagGroup. Значения платформ не дублируются в полях Item; схема не создаёт сами словарные записи платформ.

Название, описание, альтернативные названия и медиаматериалы хранятся в `Item`. Характеристики произведений задаются через теги и поля Item согласно [структуре данных](../product/foundations/dataStructure.md#компоненты-описания-произведения). `deletedAt` хранит дату пометки удаления; само наличие поля не реализует исключение произведения из поиска и рекомендаций.

ETagGroup содержит 22 группы: genre, subgenre, keyword, format, style, audience, country, originalLanguage, platform, duration, episodeDuration, episodeCount, mainStoryDuration, fullCompletionDuration, gameLength, releaseStatus, hasDefinedEnd, ageRestriction, releaseYear, gameMode, gameMechanic и perspective. Для возрастных классификаций предусмотрена единая ageRestriction, без отдельных групп ESRB/PEGI. Согласованные правила записаны в [TAG_GROUP_RULES](../../src/entities/tag/static/TAG_GROUP_RULES.ts): применимость к типам Item, количество тегов группы, участие во вкусе, согласование словарей, фиксированные значения и полуоткрытые диапазоны. Верхняя граница null означает отсутствие ограничения; время хранится в минутах. Неизвестное значение не создаёт тег; новые значения словаря требуют согласования. Tag использует справочник при документной проверке key/group; записи БД автоматически не создаются. Каждая запись ranges и фиксированного values содержит стабильный key, совпадающий с Tag.key; значения enum хранятся в TS как {key,value}. Наполнение, нормализация возраста, синхронизация производных тегов вынесены в [TODO](../TODO.md).

В схеме Item добавлены nullable-поля releaseDate (точная дата первого мирового выпуска) и ageRestriction (строковый EAgeRestriction: "0", "6", "12", "16", "18", "18++"), а также nullable-блоки movie, series и game. movie применим к movie/animatedMovie/animeMovie и содержит duration; series — к series/animatedSeries/animeSeries и содержит episodeCount, releasedEpisodeCount, episodeDuration и nextEpisodeAt; game — к game и содержит mainStoryDuration и fullCompletionDuration. Длительности — конечные положительные числа минут. episodeCount — положительное безопасное целое, releasedEpisodeCount — неотрицательное безопасное целое. Документная валидация проверяет применимость блоков и releasedEpisodeCount <= episodeCount при известных обоих значениях. releaseDate, ageRestriction, movie, series и game имеют default null и необязательны в TCreateItem. Поля внутри существующих блоков остаются необязательными без defaults; вложенные блоки не имеют _id/id/timestamps. Возрастная шкала TAG_GROUP_RULES использует тот же строковый EAgeRestriction; ключи тегов ageRestriction0/6/12/16/18 сохранены; ageRestriction18PlusPlus обозначает 18++ только для порнографических игр. Агрегации коллекций учитывают 18++ как 18 и преобразуют возраст в число для существующих числовых фильтров. Существующие BSON-документы не обновлялись. Query/bulk-обновления не гарантируют межполевую согласованность. HTTP-карточка возвращает поля Item напрямую; точные фильтры коллекций используют fields с разрешёнными путями EItemField. Feature и ItemFeature удалены из production-кода; миграция не выполнялась, поскольку данных ещё нет.

Время основной истории и полного прохождения хранится в Item.game.mainStoryDuration и fullCompletionDuration; оценки в минутах относятся к базовой игре без DLC. Диапазоны представлены отдельными Tag со стабильными ключами из TAG_GROUP_RULES.

Конечность игры задаётся тегами группы hasDefinedEnd. Прямой hasDefinedEndFalse запрещает новые действия завершения и процентного прогресса согласно [контракту библиотеки](librarySpec.md#попытки-просмотра); неизвестные метаданные не подменяются false.

Счётчики сезонов хранятся в Item.series; количество серий не описывает пользовательский прогресс.

Состояние выпуска задаётся тегами releaseStatus. Прямые releaseStatusAnnounced/releaseStatusOngoing запрещают новые действия полного завершения сезона; выпущенные, отменённые и неизвестные состояния позволяют ручное завершение.

## Подборки: границы хранения

`Collection.blocks` задаёт порядок блоков массивом. Каждый `CollectionBlock` имеет стабильный ObjectId `id` и тип group или text. Группа содержит необязательные title и description на RU/EN; группа без title отображается обычным списком. Текстовый блок содержит content на RU/EN с хотя бы одним непустым переводом. Поля группы запрещены у текстового блока, content запрещён у группы; appearance и сворачивание не предусмотрены. ID блоков уникальны внутри подборки. Произведения хранятся отдельно в ItemCollection с обязательным groupId и position внутри группы; массивы Item в блоках не хранятся.

Принадлежность определяется только по author: null означает подборку сайта, ObjectId — подборку указанного пользователя. Отдельного поля ownership нет. Теги самой подборки не хранятся. Все подборки имеют ручной состав и доступны для чтения без входа, пока не помечены удалёнными.

Проверки согласованности блоков выполняются при документной валидации. Общие query/bulk-операции не гарантируют межполевую согласованность: CollectionService.update проверяет итоговые блоки, ссылки новых/изменяемых включений и допустимость операций. Слой эндпоинтов также запрещает автору оценивать свою подборку. PATCH согласует удаление групп и перенос/удаление состава одной транзакцией с проверкой version; DELETE устанавливает deletedAt, сохраняя связи. Сам deletedAt не меняет generic delete/read. version начинается с 0, увеличивается при каждом успешном PATCH и входит в GET/POST/PATCH-ответы; старые документы без version поддерживаются как версия 0. Собственные теги, прогресс, рейтинг и счётчики подборки не вычисляются. Прежние groups и ItemCollection с groupId=null требуют отдельной миграции при наличии таких данных; миграция БД не выполнялась.

## Профиль вкуса: ограничения записи

Веса weight и explicitWeight конечны и ограничены [−1,+1], по умолчанию 0. count — неотрицательное безопасное целое число, по умолчанию 0. Явный ненулевой вес имеет приоритет над рассчитанным. Все типы контента используют общий профиль.

tagPreferences — единственный массив предпочтений: уникальные Tag, максимум 4096 записей. Диапазон длительности или количества представлен собственным Tag, поэтому отдельные featurePreferences, селекторы value/range и ссылки Feature отсутствуют. Участие группы во вкусе определяется TAG_GROUP_RULES.

Сеттеры полных массивов и документная pre-validation удаляют записи с count=0 и explicitWeight=0. Записи с count>0 сохраняются даже при нулевом weight; явные предпочтения сохраняются и без вычисляемой поддержки. Для записи следует заменять полный массив с валидаторами либо сохранять документ. Dotted/$push/$inc и доверенные bulk/pipeline-операции не обеспечивают все проверки массива и очистку. При пересборке writer должен сохранять актуальные explicitWeight, включая параллельные изменения.

Старые документы с profiles и вложенными score/samples требуют отдельного решения миграции/пересборки перед использованием новой схемы. Defaults новых полей Tag не являются миграцией сохранённых BSON-документов; lean/aggregate могут возвращать отсутствующие поля. Миграция БД и runtime-проверка не выполнялись.

## Отличия от целевых основ

- Структуры подборок представлены в `Collection`, `ItemCollection` и `UserCollection`. [Модуль эндпоинтов](../../src/endpoints/collection/collection.module.ts) реализует десять маршрутов [спецификации подборок](collectionsSpec.md#маршруты), включая чтение состава и фильтров. Общий список, поиск подборок и административное управление подборками сайта в этот модуль не входят. `UserItem` независимо хранит статус, оценку, избранное, заметку и попытки.
- `UserTasteProfile` хранит общий профиль только по тегам, включая диапазонные категории, включая явные пользовательские настройки. Структура соответствует [согласованному V1](../product/foundations/recommendations.md); вычисление весов, фоновые задачи и операции редактирования настроек ещё не реализованы.
- В `Item` нет embedding произведения. Необязательный embedding в `Tag` относится к тегу и не заменяет представление произведения.
- Сущности `Source` и `SourceItem` удалены из кода; `ItemBan.item` ссылается напрямую на `Item._id`.

Это различия текущих структур и целевых требований, а не перечень новых коллекций для автоматического создания. Способ реализации определяется отдельно.

В API реализованы 19 маршрутов [аккаунта и авторизации](accountAndAuthSpec.md), десять маршрутов подборок и семь маршрутов изменения [личной библиотеки](librarySpec.md#реализованные-операции-библиотеки). Kodik-клиент, сборщик страниц и сервис записи артефактов источников в S3 удалены; сценарий сбора фильмов и импорт не реализованы. Сущности рекомендаций пока не подключены к пользовательским операциям. Краткий статус находится в [навигаторе](../README.md).

Проверка была статической. Работающая база данных, фактическое создание индексов и поведение API не проверялись. Наличие схем и репозиториев само по себе не подтверждает реализацию соответствующего пользовательского процесса.

Сущность SourceItem удалена из кода. Проверка запретов в рекомендациях сопоставляет Item._id напрямую с ItemBan.item. Данные MongoDB не изменялись.
