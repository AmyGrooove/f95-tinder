# Сущности API

Описание текущего содержимого `apps/api/src/entities`: 22 самостоятельные сущности, отсортированные по алфавиту. Поля корневых и вложенных схем и состав AppModule сверены 24 октября 2026 года; UserItem и состав модулей обновлены 25 октября 2026 года. Пользовательские операции описаны в [обзоре API](readme.md) и отдельных контрактах.

Документ описывает реализацию структур хранения. Целевые требования находятся в [основах проекта](../product/foundations.md), состав первого этапа — в [границах MVP](../product/mvpScope.md).

Для самостоятельных сущностей объявлены отдельные MongoDB-коллекции с такими же именами, `_id`, `createdAt`, `updatedAt`, свой модуль и репозиторий. Временные метки включаются общим плагином `DatabaseModule`. Все 22 модуля подключены в `AppModule`; каждый регистрирует свою модель и экспортирует репозиторий.

В колонке «Связи» стрелка обозначает ссылку на другую сущность, а вложенные структуры указаны отдельно. Ссылки на произведения содержат ObjectId сущности `Item`; тип произведения хранится в самом `Item`.

## Связи с объектами каталога

Ключи справочников Tag, Feature, ItemRelationRole и Source сохраняют тип string и ограничения формата/уникальности. Известные программной логике ключи вынесены в EFeatureKey (hasDefinedEnd, releaseStatus) и ESourceKey (kodik). Эти enum используются в сервисах и не ограничивают состав записей в БД.

Все произведения хранятся в коллекции `Item`. Поле `type` задаёт вид произведения; перечисление `EItemType` определяет `movie`, `series`, `animatedMovie`, `animatedSeries`, `animeSeries`, `animeMovie` и `game`. Отдельной сущности `Movie` и вложенной ссылки `ItemId` нет: `CollectionItem`, `ItemFeature`, `ItemMetric`, `ItemTag`, `RelationSide`, `SourceItem`, `UserItem` ссылаются непосредственно на `Item` через ObjectId.

Согласованные границы карточек описаны в [структуре данных](../product/foundations/dataStructure.md#произведение--item): один сезон — отдельный Item сериального типа, сезоны объединяются коллекцией `franchise`, DLC входят в Item игры. Существующие ссылки позволяют хранить такое объединение и независимые UserItem сезонов. Схема Item проверяет допустимость `type`, но сама по себе не обеспечивает разделение внешних записей по сезонам и исключение отдельных DLC; импорт пока не реализован.

Версии одной игры для разных платформ используют общий Item и общий UserItem пользователя. Перечень доступных платформ хранится через несколько ItemTag с Tag группы `platform`, добавленной в ETagGroup. Значения платформ не дублируются в полях Item или ItemFeature; схема не создаёт сами словарные записи платформ.

Название, описание, альтернативные названия и медиаматериалы хранятся в `Item`. Характеристики произведений задаются через теги и features согласно [структуре данных](../product/foundations/dataStructure.md#компоненты-описания-произведения). `deletedAt` хранит дату пометки удаления; само наличие поля не реализует исключение произведения из поиска и рекомендаций.

Для игр согласованы определения Feature с ключами `mainStoryDuration` и `completionistDuration`: ориентировочное время основной истории и полного прохождения базовой игры без DLC соответственно. Оба имеют group=`technical`, valueType=`number`, unit=`minute`; значения хранятся отдельно в ItemFeature. Существующие схемы поддерживают такие определения без новых полей. Словарные записи и значения в рабочей БД не создавались и не проверялись.

Feature `hasDefinedEnd` имеет valueType=`boolean`, group=`null`, unit=`null`; его ItemFeature хранит наличие конечного прохождения базовой игры. Отсутствие записи означает неизвестность. UserItemService при известном false ограничивает новые действия завершения и процентного прогресса для game согласно [контракту библиотеки](librarySpec.md#попытки-просмотра). Общие схемы Feature/ItemFeature не требуют новых полей; запись определения и значения в рабочей БД не создавались и не проверялись.

Для сезонов `series`, `animatedSeries` и `animeSeries` согласованы `episodeCount` (общее число серий, group=`technical`) и `releasedEpisodeCount` (число вышедших серий, group=`release`). Оба определения имеют valueType=`number`, unit=`null`. Правила целочисленности, известных/неизвестных значений и согласованности счётчиков описаны в [структуре данных](../product/foundations/dataStructure.md#features); общая схема ItemFeature сама по себе их не проверяет. Словарные записи и значения этих счётчиков в рабочей БД не создавались и не проверялись.

Feature releaseStatus имеет group=`release`, valueType=`string`, unit=`null`; для сезонов определены announced, ongoing, released и cancelled. UserItemService блокирует новые действия полного завершения сезона только при известных announced/ongoing. Неизвестное состояние не запрещает ручной completed. Это проверка сервиса, а не enum-ограничение общей схемы Feature/ItemFeature; см. [контракт библиотеки](librarySpec.md#попытки-просмотра).

## Подборки: границы хранения

`Collection.blocks` задаёт порядок блоков массивом. Каждый `CollectionBlock` имеет стабильный ObjectId `id` и тип group или text. Группа содержит необязательные title и description на RU/EN; группа без title отображается обычным списком. Текстовый блок содержит content на RU/EN с хотя бы одним непустым переводом. Поля группы запрещены у текстового блока, content запрещён у группы; appearance и сворачивание не предусмотрены. ID блоков уникальны внутри подборки. Произведения хранятся отдельно в CollectionItem с обязательным groupId и position внутри группы; массивы Item в блоках не хранятся.

Принадлежность определяется только по author: null означает подборку сайта, ObjectId — подборку указанного пользователя. Отдельного поля ownership нет. Теги самой подборки не хранятся. Все подборки имеют ручной состав и доступны для чтения без входа, пока не помечены удалёнными.

Проверки согласованности блоков выполняются при документной валидации. Общие query/bulk-операции не гарантируют межполевую согласованность: CollectionService.update проверяет итоговые блоки, ссылки новых/изменяемых включений и допустимость операций. Слой эндпоинтов также запрещает автору оценивать свою подборку. PATCH согласует удаление групп и перенос/удаление состава одной транзакцией с проверкой version; DELETE устанавливает deletedAt, сохраняя связи. Сам deletedAt не меняет generic delete/read. version начинается с 0, увеличивается при каждом успешном PATCH и входит в GET/POST/PATCH-ответы; старые документы без version поддерживаются как версия 0. Собственные теги, прогресс, рейтинг и счётчики подборки не вычисляются. Прежние groups и CollectionItem с groupId=null требуют отдельной миграции при наличии таких данных; миграция БД не выполнялась.

## Отличия от целевых основ

- Структуры подборок представлены в `Collection`, `CollectionItem` и `UserCollection`. [Модуль эндпоинтов](../../src/endpoints/collection/collection.module.ts) реализует десять маршрутов [спецификации подборок](collectionsSpec.md#маршруты), включая чтение состава и фильтров. Общий список, поиск подборок и административное управление подборками сайта в этот модуль не входят. `UserItem` независимо хранит статус, оценку, избранное, заметку и попытки.
- `UserTasteProfile` хранит один документ на пользователя с фиксированными профилями по типам Item. Версия механизма рекомендаций в этой структуре не хранится; разные представления профиля по версиям ещё не отражены.
- В `Item` нет embedding произведения. Необязательный embedding в `Tag` относится к тегу и не заменяет представление произведения.
- `Source` и `SourceItem` описывают источники и внешние идентификаторы. Выгрузки в S3, пакеты AI-обработки, согласования и отчёты не представлены в этих корневых схемах.

Это различия текущих структур и целевых требований, а не перечень новых коллекций для автоматического создания. Способ реализации определяется отдельно.

В API реализованы 19 маршрутов [аккаунта и авторизации](accountAndAuthSpec.md), десять маршрутов подборок и семь маршрутов изменения [личной библиотеки](librarySpec.md#реализованные-операции-библиотеки). Для источников есть Kodik-клиент, сборщик страниц и запись артефактов в S3; сценарий сбора фильмов и импорт ещё не реализованы. Сущности рекомендаций пока не подключены к пользовательским операциям. Краткий статус находится в [навигаторе](../README.md).

Проверка была статической. Работающая база данных, фактическое создание индексов и поведение API не проверялись. Наличие схем и репозиториев само по себе не подтверждает реализацию соответствующего пользовательского процесса.
