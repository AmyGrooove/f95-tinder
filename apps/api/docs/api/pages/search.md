## Реализованный общий поиск

[SearchController](../../../src/endpoints/search/controllers/search.controller.ts) и [SiteSearchService](../../../src/endpoints/search/services/siteSearch.service.ts) подключены через SearchEndpointModule в AppModule.

`QUERY /search` принимает JSON-объект и возвращает `Accept-Query: application/json`, `Cache-Control: no-store`. К маршруту применяются общая защита от частых запросов и CSRF-проверка QUERY.

```json
{
  "search": "matrix",
  "page": 1,
  "limit": 10,
  "items": {
    "types": ["movie"],
    "fields": [{ "field": "releaseDate", "min": "1990-01-01" }],
    "sort": "rating"
  },
  "collections": { "sort": "updatedAt", "direction": "desc" }
}
```

Параметры:

- `search`: обязательная строка, 1–200 символов после удаления пробелов по краям; пустой запрос не открывает каталог
- `page`: целое число от 1, по умолчанию 1; одна и та же страница применяется независимо к трём группам
- `limit`: целое число от 1 до 50, по умолчанию 10, на каждую группу
- Фильтры и обычные сортировки применяются в Meilisearch ко всему индексу до пагинации. 10000 ограничивает глубину доступных страниц после фильтров и ранжирования, а не исходный набор кандидатов; смещение `(page - 1) * limit >= 10000` отклоняется с 400
- Неизвестные поля тела отклоняются глобальным ValidationPipe; page и limit передаются JSON-числами

Условия групп необязательны и независимы:

| Группа        | Фильтры                                                                                             | Значения `sort`                               |
| ------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `items`       | `types: EItemType[]`, `tagIds: ObjectId[]`, `fields: [{field,min?,max?}]`, `ratingMin`, `ratingMax` | `relevance`, `title`, `releaseDate`, `rating` |
| `users`       | Нет                                                                                                 | `relevance`, `username`, `displayName`        |
| `collections` | `types: ECollectionType[]`, `authorIds: ObjectId[]`                                                 | `relevance`, `title`, `updatedAt`             |

`tagIds` требует совпадения всех выбранных существующих тегов, без неявного добавления предков. `types` и `authorIds` допускают любое из выбранных значений. `authorIds` содержит ID создателей подборок, а не их имена; подборки сайта с author=null при таком фильтре не проходят. Массивы непустые и без повторов; максимум 100 tagIds/authorIds.

`fields.field` использует EItemField: releaseDate, ageRestriction, movie.duration, series.episodeCount, series.releasedEpisodeCount, series.episodeDuration, series.nextEpisodeAt, game.mainStoryDuration, game.fullCompletionDuration. Для каждого поля нужна хотя бы одна включительная граница; одно поле нельзя передавать повторно. Числовые границы — конечные JSON-числа. Даты — YYYY-MM-DD или строгий ISO 8601 со временем и часовым поясом. Границы min > max и неподходящие типы дают 400. Возраст 18++ для диапазона трактуется как 18. Неизвестное значение не удовлетворяет диапазону. Фильтр общей оценки использует ItemStats.ratingAverage от 1 до 10, неизвестные оценки исключаются.

Каждая группа принимает `direction: asc|desc`. По умолчанию relevance/rating/releaseDate/updatedAt идут по убыванию, title/username/displayName — по возрастанию. `items.language` и `collections.language` принимают ru/en (по умолчанию ru): если название на выбранном языке отсутствует, используется второй язык. В индекс записываются отдельные sortTitle.ru/en с резервным переводом, обрезкой пробелов и приведением к нижнему регистру, а также sortUsername/sortDisplayName. Обычный порядок определяется строковой сортировкой Meilisearch; MongoDB collation для него не используется. Неизвестные даты и оценки остаются в конце при обоих направлениях, равенства разрешаются по ID.

Поиск публичный: авторизация не требуется, cookie не проверяется. Персональная сортировка не поддерживается; `items.sort=recommended` отклоняется с 400 как некорректное значение. В ответе не раскрываются личные состояния.

Обратная релевантность (`sort=relevance`, `direction=asc`) обходит весь индекс пакетами по 500 ID через documents API и текстовые запросы с фильтрами и id IN и выбирает страницу по _rankingScore по возрастанию, затем ID. Обычная релевантность по убыванию обслуживается одним поисковым запросом. Полный проход обратной релевантности может быть значительно дороже обычной выдачи; исторические измерения изолированного стенда сохранены в [отчёте](../../../search-audit-20261028/REPORT.md), текущий контракт после удаления персональной сортировки на стенде не проверялся. Отдельных фоновых пользовательских задач, кэша результатов и новых HTTP-операций нет.

Защита от опечаток явно включена для всех трёх индексов: с 5 символов допускается одна ошибка, с 9 — две. Это нечёткое сопоставление Meilisearch, без отдельного исправления раскладки или транслитерации.

Ответ 200:

```json
{
  "items": { "hits": [], "estimatedTotalHits": 0 },
  "users": { "hits": [], "estimatedTotalHits": 0 },
  "collections": { "hits": [], "estimatedTotalHits": 0 }
}
```

Поля карточек:

| Группа               | Поля                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------ |
| `items.hits[]`       | `id`, `type`, `title: {ru,en}`, `media: [{src,language,type}]`                             |
| `users.hits[]`       | `id`, `username`, `displayName`, `avatarUrl: string \| null`                               |
| `collections.hits[]` | `id`, `type`, `title: {ru,en}`, `media: [{src,language,type}]`, `authorId: string \| null` |

Поиск выполняется через три индекса Meilisearch. У Item участвуют все типы, названия RU/EN, aliases и описания RU/EN; у коллекций — названия и описания RU/EN; у пользователей — username/displayName. Порядок полей: название → aliases → описание, username → displayName. Порядок правил ранжирования: sort → words → typo → attribute → proximity → exactness; sort активен только при явной сортировке, иначе сохраняется текстовый порядок; при равенстве предшествующих правил совпадение в более приоритетном поле выше. Нулевые совпадения дают пустую группу. Описания, aliases, оценки и личное состояние в карточку не входят. Личное скрытие коллекции не исключает её из общего поиска.

Ошибки возвращаются в существующем формате `{error:{code,message,details,requestId}}`: 400 — некорректное тело, фильтры или недоступная глубина страницы; 403 — CSRF-проверка; 429 — ограничение запросов; 503 — первоначальная индексация ещё не завершена либо недоступна зависимость поиска. Частичная успешная выдача при ошибке одной категории не возвращается.

Первоначальное заполнение и последующая синхронизация выполняются фоновой задачей BullMQ, запускаемой при старте и раз в минуту, с дедупликацией и повторными попытками. Последующие запуски индексируют изменения по updatedAt с минутным перекрытием; мягко и физически удалённые записи удаляются из индексов при сверке ID. Item обновляется полным проходом при каждом запуске, чтобы изменения TagItem/Tag и ItemStats попадали в фильтры и сортировки без изменения updatedAt самого Item; User и Collection сохраняют обновление по собственному updatedAt. Карточки выбранной страницы загружаются из MongoDB в порядке поисковых ID; отсутствующие и удалённые записи пропускаются, что может временно укоротить страницу. estimatedTotalHits обычного поиска — оценка Meilisearch после фильтров; для обратной релевантности это подсчитанное число обработанных совпадений. Фильтры и обычные сортировки используют состояние последней успешной индексации, поэтому карточка уже может содержать более новые данные. При очереди или ошибке задержка обновления текстового индекса превышает минуту. Между запросами и пакетами нет атомарного снимка индекса/каталога; параллельная индексация, удаления и изменения каталога могут менять состав и порядок. Для неизменного индекса весь набор совпадений обрабатывается без окна кандидатов.

## Уточнить

Для будущего каталога без запроса остаются иерархия тегов и сочетания внутри групп, формула популярности, справочники фильтров и расширение карточок оценками и личным состоянием. Контракт текстового поиска определён выше.

Анонсы по умолчанию участвуют в обычном каталоге. Личные статусы и «Не рекомендовать» не исключают произведения без явно выбранного условия. Скрытые коллекции также доступны по умолчанию, пользовательские коллекции участвуют в прямом поиске без условия допуска на главную. В рекомендательном режиме исключение «Не рекомендовать» обязательно.

## Проверка результата

Проверять поиск по альтернативным названиям, совместное применение условий и пагинации, различия обычного и рекомендательного режимов, гостевые/личные поля, отсутствие нуля вместо неизвестной оценки. Сохранение query в URL страницы — задача клиента. Runtime-проверки не выполнялись.
