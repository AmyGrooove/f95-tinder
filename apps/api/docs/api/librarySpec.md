# Личная библиотека: спецификация API

Контракт UserItem обновлён 25 октября 2026 года по контроллеру, сервису и схемам. Реализованы семь операций изменения и пакетное краткое чтение QUERY /userItems по ID UserItem. Чтения по ID Item, полного чтения записи и выдачи библиотеки пока нет. Контракт и TTL проверены локальными тестами; миграция существующей БД не выполнялась.

Связанные документы: [принципы библиотеки](../product/foundations/library.md), [сущности](entities.md), [устройство API](readme.md).

## Реализованные операции библиотеки

| Метод  | Путь                                 | Назначение                                                                         |
| ------ | ------------------------------------ | ---------------------------------------------------------------------------------- |
| QUERY  | `/userItems`                         | Краткие собственные записи по JSON-телу { ids }, где ids — ID UserItem             |
| POST   | `/userItems`                         | Создать запись библиотеки: `{ itemId, status }`, только пять библиотечных статусов |
| POST   | `/userItems/skip`                    | Создать временное исключение: `{ itemId }`                                         |
| POST   | `/userItems/block`                   | Создать постоянное исключение: `{ itemId }`                                        |
| PATCH  | `/userItems/:id`                     | Атомарно изменить переданные `status`, `rating`, `isFavorite`, `note`              |
| DELETE | `/userItems/:id`                     | Удалить личную запись вместе с исключением и всеми сохранёнными данными            |
| POST   | `/userItems/:id/attempts`            | Добавить попытку просмотра                                                         |
| PATCH  | `/userItems/:id/attempts/:attemptId` | Изменить переданные поля попытки                                                   |

`:id` — ID UserItem, не Item. Все операции требуют cookie `__Host-accessToken`, действующий JWT, активную серверную сессию своего пользователя и существующий аккаунт; иначе 401. Для операций изменения чужая или отсутствующая запись возвращает 404. Создание требует существующий неудалённый Item; недоступное произведение даёт 404, существующая пара пользователь/Item — 409. POST skip/block не изменяют существующую запись и не продлевают пропуск. Просроченный skipped перед созданием новой записи удаляется условным запросом. Существующие записи доступны для редактирования после мягкого удаления Item.

POST возвращает 201, PATCH — 200; ответ содержит `id`, `itemId`, `status`, nullable `expiresAt`, `rating`, `isFavorite`, `note`, `attempts`, `createdAt`, `updatedAt`. Даты передаются строками ISO 8601. DELETE возвращает 204 без тела и не меняет членство в подборках. Все ответы имеют Cache-Control:no-store.

## Пакетное краткое чтение

QUERY /userItems принимает Content-Type: application/json и тело { ids: string[] }: от 1 до 60 уникальных ObjectId записей UserItem. ID произведений не используются для поиска записей. Регистр hex-символов не влияет на поиск или проверку дубликатов. Пустой список, повторяющиеся/некорректные ID, неверные типы и неизвестные поля дают 400.

Ответ 200 — массив { id, itemId, rating, isFavorite, status } в порядке запроса. Чужие, отсутствующие и просроченные skipped пропускаются одинаково, без 404 и без null-заглушек. Если ничего не найдено, возвращается []. Сохраняются доступные записи после мягкого удаления Item; наличие Item не проверяется. Заметка, попытки, срок и служебные даты не загружаются и не возвращаются. Пагинации нет; чтение не создаёт, не обновляет и не удаляет записи. Ответ содержит Cache-Control: no-store и Accept-Query: application/json.

Недействительный JWT, сессия или отсутствующий аккаунт дают 401; применяются общие throttling и CSRF-проверки origin. CORS разрешает QUERY в дополнение к прежним методам. Работа через внешний reverse proxy и браузер отдельно не проверена.

## Статусы и исключения

Пять библиотечных статусов: `planned`, `inProgress`, `onHold`, `completed`, `dropped`. `skipped` и `blocked` — дополнительные взаимоисключающие состояния той же записи, вне обычной библиотеки и распределения её пяти статусов. Статуса none нет; отсутствие UserItem означает отсутствие личной записи. Показ произведения сам по себе запись не создаёт.

- `skipped`: временное исключение из рекомендаций на 90 суток. Допустимы только `rating=null`, `isFavorite=false`, `note=null`, `attempts=[]`; несовместимое конечное состояние возвращает 409. Добавление личных данных без смены статуса также запрещено.
- `blocked`: постоянное исключение до явного изменения или удаления пользователем. Прежние оценка, избранное, заметка и попытки сохраняются; автоматического срока удаления нет.
- PATCH принимает все семь статусов. При переходе в skipped записывается `expiresAt=сейчас+90 суток`; повтор того же статуса не продлевает срок. При переходе в любой другой статус `expiresAt` очищается.

Для `expiresAt` объявлен TTL-индекс с `expireAfterSeconds:0` и фильтром `status=skipped`. MongoDB удаляет документы в фоне, а не точно в момент истечения. Просроченная запись уже не возвращается кратким QUERY-чтением, не редактируется через PATCH (404) и не мешает созданию новой записи. DELETE может удалить её до TTL-очистки. Библиотечные и blocked-записи TTL не затрагивает. Выдача рекомендаций ещё не реализована; её потребители должны исключать blocked и только непросроченные skipped.

## Изменение личных полей

PATCH `/userItems/:id` принимает одно или несколько полей `status`, `rating`, `isFavorite`, `note`; пропущенные сохраняются. Пустое тело, неизвестные поля и null в status/isFavorite отклоняются. Оценка — целое число 1–10 либо null для очистки; заметка — строка либо null, пробелы по краям удаляются, пустая строка становится null. Проверяется итоговое состояние всей записи: совместимую очистку личных полей и переход в skipped можно передать одним PATCH, но попытки этим маршрутом удалить нельзя. Отдельных PATCH-маршрутов личных полей нет; владельца, itemId, expiresAt и массив attempts через него менять нельзя.

## Попытки просмотра

Попытка содержит `id`, `isCompleted`, nullable `progress`, `unit`, nullable `startedAt`, nullable `completedAt`. Собственного status больше нет. `isCompleted=true` означает полный просмотр, а не просто прекращение попытки. По умолчанию false. Дата завершения не предшествует началу; даты могут быть неизвестны и не выставляются автоматически.

`progress` — неотрицательное безопасное целое число либо null. `unit` — minute (по умолчанию), percent или episode; для percent допустимы только 0–100. В episode прогресс означает число полностью просмотренных серий сезона. Смена unit не конвертирует прогресс; валидируется итоговая пара unit/progress. Полный просмотр не выводится автоматически из прогресса и не устанавливает его автоматически.

Для конечных игр критерий прохождения и процентный прогресс определяет пользователь. completed и isCompleted=true не требуют progress=100; отдельной цели или режима прохождения в запросе и схеме нет. Эти отметки не подтверждают прохождение всего необязательного контента. Текущая реализация уже сохраняет независимость прогресса и завершённости.

Единица episode допустима только для Item типов series, animatedSeries и animeSeries. Если итоговая история содержит такую попытку, сервис проверяет тип Item в той же транзакции; отсутствие Item или другой тип дают 400. Мягко удалённый сезон остаётся допустимым. Общая схема попытки разрешает единицу episode, но междокументное ограничение типа проверяет сервис. Значения episodeCount и releasedEpisodeCount для ограничения личного прогресса сейчас не загружаются. Например, `{ "unit": "episode", "progress": 5 }` задаёт пять полностью просмотренных серий; это не номер последней открытой серии.

Для Item типа game с прямым тегом `hasDefinedEndFalse` группы `hasDefinedEnd` возвращается 409 при создании записи со статусом completed, явной установке этого статуса через PATCH, создании/установке isCompleted=true у попытки, создании/установке unit=percent или вводе числового progress в существующую процентную попытку. Проверка использует Feature с ключом hasDefinedEnd и valueType=boolean и ItemTag со значением false. Отсутствие определения/значения не приравнивается к false; для других типов Item это ограничение не применяется.

Для сезонов типов series, animatedSeries и animeSeries с прямым тегом releaseStatusAnnounced или releaseStatusOngoing группы releaseStatus возвращается 409 при создании UserItem со статусом completed, явной установке completed через PATCH и создании/установке isCompleted=true у попытки. Проверка использует Feature с ключом releaseStatus, valueType=string и ItemFeature соответствующего сезона. Отсутствующее определение/значение, нераспознанный статус, released и cancelled не блокируют ручную отметку завершения. Числа серий не используются для вывода состояния выпуска; процентный прогресс этим правилом не ограничивается. Другие статусы UserItem сохраняют прежние условия применимости.

Проверки в PATCH и POST attempts выполняются внутри существующей транзакции; при создании UserItem проверка предшествует удалению просроченного skipped и вставке новой записи. Старые значения не очищаются автоматически. Изменение оценки, заметки, других статусов или дат попытки, сброс isCompleted в false, очистка progress через null и переход с percent на minute не блокируются этим правилом. Обычные ограничения статусов и попыток сохраняются, включая запрет новых попыток в planned/blocked.

Для `inProgress`, `onHold`, `completed`, `dropped` нужна хотя бы одна попытка. При создании записи или установке такого статуса, если попыток нет, создаётся первая с неизвестными датами и прогрессом. При установке completed последняя по порядку массива попытка получает isCompleted=true. Смена на другой статус не сбрасывает завершённость прежних попыток. Если история уже есть, смена статуса не создаёт новую попытку.

В planned и blocked существующая история сохраняется и редактируется, но добавление новой попытки запрещено (409). В skipped история запрещена целиком. Повторный просмотр добавляется через POST attempts после выбора одного из четырёх статусов, допускающих попытки.

POST attempts принимает необязательные `isCompleted`, `progress`, `unit`, `startedAt`, `completedAt`; PATCH — любое непустое подмножество этих полей. Nullable только progress и даты. Создание и редактирование попыток не меняют статус UserItem. Порядок массива — порядок добавления; изменение дат не переупорядочивает историю. Массив целиком не заменяется; удаления отдельной попытки в текущем API нет.

Все PATCH и создание попытки читают и обновляют запись в MongoTransactionService с проверкой владельца. Схема процента проверяет верхнюю границу дополнительно к endpoint-валидации. Полные правила сочетания статуса и истории контролируются сервисом, а не MongoDB-ограничением.

## Совместимость и проверка

Поддержка единицы episode, ограничений hasDefinedEnd и проверки releaseStatus сезона добавлена после проверок, перечисленных ниже. Новый запуск unit- и интеграционных тестов для них не выполнялся; исторические результаты не подтверждают новое поведение.

QUERY /userItems проверен локально: 116 unit-проверок UserItemController (включая генерацию описания QUERY в OpenAPI 3.2) и 85 HTTP-интеграционных проверок UserItemController на одноразовых MongoDB 8.0.17 и Redis 8.2.3. Проверены краткий ответ, порядок ID, доступ владельца, отсутствующие/чужие записи, просроченный skipped, неизменность данных, авторизация и CORS/CSRF. Браузер, Swagger UI и внешний reverse proxy не проверялись.

25 октября 2026 года прошли 103 проверки UserItemController с подменённым сервисом и 118 HTTP-интеграционных тестов UserItemController и CollectionReadController на одноразовых MongoDB 8.0.17 и Redis 8.2.3. Проверены создание исключений, конфликты, ограничения skipped, срок и фактическое TTL-удаление, сохранность blocked/библиотеки, попытки и проценты, авторизация, откат, конкурентные изменения и личные фильтры карточек коллекций. TypeScript-проверка с тестами и ESLint изменённых тестов прошли. Это локальная проверка, а не подтверждение состояния рабочей БД или её миграции.

Реализация находится в [модуле эндпоинтов](../../src/endpoints/userItem/userItem.module.ts). После успешной записи или commit эти операции ставят через BullMQ пересчёт TasteProfile только для тегов затронутого Item. Для update и попыток задача ставится только при фактическом изменении оценки, избранного, участия в skipped или числа завершённых попыток с ограничением до трёх; заметка, даты и прогресс сами по себе пересчёт не запускают. Завершённые попытки дают +0,1 каждая, максимум +0,3 к вкладу Item и не более +1 суммарно; при оценке 1–4 бонус не применяется; подробности — в [системе рекомендаций](../product/foundations/recommendations.md#пересчёт). При фактическом изменении rating или удалении UserItem с оценкой дополнительно ставится пересчёт ItemMetric.ratingAverage и ratingsCount только для затронутого Item. Повторные задачи объединяются по Item; изменение во время расчёта сохраняет один повторный запуск. Удаление последней оценки сбрасывает значения в null и 0. Создание UserItem не задаёт оценку; изменения остальных полей и удаление записи без оценки не запускают пересчёт рейтинга. Периодический пересчёт удалён. Ошибка постановки передаётся вызывающему коду, хотя изменение библиотеки уже сохранено; атомарной доставки между MongoDB и Redis и автоматического восстановления пропущенных событий нет. Остальные поля ItemMetric и журнал действий этими операциями не пересчитываются. UserRecommendationState удалён из исходников и AppModule; учёт показов сейчас не реализуется.

Перед использованием существующей БД нужно проверить старые документы: перенести `attempt.status=completed` в `isCompleted=true`, остальные прежние статусы — в false, затем удалить attempt.status. Записи без обязательной попытки необходимо согласовать с новым инвариантом. Если в прежней UserRecommendationState есть данные, отдельно определить перенос исключений и временных пропусков; активное исключение соответствует blocked, но конфликт с существующей библиотечной записью требует осознанного выбора, поскольку теперь статус один. Исходники не удаляют старую коллекцию в БД и не выполняют миграции автоматически. Проверить применение TTL-индекса отдельно; наличие объявления не доказывает его развёртывание.
