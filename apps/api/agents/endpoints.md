# Endpoint implementation routes

Read when changing HTTP use cases under `src/endpoints`. The [API overview](../public/docs/api/readme.md) explains implemented behavior; the linked specifications own detailed route contracts. Verify facts against production code before changes.

## Request flow diagrams

The human-facing [endpoint catalog](../public/docs/api/endpoints.md) lists all 37 connected product operations and four AppController/HealthController routes. Individual operation flows live in [docs/api/requestFlows](../public/docs/api/requestFlows/readme.md), grouped into auth, account, catalog, userItems, collections and service pages, and render in `/knowledge/`. Each operation has a stable anchor, example, diagram, consistency/error notes and source references. Follow the guide, update the catalog and link each area page from [the knowledge sidebar](../public/knowledge/sidebar.md) for navigation and search.

Maintain an existing diagram in the same change whenever its endpoint's access checks, branches, called services, entity reads/writes, transaction boundaries, events, jobs, external calls or HTTP-response timing change. Changes to shared/background handlers require checking diagrams that reference those handlers. Adding, renaming or removing a route also requires updating the catalog, route counts, headings and links. Internal refactoring that preserves the depicted behavior needs no redraw. Verify controller/module wiring, actual call sites and job/event handlers; an import graph is not an execution trace. Keep simple action labels and entity names in the diagram, and source links and implementation details below it. Show only real events, distinguish awaited enqueueing from background execution, and document failures that can happen after a committed transaction. Do not present planned operations or static inspection as observed runtime behavior.

Use Mermaid `flowchart TD` blocks with `accTitle`/`accDescr`, the guide's shapes and shared semantic classes; do not duplicate palette definitions or per-diagram configuration. Verify rendering and navigation in knowledge when possible, and explicitly report a browser-verification limit otherwise. Read [runtime context](runtime.md) when changing the renderer, local assets or palette.

## Ownership and composition

Public `QUERY /tags` is owned by [TagEndpointModule](../src/endpoints/tag/tag.module.ts). Its [contract](../public/docs/api/pages/search.md#справочник-тегов) covers filtering, search and pagination for Item tag selection. [SyncTagSearchJobHandler](../src/endpoints/tag/services/syncTagSearchJobHandler/core/syncTagSearchJob.handler.ts) refreshes the separate `site_tags` index from MongoDB weekly, with startup catch-up and a checkpoint after successful synchronization.

[AppModule](../src/app/app.module.ts) imports six product HTTP endpoint modules, with 37 product routes in total, and directly registers AppController for the status page and background routes. Controllers own HTTP bindings and DTO boundaries; endpoint services own authentication, business validation, transactions and response mapping. Entity modules export model-specific repositories. Import the owning module and reuse its repository instead of creating another persistence client. See [data access](data-access.md) for generic repositories and transaction semantics, [security](security.md) for cookies and session validation, and [runtime](runtime.md) for global HTTP setup.

For public QUERY /search, start at [SearchController](../src/endpoints/search/controllers/searchController/core/search.controller.ts), [SiteSearchService](../src/endpoints/search/services/siteSearchService/core/siteSearch.service.ts) and [the search contract](../public/docs/api/pages/search.md#реализованный-общий-поиск). JSON accepts search, cursor, limit (10, 20 or 50; default 20), group selection via types, and per-group filters and sort. It returns items, collections, users and nextCursor (string or null). Groups progress independently; excluded and exhausted groups are empty arrays. The cursor binds the effective query and limit. Continuation uses one extra hit per active group up to 10000 matches per group. MongoDB hydrates public cards in index order, so missing records may shorten a batch without ending it. Ascending relevance scans index IDs in batches before selecting a globally ranked slice. Read [search data access](data-access.md#search) for synchronization and consistency boundaries.

## Library invariants

All seven library mutations return HTTP 204 with an empty body. QUERY /userItems returns summaries.

UserItemEndpointModule imports ItemStatsModule and SiteStatsModule. Every contributing UserItem write must call UserItemStatsService.update with itemId, immutable previous/next metric states and the same active MongoDB transaction session. The service applies deltas to ItemStats and, when ratings change, SiteStats. Unchanged metric inputs do not write aggregates. Expired skipped cleanup has no metric effect. See [data access](data-access.md) for the write contract.

The seven `/userItems` mutations and summary QUERY authenticate the access cookie, active owned session and existing User. The route `:id` is a UserItem ID. Ownership is part of repository read/write filters; foreign and absent records return 404 for mutations. Creation requires a nondeleted Item and maps duplicate user/item pairs to 409. Existing library records remain editable after their Item is soft-deleted. QUERY /userItems accepts JSON {ids} with 1–60 unique UserItem ObjectIds (case-insensitive uniqueness), returns only id/itemId/rating/isFavorite/status in request order and omits foreign, missing and expired skipped entries. It uses an explicit MongoDB projection, makes no writes and remains available after Item soft deletion. It does not read by Item ID or load notes/attempts. Cache-Control is no-store; Accept-Query is application/json.

PATCH `/userItems/:id` accepts one or more of status, rating, isFavorite and note, preserves omitted fields and rejects an empty body. There are no separate field PATCH routes. Rating and note can be cleared with null. Creation, deletion and mutations involving attempts use MongoTransactionService transactions. DELETE removes the UserItem and embedded attempts without changing collection membership. Metric-relevant changes update ItemStats counters/average and SiteStats rating totals synchronously through UserItemStatsService in the same transaction. The search sync job computes ratingScore from these aggregates for item rating sort.

UserItem has five library statuses plus skipped and blocked. POST /userItems accepts only library statuses; POST /userItems/skip and /block accept itemId and create exclusions, returning 409 for existing pairs. Skipped must have no rating, favorite, note or attempts and expires after 90 days through a partial TTL index. Expired skips are treated as absent by mutations; creation conditionally removes an expired skip. Blocked preserves prior personal data. Switching away from skipped clears expiresAt. InProgress/onHold/completed/dropped require an attempt, created only when none exists; completed marks the last attempt isCompleted=true. Attempts have no status; their create/update does not change the parent status. Planned/blocked retain editable history but forbid new attempts. Progress is nullable nonnegative safe integer minutes, integer percent 0..100, or a count of fully watched episodes. Minute remains the default; changing units does not convert progress or infer completion. When final attempts contain unit=episode, UserItemService checks Item type in the same transaction: only series, animatedSeries and animeSeries are accepted, including soft-deleted seasons; missing or other Items give 400. Item episode counts do not currently bound progress. Unknown dates remain null; completedAt cannot precede startedAt. See the library contract for compatibility/migration requirements. Episode support has not had a new unit/integration test run.

UserItemEndpointModule imports TagItemModule for completion checks. UserItemService.validateCompletion uses TagItemRepository.checkHasTagKeys with the existing transaction session and ETagKey constants. A game with the direct hasDefinedEndFalse tag rejects new completion and percent-unit/numeric percent-progress actions with 409. For season Items only direct releaseStatusAnnounced/releaseStatusOngoing tags reject new explicit completion; other and missing states preserve manual completion. Existing history is not rewritten and unrelated edits retain their prior behavior. Completion integration fixtures were updated to direct tags on 26 October 2026; execution remains blocked by the unavailable Docker runtime.

## Collection invariants

Collection stores metadata and ordered group/text blocks with stable ObjectId ids. ItemCollection stores membership, required groupId and position within the group. UserCollection stores independent reactions. All collections are public. Site tag collections have a Tag reference and automatic composition; franchises and user collections retain manual composition. An author of null means site ownership; the user routes grant no administrative override. Read metadata contains version and blocks, with no membership or user reactions.

CollectionService.create assigns the verified user as author, validates unique block/item IDs and group references, checks nondeleted Items and creates metadata plus membership in one transaction. Update validates the final block set, exact supplied block order, conflicting changes and group references. CollectionRepository.updateVersioned atomically matches ID, author, deletedAt:null and expected version, then stores the next version. Missing stored version is supported as 0. Membership upserts and removals use the same transaction session; moves precede removal of remaining memberships in removed groups. Stale or exhausted versions return 409. DELETE conditionally sets deletedAt and retains membership, reactions and library data.

CollectionContentService checks collection/group availability, validates numeric/date field bounds and maps DTOs. ItemCollectionRepository.getFilterOptions, countAvailableItemsByGroup and readContentPage own aggregation; [createItemCollectionsPipeline](../src/entities/itemCollection/services/itemCollectionRepository/functions/createItemCollectionsPipeline) applies allowlisted EItemField paths directly to Item, using ITEM_FIELD_DEFINITIONS for types and labels. Null/missing/incorrectly typed values do not satisfy field bounds. Tags still match direct assignments without hierarchy expansion; categorical and boolean-like metadata use tags.

Public QUERY /collections/:id/items accepts cursor and limit and returns nextCursor (string or null) and blocks. Cards are nested in group blocks. The cursor is scoped to the collection ID and version and follows group order, position, and membership ID. PATCH /collections/:id/user updates only supplied reaction fields. Author-only PUT /collections/:id/poster accepts multipart file and saves a WebP in collections/<id>/poster/. POST /collections accepts JSON without media. PATCH /collections/:id uses separate blocks and items changes with add, update, move, and remove arrays. The service resolves anchors and persists collection metadata and membership in one version-checked transaction.

Reaction reads return false/null/false without inserting absent records. Reaction writes update only the requested field by verified user/collection IDs, using defaults for the first insert. Concurrent first-insert duplicate-key races retry without upsert. A non-null rating of one's own collection returns 409; clearing it is allowed. Hiding does not restrict direct reads. Text search and site-collection administration are outside the current module.

## Persistence boundaries

Use [the entity inventory](../public/docs/api/entities.md) to locate the 20 schemas and their relationships. Schema validators and declared indexes do not establish deployed indexes or enforce every cross-document invariant. Generic query/bulk writes bypass some document checks; endpoint services must validate the operation they construct. Current source does not establish migration of earlier records or live MongoDB transaction support.
