# Endpoint implementation routes

Read when changing HTTP use cases under `src/endpoints`. The [API overview](../docs/api/readme.md) explains implemented behavior; the linked specifications own detailed route contracts. Verify facts against production code before changes.

## Request flow diagrams

The human-facing [endpoint catalog](../docs/api/endpoints.md) lists all 40 connected product operations and four AppController/HealthController routes. Individual operation flows live in [docs/api/requestFlows](../docs/api/requestFlows/readme.md), grouped into auth, account, catalog, userItems, collections and service pages, and render in `/knowledge/`. Each operation has a stable anchor, example, diagram, consistency/error notes and source references. Follow the guide, update the catalog and link each area page from [the knowledge sidebar](../knowledge/sidebar.md) for navigation and search.

Maintain an existing diagram in the same change whenever its endpoint's access checks, branches, called services, entity reads/writes, transaction boundaries, events, jobs, external calls or HTTP-response timing change. Changes to shared/background handlers require checking diagrams that reference those handlers. Adding, renaming or removing a route also requires updating the catalog, route counts, headings and links. Internal refactoring that preserves the depicted behavior needs no redraw. Verify controller/module wiring, actual call sites and job/event handlers; an import graph is not an execution trace. Keep simple action labels and entity names in the diagram, and source links and implementation details below it. Show only real events, distinguish awaited enqueueing from background execution, and document failures that can happen after a committed transaction. Do not present planned operations or static inspection as observed runtime behavior.

Use Mermaid `flowchart TD` blocks with `accTitle`/`accDescr`, the guide's shapes and shared semantic classes; do not duplicate palette definitions or per-diagram configuration. Verify rendering and navigation in knowledge when possible, and explicitly report a browser-verification limit otherwise. Read [runtime context](runtime.md) when changing the renderer, local assets or palette.

## Ownership and composition

[AppModule](../src/app/app.module.ts) imports six product HTTP endpoint modules, with 40 product routes in total, and directly registers AppController for the status page and background routes. Controllers own HTTP bindings and DTO boundaries; endpoint services own authentication, business validation, transactions and response mapping. Entity modules export model-specific repositories. Import the owning module and reuse its repository instead of creating another persistence client. See [data access](data-access.md) for generic repositories and transaction semantics, [security](security.md) for cookies and session validation, and [runtime](runtime.md) for global HTTP setup.

## Public item reading

[ItemEndpointModule](../src/endpoints/item/item.module.ts) imports ItemModule and provides [ItemController.getById](../src/endpoints/item/controllers/item.controller.ts) and [ItemService](../src/endpoints/item/services/item.service.ts). Public GET /items/:id accepts an ObjectId through MongoObjectIdHandler, does not authenticate cookies, returns 400 for invalid IDs and the same 404 for missing/deleted Items, and sets Cache-Control:no-store. See [the response contract](../docs/api/pages/item.md#реализованное-публичное-чтение-item-01).

[ItemRepository.findDetailsById](../src/entities/item/services/item.repository.ts) performs a read-only aggregation of Item, direct TagItem/Tag and both sides of ItemRelation with the opposite Item/Relation. The response exposes nullable releaseDate, ageRestriction, movie, series and game instead of a features array. ItemService maps nested fields explicitly and serializes releaseDate/nextEpisodeAt to ISO 8601. Tags sort by relevanceScore descending then tag ID; relations sort by relation ID. Missing dictionary references and missing/deleted related Items are omitted. No personal data, metrics, source links or collections are loaded. On 26 October 2026, Item tests were updated for exact fields, nullable blocks, ISO dates and unified tags. All 38 service/controller unit tests passed, as did scoped TypeScript, ESLint and formatting checks. The updated HTTP integration suite could not start because no working Docker runtime was available; its earlier passing result predates Feature removal. The full `npm run type-check` passed after adapting the remaining test references to Tag and collection fields and removing the test for the deleted Feature-value helper.

## Library invariants

UserItemEndpointModule imports UserTasteProfileModule, ItemStatsModule and SiteStatsModule. Every contributing UserItem write must call UserItemStatsService.update with itemId, immutable previous/next metric states and the same active MongoDB transaction session. UserItemService connects create/skip/block/remove and update/attempt mutations; create/remove now also use transactions. The service applies deltas to ItemStats and, only when ratings change, SiteStats. Unchanged metric inputs do not write aggregates. Expired skipped cleanup/TTL has no metric effect. See [data access](data-access.md) for the mandatory write contract. Taste recalculation remains asynchronous after commit: enqueue only on rating, favorite or skipped membership changes for update/attempt mutations; create/skip/block/remove also enqueue. Note-only and attempt-only changes do not enqueue taste. Queue insertion failures can still occur after a committed UserItem/metric transaction.

The seven `/userItems` mutations and summary QUERY authenticate the access cookie, active owned session and existing User. The route `:id` is a UserItem ID. Ownership is part of repository read/write filters; foreign and absent records return 404 for mutations. Creation requires a nondeleted Item and maps duplicate user/item pairs to 409. Existing library records remain editable after their Item is soft-deleted. QUERY /userItems accepts JSON {ids} with 1–60 unique UserItem ObjectIds (case-insensitive uniqueness), returns only id/itemId/rating/isFavorite/status in request order and omits foreign, missing and expired skipped entries. It uses an explicit MongoDB projection, makes no writes and remains available after Item soft deletion. It does not read by Item ID or load notes/attempts. Cache-Control is no-store; Accept-Query is application/json.

PATCH `/userItems/:id` accepts one or more of status, rating, isFavorite and note, preserves omitted fields and rejects an empty body. There are no separate field PATCH routes. Rating and note can be cleared with null. Creation, deletion and mutations involving attempts use MongoTransactionService transactions. DELETE removes the UserItem and embedded attempts without changing collection membership. Metric-relevant changes update ItemStats counters/average and SiteStats rating totals synchronously through UserItemStatsService in the same transaction. ratingScore is computed only when ranking recommendations.

UserItem has five library statuses plus skipped and blocked. POST /userItems accepts only library statuses; POST /userItems/skip and /block accept itemId and create exclusions, returning 409 for existing pairs. Skipped must have no rating, favorite, note or attempts and expires after 90 days through a partial TTL index. Expired skips are treated as absent by mutations; creation conditionally removes an expired skip. Blocked preserves prior personal data. Switching away from skipped clears expiresAt. InProgress/onHold/completed/dropped require an attempt, created only when none exists; completed marks the last attempt isCompleted=true. Attempts have no status; their create/update does not change the parent status. Planned/blocked retain editable history but forbid new attempts. Progress is nullable nonnegative safe integer minutes, integer percent 0..100, or a count of fully watched episodes. Minute remains the default; changing units does not convert progress or infer completion. When final attempts contain unit=episode, UserItemService checks Item type in the same transaction: only series, animatedSeries and animeSeries are accepted, including soft-deleted seasons; missing or other Items give 400. Item episode counts do not currently bound progress. Unknown dates remain null; completedAt cannot precede startedAt. See the library contract for compatibility/migration requirements. Episode support has not had a new unit/integration test run.

UserItemEndpointModule imports TagItemModule for completion checks. UserItemService.validateCompletion uses TagItemRepository.checkHasTagKeys with the existing transaction session and ETagKey constants. A game with the direct hasDefinedEndFalse tag rejects new completion and percent-unit/numeric percent-progress actions with 409. For season Items only direct releaseStatusAnnounced/releaseStatusOngoing tags reject new explicit completion; other and missing states preserve manual completion. Existing history is not rewritten and unrelated edits retain their prior behavior. Completion integration fixtures were updated to direct tags on 26 October 2026; execution remains blocked by the unavailable Docker runtime.

## Collection invariants

Collection stores metadata and ordered group/text blocks with stable ObjectId ids. ItemCollection stores membership, required groupId and position within the group. UserCollection stores independent reactions. All collections are public. Site tag collections have a Tag reference and automatic composition; franchises and user collections retain manual composition. An author of null means site ownership; the user routes grant no administrative override. Read metadata contains version and blocks, with no membership or user reactions.

CollectionService.create assigns the verified user as author, validates unique block/item IDs and group references, checks nondeleted Items and creates metadata plus membership in one transaction. Update validates the final block set, exact supplied block order, conflicting changes and group references. CollectionRepository.updateVersioned atomically matches ID, author, deletedAt:null and expected version, then stores the next version. Missing stored version is supported as 0. Membership upserts and removals use the same transaction session; moves precede removal of remaining memberships in removed groups. Stale or exhausted versions return 409. DELETE conditionally sets deletedAt and retains membership, reactions and library data.

CollectionContentService checks collection/group availability, validates numeric/date field bounds and maps DTOs. ItemCollectionRepository.getFilterOptions, countAvailableItemsByGroup and readContentPage own aggregation; [createItemCollectionsPipeline](../src/entities/itemCollection/functions/createItemCollectionsPipeline) applies allowlisted EItemField paths directly to Item, using ITEM_FIELD_DEFINITIONS for types and labels. Null/missing/incorrectly typed values do not satisfy field bounds. Tags still match direct assignments without hierarchy expansion; categorical and boolean-like metadata use tags.

Collection item pages use QUERY `/collections/:id/items` with a JSON body (ItemCollectionsBodyDto). Tags and excluded tags are ObjectId arrays; fields are nested {field,min?,max?} objects, not a serialized JSON string. Field bounds are inclusive and require at least one bound; duplicate fields are rejected. Collection item pages are public, do not authenticate cookies and do not load or return UserItem data. Personal state can be read through QUERY /userItems only when UserItem IDs are known; lookup by Item remains unimplemented (LIB-01). Personal item filters statuses, isInLibrary and isFavorite are unsupported and rejected as unknown query fields. ratingMin/ratingMax filter by stored ItemStats.ratingAverage before counting and pagination, are public and accept inclusive numeric bounds 1–10 (including fractions) with min <= max; absent metrics and null averages are excluded. UserItemStatsService updates ratingAverage and ratingsCount in the UserItem transaction; there is no periodic metric rebuild. Rating filters hide text blocks like other active filters. Pagination counts Items, not display blocks. sort=relevanceScore is allowed only for type=tag collections (400 otherwise), uses stored ItemCollection.relevanceScore, and defaults to descending; explicit asc/desc are supported. Null/missing scores sort last, ties use membership _id, and grouped mode preserves group order. Sorting runs before pagination; collection/title defaults and response shapes remain unchanged. Tag collections owned by the site receive scores asynchronously from direct TagItem assignments through collection.synchronizeTags; see jobs-and-mail.md for delivery limits. Mode availability is global: flat always, grouped for at least two nonempty groups or any text block. Filter options cover the whole collection and reject all query fields, including groupId; item pages still support groupId. See the contract for exact query parsing, sort stability, defaults and errors.

[createCollectionDisplayBlocks](../src/endpoints/collection/functions/createCollectionDisplayBlocks) repeats group headers for continuation pages and anchors text to the next nonempty group's first Item; trailing text belongs to the last nonempty page. Text appears only in unfiltered grouped mode; groupId is a filter. Itemless collections emit text only on page 1. Collection reads use Cache-Control:no-store; no shared collection cache is implemented.

Public QUERY /collections is handled by [CollectionReadController.query](../src/endpoints/collection/controllers/collectionRead.controller.ts) and [CollectionService.query](../src/endpoints/collection/services/collection.service.ts), using [QueryCollectionsBodyDto](../src/endpoints/collection/dto/body/queryCollections.body.ts). Optional itemIds contains 1–60 unique case-insensitive Item ObjectIds and matches any saved ItemCollection membership; Item existence/deletedAt is not checked. Optional type filters collection type; franchise additionally requires author=null. CollectionRepository.querySummaries filters deletedAt=null and membership before count/pagination, limits each membership lookup to one match, and projects only summary fields. The response contains id/type/authorId/title/media cards and standard pagination, with page=1, limit=20 (maximum 60), sorted by createdAt/_id descending. Invalid fields, explicit null and unsafe offsets give 400; empty matches give 200. [CollectionQueryBodyInterceptor](../src/endpoints/collection/interceptors/collectionQueryBody.interceptor.ts) rejects non-object raw bodies before ValidationPipe, whose optional DTO fields alone do not reject an empty array. No cookie authentication, personal data, writes or Meilisearch are involved; no-store, Accept-Query and common CSRF/throttling apply. The local CollectionReadController suites passed 76 unit and 93 HTTP integration tests on disposable MongoDB 8.0.17/Redis 8.2.3; browser and external proxy behavior remain unverified.

Reaction reads return false/null/false without inserting absent records. Reaction writes update only the requested field by verified user/collection IDs, using defaults for the first insert. Concurrent first-insert duplicate-key races retry without upsert. A non-null rating of one's own collection returns 409; clearing it is allowed. Hiding does not restrict direct reads. Text search and site-collection administration are outside the current module.

## Persistence boundaries

Use [the entity inventory](../docs/api/entities.md) to locate the 20 schemas and their relationships. Schema validators and declared indexes do not establish deployed indexes or enforce every cross-document invariant. Generic query/bulk writes bypass some document checks; endpoint services must validate the operation they construct. Current source does not establish migration of earlier records or live MongoDB transaction support.
