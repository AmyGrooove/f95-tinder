## Composition and reuse

[AppModule](../src/app/app.module.ts) imports config, logger, database, cache, throttling, scheduler, health and 16 entity modules. [HealthModule](../src/infrastructure/health/health.module.ts) additionally imports jobs, mail, search and storage, making their initialization part of the application graph. Removing a health dependency can therefore also change provider and worker startup.

Product HTTP endpoints, application event handlers and cron use cases belong in `src/endpoints`, grouped under a suitable existing slice or a dedicated slice when none fits. `src/app` owns application composition, initialization and AppController with its status page, background routes and related helpers and assets. UserItem metric coordination lives in `src/endpoints/userItem/services/userItemStatsService/core/userItemStats.service.ts`.

The old recommendation subsystem, taste profiles and tag-weight jobs were removed on 5 November 2026. [RecommendationsModule](../src/endpoints/recommendations/recommendations.module.ts) exports internal `RecommendationsService.readPopularItemIds` and `readNewItemIds` operations. They delegate to [RecommendationCandidatesService](../src/endpoints/recommendations/services/recommendationCandidatesService/index.ts), which verifies the token, active owned session and existing user, then prepares a context with the session country and site average for reuse across candidate sources. Each source accepts one Item type and defaults to 20 IDs. The new releases source passes an inclusive 90-day release window to ItemRepository. See the [recommendation plan](../public/docs/todos/recommendations/implementationPlan.md) for the full feed contract.

[FallbackRecommendationsService](../src/endpoints/recommendations/services/fallbackRecommendationsService/index.ts) is an internal provider in RecommendationsModule. It uses one prepared context to combine popular and new release candidates for one Item type, returning up to 100 unique IDs with a 60/40 target and filling shortages from the other source. `RecommendationsService.readFallbackItemIds` prepares that context once, requests the selected types (all types by default) and interleaves the resulting ID lists in EItemType declaration order.

`RecommendationsService.readFallbackItems` uses the ordered IDs to read current Item cards through the same poster projection as site search.

`RecommendationsService.readFallbackPage` saves the ordered fallback IDs in Redis for 10 minutes and uses CursorService to continue fixed slices. The cursor and the Redis key are bound to the verified user, session country, effective filters and page size. Missing lists raise `RecommendationCursorExpiredError` with code `RECOMMENDATION_CURSOR_EXPIRED`. Continuing a list does not regenerate candidates or renew its TTL. The repository rechecks the eligibility of the slice before returning poster cards, without advancing beyond that slice to fill removed positions.

Library mutations preserve existing fallback lists and cursors until the list TTL expires. A request without a cursor builds a new list from current data. Each page still rechecks current eligibility, so removed cards can shorten a slice while its positional boundaries remain fixed.

[Recommendation trainer](../tools/recommendationTrainer/main.py) is a local Python CLI that reads the recommendation JSON fixtures, builds a binary user-item matrix and trains shared ItemCF and implicit ALS models across all Item types. Pass `--user` as a fixture username or ID, optionally `--type` and `--limit`, to print per-type candidates and scores as JSON. The CLI excludes positive history and blocked Items, and reports `requiresFallback` below five positive interactions. These diagnostic candidates precede canonical API eligibility filters. `--output` exports one BSON document per model and `--save-to-mongo` inserts that document into `RecommendationModel` using `MONGO_URL`. Both modes work without a selected user. Setup, commands and binary layout are in the [recommendation plan](../public/docs/todos/recommendations/implementationPlan.md#запуск-обучения). MongoDB training input and scheduled training remain planned.

`RecommendationsService.loadLatestModel()` reads the newest model by `createdAt` and `_id` through RecommendationModelRepository. The [Mongoose schema](../src/entities/recommendationModel/schemas/RecommendationModel.schema.ts) uses the trainer's `RecommendationModel` collection. The repository reads lean documents with BSON binary fields promoted to Buffer. The decoder validates the stored values and accepts up to [128 ALS factors](../src/endpoints/recommendations/services/recommendationsService/static/MAX_ALS_FACTORS.ts) before allocating the Gram matrix. An empty collection returns null. The feed passes `isInvalidModelIgnored: true` to log invalid artifacts and fall back. A failed ALS factorization also triggers fallback. Unexpected failures propagate, and direct callers get the invalid artifact error by default.

`calculateItemCfCandidates` accumulates Float32 neighbor weights. `calculateAlsCandidates` calculates a user vector with Cholesky factorization using the Gram matrix prepared when the model is decoded, then scores Item factors. Both sort by score, training popularity and model item order. They exclude positive history by default. The feed sets `isPositiveCandidateAllowed: true` and applies repository eligibility before RRF.

[`RecommendationFeedService.readPage`](../src/endpoints/recommendations/services/recommendationFeedService/index.ts) is the internal personalized feed entry point. A new list reads current positive UserItem signals and loads the newest MongoDB model when there are at least five distinct signals. Personal ranking requires five or more of those Items to be nondeleted and known to the model. The feed combines up to 500 eligible candidates per algorithm and type using equal-weight RRF. The per-type mix targets 70% personal, 20% new and 10% popular, with 60/40 fallback for a type without personal candidates. A library filter allowing planned and at least one other status enables the 5% planned bonus. A direct sequel to an eligible positive source gets a 50% bonus in the personal channel. The higher bonus applies before mixing. The feed reuses the fallback snapshot lifecycle with its own cursor scope and rechecks eligibility on each slice. See the [API overview](../public/docs/api/readme.md#recommendations) for the current calls.

Read [endpoint routes](endpoints.md) for task-specific controllers, services, repositories and invariants. [The endpoint catalog](../public/docs/api/endpoints.md) links to request-flow diagrams, and [the API overview](../public/docs/api/readme.md) links the current contracts. AppController exposes the status page and background routes described in [runtime](runtime.md).

[Entities](../src/entities) contains 18 persistence slices. Use [data access](data-access.md) for repository APIs and [the entity inventory](../public/docs/api/entities.md) for fields and relationships. Item is the single catalogue entity, referenced directly by ObjectId. The `@entities/*` and `@endpoints/*` aliases are defined in [tsconfig.json](../tsconfig.json); entity barrels are absent. Target requirements and planned scope are in [product documentation](../public/docs/product/readme.md).

Shared helpers live under [shared](../src/shared): type checks, regex escaping and AsyncLocalStorage request context. Pagination helpers live under [database functions](../src/infrastructure/database/functions). Function and decorator objects commonly expose an `index.ts` entrypoint and keep implementation in `core/`; reuse those public entrypoints where available.
