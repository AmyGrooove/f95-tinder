# Data access

Read for persistence, pagination, Redis cache or Meilisearch changes. Configuration is described in [runtime](runtime.md).

## MongoDB

Rating/favorite taste signals use ratings 1-4: (rating-5)/4, 5-6: 0, 7-10: (rating-6)/4. Favorite supplies a floor of 0.5 except that ratings 1-4 retain their negative signal: favorite with no rating or rating 5-8 gives 0.5; ratings 9/10 remain 0.75/1. Each Item is still one observation. The relation pipeline uses the positive part of the same signal. Calculated tag preference is sum(signal*relevanceScore)/(count+5); five is neutral shrinkage strength, not a calibrated probability. For example, five unrated favorites at relevance 1 yield weight=0.5, count=5, effective preference=0.25. Nonzero explicitWeight bypasses shrinkage. These initial coefficients have not been validated for recommendation quality.

ItemRelationRole.bonusMultiplier stores a finite recommendation bonus multiplier >= 1, default 1 (no boost), for the candidate's role relative to the source Item. It is optional in TCreateItemRelationRole. Ranking uses the candidate-side role, computes (multiplier - 1) times positive source sympathy and takes the maximum across both relation orientations and all sources. A missing multiplier is read as 1; role values were not backfilled or configured by this implementation.

[RecommendationsService.find](../src/endpoints/recommendations/services/recommendations.service.ts) is an internal application service exported by RecommendationsModule, registered in AppModule without HTTP controllers. It reads the current profile and SiteRatingsMetricRepository.readRatingBaseline (one persisted site prior, stored average with a 5.5 fallback when absent or null), validates field/rating ranges, collection/group context and library conflicts, then calls [ItemRepository.readRecommendations](../src/entities/item/services/item.repository.ts). The caller owns collection access authorization. Query ObjectIds and Date bounds are already typed; no transport DTO is implied. Pagination reuses the existing helpers, defaults to page 1/limit 20 and caps explicit limits at 100. Unsafe offsets are rejected.

The Item-owned recommendation pipeline filters nondeleted Items, types, exact tag membership, known numeric/date ranges, optional collection/group membership, personal and global bans and library statuses before ranking. Global bans match exact SourceItem source/externalId pairs. Blocked, active skipped and globally banned candidates are excluded by default. With isIncludingExcluded=true they remain in a final ranking group, while deleted Items, explicit excludeItemIds, filters and library constraints remain hard exclusions; expired skipped remains eligible even before TTL cleanup, while skipped with null/missing expiry stays excluded. Library include allows outsiders plus selected library statuses, only restricts to selected statuses and cannot coexist with include, and exclude wins. include:[] means outsiders only; only:[] means no results.

Ranking uses only known, type-applicable taste tags with positive relevance. Confidence is count/(count+5) for calculated preferences, with no confidence reduction of nonzero explicitWeight. Graph traversal through Tag.parents removes known assigned ancestors when a more specific assigned known tag exists. tasteScore=sum(preference*relevanceScore*weightModifier)/sum(weightModifier), or 0 with no significance. All tags share one weighted mean; no group averaging or inferred parent assignment. baseScore=1+tasteScore/2, plannedBoost=0.2, finalScore=baseScore*(1+plannedBoost+relationBoost). Relation sources must exist, be nondeleted and have a current positive rating/favorite contribution; skipped is excluded, retained blocked reactions may contribute, and completion is not required. Relationship source contribution and tag preferences use rating/favorite only; role/relationship ranking does not mutate the profile.

[createItemRatingScoreExpression](../src/entities/itemMetric/functions/createItemRatingScoreExpression/index.ts) owns the reusable MongoDB expression (n*R+20*C)/(n+20), falling back to C for unrated Items and to 5.5 when no site ratings exist. The recommendation query joins metrics once, uses raw ratingAverage for range filters and the shared ratingScore expression for tie-breaking using the saved site average. It rounds finalScore to 12 decimals, sorts eligible candidates before included exclusions, then by finalScore (descending by default, or the requested direction), ratingScore descending and Item._id ascending before a facet returning items and total, with allowDiskUse enabled. [IRecommendedItem](../src/entities/item/types/IRecommendedItem.ts) projects _id/type/title/media plus score components. candidateItemIds optionally restricts the input set, including an empty set. Site search does not use personalized recommendation ranking. There is no general per-user candidate cap, random shuffle, result cache, exposure history or snapshot between calls. Runtime correctness and performance on a live database still require verification; find no longer scans ratings to calculate the site mean.

[DatabaseModule](../src/infrastructure/database/database.module.ts) creates the Mongoose connection with `autoIndex: true` and registers global [timestamp](../src/infrastructure/database/functions/applyTimestampsPlugin/core/applyTimestampsPlugin.ts), [version-key](../src/infrastructure/database/functions/applyVersionKeyPlugin/core/applyVersionKeyPlugin.ts) and [toJSON](../src/infrastructure/database/functions/applyToJsonPlugin/core/applyToJsonPlugin.ts) plugins. The timestamp plugin enables timestamps only when the schema has no explicit setting, preserving `false` and custom timestamp options. The version-key plugin sets versionKey:false on every schema. Connection plugins also apply to child schemas. The JSON transform preserves a prior transform, enables virtuals, converts `_id` to string `id` and removes `_id` and `__v`. These are document serialization rules; do not assume every query result has already been serialized.

Connection options and plugin registration are shared with the integration-test bootstrap through [createDatabaseOptions](../src/infrastructure/database/functions/createDatabaseOptions/index.ts).

These generic classes are not registered as model-specific providers by DatabaseModule. The 19 entity repositories compose them through public readonly `read`, `write`, `pagination`, `bulk` and `aggregation` properties, using one injected `Model<HydratedDocument<Entity>>` without a default sort; see [TagRepository](../src/entities/tag/services/tag.repository.ts). Schema classes supply the raw data types; root classes extend [MongoEntity](../src/infrastructure/database/types/MongoEntity.ts) to inherit `_id`, `createdAt` and `updatedAt` declarations without adding schema paths or defaults. `HydratedDocument<Entity>` supplies the document type required by the existing repository core. Derived `TCreate<Entity>` aliases live in schema files and use [TCreateEntity](../src/infrastructure/database/types/TCreateEntity.ts) to omit generated fields, make explicitly listed defaulted fields optional and replace explicitly listed nested field types. The helper omits generated fields only from MongoEntity-compatible root types; child types retain their own fields, including explicit updatedAt. All-optional child create types remain `Partial<Child>`. Nested overrides are removed from the original shape before being merged, preserving nested create defaults without duplicating storage interfaces. Reuse the entity boundary rather than creating another persistence client. Reads and single-document mutations can return `null`. `updateById` and `updateByFilter` request the updated document unless the caller supplies `options.new`. `MongoReadRepository.findMany` uses the configured default sort only when no caller sort is supplied.

[UserRepository.createNew(options?)](../src/entities/user/services/user.repository.ts) generates a lowercase username and camelCase displayName with three trailing digits from entity-owned word lists, a 24-byte random base64url access code and its SHA-256 hash, and creates the user with schema defaults. It returns `{ user, accessCode }`; expose only an explicit response allowlist. [SessionRepository.createNew(props, options?)](../src/entities/session/services/session.repository.ts) accepts a preassigned session ID, user ID, refresh token and optional userAgent/country, computes the SHA-256 token hash and 120-day expiry, and returns the created document. Both forward the caller's transaction session; neither starts a transaction nor issues JWTs. AuthService owns registration orchestration and username-collision retries.

[UserRepository](../src/entities/user/services/user.repository.ts) also owns `findByAccessCode`, `reissueAccessCode` and `replacePassword`. Access-code operations use SHA-256 and require an account without a password; reissue returns `{ user, accessCode }`, with a nullable user when the old code or account state no longer matches. Password replacement matches user ID, email and the previous password hash before updating. Mutations accept the caller's transaction session and return documents or null without HTTP exceptions.

[SessionRepository](../src/entities/session/services/session.repository.ts) owns `findActive`, `findActiveByUser`, `deleteActive`, `deleteOthers`, `deleteByUser` and `updateRefreshToken`. Single-session operations require both session and owner ObjectIds; active operations explicitly check expiresAt. The list selects device/country/date fields and sorts newest first. Refresh updates hash the new token, extend expiry by 120 days and record lastRefreshedAt. Supplying currentRefreshToken additionally requires its SHA-256 hash to match in the same atomic update; SessionService.refresh always supplies it. Reissue of the access code updates an already authenticated session without that extra filter. Transaction ownership, JWT issuance, HTTP errors and response mapping remain in endpoint services.

`updateByFilter` and `deleteByFilter` each execute one `findOneAndUpdate` or `findOneAndDelete`, accepting schema-typed filters and options through the existing `entityRepository.write`. Endpoint services supply verified ownership to entity operations rather than trusting body/query ownership or using read-then-write by ID. They map missing/foreign records to the endpoint's declared HTTP error. Repositories do not decide authorization, start transactions or create HTTP exceptions.

`updateById`, `updateByFilter` and `updateMany` default `runValidators` to true while preserving explicit false, session and other caller options. Update validators cover supported operators and changed paths only: `$inc`, array operators and pipelines do not guarantee whole-document invariants. `bulkWrite` updates and update pipelines remain trusted low-level APIs without full schema validation. Future endpoints must construct allowed updates from validated DTOs, never accept client MongoDB filters, operators, projections or QueryOptions, and validate business invariants in their application-service.

[AppModule](../src/app/app.module.ts) imports 19 entity modules. Each registers its own model and exports its repository; SourceModule additionally exports its reusable collection/client/writer services. Consumers import the owning module. AuthModule, AccountModule, UserItemEndpointModule, CollectionEndpointModule and ItemEndpointModule provide HTTP use cases; catalogue import and ranking orchestration are not implemented.

[Item](../src/entities/item/schemas/item.schema.ts) is the single catalogue entity for all content types and stores required type (EItemType: movie, series, animatedMovie, animatedSeries, animeSeries, animeMovie, game), title={ru,en}, aliases:string[], description={ru,en}, media:MediaSrc[] and nullable deletedAt. Title requires at least one non-whitespace translation. Aliases and media default to []; description defaults to {ru:null,en:null}; deletedAt defaults to null. Aliases must contain non-whitespace text. TCreateItem makes aliases, description, media and deletedAt optional. MediaSrc reuses the shared embedded schema with src, nullable language and type; EMediaType defines POSTER, SCREENSHOT and TRAILER. Generated _id and timestamps follow the standard MongoEntity/connection-plugin setup. ItemModule is imported by AppModule and exports ItemRepository. No title uniqueness or MongoDB text index is declared; Meilisearch indexing is described under [Search](#search). Catalogue references are direct ObjectId references to Item: ItemMetric.item, ItemTag.item, RelationSide.item, SourceItem.item, UserItem.item; SourceItem.item remains nullable. Their indexes use item (or first.item/second.item) instead of item.type/item.id. Separate Movie/Game entities are not part of the target model; type-specific characteristics use embedded Item blocks and tags. Existing Movie documents, embedded references and database indexes were not migrated. deletedAt does not install a global query filter. Library creation, collection content reads and site search explicitly require nondeleted Items; general catalogue listing, import and merge/split orchestration are not implemented.

[Item](../src/entities/item/schemas/item.schema.ts) also supports nullable releaseDate (exact first worldwide release date) and ageRestriction (string EAgeRestriction: "0", "6", "12", "16", "18", "18++"), plus nullable embedded movie, series and game blocks. movie applies to movie/animatedMovie/animeMovie and contains duration. series applies to series/animatedSeries/animeSeries and contains episodeCount, releasedEpisodeCount, episodeDuration and nextEpisodeAt. game applies to game and contains mainStoryDuration and fullCompletionDuration. Durations are finite positive minutes; episodeCount is a positive safe integer and releasedEpisodeCount is a nonnegative safe integer. Document validation rejects incompatible blocks and released counts above known totals. releaseDate, ageRestriction, movie, series and game default to null and remain optional in TCreateItem. Fields inside present blocks remain optional without defaults. Embedded blocks have no _id, id or timestamps. TAG_GROUP_RULES reuses the string EAgeRestriction values for the age scale and retains stable ageRestriction0/6/12/16/18 tag keys; ageRestriction18PlusPlus represents 18++ for pornographic games only. Document validation limits 18++ to game Items; it does not infer pornographic content. Collection aggregations treat 18++ as 18 and convert age strings to numbers internally to preserve numeric age filters and filter options. Existing BSON was not backfilled; stored numeric ages require a separate migration to the string contract. Generic query/bulk updates do not guarantee these cross-field rules. Item detail aggregation reads expose stored fields directly. Exact collection filters use the allowlisted EItemField paths and ITEM_FIELD_DEFINITIONS. Feature/ItemFeature production modules and feature taste selectors were removed; no migration or dictionary seeding was performed.

The agreed catalogue granularity is one Item per season for series, animatedSeries and animeSeries, with no aggregate series Item. Seasons are grouped through Collection(type=franchise) and CollectionItem; each season has its own UserItem. DLC belong to the game Item and have no separate Item/UserItem. These are catalogue-normalization rules from the [data structure requirements](../docs/product/foundations/dataStructure.md); the Item schema validates the type enum but does not enforce season splitting or DLC exclusion. Franchise membership alone does not identify the next season. Item and collection response DTOs reuse EItemType directly.

Season continuations, prequels and spin-offs use the existing Relation and ItemRelationRole mechanism. Relation has no type field: first/second each contain an Item and the role of that Item relative to the opposite Item. Those field positions do not imply chronology. A next-season association uses a direct continuation link between adjacent seasons; franchise membership alone is insufficient. Such links do not automatically establish consumption prerequisites. ItemRelationRole.group is nullable and defines all, video and game: all is an explicitly shared role category, video covers the six audiovisual Item types, game covers games, and null leaves the category unspecified. This is dictionary grouping, not Item-type enforcement. Existing role records with group=movie need separate classification into the supported groups because movie is no longer a permitted group; no database migration was performed. No role dictionary records or relationship data were seeded or verified in a database.

Tag.key, ItemRelationRole.key and Source.key use camel-case string identifiers with unique indexes. ETagKey names only the fixed keys interpreted by library rules: hasDefinedEndFalse, releaseStatusAnnounced and releaseStatusOngoing. It does not enumerate the whole dictionary. ESourceKey names kodik for KodikService.getSource.

Platform versions of the same game share one Item and one UserItem per user. Available platforms are represented by separate Tag records with ETagGroup.PLATFORM (platform), linked through ItemTag; multiple platforms can belong to the same game. Do not duplicate platform values in Item fields. These tags describe game availability, not user device ownership. Item and collection-filter tag response DTOs reuse ETagGroup directly. The enum addition does not seed platform records or implement platform-specific progress or ratings.

ETagGroup now supports 21 groups: genre, subgenre, keyword, format, style, audience, country, originalLanguage, platform, duration, episodeDuration, episodeCount, mainStoryDuration, fullCompletionDuration, releaseStatus, hasDefinedEnd, ageRestriction, releaseYear, gameMode, gameMechanic and perspective. Age classifications share ageRestriction; separate ESRB/PEGI groups are not defined. [TAG_GROUP_RULES](../src/entities/tag/static/TAG_GROUP_RULES.ts) defines approved type applicability, cardinality, taste participation, controlled dictionary approval, fixed values and half-open ranges; null upper bounds are unbounded and duration bounds use minutes. Unknown values do not establish tags; dictionary additions require approval. Range entries and fixed enum entries have stable key values matching Tag.key. Enum entries are {key,value}; numeric-year tags use releaseYear followed by the canonical integer. Tag document validation rejects keys outside a fixed group definition; dictionary groups without populated values remain subject to the approval workflow. Query/bulk writes do not guarantee that cross-field check. Import, unknown-value review, age normalization, derived tag synchronization and dictionary seeding remain pending in [TODO](../docs/TODO.md).

The agreed Tag identity rule is one canonical concept across Item types: a shared theme uses the same Tag, while identical names with different meanings use distinct Tags. Descriptions clarify meaning and aliases refer to that same concept. The existing key/name/description/aliases fields support this contract; semantic normalization is not enforced by the schema. A shared Tag does not imply equal recommendation weights across Item types, and genre-name equality alone does not establish comparability. These are catalogue and recommendation requirements, not an implemented transfer algorithm.

[ItemTag](../src/entities/itemTag/schemas/itemTag.schema.ts) stores required finite relevanceScore in (0,1] and a unique item/tag pair. The agreed meaning is how strongly the Tag's property is expressed in the Item: 1 is maximum expression. Zero and negative values fail schema validation; a zero-expression association should be deleted instead. It is not annotation confidence, correctness probability or user preference. A missing ItemTag is unrecorded association, not proven absence of a property. Platform membership uses relevanceScore=1. Intermediate-value annotation and calibration rules are not defined, so equal scores across tags or Item types are not automatically comparable. ItemRepository.findDetailsById currently uses this value to sort direct tags descending and does not expose it in the response; recommendation scoring is not implemented.

Game duration estimates live in Item.game.mainStoryDuration and fullCompletionDuration as positive finite minutes, excluding DLC. Either estimate can be unknown independently. Range tags use stable keys in TAG_GROUP_RULES, without storing duplicate numeric bounds in Tag.

Game finite-completion metadata uses tags in group hasDefinedEnd. UserItemService checks the direct hasDefinedEndFalse tag through ItemTagRepository.checkHasTagKeys using the caller transaction session to preserve game completion and percent-progress restrictions. Missing metadata remains unknown.

For finite games the user chooses their own completion criterion and percent estimate; no completion-mode/goal field is required or stored. Existing UserItem operations already allow completed/isCompleted=true independently of progress, with no automatic conversion to 100%. Do not infer completion of all optional content or equal consumption volume across users from those flags.

Season counts live in Item.series.episodeCount and releasedEpisodeCount. The total is a positive safe integer, released is nonnegative, and document validation requires released <= total when both are known. Unknown counters are omitted inside the block, not replaced with zero. Counts are per season, not user progress.

Season release status uses group releaseStatus and fixed keys releaseStatusAnnounced, releaseStatusOngoing, releaseStatusReleased and releaseStatusCancelled. Direct announced/ongoing tags forbid new explicit completion actions for season Items; other and unknown states allow manual completion. Counts do not infer release state, and metadata changes do not rewrite historical user flags.

[Kodik field mapping](../docs/sources/kodik/mapping.md) describes proposed normalization and approval rules, not an implemented importer.

The agreed [tag dictionary](../import/tags/tags.json) is a single JSON file with a root array of `{group,tags}` objects: 21 groups, 1184 tags and 216 parent relations. It replaces the former group files in `docs/research/tagDictionary` without changing their records. Each tag has `key`, bilingual `name`/`description`, string `aliases` and `parents` containing immediate parent keys (resolved to ObjectId on import), with group supplied once for each group's tags. Descriptions define meaning; aliases are synonyms and omit exact repetitions of names. `weightModifier=1` is omitted because Tag supplies that default. Research provenance/mappings/approval/review/summary/validation blocks were previously removed without archival. Platform tags and 45 year tags are in the platform and releaseYear groups. This is agreed dictionary content, not database seeding or an implemented import-package contract.

Before consuming this file, inspect [TAG_GROUP_RULES](../src/entities/tag/static/TAG_GROUP_RULES.ts), [checkIsTagKeyAllowed](../src/entities/tag/functions/checkIsTagKeyAllowed/core/checkIsTagKeyAllowed.ts) and [Tag](../src/entities/tag/schemas/tag.schema.ts). The current key/group check accepts all 1184 dictionary entries, including the four releaseYear ranges and all six gameMode values. Individual year tags are prepared for 1990..2030; zero is invalid, and 2030 is not the production maximum. Production additionally defines gameLength with shortGame/longGame, without a matching group in the dictionary; consolidation does not add these tags or establish an agreed code fix. See [catalogue keys](../docs/product/foundations/catalogKeys.md#расхождения-с-production). No database import, migration or runtime verification follows from the file.

Dictionary `parents` entries contain immediate parent keys; persistence uses ObjectIds. Resolve references across groups and preserve an acyclic graph; aliases are not parent relations. One meaning has one Tag across Item types, but equal names do not prove equal meaning. `keyword/survivalTheme` differs from `gameMechanic/survivalGameplay`; game modes belong to gameMode, not format. Country means production country; originalLanguage excludes translations and keeps Tagalog distinct from Filipino and Mandarin distinct from the wider Chinese language family. Platform means an available released version or mode, excluding stores, user device ownership and input methods.

[LanguageText](../src/entities/shared/schemas/languageText.schema.ts) stores nullable ru/en translations, each defaulting to null. Dictionary descriptions and RelationSide.roleNameOverride are bilingual objects defaulting to empty translations. Tag and ItemRelationRole keys use CAMEL_CASE_REGEX and unique indexes; group and unit fields are nullable where declared. Tag aliases are nonempty strings; its group enum currently retains GENRE and SUBGENRE separately. [Tag.parents](../src/entities/tag/schemas/tag.schema.ts) stores immediate parent Tag ObjectIds, defaulting to an empty array; multiple parents are allowed, with no stored children or ancestor closure. Document validation/save, insertMany and bulkWrite reject self-parenting and duplicates. Parent updates require a complete array and a concrete _id, including bulk updates; dotted/array operators, aggregation update pipelines, upserts and lean insertMany are rejected. Document saves replace the complete modified array to avoid duplicate concurrent pushes. Updates to other fields, including the weight-modifier job, retain their existing behavior. Referenced-tag existence and whole-graph cycle checks are not implemented; an acyclic graph remains a content contract. ItemTag assignments do not infer parents. [EUnit](../src/entities/shared/schemas/EUnit.ts) defines MINUTE, PERCENT, EPISODE, USD and RUB; ItemAttempt permits MINUTE, PERCENT and EPISODE. The current application registers 19 root entity schemas. Their collection names match schema class names. Source declarations do not establish deployment of collections or indexes.

CollectionItem and UserCollection reference Collection through the required ObjectId field `collectionId`. CollectionItem also stores nullable relevanceScore, default null, validated as a finite number in (0,1] when present; upsertForCollection preserves it when omitted and updates it when supplied. HTTP composition writes do not accept this field. Their query filters, aggregation matches and compound indexes use this field. Existing documents with `collection` and indexes on that field require migration before using the updated API; no database migration was performed.

[Source](../src/entities/source/schemas/source.schema.ts) uses a unique camelCase key and nullable logoUrl/baseUrl/apiUrl. [SourceItem](../src/entities/sourceItem/schemas/sourceItem.schema.ts) permits item=null before matching, has unique(source,externalId) and allows multiple source records for one Item. [ItemMetric](../src/entities/itemMetric/schemas/itemMetric.schema.ts) stores ratingsCount, nullable ratingAverage, ratingDistribution, favoritesCount, completedAttemptsCount and statusCounts. It has no ratingsSum or saved ratingScore. ItemMetricRepository.applyChanges accepts counter deltas and the caller’s ClientSession, applies them in an update pipeline, then derives ratingAverage from the ten distribution buckets divided by ratingsCount; no ratings means null. Completed attempts are uncapped; blocked reactions and attempts contribute, while statusCounts contains only planned/inProgress/onHold/completed/dropped.

[SiteMetric](../src/entities/siteMetric/schemas/siteMetric.schema.ts) uses generated ObjectIds and a unique key discriminator. SiteRatingsMetric (key=ratings) stores sum, count, nullable average; updatedAt records the last change. SiteRatingsMetricRepository.applyChanges updates sum/count and average atomically in the caller’s transaction; count=0 means average=null. readRatingBaseline reads the saved average and uses DEFAULT_SITE_RATING_AVERAGE only when missing/null. Both repositories validate the resulting document before commit because Mongoose update-pipeline writes do not apply ordinary update validators. Their upsert pipelines explicitly initialize createdAt with $NOW only when absent; Mongoose maintains updatedAt.

Every application mutation of UserItem must capture an immutable metric state before modification and call [UserItemMetricsService.update](../src/endpoints/userItem/services/userItemMetrics.service.ts) with itemId, previous/next states (null for create/delete), and the same active transaction session as the UserItem write. getState copies rating, favorite, status and the completed-attempt count. The service computes deltas, skips unchanged metrics, updates ItemMetric first and SiteMetric only on rating changes, sequentially. UserItemService connects create, skip, block, update, delete and attempt mutations; all run through MongoTransactionService. Its local transaction wrapper retries duplicate-key conflicts on metric initialization up to three attempts; ordinary transient transaction retries remain with the driver. UserItem uniqueness conflicts are not retried as metric conflicts. Skipped records have no contributing data or counted status, so expired-skip cleanup/TTL needs no metric decrement. Raw model/generic repository writes bypass this coordination and must not be used for contributing UserItem mutations. No metric cron, queue event, full scan, startup rebuild or automatic backfill is registered. Metrics and UserItem commit or roll back together; taste-profile enqueue remains separate after commit. No database reset or reconciliation was run. Session declares refresh-hash uniqueness, a user/expiry lookup and sessionExpiryTtl with expireAfterSeconds:600. Refresh, code reissue and password change update lastRefreshedAt through SessionRepository.updateRefreshToken.

Raw artifact uploads are provided by SourceDataWriterService and StorageService. Import runs, approvals, provenance and publication checkpoints are not represented by current root entities; their application workflow remains to be implemented.

[BannedItem](../src/entities/bannedItem/schemas/bannedItem.schema.ts) stores import/recommendation bans by required Source ObjectId and exact externalId, with nullable reason and countries using the shared [ECountry](../src/entities/shared/schemas/ECountry.ts) enum. Empty countries (the default) means a global ban; a nonempty array limits the ban to those countries. unknown is the bucket for unresolved or unsupported countries. The unique pair index is named bannedItemSourceExternalIdUnique. BannedItemModule is imported by AppModule and exports BannedItemRepository. A ban does not require an Item or SourceItem to exist. ItemRepository.readRecommendations excludes candidates through matching SourceItem records and global or matching-country bans; RecommendationsService.find accepts optional country, defaulting to unknown when omitted; import enforcement is not implemented. The index is declared in source only; no database migration or runtime verification was performed.
Tag.weightModifier is a finite nonnegative number defaulting to 1. Taste eligibility comes from TAG_GROUP_RULES.isUsedForTaste, not a per-Tag schema flag. [TagWeightModifiersModule](../src/endpoints/tagWeightModifiers/tagWeightModifiers.module.ts) schedules daily recalculation at 03:00 Europe/Moscow through JobsModule. For each taste-enabled group, ItemTagRepository.getUsageCounts counts distinct nondeleted Items of the group's allowed types that have at least one group tag, and distinct supporting Items per tag; relevanceScore is not used. The handler writes clamp(ln((N+1)/(n+1)), 0.25, 2), or 1 when N or n is zero, to existing group Tags through bulkWrite. Other groups and null groups are untouched. This uses group-tag presence as an approximation of metadata completeness. See [jobs](jobs-and-mail.md#tag-weight-modifiers) for scheduling and retry behavior.

[UserTasteProfile](../src/entities/userTasteProfile/schemas/userTasteProfile.schema.ts) stores one document per user with a single global tagPreferences array. Each entry has weight/explicitWeight (finite [-1,1], default 0) and count (nonnegative safe integer, default 0). Tags are unique with a 4096-entry cap. Full-array setters and document validation remove entries with count=0 and explicitWeight=0; explicit-only entries remain. Replace the complete array with validators or save a document; dotted/operator/bulk writes do not guarantee whole-array pruning or uniqueness. [UserTasteProfileRepository.tryReplaceCalculatedPreferences](../src/entities/userTasteProfile/services/userTasteProfile.repository.ts) merges calculated entries only for the affected tag IDs with a raw pre-calculation snapshot, preserves unrelated entries and nonzero explicit weights, clears unsupported affected calculated values, and conditionally replaces the full array using an exact raw-array comparison. A conflict or concurrent first-insert returns false so the caller rereads and recalculates. Missing empty profiles are not inserted. [UserTasteProfileRecalculationService](../src/entities/userTasteProfile/services/userTasteProfileRecalculation.service.ts) computes sum(signal × relevanceScore) / count; count includes neutral ratings but excludes zero relevance, skipped records and records without rating/favorite, even when attempts are completed. Each Item contributes once using rating/favorite only; ratings 1-4 retain priority over favorite. Completed attempts do not affect weight/count. UserItemRepository.getTasteInputs filters the user library through an ItemTag lookup for affected tags before returning only item/rating/isFavorite calculation inputs; attempts are not fetched. getTasteTags also filters by those tag IDs. ItemTagRepository.getTasteTags joins existing nondeleted Items and taste-enabled Tags; the service also checks group/type applicability. Only directly assigned tags participate; parents are not inferred. Explicit settings do not contribute to count; catalogue weight modifiers and confidence are applied by recommendation ranking without changing the stored profile. See [V1](../docs/product/foundations/recommendations.md) and [jobs](jobs-and-mail.md).

[UserItem](../src/entities/userItem/schemas/userItem.schema.ts) stores seven non-null statuses: five library statuses plus skipped and blocked, nullable integer rating 1..10, favorite, nullable trimmed note, nullable expiresAt and attempts with explicit ObjectId identifiers. Attempts contain isCompleted, nullable safe-integer progress, minute/percent/episode unit and nullable dates; percent is capped at 100. Episode means fully watched episode count; the endpoint service permits it only for series, animatedSeries and animeSeries, checking Item type inside the mutation transaction without excluding soft-deleted Items. The embedded schema does not enforce that cross-document type restriction or bounds from Item episode counts. Minute remains the default, and units do not convert progress or infer completion. The unique user/item pair covers library entries and exclusions. A partial expiresAt TTL index deletes only skipped records; the endpoint service forbids personal data/attempts for skipped and clears expiry on other statuses. At least one attempt is required for inProgress/onHold/completed/dropped by the endpoint contract. Blocked retains existing history. UserRecommendationState is removed; exposure history is not implemented. Existing attempt.status data needs explicit migration to isCompleted before deployment; no live data migration has been performed.

The [User schema](../src/entities/user/schemas/user.schema.ts) trims and lowercases username/email; empty email becomes null. New usernames are normalized before storage; existing database records are not migrated automatically. External identifiers, hashes and dictionary keys retain exact comparison. The unique email partial filter is `{ email: { $type: "string" } }`; linked-account uniqueness uses `{ "linkedAccounts.provider": { $type: "string" }, "linkedAccounts.externalId": { $type: "string" } }`, allowing multiple users with null email or empty linkedAccounts. A whole-array validator rejects repeated providers within a user, which a unique multikey index alone does not prevent. Future account linking must replace the full array with `$set` and validators; `$push`, `$addToSet` and dotted updates do not enforce this whole-array contract. Lookup must use `linkedAccounts: { $elemMatch: { provider, externalId } }` to match both fields within one element. OAuth/linking is not implemented.

Uniqueness depends on deployed MongoDB indexes, not an availability precheck. Account services map relevant duplicate-key errors to HTTP 409. Source index declarations and autoIndex do not safely migrate conflicting existing indexes or normalize stored data. Session expiry is explicitly checked for authorization independently of TTL cleanup.

Code-only login queries User.accessCodeHash using a SHA-256 hex digest of the 24-byte random base64url code generated by UserRepository.createNew, with passwordHash required to be null. The partial unique userAccessCodeHashUnique index covers string accessCodeHash values and excludes null/missing values. Existing bcrypt-backed access codes are intentionally unsupported; no stored data was migrated and deployment of this index was not verified. Do not use password-style bcrypt comparison or scan users for this lookup.

[User](../src/entities/user/schemas/user.schema.ts) normalizes username/email, stores nullable bcrypt passwordHash and SHA-256 accessCodeHash with select:false, and supports Google/Yandex linked-provider records. Before setup email/password are absent; setup conditionally sets both and clears accessCodeHash. UserSettings owns locale with RU/EN values and RU default. [Session](../src/entities/session/schemas/session.schema.ts) stores user, refreshTokenHash, userAgent, expiresAt and lastRefreshedAt. See [security](security.md) for the implemented login, setup, recovery and session lifecycle.

User has a local toJSON transform removing passwordHash/accessCodeHash, composed with the global id transform. Session has no local hash-removal transform. select:false hides hashes from default reads, but explicit selections/create results can contain them; lean, aggregate and toObject do not provide an HTTP response allowlist. Endpoint DTOs map responses explicitly.

Source inspection does not prove data migrations, deployed unique indexes, transaction topology or external-service behavior. Check the intended runtime environment separately; documentation updates do not require starting the application or connecting to a database.

[MongoTransactionService.run](../src/infrastructure/database/services/mongoTransaction.service.ts) accepts run(callback, options?), starts a session, passes the optional options to withTransaction and ends the session in finally. The options type is derived from the installed ClientSession.withTransaction; existing callers retain their behavior. New operation services can explicitly supply snapshot/majority/primary concerns; this does not configure or verify the actual MongoDB deployment. Pass the received session to participating repository operations; transaction scope alone does not attach it to arbitrary queries.

Pagination defaults to page 1 and limit 20, floors finite values and clamps explicit limits to 1–100 through [normalizePagination](../src/shared/functions/pagination/normalizePagination/core/normalizePagination.ts). The paginated repository normalizes a non-empty caller sort through Mongoose Query.sort, otherwise uses a non-empty defaultSort, otherwise `{ _id: -1 }`. Object, string and tuple forms are supported without mutating caller/default sort objects. An absent `_id` is appended as the last descending tie-breaker; an explicit `_id` retains its direction and position. Equal sort values therefore have deterministic ordering, but offset pagination can still shift during concurrent writes. The repository runs items and count sequentially when a session is present, otherwise concurrently. [createPaginatedResult](../src/shared/functions/pagination/createPaginatedResult/core/createPaginatedResult.ts) returns items, page, limit, total, pages and next/previous flags.

[MongoObjectIdHandler](../src/infrastructure/database/handlers/mongoObjectId.handler.ts) validates 24-character hexadecimal route parameters and converts them to Types.ObjectId, returning 400 for invalid input. It is reusable at controller parameter boundaries and has no entity dependencies.

## Search

[SearchService](../src/infrastructure/search/services/search.service.ts) exposes `ensureIndex`, `hasIndex`, `upsert`, `search`, `readDocumentIds`, `delete`, `deleteMany` and `clear`. `ensureIndex` creates missing indexes with primary key `id` and updates configured searchable, displayed, filterable, sortable attributes, ranking rules, pagination and typo-tolerance settings. Concurrent initialization of the same index shares a promise within the service instance; it is not a persistent or distributed lock.

Single-document mutations, upsert, clear and index initialization accept `isWaitForTask`, defaulting to false; `deleteMany` always waits. Waited tasks have a 120-second timeout and must finish with status `succeeded`, otherwise the operation throws with the task error as its cause. Successful enqueueing alone does not prove searchability. Search maps results into [ISearchResult](../src/infrastructure/search/types/ISearchResult.ts).

[SearchEndpointModule](../src/endpoints/search/search.module.ts) owns site search and its BullMQ synchronization job. [SearchSyncSchedulerService](../src/endpoints/search/services/searchSyncScheduler.service.ts) enqueues `search.synchronize` at bootstrap and every five minutes with deduplication; queue failures are logged and retried at the next tick. [SyncSearchJobHandler](../src/endpoints/search/handlers/syncSearchJob.handler.ts) uses entity repositories and explicit allowlists to populate `site_items`, `site_users` and `site_collections` in batches of 500. Item and collection titles and descriptions are bilingual; Item aliases are indexed. User documents contain only id, username, displayName and avatarUrl. Ranking uses sort, words, typo, attribute, proximity and exactness; sort is first so explicit ordinary ordering applies before text-relevance tie breakers; searchable attribute order is title/aliases/description or username/displayName. Nested RU/EN translations share their parent's priority. Each index permits the first 10000 search hits. Typo tolerance is explicitly enabled with oneTypo=5 and twoTypos=9.

A Redis checkpoint (`siteSearch:checkpoint:v2`, no TTL) is advanced to the run's start only after all three indexes and their Meilisearch tasks succeed. Missing checkpoint or any missing index causes a full scan; later runs scan User/Collection updatedAt with a 60-second overlap for ordinary transaction commits, using _id keyset batches. ItemRepository.readSearchIndexBatch scans all Items on every run and joins existing ItemTag/Tag records and ItemMetric ratings, because those changes need not update Item.updatedAt. Indexed metadata contains tag IDs, numeric fields/date milliseconds, ratings, known-value flags, normalized title variants and collection updatedAt. Writes must preserve the normal timestamp contract. Each run also traverses all indexed IDs and removes missing or soft-deleted source records, covering physical deletions. This traversal and delta queries need workload/performance validation before large-scale deployment; no source query indexes were added. Changing the indexed document shape requires invalidating/versioning the checkpoint to reindex unchanged records.

[SiteSearchService](../src/endpoints/search/services/siteSearch.service.ts) returns 503 until initial synchronization succeeds or a dependency fails. It builds typed, allowlisted Meilisearch filter expressions and explicit sorts before requesting the requested page; sort ties use id and unknown date/rating flags keep nulls last. Search is public and does not read profiles or authenticate cookies; personal library state is never exposed. Cards are hydrated with explicit MongoDB projections in hit order and removed records are suppressed. Native filters/sorts/count estimates reflect the indexed state, while card fields can already be newer. Search text and DTO contracts remain in [the search contract](../docs/api/pages/search.md).

[SearchService.iterateMatches](../src/infrastructure/search/services/search.service.ts) enumerates documents through the documents API (independent of search maxTotalHits), then queries each bounded ID batch with the same text/filters and id IN. The 10000-hit limit restricts page depth only. Ascending relevance consumes all matching batches with this traversal and a bounded top window of _rankingScore ascending/id. Normal descending relevance and ordinary sorts request a single native search page. This full traversal can be expensive and has no atomic snapshot across concurrent index writes, no result cache and no asynchronous HTTP job protocol. Live correctness, cutoff behavior and throughput still require validation.
