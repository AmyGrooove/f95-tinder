# Jobs and mail

Read for background work, retry policies, queue contracts or sending email. Configuration and startup wiring are in [runtime](runtime.md).

## Queue API and registration

[JobsModule](../src/infrastructure/jobs/jobs.module.ts) configures BullMQ from the Redis configuration and exports `JobService` and `JobsHealthService`. The queue is `jobs`, prefixed with the app name. [JobService](../src/infrastructure/jobs/services/job.service.ts) exposes `add`, `get`, `list`, `update`, `cancel` and `retry`.

Use [defineJob](../src/infrastructure/jobs/functions/defineJob/core/defineJob.ts) for a typed definition with a name, payload version and retry delays. Register a Nest provider implementing `handle(payload, context)` and decorate it with [JobHandler](../src/infrastructure/jobs/decorators/JobHandler/core/JobHandler.ts). [JobRegistryService](../src/infrastructure/jobs/services/jobRegistry.service.ts) discovers providers and rejects duplicate handler names or missing handle methods. Import the handler's owning module so discovery can see the provider.

Persisted envelopes include name, version, payload, retry delays and cancellation state. [JobProcessorService](../src/infrastructure/jobs/services/jobProcessor.service.ts) checks the envelope and handler version before execution. Missing handlers and incompatible versions are unrecoverable. A version change therefore affects already queued jobs.

The number of attempts is retry-delay count plus one, using custom backoff. [JOBS_SETTINGS](../src/infrastructure/jobs/static/JOBS_SETTINGS.ts) sets concurrency to 10; completed jobs retain up to seven days/1,000 entries and failed jobs up to fourteen days/2,000 entries.

Handlers receive an ID, attempt, progress updater and `throwIfCancelled`. Progress must be an integer from 0 to 100. Cancellation is cooperative: the processor checks before and after the handler, and long-running handlers should use the same context check. It does not undo external effects. `NonRetryableJobError` disables automatic retry; `JobCancelledError` follows the cancellation result path.

`update` permits only matching queued jobs; `retry` permits failed jobs and resets attempt counters. `list` filters by definition name and supports states and an opaque cursor; it scans at most 500 queue entries per call. Its default limit is 50, permitted range 1–100. Inspect [job details](../src/infrastructure/jobs/types/IJobDetails.ts) before exposing these results through a future endpoint.

[ItemRatingsModule](../src/endpoints/itemRatings/itemRatings.module.ts), imported by AppModule and UserItemEndpointModule, exports [ItemRatingsRecalculationService](../src/endpoints/itemRatings/services/itemRatingsRecalculation.service.ts). Its enqueue(itemId) schedules `item.recalculateRatings` (version 2, string Item ObjectId payload) through the existing jobs infrastructure after a UserItem rating actually changes or a rated UserItem is deleted. Update events are queued only after the MongoDB transaction commits. Creation currently has no rating input; unrated deletes, unchanged ratings and edits to other fields enqueue no rating job. Skipped entries cannot retain ratings, so their TTL deletion needs no rating event. Deduplication uses definition name + Item ID with keepLastIfActive:true and no TTL: waiting requests merge and events during processing retain one follow-up run. Retry delays are 5,000/30,000/120,000 ms. [RecalculateItemRatingsJobHandler](../src/endpoints/itemRatings/handlers/recalculateItemRatingsJob.handler.ts) checks Item existence (including soft-deleted Items), aggregates current ratings for that Item, checks cancellation and upserts only ratingAverage and ratingsCount. Other fields are preserved and receive schema defaults on insert. No cron, full scan, startup rebuild or HTTP trigger remains. Queue insertion errors propagate after persistence; the MongoDB/Redis gap has no durable recovery. See [data access](data-access.md) for counting semantics.

## Tag weight modifiers

[TagWeightModifiersModule](../src/endpoints/tagWeightModifiers/tagWeightModifiers.module.ts), imported by AppModule, composes TagModule, ItemTagModule, JobsModule and SchedulerModule. [TagWeightModifiersSchedulerService](../src/endpoints/tagWeightModifiers/services/tagWeightModifiersScheduler.service.ts) enqueues [RECALCULATE_TAG_WEIGHT_MODIFIERS_JOB](../src/endpoints/tagWeightModifiers/static/RECALCULATE_TAG_WEIGHT_MODIFIERS_JOB.ts) (`tag.recalculateWeightModifiers`, version 1, null payload) daily at 03:00 Europe/Moscow. The job uses simple deduplication with its definition name and no TTL, suppressing repeated enqueues while pending, running or awaiting retry across application instances. Retry delays are 5,000, 30,000 and 120,000 ms. There is no startup catch-up if the scheduler was offline at the scheduled time, and no HTTP trigger.

[RecalculateTagWeightModifiersJobHandler](../src/endpoints/tagWeightModifiers/handlers/recalculateTagWeightModifiersJob.handler.ts) processes taste-enabled TAG_GROUP_RULES groups sequentially, checks cooperative cancellation before each group and before writes, and reports group progress. It reads group tag IDs, obtains catalogue usage through ItemTagRepository.getUsageCounts and updates only weightModifier on matching group Tags. Writes are idempotent, unordered bulk operations per group; a failed or cancelled run can leave some groups updated until a later successful recalculation. This does not recalculate UserTasteProfile. Counting semantics and the formula are described in [data access](data-access.md).

## Taste profile recalculation

[UserTasteProfileModule](../src/entities/userTasteProfile/userTasteProfile.module.ts), already imported by AppModule, imports UserModule, UserItemModule, ItemTagModule and JobsModule. It exports [UserTasteProfileRecalculationService](../src/entities/userTasteProfile/services/userTasteProfileRecalculation.service.ts) alongside its repository and registers [RecalculateUserTasteProfileJobHandler](../src/entities/userTasteProfile/handlers/recalculateUserTasteProfileJob.handler.ts). `enqueue(userId, itemId)` schedules [RECALCULATE_USER_TASTE_PROFILE_JOB](../src/entities/userTasteProfile/static/RECALCULATE_USER_TASTE_PROFILE_JOB.ts), name `userTasteProfile.recalculate`, version 2, `{userId,itemId}` string ObjectId payload, retries 5,000/30,000/120,000 ms. Deduplication uses name + user ID + Item ID with BullMQ `keepLastIfActive:true`, without TTL: waiting/delayed requests merge; active requests preserve one follow-up run created atomically when the current job finishes. No User revision field or additional Redis coordination is used.

UserItemService passes the affected Item ID after create/skip/block/remove. Update and attempt mutations enqueue after commit only when rating, favorite, skipped membership or completed-attempt count capped at three changes. Note-only, dates/progress-only, unchanged inputs and additional attempts above the cap enqueue no taste job. No periodic cron or startup rebuild is registered. The handler reads the affected ItemTag IDs and recalculates only those tags from current matching UserItems, including records with completed attempts but no rating/favorite. Unrelated calculated tags and all nonzero explicit settings are preserved. Each publication uses a raw profile snapshot taken before calculation; on conflict the handler rereads and recalculates, preventing concurrent Item jobs from publishing stale overlapping values. It checks cooperative cancellation before each calculation/publication. Completed attempts add 0.1 each, capped at 0.3 and a total signal of 1; ratings 1-4 retain their negative signal without a bonus. Deleted/missing users are skipped. The old profile remains usable until publication. See [data access](data-access.md) for calculation and persistence rules.

MongoDB commit and queue insertion are separate: enqueue failures propagate after the library change has committed. Recovery from that gap or Redis loss, catalogue-change triggers, and direct/generic repository writes are not implemented. Use the exported enqueue method when adding an application mutation that must invalidate taste.

## Mail delivery

Preserve the existing path: [MailService.send](../src/infrastructure/mail/services/mail.service.ts) → `JobService.add` → [SendMailJobHandler.handle](../src/infrastructure/mail/handlers/sendMailJob.handler.ts) → Resend. The service validates recipient, subject and text/HTML, serializes Buffer attachments to base64 and returns a queue ID with `status: "queued"`. It does not return a provider delivery ID.

[SEND_MAIL_JOB](../src/infrastructure/mail/static/SEND_MAIL_JOB.ts) is `mail.send`, version 2, with retry delays of 1,000, 5,000 and 30,000 ms. [MailModule](../src/infrastructure/mail/mail.module.ts) creates the Resend client from `RESEND_ACCESS_SECRET`; the sender domain comes from `MAIL_DOMAIN`. Sender keys and display names are defined in [MAIL_SENDERS](../src/infrastructure/mail/static/MAIL_SENDERS.ts), defaulting to `no-reply`.

The handler checks cancellation before delivery, prefers nonempty HTML while retaining optional text, uses idempotency key `mail.send:<queueJobId>`, and rejects provider errors or missing delivery IDs. Its result is `{ id: providerDeliveryId, status: "sent" }`. Keep queue and provider identifiers distinct.

[MailHealthService](../src/infrastructure/mail/services/mailHealth.service.ts) calls Resend `domains.list()` and checks for provider errors. This checks an API operation, not successful email delivery. [JobsHealthService](../src/infrastructure/jobs/services/jobsHealth.service.ts) checks queue counts; that is not proof that a handler has completed work.
